## What it is
`/calendar/open-services`: one page that lists every OPEN job that is not a renewal or a tax return, grouped by who we are waiting on (or by service), with the step, the step date on record, and whether the follow-up time set on the step has passed. READ-ONLY: each row only has "Open workspace" (`/flows/<job id>`). It reads the step settings Antonio filled in (`pipeline_stages.waiting_on`, `sla_days`, `completes_service`), so a new service with steps and jobs appears with no code change. It is its own page next to the calendar; the live calendar page (`app/(dashboard)/calendar/page.tsx`, `components/calendar/*`) is NOT edited and release 1 adds NO layout around it (a layout is the one piece a switch cannot protect; the tab bar on /calendar is a later, separate release).

## Business rules
- **Switch** `app_settings.open_services_audience` = `off` | `owners` | `all`. Default off. ANY other value (typo, `true`, object, missing row, read error) = off. **In release 1a it is flipped by SQL only** (no screen yet). The value is JSON text, so keep the inner quotes: `insert into app_settings (key, value) values ('open_services_audience', '"owners"'::jsonb) on conflict (key) do update set value = excluded.value, updated_at = now();` (use `'"all"'` / `'"off"'` for the other states); read it back with `select key, value, updated_at from app_settings where key = 'open_services_audience';`. Until release 1b, any admin can ALSO write the key through the generic `PUT /api/app-settings` (which trusts `isAdmin`), and the page re-reads the setting on every request so a change is immediate. Release 1b adds the Maintenance select, an owner-only branch of that route, and a `GET` that returns 500 on a real read error. **Known, separate:** `app_settings` has row-level security OFF and `anon`/`authenticated` hold write grants (all environments, verified 2026-10-07) — anyone logged in, even a client, or holding the public key, can write ANY setting directly, this one included. The page's data is still gated by the staff-role check (`isStaffUser`), so it is a switch-integrity issue, not a data leak; tracked as its own job. The page reads the setting directly (`audience.ts`, not `getAppSetting`, which swallows database errors) so a failed read is logged and fails closed.
- **Who** (`lib/open-services/access.ts`): `all` = `isStaffUser` (not client, not managed partner) AND an explicit role written on the login (`app_metadata.role` must be non-empty text: an account with NO role counts as legacy staff elsewhere in the CRM, but not on this page — production has none today); `owners` = staff AND `isOwnerOnly` (Antonio + `NEXT_PUBLIC_EXTRA_OWNER_EMAILS`; on production that variable may be unset, so "owners" can mean Antonio ALONE). Never `isAdmin`.
- **Open** = `isLiveDeliveryStatus` (lib/services/stages.ts): anything not completed / cancelled / canceled / inactive (NULL status = open). Job `is_test` must not be true; the company must not be `is_test` / `is_internal`; a person-only job's contact must not be `is_test`. Blocked / on-hold jobs and jobs of a company that is NOT OPERATING (status Suspended, Offboarding, Cancelled or Closed — `PARKING_COMPANY_STATUSES` in build.ts) are KEPT, badged and "paused": never counted late. A company that is Pending Formation or Delinquent is live work: its jobs can run late and only carry a badge. (Do not assume a Company Formation job sits on a Pending Formation company: formation accounts are Active with portal tier `formation`, and a job before the Articles exist may have no account at all.)
- **Excluded by data, not by name**: a job whose service card carries `metadata.closes_only_by_filing` (renewals) or `metadata.hidden_from_open_services` (tax returns) — matched by the card link OR `metadata.delivery_service_type` (same match as the renewal-close rule; some jobs are not linked to their card). Excluded jobs are counted once each and shown in a permanent "Not shown on this page" line, named from the card's `display_name`.
- **Who is waiting** (six states): `us`, `client`, `outside` ("Outside office" = IRS, state or bank), `date`, `none` ("Nobody (close it?)" — also any open job sitting on the done step), `unset` ("Not set"). A group where EVERY job is "Not set" is collapsed (data rule; `Group.collapsible`, judged on the whole unfiltered group); a filter that matches inside, or "Show jobs", opens it, and "Hide jobs" is offered only on such a group (never on a mixed group that a filter has narrowed to its Not-set jobs).
- **Late** = days since the job's `stage_entered_at` minus the step's `sla_days`, only when `sla_days > 0`, the step is not a `date` step, the job is not parked, and the result is strictly greater than 0. No step date → "date unknown", never late. There is NO fallback to `stage_history` (three different shapes; two live routes — `app/api/portal/wizard-submit/route.ts`, `app/api/lease-signed/route.ts` — change `stage` without stamping `stage_entered_at`, so the date can be too old). Three more writers move a job WITHOUT stamping: `reactivateSD` (lib/operations/service-delivery.ts), `resumeDelivery` (trackers actions) and the AI `advance_service_stage` tool — a job can therefore read "since <old date> · 20 d · 17 d late" right after someone moved it. Antonio decided (2026-10-08): the stamping fix is its own later job. A job sitting on the DONE step can also be "late" (it is listed under "Nobody (close it?)", the clock keeps running because the step has days set).
- Order inside a group: most late first, then oldest step date, then oldest job, then id (total order). Each group shows 25 rows; "Show more" adds 25 (URL `more=<group>~<n>`, clamped 25–5000 = `MAX_LIMIT`). A group that still has more than the ceiling shows a plain note ("narrow with search or a filter") instead of a button that does nothing (`Group.capped`).

## How it's built
- **Tables read (service client, after the guard):** `service_deliveries`, `pipeline_stages`, `catalog_entries` (cards with the two flags), `accounts`, `contacts`. No writes. No new tables or columns. The loader REFUSES to run (page shows "Could not load") if no card carries `closes_only_by_filing` (renewals) or none carries `hidden_from_open_services` (tax — i.e. the migration has not run), so switching the page on out of order can never flood it with tax returns or renewals.
- **Key files:** `lib/open-services/audience-shared.ts` (pure setting parse, client-safe), `access.ts` (pure rule), `audience.ts` (server: reads the setting on every request, `requireOpenServicesAccess()` cached per request, returns the proof the loader demands), `types.ts` + `params.ts` (pure, client-safe; URL state, hostile-input parsing), `build.ts` (pure builder; no service name in code), `load.ts` (throwing, keyset-paged loader), `app/(dashboard)/calendar/open-services/{page,loading,error}.tsx`, `components/open-services/open-services-view.tsx` (client; all state in the web address, server re-renders), migration `scripts/migrations/20261007-0100-open-services-hidden-flag.sql` (+UNDO).
- **No server actions, no data API route:** the only entry to the data is the page route behind the guard (a client can POST a server action to any page route; there are none here).
- **Data flow:** page → `requireOpenServicesAccess()` (denied → `notFound()`) → `loadOpenServicesInputs(access)` (throws on any read error; the page then shows "Could not load", never an empty list) → `buildOpenServices()` → client view.

## Gotchas, invariants & past bugs
- The migration flags the tax card; production has `tax_return` only (no `tax_return_one_time` card, no such jobs). A one-time tax job created later with no card would NOT be hidden — the migration's acceptance count compares jobs matched by the flag with ALL open `Tax Return%` jobs.
- Day-one data is uncomfortable by design: a dated snapshot, checked read-only on PRODUCTION by the System Counselor 2026-10-08 00:37 UTC: 700 open jobs, 5 test/internal, 424 hidden after the migration (Annual Report 181, RA 160, Tax Return 83), 271 shown (CMRA 226, Banking Fintech 19, ITIN 11, Client Onboarding 7, Company Formation 5, Company Closure 2, EIN Change Name 1 — the counts move with the business), 221 with no step date (218 CMRA), 35 past follow-up. Job statuses in production are only completed / active / cancelled / blocked (all 108 blocked jobs are renewals, hidden), so nothing is mis-classified; 0 shown jobs sit on a non-Active company; 45 jobs have a waiting-on set, 226 are "Not set" (all CMRA). All 14 Banking jobs at "Application Submitted" had a client banking form with `reviewed_at` NULL while the step is set `outside`. **Antonio decided 2026-10-08 (plan decision 4): leave it as it is** — in his words the jobs really were submitted to the bank and the form was only never marked reviewed; the step stays "outside", and marking those forms reviewed is a later data tidy-up, not part of this release. CMRA steps are bulk-created placeholders (215 of 226 created 2026-03-20). These are data questions for AFTER ship (build the system first, fix data after).
- Quick-create (`POST /api/service-deliveries`, the "new job" button) inserts a job with status `Not Started` and step `intake` and no step date: it appears as "step not in settings" / "date unknown" until someone moves it (known, harmless on this page). A blocked job belonging to a company that has since been Closed stays "blocked · company closed · parked" — closing the company cancels only the ACTIVE sibling jobs. The load-failure path is logged AND sent to Sentry (tag `area: open-services`).
- Layout: the six-column row switches on at 1100px (Tailwind `min-[1100px]:`), not at the 768px `md` size — the table needs ~950px next to the 256px side menu, and below that (a laptop split view or a floating window) the stacked card layout is used; at 768–1030px the old breakpoint clipped the "Open workspace" button.
- Renewals are filed from TWO places (Calendar "Mark Filed" and the To-Do board card via `/api/crm/renewal/file`); both use `fileRenewal`. This page touches neither.
- Pipeline Overview counts only `status='active'` and requires `account_id`; this page includes NULL/blocked/"Active"-cased jobs and person-only jobs, so the two will differ by design.
- Conditions for `all` staff (Antonio's three, plus two added in the 2026-10-08 ship plan; the Banking meaning was answered 2026-10-08 and is no longer a condition): release 1b shipped; the page's load measured (it re-renders on every task event and runs ~15 reads per render); the missing-date stamping fix (wizard-submit, lease-signed) done as its own job; the tab bar on /calendar added later (Suspense-isolated, fails to nothing) after a real renewal has been filed under the C0 rule.
- The loader's guard checks that SOME card carries each flag, not WHICH. If one renewal card lost its flag while the other kept it, the page would still load and list that renewal type. The visible check is the permanent "Not shown on this page" line: it must name Annual Report, State RA Renewal and Tax Return.
- A denied visitor gets the not-found page; because `loading.tsx` streams a neutral grey skeleton first, the HTTP status can be 200 with a not-found body. No page content or title is sent before the guard.
- Map/Set iteration needs `Array.from(...)` in this repo (downlevel target).

## How to verify current state
1. `select slug, metadata->>'hidden_from_open_services', metadata->>'delivery_service_type' from catalog_entries where catalog_id='services' and metadata->>'hidden_from_open_services'='true'` → the tax card(s).
2. `select value from app_settings where key='open_services_audience'` (no row = off).
3. Tab numbers vs a direct count: open = status NULL or not in (completed, cancelled, canceled, inactive), `is_test` not true, company not test/internal, minus jobs matched by the two card flags.
4. `npx vitest run tests/unit/open-services-*.test.ts` (access, params, builder, rules — company statuses, every job in exactly one place, order tie-breaks, the paging ceiling —, wiring).
