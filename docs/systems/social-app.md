## What it is
**TD Social** is ONE iPhone app (private TestFlight first) for TD Talk, Portal chats, WhatsApp, the CRM Inbox and Marketing Chat, with three layers of who sees what (Antonio + Jodi: five tabs; Luca: four, Inbox = support@ only; Rocco: Marketing Chat only). It is a thin native SwiftUI shell with one web view per tab showing the EXISTING screens; real Apple phone alerts and the icon number come from the server (Step 2). The full approved plan (5 tabs, layers, 11 decisions, steps 0–6, risks, UX wording) lives in storage: My files › CRM Projects › TD SOCIAL › `TD SOCIAL - complete plan (APPROVED v1).md`; the Step 1 audit and fix list are next to it. ## How app mode works
- **The switch.** The native app adds ` TDSocial/<version>` to its web view's browser name (user agent). `lib/app-mode/app-mode.ts` (`isAppModeUserAgent`, token `TDSocial/`, exact and case-sensitive) decides; `lib/app-mode/server.ts::getAppMode()` reads it on the server once per page load. It is a LAYOUT hint, never a security switch (the client controls its own user agent): every login, two-step check and permission rule runs exactly as before.
- **Telling the page.** Layouts wrap their content in `components/app-mode/app-mode-provider.tsx` (`<AppModeProvider initial={appMode}>`): a `display: contents` wrapper (adds no box) that carries `data-app-mode="true"` (rendered by the server, so no flash) and provides `useAppMode()` (`lib/app-mode/app-mode-context.ts`, a plain .ts so pure modules can read it). The answer is frozen per document. **The marker is also put on the page's root element** (`document.documentElement`, by an effect in the provider, taken off again when the layout goes away): the wrapper cannot reach what a screen draws OUTSIDE it — pop-ups, menus, tool tips, the search box, toasts and the Reply pop-up are attached to the page root (React portals; 16 files use `createPortal`, the Reply pop-up attaches to `document.body`). Without it the 44 px / 12 px rules missed all of them (measured: the Reply pop-up had 29 small controls and 5 small texts; with the root marker 5 and 0). Only ONE provider per layout chain may do this (two nested ones would fight over the root marker): the dashboard and TD Talk layouts each wrap once; Marketing wraps ALL its pages once in `app/marketing/layout.tsx` — only when the browser name says app (a normal browser gets no wrapper at all), and this also covers the lead page that opens inside the full-screen window (`app/marketing/window/[id]`, outside the `(app)` layout).
- **Hiding web-only parts.** CSS: anything with the class `app-hide` disappears inside the app (`app/globals.css`). Used for TD Talk's "Sound is on" bar and Voice switch and the Portal chats notification bell.
- **Dashboard (CRM) screens** (`app/(dashboard)/layout.tsx`, `components/dashboard/embedded-shell.tsx`): app mode reuses the floating-window machinery's idea (see dashboard-navigation.md "Window mode") but is NOT a frame. `bare = embedded || appMode`: `ChromeOnly` renders nothing in the app (no sidebar, top bar, notes, floating chat, AI panel, capture, command palette, realtime toasts/sounds, service worker, pull-to-refresh), the chrome's data queries are skipped, `ShellFrame`/`ShellMain` drop the sandbox offset and the phone top-bar padding. `HiddenInWindows` keeps the Supabase notice in the app (one line, tap to read). The window bridge and window manager stay frame-only (`EmbeddedProvider initial={embedded}` unchanged). In the app the main area is a column and `ShellBody` takes the remaining height under the notice so a chat's message box stays on screen. Dark mode is off in the app (light only in the first release): `ThemeScript`/`ThemeSync` do not run.
- **TD Talk** (`app/talk/layout.tsx`, `components/talk/talk-shell.tsx`): in the app no service worker, no sound pop-ups, no "turn on notifications" strip; the screen starts at the top (no sandbox offset); the notice stays as one line.
- **Inbox / WhatsApp** (`components/inbox/inbox-shell.tsx` and friends): no channel buttons or action row (the app's tabs do that; the web channel is chosen by the URL `?channel=whatsapp`), a round Compose button bottom-right (lists only), a "Folders" sheet (the folder column does not exist on a phone), the mailbox / search / filter rows hide while an email or chat is open, tours never start by themselves, the web sound picker is hidden, the WhatsApp "not connected" warning is one line (tap to unfold), an open email shows the short toolbar (`lib/inbox/app-thread-actions.ts` decides the list — Reply, archive, read/unread, delete or restore; the rest under "…"; drawn by `components/inbox/app-thread-actions.tsx` with the same handlers the computer layout uses) and an email wider than the phone is shrunk to fit (`lib/inbox/fit-scale.ts`, `components/inbox/email-html-frame.tsx`; a transform shrinks what you SEE, not the room the email takes, so the frame's own vertical scroll is switched off while it is shrunk — otherwise it scrolled through a blank band as tall as the difference: measured 4,462 px document inside a 2,541 px frame). The Folders sheet is a labelled dialog and the sheet and the "…" menu close with Escape. The row action icons on the list rows are kept on purpose (Antonio's mobile row-level archive/trash).
- **Portal chats** (`app/(dashboard)/portal-chats/page.tsx`): the notification bell is hidden; the row of six tabs scrolls sideways (`app-tabs-scroll`); "← Back" sits on the client's name line (`app-conv-header`); the page root is sized "the whole screen minus the CRM's 4rem top bar", which the app does not have, so it carries `app-fill` (full height in the app; the normal CRM keeps `calc(100vh - 4rem)`) — before, a 64 px dead strip sat under it (about 12 px while the Supabase notice shows). Rules in `app/globals.css`.
- **Marketing** (`app/marketing/(app)/layout.tsx`, `app/marketing/layout.tsx`, `components/marketing/chat-workspace.tsx`, `lead-windows-host.tsx`, `app/marketing/(app)/chat/page.tsx`): in the app Marketing is the Chat and nothing else — no side menu, a slim top bar ("TD Marketing" + IT | EN), the Supabase notice as one line, no tour / sound / push banner / news strip / lead search, light only; the amber "Viewing as … / Exit view" strip STAYS, as one line (a safety notice: Antonio sees the team as its owner and what he does is recorded under his own email — hiding it was a bug-hunter finding). The two-screen choice follows the chat that really EXISTS (`current`), never the id asked for (`sel`): a created chat whose list refresh failed used to hide the list AND show no chat and no back arrow. The Chat screen is two screens one at a time below 768 px (the list, then the open chat with a back arrow) in ANY browser; from 768 px up it is the same two columns as before. A lead opened from the chat list is a full-screen page with a back arrow (one at a time, no dock) instead of a floating window.
- **Sizes** (`app/globals.css`, app only): icon-only buttons and links get a 44 px tap area; boxes you type in at least 44 px tall; buttons with text at least 44 px tall (switches / check boxes / radios keep their shape); the web screens' 10 / 10.5 / 11 px text is raised to 12 px.

## Rules
1. App mode is a layout hint. It must never grant, hide or change DATA or permissions.
2. The normal browser (computer or phone) must not change. Every app-only rule is behind `useAppMode()`, the `data-app-mode` marker or the server's `getAppMode()`; the two exceptions that also help phone browsers are the Marketing Chat two-screen layout (below 768 px) and `flex-wrap` on the open email's Note / Copy link row.
3. Never put the window bridge or the window manager behind app mode (they are frame-only).
4. A notice that carries real information (Supabase incident, WhatsApp not connected) is shortened to one line in the app, never hidden.
5. The zoom lock (`maximumScale: 1`, `userScalable: false` in `app/layout.tsx`, `app/talk/layout.tsx`, `app/portal/layout.tsx`) is NOT touched in Step 1b: removing it risks the iPhone zooming into every box you type in; decide on a real iPhone (Step 4).
6. Do not measure in the sandbox without removing its extras: the sandbox adds an orange bar (10 px text) and a 40 px top offset that production does not have, which inflates every number.
7. EVERY app-only CSS rule starts with `[data-app-mode="true"]`, and the helper classes (`app-hide`, `app-tabs-scroll`, `app-conv-header`, `app-compact-taps`, `app-fill`) do nothing without it. `tests/unit/app-mode-css.test.ts` reads the real stylesheet and checks every selector — one unscoped rule would change the computer CRM for everybody.
8. A notice that carries a safety meaning (Supabase incident, WhatsApp not connected, Marketing "Viewing as") is never dropped in the app; and measure INSIDE iframes too (the lead page runs inside one): `capture.cjs --frames`, `flow1c.cjs leadpage`.

## Server pieces (Step 2) — pull request C2: the Apple alert sender and the phone leg
No database file, no new route. Files: `lib/app/apns-key.ts` (is the key set; no imports), `apns.ts` (signing, the request, Apple's answers, the HTTP/2 connection), `phone-wording.ts` (what a lock screen may show), `phone-recipients.ts` (who may be told), `phone-badge.ts` (the icon number for one person by id), `send-to-phones.ts` (the leg), `phone-leg.ts` (the doorway the two senders call).
- **Where it hooks in:** `sendPushToAdminUsers` (so `sendPushToStaff` / `sendPushToStaffExcept`) and `sendMarketingPush` call `startPhoneLeg(...)` FIRST, before any early return, and await it at the end (`try { web } finally { await phone }`); the browser code moved one step down into `sendAdminWeb` / `sendMarketingWeb` unchanged. The phone leg is **in addition to** the browser alert, never instead of it: computers and the old home-screen web apps keep every alert they had. It never throws.
- **Switches, in this order, each ending the leg quietly:** (1) the three Apple values are set (`APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_PRIVATE_KEY`; checked in `phone-leg.ts` with NO imports and NO database read, so until Antonio sets them production is exactly as before); (2) the `social_app_enabled` setting is true; (3) this server knows its own bundle id (from the real database address; unknown = nothing); (4) the kind goes to phones; (5) recipients re-checked; (6) the person has not muted the alert's tab; (7) their phones (not revoked, seen in the last 45 days, bundle id = this server's).
- **Who may be told (re-checked at send time, fail closed):** staff = people the staff directory lists now; Marketing = ACTIVE member of THAT alert's team + team live + the chat permission. Capped at 25 people and 60 phones per alert.
- **What the lock screen shows** (`phone-wording.ts`; "who, never what"): ONLY `talk_direct_message` shows typed text (its own title and text, cleaned and cut). Everything else is fixed words plus at most one cleaned name the sender passes on purpose (`phoneName`): "Chat: <company>" / "Chat: a client", "New message in a client chat", "Claude replied", "<name> shared something with you", "New staff note", "A proposal needs a decision", the system notice's own text, "Test notification", Italian for Marketing ("Nuovo messaggio · <lead>", "Chiamata spostata", "Aggiornamento sulla chiamata" for a call booked, moved or cancelled by the client, "Novità in TD Marketing"). A kind not on the list shows "New notification". Channel / topic messages never go to phones; Claude's replies and shared items go only for direct and group chats (`dm`). Names lose control characters, line breaks and direction marks and are cut by whole characters (40; text 60 / 140).
- **Mutes:** a person who muted the alert's tab (TD Talk, Portal, Marketing) gets no phone alert for it. Staff notes, approvals, notices and tests belong to no tab. A failed read of the mutes means "not muted" (a mute is a convenience).
- **The icon number:** computed per person with the part-B counters under a 1.5 s cap; any failure or slowness = the alert goes WITHOUT a number (never 0); the app corrects it when opened. A badge of 0 is sent when the count really is 0.
- **Apple's answers (the rule that protects the phone list):** a phone is revoked (`revoked_at`, reason `apple_<reason>`) ONLY on 410, or on 400 with exactly `BadDeviceToken` / `DeviceTokenNotForTopic`. 403 (key or team wrong) and 429 (too many token updates) STOP the batch and remove nothing; any other 400, 404, 413, 5xx, timeout or connection error keeps the phone. A refused key writes one log line per hour per server.
- **Signing and connection:** ES256 token built once per half-hour slot and kept in memory (issue time = the slot's start); Apple's two addresses are constants (`api.sandbox.push.apple.com`, `api.push.apple.com`); the phone's token is re-checked as hexadecimal before it enters the path; one HTTP/2 connection per address per alert, always closed; requests have a 5 s limit and the whole leg 9 s; at most 8 requests in flight. Payload: title, optional body, sound, `thread-id` and `apns-collapse-id` from the tag (hashed), the link only if it is a same-site relative path, expiry one hour, topic = this server's bundle id; over 4 KB the body is dropped.
- **Logging:** only a phone's row id and Apple's short reason. Never the token, the signing token, the key or headers.
- **Two pre-checks removed** so a person with only a phone is still told: the approval alert (`lib/ai-agent/approval-notifications.ts`) and a new internal thread (`app/api/internal/threads/route.ts`) no longer look at the web subscription table first (a test fails if any staff-alert caller does).
- **Names added at the senders:** client portal messages and reactions (the company), the shared item (the sharer), Marketing lead chat and "call moved" (the lead's full name only). Files shared into a client chat pass none ("Chat: a client").
- **NOT done in this pull request (said plainly):** (a) the MEASURED real length of the phone leg on a deployed sandbox with the key set (the un-awaited alert sites now wait up to 4 s for it — see "Bug-hunter pass" — but how long it really takes is still unmeasured); (b) anything proved on a real iPhone or against Apple itself: Apple's token-update limit, TestFlight using Apple's production address, the exact 410 / 400 reasons, HTTP/2 from a Vercel server (all from memory until Step 4); (c) the WhatsApp and email alerts (part D).

- **Decision 2 — Antonio only gets what involves him.** A call moved by a person (`marketing_lead_moved`) goes to everyone who works calls; on the phone the owner (the member whose login email is the owner's work mailbox in the team's time settings, `owner_clock`) AND every CRM admin among the recipients are dropped from it UNLESS the lead has a booking link with him (`marketing_joint_links` row with status booking / booked / cancelled for that lead and team; an `open` link never used does not count). When a CLIENT moves or cancels a call with him (`marketing_call`) the owner is ADDED to the link's seller (Rocco in normal use; before this only the seller was told, so Antonio was never told). The lead is passed as an explicit `leadId` on the alert, never read from a link. Any doubt (no lead, failed read, no owner mailbox) means he is NOT told. Chat about a lead and team chats already follow who is involved (lanes and conversation members) and are untouched. His computers keep Marketing's own browser rule (the "call moved" browser alert is unchanged).
- **Wording:** the call alert says "Aggiornamento sulla chiamata" (true for booked / moved / cancelled); a TD Talk message that is only a file or a card shows "Sent an attachment" / "Shared a card" instead of the file name; the two "sent into a client chat" safety alerts have their own kind `client_share_check` ("A file was sent to a client", not "Chat: <company>"); names keep ZWNJ / ZWJ (international names) and lose lone surrogate halves.
- **Waiting and time limits:** both senders wait for the phone leg at most 4 s (`PHONE_WAIT_MS`), so no caller (the TD Talk send, the booking link) is held for the leg's full 9 s; the three alert sites nobody waited for (the client-message alert, the reaction alert, the four staff-note alerts) now wait (at most 4 s) so the function is not stopped before the alert is out; a person's mutes and icon number each get 1.5 s (`SIDE_LOOKUP_MS`) and the alert goes without them when slower; past the leg's own deadline nothing more is sent (a late alert is worse than none); a 403 / 429 stops only the Apple address it came from.
- **Honesty and Apple details:** a failed read of someone's switches means NO icon number (not a wrong one); the signing time is a minute before the slot starts; a timed-out Apple request is cancelled on the wire; a dead connection is an error, not "status 0" (found by the new fake Apple server); a pasted key that cannot be used writes one log line an hour.
- **Cheap first:** the "does this kind go to phones at all?" check now runs before the switch is read or anything is loaded, so a chatty channel costs nothing.
- **Not done (said plainly):** revoking a person's phones when their login is disabled or removed (no code does; filed for later — the staff directory already stops staff alerts for a banned login, but a stale `banned_until` is unproven); Apple's behaviour on a real phone; the measured leg time.
