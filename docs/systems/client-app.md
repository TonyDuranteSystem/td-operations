## What it is
The client portal (portal.tonydurante.us) as an iPhone app. A thin native shell shows the portal's own pages inside the app (`TDSocial/`-style "app mode"), with a native bottom bar, a Menu, phone alerts and one sign-in. It ships as **version 2.0 of the existing App Store record "MyLLC Manager"** (bundle `com.tonydurante.myllcmanager`, Apple ID 6749905082), public, for **clients and the team members they added** (no partners). Paying Tony Durante invoices works inside the app, with a server switch that hides Pay if Apple objects.

## The approved design (Antonio, 8 Nov 2026)
- **Overview** = the portal's real Overview page. **My Company is not in the app.** No in-app account deletion (staff do it from the CRM). The voice button is the record button built in another session.
- **Invoices** = the client's OWN invoicing (portal "Customers & Invoices": Setup, Customers, Sales, Vendors, Expenses), with a not-set-up card (bank account or payment link REQUIRED, first customer with an email REQUIRED, logo optional; no "Not now"). **TD Billing** is its own item (opens the portal's Expenses tab, shown only once TD has sent an invoice, carries the unpaid count).
- **Bottom bar:** Chat is the only fixed tab and the client picks four. **The Menu is a round button at the top right of every screen**; its red number counts waiting items that are not in the bar. A new client's standard set: Overview, Chat, Documents, Invoices, and a fifth = TD Billing if the client has an invoice from Tony Durante, otherwise Sign Documents. The choice is saved with the login (candidate store: `portal_user_preferences`, whose writer accepts only `tour.*` keys today).
- **Chat:** one "Topic" button next to the title (opens a short list, unread topics red and first, "Create a new topic"); no Journey Log; **Chat opens on the topic of the newest unread answer** (the website opens General first and, with several unread topics, the one with the most unread — the app uses Antonio's rule instead); the button's red number counts unread answers in the other topics.
- **Paying** = the portal's real "Pay Invoice" pop-up (card +5% fee, "Pay Now" opens the provider's page in a new tab; bank transfer with the required payment reference). **Not tried yet inside the phone app.**

## Step 2 — the server answers for the app (SANDBOX, switched OFF, 8 Nov 2026)
Three doors, all under `app/api/portal/app/`, all behind the switch `client_app_enabled` (`app_settings`; missing row = OFF = answer 503 `APP_NOT_ENABLED`; a second switch `client_app_pay_enabled` hides Pay, default ON). Nothing in the website calls them yet.
- **`GET me`** — who this login is and everything the app needs for its menu: `items` (every entry this person can open, in menu order, with the words in their language, the link and a badge), `bar` (the bottom bar), `lockedKey` (Chat), `maxBarSize` (5), `menuBadge` (the red number on the round Menu button = waiting items NOT in the bar), `payEnabled`, `company`, `kind` (`client` / `teammate`). **My Company is never listed.**
- **`PUT / DELETE bar`** — save / reset the bottom bar. The server never trusts the app: 1 to 5 entries, no duplicates, Chat must be in, every entry must be one this person can open now (codes `BAR_SIZE`, `BAR_DUPLICATE`, `BAR_NEEDS_CHAT`, `BAR_NOT_AVAILABLE`, `BAR_INVALID`). The answer is the fresh `me`.
- **`PUT / DELETE devices`** — register / remove this person's phone for alerts. Same saved-phones table as TD Social (`social_app_devices`) with the CLIENT bundle ids (`CLIENT_APP_BUNDLE_IDS` in `lib/app/environment.ts`: production `com.tonydurante.myllcmanager`, sandbox `….sandbox`); a server accepts only its own. Nothing is sent to these phones yet (Step 4).
- **Which company (found by the bug hunter, fixed):** the website's company switcher writes its cookies (`portal_account_id`, `portal_formation`, `portal_onboarding`, `portal_mode`) for the path `/portal` ONLY, so a browser never sends them to `/api/portal/app/…`. The app says it in the address instead: `?account=<id>`, `?formation=<id>`, `?onboarding=<id>`, `?mode=client|partner` (`selectionReader` in `lib/portal-app/gate.ts`, used by all three routes). The loader still passes the value through `resolveSelectedEntity`, which only honours companies the person owns; a made-up id falls back to the first company, like the website. With nothing in the address the FIRST company answers. Step 3/5: the app (or the portal page in app mode) must carry the selected company in these parameters. `tests/unit/portal-app-routes.test.ts` pins both halves (the switcher's cookie path, and that the gate and loader do not read cookies). **Lesson:** the first sandbox proof set its test cookie for the whole site, which hid this; a proof must write cookies exactly as the real page does.
- **Gate order (each tested):** switch → signed in → audience → (devices) bundle id → body → write. Audience (`resolveAppAudience` in `lib/portal-app/load.ts`): a client login, or a team member a client added (scoped to ONE company); staff → 403 `NOT_A_CLIENT`; partner (incl. a dual-role person in partner mode) → 403 `NOT_FOR_PARTNERS`; no linked record / access removed → 403 `NO_ACCESS`. Removing a phone does not need the audience check.
- **Files:** `lib/portal-app/` — `bar.ts` (pure bar rules), `assemble.ts` (pure answer), `load.ts` (gathers the facts with the SAME helpers and order as `app/portal/layout.tsx`, dependency-injected for tests), `bar-pref.ts` (reads/writes `portal_user_preferences.prefs`, key family `app.bar`, without touching other keys), `enabled.ts` (the switches), `gate.ts` (switch + sign-in). The shared menu rules gained `navLabelKey` and `resolveNavHref` in `lib/portal/nav-rules.ts` so the app and the website build the same words and links.
- **Standard bar (nobody chose yet):** an ACTIVE client = Overview, Chat, Documents, Invoices + (TD Billing if TD has invoiced, else Sign Documents). A lead or a client still being set up also gets their first step (`nav.offer` / `nav.wizard`). An ACTIVE client never gets those two in the standard bar, so a service wizard that happens to be open cannot push Documents or Invoices out (found in the sandbox proof). A saved bar keeps its own length; an entry that drops out is replaced from the standard list and comes back if it returns (the saved choice is not rewritten). **One bar per login, shared by all companies:** a save made while one company is open keeps the earlier choices that company cannot show (say TD Billing) behind the new ones while there is room (`mergeBarChoice`, max five), so setting up the bar in a company without TD Billing does not erase it for the company that has it. A choice the company COULD show but the person left out is dropped (removed on purpose). A deliberately short bar saved in a narrow company can show up as a full five elsewhere (filled from the standard list).
- **Layout not touched (on purpose):** `app/portal/layout.tsx` still computes its own facts; `load.ts` repeats the same decisions. `tests/unit/portal-app-load.test.ts` pins them and has a drift guard that fails when the layout stops using one of these helpers or company cookies. A later job can make the layout call `load.ts`.
- **PROVED in the sandbox (real logins, local server, 8 Nov 2026; company choice re-proved after the fix with the cookie written for `/portal` only, as the website does):** `me` for one client across 4 companies matches the real side menu; with the switcher cookie set to another company and nothing in the address the first company answers, `?account=` switches company, a made-up id is ignored; a save in one company leaves the other company's bar intact; save / read back / reset a bar; all 5 bar refusal codes (6 bad requests) and the 5 bad device requests (bad bundle id x2, bad token, bad Apple environment, not an object); the saved choice returns when the first company is selected again and quietly drops entries the second company lacks; register / re-register (no double row) / remove / remove again (`removed: 0`); wrong bundle id (the production id, another app's id) refused; switch off → 503 on all five calls; signed out → 401. **Not proved with a real login:** a team member (covered by unit tests with fakes only); a staff login reaching the audience check (a staff login without the second step is stopped earlier by the site's two-step rule in `middleware.ts`, 401 `MFA_REQUIRED`, before these routes run; the 403 `NOT_A_CLIENT` answer is covered by unit tests only); a partner.
- **Errors:** a helper that throws becomes `500 {code: 'SERVER_ERROR'}` (JSON), never an empty page. A failed read of the saved bar, of the portal role or of the Client / Partner mode degrades to the standard answer with a 200, the same as the website does.
- **Known gaps, not built (decide when Step 3-5 need them):** (1) the website's "team reacted" signal (Chat pulse, violet dot on Menu) is not in `me`; (2) a client cannot list or clear their own old phones: after 10 live phones registration answers 409 and the old rows go stale after 45 days or staff clear them (TD Social has the same limit); (3) the saved bar lives in the shared `portal_user_preferences` row with a read-then-write update, so a tour save at the very same instant could drop it (an atomic merge would need a database function); (4) the Pay switch accepts `false` or the text "false" only.
- **Tests:** `portal-app-bar.test.ts`, `portal-app-load.test.ts`, `portal-app-routes.test.ts`, `portal-app-enabled.test.ts`.

## Rules and gotchas
1. App mode is a layout hint, never a security switch (see `social-app.md`). Every app-only style stays behind the app marker; `tests/unit/app-mode-css.test.ts` guards the stylesheet.
2. `/api/portal/` is open to client logins by the client API allow-list but also holds staff routes: every new route there needs its own client-or-team-member check.
3. TD Social's `lib/app/environment.ts` accepts ONE bundle id per server and its doors refuse clients. The client app needs its own accepted bundle id and its own door.
4. A TestFlight build stops working 90 days after upload. A change to the app itself needs a new build and Apple's review; web changes reach the app at once.
5. Step 1 is live (it changes nothing anyone sees). Step 2's doors go live on production the moment it merges but answer 503 until `client_app_enabled` is set to `true`; no database file is needed (the bar is one more key in the existing `portal_user_preferences` row, the phones use the existing `social_app_devices` table). Switching on is the LAST step, only on Antonio's explicit word.
6. Do not build a RegExp from a template string with a constant (R115); the production build is not the dev server.
