## What it is
The client portal (portal.tonydurante.us) as an iPhone app. A thin native shell shows the portal's own pages inside the app (`TDSocial/`-style "app mode"), with a native bottom bar, a Menu, phone alerts and one sign-in. It ships as **version 2.0 of the existing App Store record "MyLLC Manager"** (bundle `com.tonydurante.myllcmanager`, Apple ID 6749905082), public, for **clients and the team members they added** (no partners). Paying Tony Durante invoices works inside the app, with a server switch that hides Pay if Apple objects.

## The approved design (Antonio, 8 Nov 2026)
- **Overview** = the portal's real Overview page. **My Company is not in the app.** No in-app account deletion (staff do it from the CRM). The voice button is the record button built in another session.
- **Invoices** = the client's OWN invoicing (portal "Customers & Invoices": Setup, Customers, Sales, Vendors, Expenses), with a not-set-up card (bank account or payment link REQUIRED, first customer with an email REQUIRED, logo optional; no "Not now"). **TD Billing** is its own item and its own screen (`/portal/invoices?tab=billing` in the app; shown only once TD has sent an invoice, carries the unpaid count).
- **Bottom bar:** Chat is the only fixed tab and the client picks four. **The Menu is a round button at the top right of every screen**; its red number counts waiting items that are not in the bar. A new client's standard set: Overview, Chat, Documents, Invoices, and a fifth = TD Billing if the client has an invoice from Tony Durante, otherwise Sign Documents. The choice is saved with the login (candidate store: `portal_user_preferences`, whose writer accepts only `tour.*` keys today).
- **Chat:** one "Topic" button next to the title (opens a short list, unread topics red and first, "Create a new topic"); no Journey Log; **Chat opens on the topic of the newest unread answer** (the website opens General first and, with several unread topics, the one with the most unread — the app uses Antonio's rule instead); the button's red number counts unread answers in the other topics.
- **Paying** = the portal's real "Pay Invoice" pop-up (card + the card fee on what is still owed, bank transfer with the required payment reference). Inside the app "Pay Now" leaves in the app's own window and the card page returns the client to the TD Billing screen (Step 3 bug-hunter fixes). **Not tried yet on a real phone.**

## Step 4 — alerts to clients' phones (SANDBOX, in a pull request, 10 Nov 2026)
The phone leg for the client app, beside (never instead of) the browser alert. Nothing is sent unless BOTH the Apple key is set (`APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_PRIVATE_KEY`; they are on the SANDBOX Vercel project; production decides separately) AND the client app switch is on (it is OFF on production), so production behaves exactly as before. The web alert is sent first/regardless; a failed or slow phone leg never fails it (the sender waits for the leg at most 4 s).
- **Doorway and hook:** `sendPushToAccount` and `sendPushToContact` (`lib/portal/web-push.ts`) start `startClientPhoneLeg` FIRST (before their early returns, so a client who only has the app, with no browser subscription, is still told), run the unchanged web send, then wait for the leg. The two callers that make client alerts name a kind: `createPortalNotification` passes its notification `type` as `clientKind`, the service-stage push passes `service`, the alert test passes `test`. `clientKind` is removed before the browser send.
- **Words (`lib/portal-app/phone-wording.ts`):** who and what KIND, never what. A closed list mapped from the notification type (chat, reaction, service/formation, document, sign, invoice, decision, wizard reminder, test; anything else = generic) with FIXED English or Italian words (the client's `contacts.language`; a team member's portal language): e.g. "New message from Tony Durante LLC", "A document needs your signature", "New invoice from Tony Durante LLC". Never a message's text, a file/service/stage name, a company name or an amount; the alert object has no title or body field at all, so nothing typed can reach a lock screen. **The wording is a proposal Antonio can change** (one table in that file).
- **Whose phones (`lib/portal-app/send-to-client-phones.ts`, `selectRecipientPhones`):** the SAME people the browser alert reaches, re-checked at send time. `contact` scope = the phones whose owner is that contact. `account` scope = the phones of the client contacts linked to the company RIGHT NOW (`account_contacts`) plus the team members of that company who are active and have the chat permission (the browser alert's own rule, `lib/portal/team/push-scope.ts`). A contact that was unlinked or a team member that was removed gets nothing; any doubt = nobody. A phone of another bundle id (TD Social) is never used; a phone not seen for 45 days is ignored.
- **The phone knows its owner (needs a small database file):** nothing in the database linked a client contact back to its login (the link lives only inside the login's token), so `social_app_devices` got two optional columns, `contact_id` and `team_account_id`, written from the SESSION when the app registers the phone (`PUT /api/portal/app/devices`; never from the request; a phone that moves to another person overwrites both). File: `scripts/migrations/20261110-0100-client-app-phone-owner.sql` (+ `.UNDO.sql`). **SANDBOX: applied. PRODUCTION: NOT applied: run it BEFORE the client app switch is turned on.** TD Social registration does not write the two columns at all, so it works with or without the file.
- **Icon number:** unread chat + documents to sign + unpaid Tony Durante invoices across the client's companies, capped at 99; honest or absent (any failure or more than 2.5 s = sent without a number; a team member's phone gets none).
- **Apple:** one connection per Apple address, 8 at a time, bounded to 60 phones and 9 s; a phone is removed only on Apple's 410 / BadDeviceToken / DeviceTokenNotForTopic; a 403 or 429 stops that address and removes NOTHING; logs hold a phone's row id and Apple's short reason only. The Apple key is team-wide and the notification topic is the app's bundle id (`com.tonydurante.myllcmanager`, sandbox `….sandbox`), so the TD Social key works for this app too (confirmed by a real delivery from the sandbox deployment to the simulator on 10 Nov 2026, after the Apple setup below).
- **Tests:** `tests/unit/client-app-phone-leg.test.ts` (wording, recipients, the sender against a fake Apple, the doorway, the two web senders, the owner at registration, the database file); each rule was broken on purpose and caught.
- **Not done / not proved:** real delivery through Apple to a REAL iPhone (to the simulator it IS proved, see the simulator section), the Italian wording on a real lock screen, a company with many logins (the cap of 60 phones), the production database file, what tapping an alert opens inside the app (Step 5 reads the alert's `url`).

## Step 2 — the server answers for the app (SANDBOX, switched OFF, 8 Nov 2026)
Three doors, all under `app/api/portal/app/`, all behind the switch `client_app_enabled` (`app_settings`; missing row = OFF = answer 503 `APP_NOT_ENABLED`; a second switch `client_app_pay_enabled` hides Pay, default ON). Nothing in the website calls them yet.
- **`GET me`** — who this login is and everything the app needs for its menu: `items` (every entry this person can open, in menu order, with the words in their language, the link and a badge), `bar` (the bottom bar), `lockedKey` (Chat), `maxBarSize` (5), `menuBadge` (the red number on the round Menu button = waiting items NOT in the bar), `payEnabled`, `company`, `kind` (`client` / `teammate`). **My Company is never listed.**
- **`PUT / DELETE bar`** — save / reset the bottom bar. The server never trusts the app: 1 to 5 entries, no duplicates, Chat must be in, every entry must be one this person can open now (codes `BAR_SIZE`, `BAR_DUPLICATE`, `BAR_NEEDS_CHAT`, `BAR_NOT_AVAILABLE`, `BAR_INVALID`). The answer is the fresh `me`.
- **`PUT / DELETE devices`** — register / remove this person's phone for alerts. Same saved-phones table as TD Social (`social_app_devices`) with the CLIENT bundle ids (`CLIENT_APP_BUNDLE_IDS` in `lib/app/environment.ts`: production `com.tonydurante.myllcmanager`, sandbox `….sandbox`); a server accepts only its own. Alerts to these phones are Step 4 (below); the phone is saved with its owner (contact or company).
- **Which company (found by the bug hunter, fixed):** the website's company switcher writes its cookies (`portal_account_id`, `portal_formation`, `portal_onboarding`, `portal_mode`) for the path `/portal` ONLY, so a browser never sends them to `/api/portal/app/…`. The app says it in the address instead: `?account=<id>`, `?formation=<id>`, `?onboarding=<id>`, `?mode=client|partner` (`selectionReader` in `lib/portal-app/gate.ts`, used by all three routes). The loader still passes the value through `resolveSelectedEntity`, which only honours companies the person owns; a made-up id falls back to the first company, like the website. With nothing in the address the FIRST company answers. Step 3/5: the app (or the portal page in app mode) must carry the selected company in these parameters. `tests/unit/portal-app-routes.test.ts` pins both halves (the switcher's cookie path, and that the gate and loader do not read cookies). **Lesson:** the first sandbox proof set its test cookie for the whole site, which hid this; a proof must write cookies exactly as the real page does.
- **Gate order (each tested):** switch → signed in → audience → (devices) bundle id → body → write. Audience (`resolveAppAudience` in `lib/portal-app/load.ts`): a client login, or a team member a client added (scoped to ONE company); staff → 403 `NOT_A_CLIENT`; partner (incl. a dual-role person in partner mode) → 403 `NOT_FOR_PARTNERS`; no linked record / access removed → 403 `NO_ACCESS`. ## Rules and gotchas
1. App mode is a layout hint, never a security switch (see `social-app.md`). Every app-only style stays behind the app marker; `tests/unit/app-mode-css.test.ts` guards the stylesheet.
2. `/api/portal/` is open to client logins by the client API allow-list but also holds staff routes: every new route there needs its own client-or-team-member check.
3. TD Social's `lib/app/environment.ts` accepts ONE bundle id per server and its doors refuse clients. The client app needs its own accepted bundle id and its own door.
4. A TestFlight build stops working 90 days after upload. A change to the app itself needs a new build and Apple's review; web changes reach the app at once.
5. Step 1 is live (it changes nothing anyone sees). Step 2's doors go live on production the moment it merges but answer 503 until `client_app_enabled` is set to `true`; no database file is needed (the bar is one more key in the existing `portal_user_preferences` row, the phones use the existing `social_app_devices` table). Switching on was the LAST step and was done on Antonio's explicit word (10 Nov 2026).
6. Do not build a RegExp from a template string with a constant (R115); the production build is not the dev server.
7. Release plan (Antonio, 10 Nov 2026): set up everything in Apple and test it privately first; the PUBLIC launch is planned for January 2027. "MyLLC Manager" (Apple ID 6749905082) is live on the App Store as version 1.3 ("Ready for Distribution"), so 2.0 is an update of that live record: nothing reaches today's users until 2.0 is released.
