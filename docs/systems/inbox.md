## What it is

The `/inbox` tab of the CRM dashboard: a **live window onto Gmail** (support@ and
antonio@ mailboxes) plus the WhatsApp/Telegram messaging groups stored in
Supabase. **Nothing Gmail-related is persisted in our DB** — every list/thread
view is fetched from the Gmail API on demand (SA + DWD impersonation, see
`lib/gmail.ts`). WhatsApp/Telegram messages live in `messaging_groups` /
`messages` and are read-only here except replies via the `send-message` Edge
Function.

## How it works

- **Page**: `app/(dashboard)/inbox/page.tsx` → `components/inbox/inbox-shell.tsx`
  (channel tabs, mailbox toggle support@/antonio@, search, bulk actions, labels

- **Conversation list**: `app/api/inbox/conversations/route.ts`. Lists Gmail
  threads (default `labelIds=INBOX`, or `q=in:<label>` / search query), fetches
  per-thread metadata, finds the external (non-TD) party, and matches their
  email against `account_contacts → contacts.email/email_2` to label the row
  with the CRM account. Polled every 30s by `conversation-list.tsx`.
  Gmail `snippet`s are HTML-entity-encoded — previews go through
  `decodeHtmlEntities` and sender names through `displayNameFromHeader`
  (both `lib/inbox/email-html.ts`) before plain-text display.
- **Thread view**: `app/api/inbox/messages/[id]/route.ts` for `gmail:<threadId>`
  IDs fetches the full thread. Each message body:
  - extracted by `extractBodyWithType` (`lib/gmail.ts`) which also returns
    the REAL MIME type as `isHtml` on the message payload — the renderer
    branches on that flag, NOT on a content sniff ("contains < and >"
    misdetected plain replies quoting `<a@b.com>` as HTML and ate every
    line break, 2026-07-08). Plain-text emails render `whitespace-pre-wrap`

- **antonio@ is Antonio's PERSONAL mailbox — admin only** (2026-07-08 audit:
  it was readable by any team login before). Enforced SERVER-SIDE in every
  route that accepts `mailbox` via `checkMailboxAccess`
  (`lib/inbox/mailbox-access.ts`); the UI toggle is additionally hidden for
  non-admins (`app/(dashboard)/inbox/page.tsx` passes
  `canUsePersonalMailbox`). Any NEW inbox route that accepts a `mailbox`

  security boundary.

## Rules / gotchas

- **Thread and message IDs are per-mailbox.** Any Gmail API call for a thread
  listed under mailbox X must impersonate X (`asUser`). The UI passes
  `mailbox=antonio|support` end-to-end (list → thread → attachment → reply →
  actions → mark-read).
- **Gmail label index lags 30–60s** after modify operations — the UI papers over
  this with optimistic cache updates, `localStorage` deleted-ids (5-min TTL),
  and delayed invalidations. Don't "fix" those without understanding this.
- **Email HTML is attacker-controlled** (anyone can email support@). Defense in
  depth is sanitize + sandboxed iframe. Never render inbound email HTML with
  `dangerouslySetInnerHTML` outside the sanitizer, and never add
  `allow-scripts` to the frame.
- **NEVER turn an attachment chip back into `<a href={attachmentUrl} target="_blank">`.**
  Gmail's `attachmentId` is a ~400-char token; in the query string of a TOP-LEVEL
  (document) navigation the request is killed at the platform edge with a **503
  before it reaches our route** — so the attachment silently never opens. The
  same URL fetched same-origin returns 200. Attachments MUST be fetched and
  opened from a blob (`AttachmentChip` in `message-thread.tsx`). Verified in prod
  2026-07-14; a short-token navigation reaches the route (500), a long-token one
  does not (503, absent from function logs, not a firewall denial).
- **Attachments are attacker-controlled, and a `blob:` URL inherits our origin.**
  Only formats that cannot script us may be rendered inline — `INLINE_SAFE` in
  `lib/inbox/attachment-open.ts` is an ALLOW-LIST (PDF + raster images). SVG /
  HTML / XML must DOWNLOAD, never open in a tab: an inline SVG attachment would
  be same-origin XSS in the staff CRM session. Never add a scriptable type.
- **A deleted email is hidden client-side by an OPTIMISTIC OVERRIDE — never by
  trusting Gmail's list**, whose label index lags 30–60s.
  `lib/inbox/conversation-reconcile.ts` owns ONE override map (`hidden` after a
  delete, `pinned` after an Undo) plus a separate unread map.
  `computeVisibleList` applies them over every payload (safe every render);
  `advanceReleases` runs ONCE per fetch (keyed on `dataUpdatedAt` — `[data]`
  skips react-query's structural-shared deep-equal polls) and releases ONLY on
  stable AFFIRMATIVE server agreement: a hide releases after 2 complete payloads
  that affirmatively lack the thread, then TOMBSTONES ~90s (Gmail's index is
  non-monotonic — that tombstone is what stops a deleted email popping back); an
  Undo PINS the row visible from its snapshot until the server confirms it is
  back; an unread override releases when the server moves OFF the pre-action
  BASELINE (never on the written value); a `partial` payload freezes ALL
  releases; the 5-min TTL is GC ONLY, never the primary release.
  **`deletedIds` and `localStorage['inbox-deleted-ids']` NO LONGER EXIST — do not
  resurrect them.** The state is `localStorage['inbox-overrides-v3']`, cleared on a
  mailbox switch; the key is versioned on the ENTRY SHAPE, so if you add or change
  a field on `RowOverride`, bump it (older builds' entries are unreadable under
  newer rules) and evict the superseded key — the blob holds real client email.
  There must be exactly ONE optimistic writer: `message-thread`
  used to also write `unread:0` straight into the conversations cache, which
  corrupted the reconcile's baseline and flickered rows back to unread — never
  add a second writer.
- **An override APPLIES by its action and is JUDGED only by the list it was born
  in — two different questions, two different fields** (`lib/inbox/view-query.ts` +
  the `RowOverride` doc comment; dev_tasks `30b5a53a` + `a06411a2`, fixed 2026-07-16).
  - **APPLY** ("is this true in the list on screen?") — a hide is a NEGATIVE claim
    derivable from what we DID, so it carries `action` and each view asks
    `hidesFromCurrentView(action, view)`: `trash` removes the row everywhere but
    Trash; `archive` strips ONLY `INBOX`, so it removes it just from inbox-scoped
    views (archiving from a folder legitimately LEAVES the mail in that folder).
    A pin is a POSITIVE claim ("this row belongs in THIS list") the action cannot
    support — it applies only in its `originView`, or an Undo injects a
    never-starred email into Starred.
  - **JUDGE** ("may this payload release it?") — `originView` only, BOTH kinds.
    Releasing needs the positive fact "this list would otherwise hold this row",
    and only the origin payload has it. Reading the action predicate as that
    evidence let a foreign list confirm a delete it had never seen: bulk-delete 12
    in the Inbox, glance at a folder, and 90s later all 12 were back.
  - The payload is **stamped with its own origin in `queryFn`** (`PayloadOrigin`);
    the reconcile is NEVER told "the view the user is on". With `keepPreviousData`
    and cache hits, the rows on screen routinely belong to another list — that skew
    is the bug generator, and stamping makes it unrepresentable. **A new dimension
    in the query key MUST be added to the stamp** (channel is in there: a WhatsApp
    payload holds no `gmail:` ids and would "confirm" every pending delete at once).
  - **The same rule binds the WRITE side: an override is stamped with the list the
    rows CAME FROM (`originViewKey`, reported up by ConversationList), never with
    the view the user has selected.** Clicking a folder flips the selection at
    once while the previous rows stay on screen and clickable for the whole fetch
    — so stamping the selection marks rows with a list that never held them, which
    then "confirms" a delete it never saw AND injects those emails into that folder
    on Undo. A pin **inherits the hide's `originView`** rather than re-deriving one:
    that is the list the snapshot came from, and it removes any dependence on the
    Undo toast's closure still holding the delete-time value.
  - **Never fall back to the raw server list when the origin is missing** — that
    un-applies every hide and flashes a just-deleted email back. Render nothing and
    let the next payload arrive. (The reconcile is safe to run over ANY stamped
    payload: foreign ids can't collide and a pin's key carries the channel. Do not
    re-add an `isWhatsApp` bypass on the render path — that was the fail-open.)
  - A row that cannot be attributed to any list (a `?thread=` deep link) is stamped
    `ORIGIN_UNKNOWN` — a value `viewKey` can never emit. **Never fall back to a REAL
    key for an unknown origin:** a real key is one some payload will match and
    "confirm" with. Unknown must mean unknown; the hide still applies and retires
    via the tombstone.
- **A label view filters by the label's ID (`labelIds`), never by `in:<name>`.**
  Gmail's `in:`/`label:` search operators take the NAME; `labelIds` and the modify
  endpoint take the ID. The sidebar sends the ID, so the old `q: in:<id>` matched
  nothing and **every custom folder in the CRM listed zero emails** — invisible for
  months because for SYSTEM labels the id IS the name (INBOX/STARRED/SENT), so only
  user folders were dead. Verified live on support@ 2026-07-16: `in:label_5` → 0,
  `in:_archive` → ~201. The ID is this view's identity everywhere else (`viewKey`
  keys on it), so resolving id→name would introduce a SECOND identity for one list
  — and it would need a labels.list call per fetch plus quoting for names with
  spaces/slashes. `-in:trash` rides along as a `q` (threads.list accepts both).
  **Lesson worth more than the fix:** a green unit test proved the query string was
  the one we intended; only a live call proved the string was meaningless to Gmail.

- **A MOVE is a hide + a pin, emitted together — never a third override kind.**
  "Restore from Trash" and the Undo of a delete are the same shape
  (`makeMoveOverrides`): the row LEAVES `from` (a hide, witnessed by `from`'s
  payload) and APPEARS in `to` (a pin, witnessed by `to`'s payload). Each half has
  exactly ONE witness and releases on its own clock — correct, because Trash and
  the destination catch up at different times. A single entry spanning two views
  would need two agree counters, two tombstones and a "half-released" state: two
  overrides wearing one struct. **If your change grows a third override kind, you
  have taken a wrong turn.**
- **The override map is keyed by (id + view) and the key is OPAQUE.** One email can
  hold two entries at once (hidden from Trash, pinned into the Inbox). The id lives
  ON the entry — never parse it back out of the key: `viewKey` embeds raw search
  text, so any separator can appear inside it and splitting hands back a wrong id,
  i.e. a hide applied to an email nobody touched.
- **EVERY intent-writer must `dropClaimsFor(id)` FIRST.** There are FOUR (row/open
  delete, Undo, Restore, and the BULK bar) — the count is the point: the first fix
  did three and the bulk bar re-opened the bug. A new user intent supersedes every
  prior claim, and a stale half is never harmless:
  - a hide left from the folder a row was deleted in still applies in the Inbox
    (a trash removes a row from there too) and **a hide outranks a pin**, so a
    restore lands the email in NEITHER list until the TTL — up to 6.5 minutes;
  - an `untrash` hide left after a re-delete holds the row OUT of Trash while it
    is genuinely IN Trash: it can never be witnessed away, so it also runs the
    full TTL. Both were shipped-then-caught on 2026-07-16.
  `findHide` ("where was this deleted from?") must ignore `untrash` hides — a
  restore is not a delete, and treating one as the answer sends the pin back to
  Trash where `to === from` drops it. Undo with no delete found is a NO-OP: drop
  claims only AFTER that check, or a second Undo click wipes the pin the first one
  created.
- **An optimistic move MUST roll back on failure** (`dropClaimsFor` in `onError`).
  The email is still in Trash; hiding it there while the toast says "try again"
  asks the user to retry on a row they cannot see — and that hide can never be
  witnessed away (Trash keeps returning the row), so it runs the full TTL.
- **A restore must never leave an email in NO list.** The untrash strips TRASH
  before anything is added, so every failure after it is a stranding risk. The
  server files down a ladder — requested destination → INBOX → put it back in
  TRASH — and returns `filedTo`, **which the client must read**: on a fallback the
  optimistic pin would otherwise sit on a folder the email isn't in, under a toast
  naming that folder. Guarding only the destination branch is not enough: that is
  the path no client can reach, while the plain restore is the one that ships.
- **Trashing never strips a custom folder label** (only INBOX/UNREAD/STARRED/
  IMPORTANT), so "restore it where it was" needs no snapshot — folders survive and
  `untrash` re-adds INBOX. KNOWN GAP: Restore-from-Trash therefore comes back READ
  and UNSTARRED, because that state is only captured at delete time and an email
  trashed an hour ago has no snapshot. The 8-second Undo restores it intact. The
  real fix is to stop stripping those labels at all — its premise is already dead
  (~201 unread emails sit in Trash today, so the "Trash would show an unread
  count" rationale is moot).
- **`toInboxView` collapses the `'INBOX'` label into `{kind:'inbox'}`.** The
  sidebar's Inbox button sends the label id `'INBOX'` and "no label" also means
  the Inbox — the SAME list. Two shapes = two view keys, and an override stamped
  with one is invisible to the other: a restore-to-Inbox pin would silently never
  apply. One list, one identity.

- **EVERY mutation argument travels as a mutation VARIABLE — the row included, not
  just the ids.** `mutationFn`/`onSuccess` read the NEWEST render's closure (react-
  query refreshes a pending mutation's options every render), and an offline PWA
  PAUSES before sending and re-reads `mutationFn` on resume. The open-email Delete
  read `selected` live: open A → Delete → drop signal → open B → reconnect and the
  server trashed **B**, a live client email, with no Undo, while A survived (found
  2026-07-16 — the same rule already written for bulk `ids`, one line away, on a
  path nobody re-checked). If you add an argument to an inbox mutation, freeze it
  at click time. Never read component state inside `mutationFn` or `onSuccess`.
  - The TTL **retires a hide through the tombstone**, never a bare drop — a hide no
    view can confirm (archive-from-a-folder) ends there, and dropping it bare pops
    the row back mid-lag. Every release is monotone. A pin just expires.
  - **Rule for any NEW override: state which list it is a claim about, and let only
    that list's payload confirm it.**
- **Trashing STRIPS `UNREAD` / `STARRED` / `IMPORTANT`, and Gmail cannot tell you
  what they were afterwards.** Any new delete path MUST snapshot them *before*
  the modify (`snapshotBeforeTrash`) and any Undo MUST hand that snapshot back so
  `untrashThread` can re-apply it — otherwise a restored email silently comes
  back read and unstarred, forever. Do NOT "fix" this by leaving `UNREAD` on
  trashed threads: the sidebar badges Trash with `threadsUnread`, so Trash would
  start showing an unread count.
  **KNOWN NARROW RACE (accepted, observed 2026-07-14):** `threads.get` is
  read-after-write lagged, so if a label was applied *seconds* before the delete
  (e.g. staff clicks Mark-unread and immediately deletes), the snapshot can miss
  it and the Undo restores the email without that one label. Verified: with the
  state settled the restore is exact (UNREAD + IMPORTANT both came back); with a
  ~2s gap the just-applied UNREAD was missed while the pre-existing IMPORTANT was
  restored. Impact is cosmetic (email returns read), never data loss — not worth
  a client-supplied "hint" that would have to be trusted.
- **The restore snapshot round-trips through the BROWSER, so it is untrusted on
  the way back in.** Always run it through `sanitizeRestorePayload` — it keeps
  only the `RESTORABLE_LABELS` allow-list, so an Undo can never be turned into
  "add an arbitrary label (TRASH / SPAM / any user label) to this message id".
- **All three delete paths must keep their Undo** (per-row trash icon, open-email
  toolbar Delete, bulk-bar Delete). They now ALL hide through the SAME override
  map — the bulk path's old react-query cache-filter is GONE — so every one of
  them needs `onRestored` (it flips the `hidden` intent to `pinned`), and a bulk
  Undo restores from the row snapshots captured at delete time. Snapshot source,
  best→worst: the raw cached row → an existing override's snapshot (a row that is
  currently PINNED is injected from its snapshot and is NOT in the raw payload) →
  the list's retained last-known copy (`conversation-list` keeps one for every
  overridden id). With none of those, an Undo restores the row INVISIBLY.
- **The selection must travel WITH the request as a mutation VARIABLE.** NEVER read
  `selectedIds` inside `mutationFn` or `onSuccess`: react-query hands `onSuccess`
  the newest render's closure, AND it PAUSES a mutation when offline and re-reads
  `mutationFn` on resume. So a checkbox ticked mid-flight gets trashed with no Undo,
  and a de-selected one gets hidden though it was never sent — sticky and persisted
  for 5 minutes (the old cache-filter self-corrected on the next refetch; an
  override does not). Freezing only one side (e.g. via `onMutate`) is NOT enough.
- **A failed bulk action must SAY SO.** The bulk path had no `onError` and a bare
  `throw new Error('Bulk action failed')` that discarded the server's body (the R099
  antipattern), so a rate-limited bulk delete of 30 emails was a silent no-op. Parse
  the server's `error` and toast it.
- **A BULK ACTION CAN PARTIALLY FAIL AND STILL RETURN HTTP 200.** The bulk branch
  uses `Promise.allSettled` and reports `succeeded` / `failed`. NEVER build a
  bulk toast from the client's own selection size — report what the SERVER did,
  and warn when `failed > 0`. Telling staff "12 emails deleted" when 3 silently
  failed is worse than an error (2026-07-14 self-review).
- **On a partial bulk failure the LIST must be refetched too, not just the toast
  corrected.** The optimistic filter removes EVERY selected row, including the
  ones Gmail refused — so a warning saying "3 failed" while those 3 emails are
  hidden sends staff hunting for mail the screen denies exists. `failed > 0` is
  therefore an explicit exception to the "don't refetch conversations on bulk
  actions" rule (that rule guards the SUCCESS path — the 2026-07-08 blank-inbox
  incident — and is untouched on it). An honest message plus a lying list is not
  a fix.
- **The attachment tab is opened BEFORE the fetch** (popup blockers) and is
  FRONTED, so it is the only surface the user is actually looking at. Any failure
  must be written into THAT tab — a toast on the tab behind it is invisible.
- **In an installed PWA we always DOWNLOAD, never `window.open`** — a standalone
  window frequently refuses to open a tab, which would silently do nothing. See
  `shouldOpenInTab`. Do not "optimise" this back into a tab open.
- Notification-style senders (Stripe, ShipStation, banks…) can be threaded
  together **by Gmail itself** (same sender + subject) — that part is
  Gmail-side behaviour, not our code.
- **One view = one Gmail thread.** The subject-based "related thread merging"
  (added `c7afbe79`, guard `106ada77`) was REMOVED 2026-07-07: Gmail `subject:`
  search is contains-match, so same-sender notifications and templated
  subjects merged threads across clients. Do not reintroduce display-time
  merging — if outbound senders fragment a conversation, fix the sender to
  pass `reply_to_message_id` / proper `In-Reply-To`.
- Known debt (audit 2026-07-07): email→account lookup is last-write-wins for
  contacts on multiple accounts; 30s polling refetches up to ~200 threads +
  the whole `account_contacts` table.

## Own-Inbox local content store (dev_task 01800da8 — added 2026-08-02, OFF by default)

Goal (Antonio): keep Google Workspace, but hold a **full local copy of every email — body AND attachments** so the CRM inbox can read/search/serve attachments from our own DB instead of live Gmail (speed + no Gmail-outage dependency). Sandbox-built + unit-tested; **dormant until turned on**. Reads are NOT repointed yet — this leg only CAPTURES.

**Where it lives:**
- Store: private bucket `email-content` (public=false, service-role only) + tables `email_message_content` (per-message ledger: composite `(mailbox, message_id)` PK, `body_path`, `body_text`, `capture_status` pending|complete|error written LAST, FK→`email_index`, RLS antonio-admin-only) + `email_attachment` (opaque `storage_path`, never the sender filename). Migration `scripts/migrations/20260801-0100-email-content-store.sql`.
- Capture engine `lib/email-store/capture.ts`: ONE `format:full` get/message (a 2nd `format:raw` get was a 2× quota tax — council 2026-08-01), `withGmailRetry` (429/5xx, half-jitter), insert-once, `capture_status=complete` written only after body + every attachment stored. Path/completeness helpers in `paths.ts`.
- Worker `lib/email-store/worker.ts`: bounded-window uncaptured detection (no full-completed-set load) + concurrency pool. Runner `runner.ts` (enumerate ids → drain, both mailboxes parallel; ~10 min; guarded CLI `scripts/backfill-email-content.ts`).
- Reconciler `lib/email-store/reconcile.ts`: the completeness safety net — lists Gmail by date window (`after:/before:`), diffs vs stored-complete, captures the gap. Does NOT trust Gmail's 7-day history cursor; heals gaps from any source.
- Automatic backfill `lib/email-store/auto-backfill.ts` + cron `/api/cron/email-content-backfill` (`*/15` off-hours, gated on app setting `email_content_backfill_enabled`, default OFF): walks date-windows backward from a cursor in `gmail_watch_state.content_backfill_*`, resumable, finishes at the mailbox's oldest email. `backfillProgress()` = X-of-Y.
- Ongoing NEW mail: cron `/api/cron/email-content-capture` (`*/10`, gated on the same switch) captures the newest not-yet-stored messages in small bounded batches (`captureBatchLive`) — safe during the workday (low volume), insert-once so it never collides with the off-hours backfill. So one switch = history + all future mail.
- Control: admin API `/api/inbox/email-backup` (GET progress, POST on/off) + CRM panel `components/dashboard/email-backup-panel.tsx` in Dev Tools (progress bars + one Turn on/off).
- Metadata-sync hardening: `indexThread` (`lib/email-index/sync.ts`) now wraps its Gmail fetch in `withGmailRetry` (a transient 429 at throughput must not silently drop a thread → an index gap the capture layer can't see). The `backfillStep` cursor-advance-past-exhausted-failure is a known remaining gap covered by the reconciler (deliberate — avoids risky surgery on the shared prod cursor).

**Remaining (not built):** repoint inbox READS to local-first + per-message Gmail fallback + signed-URL mint with `checkMailboxAccess(row.mailbox)`; RUM full-content search; deletion model (mirror-Gmail + 180-day recoverable bin + "Delete forever"). Rollout: support@ first, antonio@ last; first live run = small watched slice.
