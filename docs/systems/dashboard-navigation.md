## What it is
The CRM's left menu (`components/dashboard/sidebar.tsx`) is the one list of pages Antonio and staff move between. This doc also records the multi-window project that grew out of it: Antonio wants to open **any page from any other page without leaving the one he is working on**, in floating windows he can resize, plus a working right-hand mouse button. The full project record (his requests in his words, three council rounds, the plan) is the Word document **"FLOATING WINDOWS — The Project"** in his My Drive → CRM Projects → FLOATING WINDOWS, and the dev board job `f3f3e237`.

## Business rules (Antonio's decisions, 2026-10-05)
- The ⋯ button goes on **every** left-menu item (not just the active one).
- The browser's own right-click is **left alone** — nothing in the CRM takes it over.
- Floating windows: **at most 3**, desktop only, **resizable** (step 5 built, sandbox only).
- Nothing ships to production without his explicit "go" for that step. Steps 2–7 need their own go.

## How it's built
- **Page list:** one array (`id`, `name`, `href`, `icon`, optional badges, `adminOnly`/`ownerOnly`/`featureFlag`) in `components/dashboard/sidebar.tsx`. Every item is a real `<Link>`. **One** component, `SortableNavItem`, renders every item (a test pins "exactly one render site"), so anything added there reaches every page, including pages added later.
- **The ⋯ menu — `components/dashboard/nav-item-menu.tsx` (`NavItemMenu`):** a Radix dropdown (portalled to `<body>`, `z-[70]`, above the mobile drawer) with two actions: **Open in new tab** (a real `<a target="_blank" rel="noopener noreferrer">`) and **Copy link** (synchronous clipboard write with an honest `then/catch` toast — never a false "copied").
  - It is a **sibling** of the item's `<Link>` and is placed last in the row (after the red/violet count badges and the Team Chat dot). A button inside an anchor would navigate away when clicked.
  - Visible on hover and keyboard focus (`group-hover`, `group-focus-within`, `focus-visible`) and **always visible on touch** (`[@media(hover:none)]`). **Not rendered in reorder (edit) mode** — the drag grip owns the left edge.
  - The item name span has `min-w-0 truncate` so long names ("Pipeline Overview", "TD Communication") shorten instead of wrapping next to the button.
- **Helpers — `lib/nav/nav-link.ts`:** `isInternalNavHref` (only a normal CRM path: one leading slash, no scheme, no `//host`, no backslash, no control characters) and `absoluteNavUrl` (origin + path for "Copy link"; `null` for anything unsafe). The same gate is meant for the future window system's "never open an outside/`javascript:` address, and re-check on restore" rule.
- **Tests:** `tests/unit/nav-link.test.ts` (helpers) and `tests/unit/sidebar-nav-menu-wiring.test.ts` (structure: sibling not child, hidden in edit mode, one render site, truncate, touch/keyboard reveal, safe new-tab anchor, honest copy).
- **Items deliberately NOT in the menu:** the Tasks board (`/tasks`) — retired from the sidebar (comment above the array); its page still exists at its address.

## Window mode (dev job `f3f3e237` steps 3-4; OFF by default; sandbox only)
A page loaded inside a frame (a future floating window) must not repeat the whole CRM around it. The shared layout `app/(dashboard)/layout.tsx` therefore supports **window mode**:
- **The switch:** `floating_windows_enabled` in `app_settings` (toggle: Dev Tools → Maintenance → "Floating windows (window mode)"). **Default OFF and FAILS CLOSED** (`isFloatingWindowsEnabled` in `lib/settings.ts`: only a stored `true` enables it; a read error means off) — the opposite of the chat switch, because this turns on a NEW behaviour in the layout every page shares. While it is off, nothing about page loads changes anywhere.
- **Decision:** the layout reads the switch on EVERY load now (`windowsEnabled`, step 5 — the main page needs it to decide whether to mount the window manager) and a page is a window only when `isFramedNavigation(headers().get('sec-fetch-dest'))` (`lib/embed/embedded-request.ts`, true only for a frame's FIRST load) AND the switch is on. It is a UI hint, never a security switch: the login check (`getUser` + redirect) runs first, for every request.
- **Frozen once:** `EmbeddedProvider` (`components/dashboard/embedded-shell.tsx`) reads the value ONCE (`useState(initial)`). A later refresh of the same frame is labelled `empty` by the browser, so following the server's latest answer would flip the window back into a full CRM and wipe the screen. A hard navigation inside the frame is a new document and decides again.
- **The service worker must not re-request framed loads** (`public/dashboard-sw.js`, see `pwa.md`): `fetch(event.request)` makes the browser drop the label, so a window loaded as the full CRM whenever the worker was active (browser QA 2026-10-05). **That fix must ship, and be picked up by each browser's worker update (the update banner / SKIP_WAITING), BEFORE the switch is turned on for anyone.**
- **Same tree shape:** every piece of chrome (banner, service-worker registration, alert sounds/toasts, pull-to-refresh, left menu, header, Cmd+K palette, AI panel, notes, capture tools, floating chat) is still rendered in place inside `<ChromeOnly>`, which renders nothing in a window and adds no markup in the normal CRM. `UiEventListener` (keeps a window's data fresh) and the main scrolling area (`ShellMain`) stay.
- **Skipped in a window:** the badge-count queries, the AI-agent setting lookup and the floating-chat setting lookup (first load only; refreshes still run them — a cost still to measure).
- **History safety (council round 2 blocker):** a frame's history entries join the BROWSER TAB's history, so a page's "back" would step the whole tab and destroy every window. Inside a window `history.back()` is a no-op (`EmbeddedProvider`; Next's `router.back()` calls it), the shared `BackButton` renders nothing, and `useSelectionHistory` REPLACES the entry instead of pushing. **Per-page back arrows that call `router.back()` directly (account/contact/lead/partner/flow detail pages) are dead buttons inside a window until the window chrome (step 5) owns back/forward.**
- **Test page (removed before shipping):** a throwaway admin page (`/dev-tools/window-spike`) loaded 3 real pages in frames and reported per frame whether it was a bare page, a quiet one, and survived a refresh / reload-all-three; it passed 3/3 in browser QA on 2026-10-05 and was deleted with its helper (`spike-evaluate`) and `SpikeBridge` so nothing test-only ships. The same checks are now covered by the window manager's own behaviour, the unit suite and the browser sweep of all 31 menu pages.
- **Tests:** `embedded-request`, `embedded-shell-wiring`, `floating-windows-switch`, `dashboard-sw-iframe-passthrough`.
- **NOT done / not verified:** behaviour when several frames refresh the login token at once after it expires (the Supabase refresh-token reuse setting is unknown — needs the ~1 hour sign-in test); the root layout's sandbox banner still shows inside a frame (cosmetic, sandbox only); toasts render inside the frame.

## The window manager (step 5; sandbox only; behind the same switch)
- **Mounted once** in `app/(dashboard)/layout.tsx`, outside `<main>`, inside `<ChromeOnly>` (a window can never spawn windows) and only when `windowsEnabled` (off = never mounts = the kill switch). Component: `components/windows/window-manager.tsx` (draws and wires); rules: `lib/windows/window-model.ts` (pure, tested); remembered state: `lib/windows/windows-storage.ts`; messages: `lib/windows/window-messages.ts`; the frame's side: `lib/embed/window-bridge.ts` (installed by `EmbeddedProvider` in a window); opener: `requestOpenWindow(href, title)` in `lib/windows/windows-context.ts` (a DOM event, so anything can open a window).
- **Rules:** max 3 (`MAX_WINDOWS`); desktop only (renders nothing under 1024px wide, ⋯ entry is `hidden lg:flex`); the same page is brought to the front, not duplicated; a window may only show a page whose first path segment is on the ALLOW-LIST `WINDOW_PAGE_ROOTS` (mirrors `app/(dashboard)/` folders — a unit test fails when a folder is added there and not to the list; a block-list would have let `/lease`, `/offer`, `/pay`, `/portal`… through). Whether the current person may see a page is still the server's job (an admin-only page opened by a non-admin redirects to home inside the window).
- **Window chrome:** title bar (drag), Back / Forward / Reload, Minimise, "Open in a separate browser window", "Open in the main page" (dock), Close; 8 resize handles; min 480×320, default ≈1040×680, clamped to the screen and below the sandbox banner; the title bar can never leave the screen. Minimised windows stay alive (hidden, not removed) so typing is not lost, with chips at the bottom centre. Stacking: root `z-[44]` (below notes 45 / chat 46 / in-page overlays 50+), own stacking context, never `role="dialog"` (the chat's auto-pop looks for dialogs), excluded from screen captures (`data-capture-tool-ui`; frames would render blank). A transparent sheet covers the frames during drag/resize (frames swallow the mouse).
- **Frame ↔ main page messages** (`td-win`, same-site only, receiver checks `e.origin` AND that the sender is one of its own frames / its own parent): frame→main `loc` (path+query+title, also from `popstate`/title changes), `focus` (click inside a window brings it to front without eating the click), `key` (Cmd/Ctrl+K opens the main page's search), `dirty-answer`; main→frame `go` (client-side navigation for Back/Forward), `ask-dirty`.
- **History (council blockers):** inside a window `history.back()` no longer touches the tab (it asks the main page to step the window back) and `pushState` becomes `replaceState`, so a window never adds entries to the tab's history; the window's own Back/Forward use a trail the main page keeps (`Trail` in the component) and navigate the frame by message. A page's own "←" arrow (`router.back()` → `history.back()`) is routed to the window's own Back (the frame posts `back`, the main page walks that window's trail); the shared `BackButton` is still hidden inside a window.
- **Unsent typing:** the frame remembers fields the person typed in (trusted `input` events only); closing / popping out / docking asks the frame (`ask-dirty`) and warns only if a typed-in field STILL holds text (typed-then-sent is not "unsaved"); a frame that doesn't answer in 500 ms is treated as clean.
- **Signed out / dead:** a window that lands on `/login` or `/mfa` (or a page outside the list, or a `404` title) removes its frame and shows "signed out" / "no longer available" with a Close button — a login inside a frame would sign the whole tab in.
- **Remembered per person, per computer:** `td-windows-v1:<userId>` in localStorage (url, title, minimised, size, position — addresses re-validated on load, max 3); other people's keys are pruned at start; cleared at the Sign-out button AND on Supabase `SIGNED_OUT` (expiry, ban, reset). Storage failures never break anything.
- **Opening one (step 6):** four doors, one opener (`requestOpenWindow` → the manager). (1) left-menu ⋯ → "Open in floating window"; (2) the **"Open in a window"** button in the left menu's footer (`components/dashboard/windows-launcher.tsx`) — it is handed the SAME `orderedNav` array the menu renders (already filtered for admin-only / owner-only / feature-flag), so nobody can launch a page the menu hides; (3) **Option/Alt-click** on a left-menu item (`lib/windows/open-intent.ts`: Alt + plain left click only — Cmd/Ctrl-click (new tab) and Shift-click (new window) stay the browser's own, per Antonio's "leave native mouse behaviour alone"); (4) in the search palette **Cmd/Ctrl+Enter**, or Cmd/Ctrl/Option-click on a result, opens it as a window (plain Enter/click unchanged). All four appear only when the switch is on AND the screen is ≥1024px: callers intercept only when `canOpenWindowNow()` is true, so on a narrow screen the normal navigation still happens (council: an intercepted click that opens nothing strands the person). Errors: "You already have 3 windows open", "This page can't be opened in a window", "…only available on a computer-size screen".
- **Bug-hunt fixes (2026-10-05, two bug-hunter passes; the first was reproduced live in the browser):** windows are drawn in STABLE creation order and stacked by z-index only (re-ordering the elements reloaded a window's page when it was brought to the front AND stranded the full-screen drag sheet, locking the CRM — drag also ends on `lostpointercapture`); the manager is never built inside a frame or a pop-out browser window (`window.self !== window.top`, pop-outs are opened with a `td-popout-…` name) and, once on, stays on for the life of the page (a failed settings read on a later refresh cannot tear windows down; `enabled` is read once); `canOpenWindowNow` also refuses inside a frame; windows hidden by a narrow screen forget their frame seeds so they return at the page they were on; signed-out/gone windows are removed and re-openable; minimised windows with unsent typing are restored before the question is drawn; Reload is guarded like Close; the trail ignores `replaceState` (the frame reports `replace`), un-does a Back that the frame never answered (3 s), and `history.go/forward` are patched like `back`; typing tracking is text-like fields only; dot-segment addresses (`/accounts/%2e%2e/portal`) and wrong-case roots are refused; `WindowsCrashGuard` wraps the manager; a push-notification click now asks the top-level page to navigate itself (`td-navigate` over a MessageChannel, answered by `SwRegister`) and only falls back to a full reload if it never answers, so windows survive it.
- **Known limits / unverified:** a chat/inbox thread marks itself read when its page opens (also inside a window, and when a window is restored on reload) — not yet tied to window focus; refreshing the main page reloads every window (typing inside them is lost; no `beforeunload` warning); a service-worker update reload reloads the frames; the push-notification click handler (`dashboard-sw.js` `client.navigate`) still reloads the main page and so closes nothing but reloads every window; ~1h login-token expiry with 3 frames not yet tested; installed Mac app "separate window" behaviour unverified; Document Picture-in-Picture ("always on top of other apps") was considered and left out.
- **Narrow screens:** below 1024px nothing is drawn, nothing is re-clamped and nothing is re-saved (remembered windows keep their real size); remembered windows load against at least a desktop-size screen.
- **Tests:** `window-model`, `window-messages-storage`, `window-manager-wiring`, `window-launch-wiring`, `embedded-shell-wiring`.

## The windows tour (dev job `f3f3e237`, 2026-10-06)
A "learn by doing" guided tour of floating windows, requested by Antonio after he saw the WhatsApp inbox tour (`components/inbox/whatsapp-tour.tsx`, react-joyride): plain English, a practical example in every step, the person DOES each action, and a feedback box. Reviewed by the system counselor, a UX specialist (Erika Hall lens) and the bug hunter BEFORE building; their findings shaped it.
- **Not built on react-joyride.** Its dimming overlay blocks the very clicks this tour asks for (Radix menus, dragging a window, the tray tab) and cannot follow a dragged window. It is a small card in a corner (`components/windows/windows-tour.tsx`, z-[47]: above windows 44 / notes 45 / chat 46, under menus 70) plus a glowing ring that follows its target every animation frame. Never `role="dialog"` (the floating chat's auto-pop looks for dialogs); Esc does NOT end it (Esc also closes the menus the person is using); collapsible, can move to the other side; respects reduced motion.
- **All wording + rules are pure and unit-tested in `lib/windows/tour-steps.ts`:** 8 steps (welcome · open from the launcher · move/resize · the title-bar buttons (read-only) · hide/restore · Option/Alt-click · close · wrap-up). Each act step has: what it is, "For example", "Try it", a waiting line and a done line. Key names are the person's own (`Option (⌥)`/`Alt`, `Command (⌘)`/`Ctrl`) via `detectPlatform`/`fillKeys`. Practice pages are ONLY Accounts and Leads (Portal Chats/Inbox mark client messages read when opened, also in a window). Pop-out and "Move to the main page" are EXPLAINED, never practised (they end/replace the screen).
- **Steps finish on REAL events.** The window manager emits `td-window-event` (`lib/windows/window-events.ts`: opened {id,url,reused}, moved, resized, minimized, restored, closed {reason: closed|popout|docked}) from the exact places that act on a person's click/drag — never from state diffs (a screen resize, a reload or sign-out also change state). A bare click on the bar is not a move (`classifyDrag`, 20 px). `lib/windows/windows-store.ts` mirrors "which windows exist" for the tour (`useWindowsSnapshot`). The only way past an unfinished step is **Skip this step** (no "I did it").
- **It adapts instead of dying:** `precheck()` per step — 3 windows already open → it practises on one of them and says so; practice window closed → another one, or "Open Accounts for me"; Option-click step blocked if a 4th window would be needed; nothing left to close → auto-done; a plain click that navigates the page gets a gentle nudge; screen narrower than 1,024 px pauses the card. The tour only ever asks the person to close windows IT SAW them open. Windows are marked `data-win-id`/`data-win-part` (titlebar, minimize, close, popout, dock, tray-chip, resize-*) so the ring can find them; the launcher button is `data-tour="win-launcher"`.
- **Entry points:** "Take the 1-minute tour" is the first row of the launcher menu; a NEW tag on the launcher button for 30 days per browser; ONE polite pop-up per person per browser (a persistent toast "New: floating windows — Take the tour? [Show me] [Not now]", key `td-windows-tour-prompted:<userId>`) — NOT a forced start, because the feature is already live. It waits ~10 s, retries while the person types, and never shows to someone who already has windows open, while another tour is open, while the "new version" bar is up (`data-update-banner`), or when the browser can't remember (private mode). The step is kept in `sessionStorage` so a reload (the update banner) resumes it.
- **One tour at a time:** `lib/ui/tour-lock.ts`, taken by both this tour and the WhatsApp tour. The WhatsApp tour also no longer AUTO-starts inside a window's frame or a pop-out browser window (it used up the person's one-time flag where they couldn't see it) nor on top of another tour.
- **Feedback box ("Something off, or an idea?") on every card** (and "Tell us what's off with windows" at the bottom of the launcher menu for after the tour). Sends the note + step + state + Mac/other + screen width + window count + tour version — nothing from the pages. `POST /api/team/windows-feedback` (staff only, `isStaffUser`) → `postTeamMessage` into the Team Chat channel **`td-windows-feedback`** on behalf of the sender, ending with a real `@Antonio` mention that WE add. It deliberately does NOT use the normal team send route: that one starts the @claude worker on "@claude" in a message, pushes every device and has no limits. Everything the person types is defused (`lib/windows/tour-feedback.ts`: every `@` gets a zero-width space, identifiers redacted), 3–1,500 characters, a repeat within 2 minutes answers "ok" without posting twice, 20 notes/hour/person, plain errors (R099). **The channel is never created silently — Antonio creates `td-windows-feedback` in Team Chat; until then the box says exactly that.** Channel ids differ between sandbox and production; it is looked up by slug.
- **Clearer words (UX review), done in the same change:** the feature is "Open in a window" everywhere (it was also "Open in floating window"); the title-bar dock button is "Move to the main page (replaces the page behind)" with a Replace icon (it looked like "make bigger"); "Minimize" (American, like the rest of the CRM); the tray tab says "Click to bring this window back"; pop-out browser windows no longer show "Open in a window" entries that did nothing (`useWindowsAvailable()`/`canOpenWindowNow()` are false in a frame or a pop-out).
- **Tests:** `tour-steps`, `tour-feedback`, `tour-lock-and-window-events`, `windows-tour-wiring`.
- **Known limits:** per browser (Antonio on 3 computers sees the prompt 3 times); not re-tested with a real touch screen (the tour is desktop-only); the ring follows by polling each frame (cheap, stops when the step has no target).

## Gotchas, invariants & past reviews
- **Do not move the button inside the `<Link>`.** The Accounts and Leads *rows* are whole-row links; a nested button there navigates away. The Contacts row is a clickable box (`router.push` + Enter key) where a nested button's Enter would also open the contact. Row ⋯ buttons are **deferred** and need their own structure (overlay/sibling), not nesting.
- **Hover does not exist on phones/keyboards** — never make the reveal hover-only.
- **Installed-app behaviour is UNVERIFIED:** how a standalone (installed) app window treats a new tab or window (see `lib/inbox/attachment-open.ts` ~116-121 and `pwa.md`). Test "Open in new tab" in the real installed Mac app.
- **Menu-library focus return is unverified here:** Radix returns focus to the trigger on close. Harmless for these two actions; matters later if a menu item ever opens a form (the new-lead form auto-focuses its first field). Pass `onCloseAutoFocus` preventDefault for such items.
- **Per-page extra actions ("New lead", "New account") are deferred.** Three reviewers said not to mix "open a page" and "create a record" in one menu; the create dialogs are mounted only inside their own pages and navigate the mounting page after saving.
- **The window system (steps 2–7) has strict conditions from the council** — see the project record: same-origin dashboard paths only (re-checked on restore); remembered windows per signed-in person and cleared at sign-out; the launcher reuses the left menu's permission filter; a push-notification click must not wipe windows; chat marked read only when its window is focused; off-by-default runtime switch; one-day iframe spike before any window code; the shared layout decides "I am in a window" **once at first load and locks it** (refreshes use a different request label).
- **Known open gap, not part of this work:** `/code-tasks` is hidden from non-admins in the menu but has no page-level admin guard and is not in middleware's `ADMIN_ONLY_PATHS` (unverified whether a non-admin can open it by address).
