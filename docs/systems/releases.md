## What it is
Every change that reaches the live CRM carries a small **release note** written in plain English for the team (Antonio, Luca, support). Four places show it:
1. **The blue update bar** (CRM only) gets a **"See what's new"** button. It opens a panel under the bar listing every note newer than the page's own build, newest first, with a picture when something looks different. Nothing reloads while the panel is open (typed work is safe); **Refresh now** is a button in it.
2. **Releases** (left menu, `/releases`) — the whole history, newest first, grouped by day (New York time), filters New / Improved / Fixed, and a link to show the **behind-the-scenes** changes (hidden by default).
3. **The "..." menu** at the top right of the CRM header — a **Releases** entry (a plain in-page link to `/releases`); the menu lists every entry vertically (Help, Notifications, Test, Releases), added 2026-11-12 at Antonio's request.
4. The note files themselves in git (`content/releases/`) — the permanent record.

## Parts
- **Note files** `content/releases/<id>.json` — `id` = file name = `YYYY-MM-DD-HHMM-short-name` (UTC, lower case); fields `title` (≤100), `tag` (`new` | `improved` | `fixed` | `behind-the-scenes`), `text` (≤700, plain English: what it does and WHERE to see it), optional `points` (≤6 short lines), optional `screenshot` (a file in `public/release-notes/`, sandbox test data only — never a real client). Start one with `node scripts/new-release-note.js <short-name>`. Rules and checks: `lib/release/release-notes.ts` (`noteProblems` is the single definition of "well formed").
- **Compiled INTO the build, not read from a database or disk at run time.** `next.config.js` calls `scripts/release-notes-env.js` while loading its config and puts two values into `env`: `RELEASE_NOTES_JSON` (server only — read ONLY by `lib/release/bundled-notes.ts`) and `NEXT_PUBLIC_NEWEST_NOTE` (the newest note id; read by `lib/release/own-release.ts` as `OWN_NEWEST_NOTE` = the page's "I have seen everything up to here" mark). Why: the description always matches the exact build it ships with, no production database step, and `/api/release` keeps its fail-quiet no-DB design. A damaged note file is skipped with a warning at build time and dropped at run time — it can never stop a build or a page; CI (the unit test) is what keeps it out of main.
- **`GET /api/release/notes?since=<note id>`** (`app/api/release/notes/route.ts`) → `{ version, notes, more }`: every note newer than `since`, newest first, without behind-the-scenes ones, at most 25 (`more` counts the rest). No usable `since` (a page built before notes existed, a damaged value) → NOTHING, never everything. Behind the normal login, `no-store`, a baked constant — no database, no Gmail. `GET /api/release` (the minute-by-minute check) is deliberately untouched and carries no notes.
- **`lib/hooks/use-release-notes.ts`** — asked ONCE when the bar appears (plus up to 3 retries 15 s apart if the answer did not come from the announced release yet — `version` must equal the release the bar announces, so a rollout's older instance cannot describe the wrong release). Any failure → no description; the bar works exactly as before.
- **Bar + panel** — `components/shared/update-banner.tsx` (button only when `checkRelease` and there is at least one note) + `components/releases/release-notes-panel.tsx` + `components/releases/release-note-card.tsx` (shared with the page). The panel's "All releases" link opens a NEW tab on purpose: this page is older than the live site, so an in-page navigation would reload it and lose what is typed.
- **Page** `app/(dashboard)/releases/page.tsx` — server component over the baked notes; filters are plain links (`?tag=`, `?all=1`). Menu item `releases` in `components/dashboard/sidebar.tsx`; `releases` is in `WINDOW_PAGE_ROOTS` (`lib/windows/window-model.ts`).
- **Push gate** `scripts/check-release-note.sh`, called from `.husky/pre-push` (after the R107 doc check): a push that changes APP code (`app/`, `components/`, `lib/`, `public/` except `public/release-notes/`, `middleware.ts`, `next.config.js`) must ADD a note file; tests/docs/scripts/hooks alone need none. It also requires each new note's id to sort AFTER the newest note on `origin/main`, so no page can be built "between" and miss it. Override (rare, deliberate): `ALLOW_RELEASE_NOTE_SKIP=1 git push …`. A change nobody will see still gets a note, tagged `behind-the-scenes`.

## The rules
- **A release is not a PR, a job or a deploy.** Sessions merge many changes a day and some builds are skipped. So the panel lists ALL notes newer than the page's build, not "the" note of the latest release.
- **Write the note LAST**, after the final diff, and reread it against what actually shipped — a note written before the change shrank would overstate. Only claim what a person can do or see; if a feature is switched off or not live, say so or tag it behind-the-scenes.
- **No technical words** in a note: no file names, code names, table names, PR/job numbers, "migration", "endpoint", "sandbox".
- **Pictures** are real screenshots from the sandbox with test data. They are public static files (the middleware does not gate `.png`), so never a real client's name, email, amount or document.
- **Descriptions appear one release late the first time:** a page already open when this feature shipped runs old code that knows nothing about notes. From the release after that, every bar can describe what is coming.
- **Not the same as "What's New":** that name already means the portal-chat staff feed, the Calendar news tab and Marketing news. This feature is called **Releases** everywhere.
- Notes are NOT business data: no price, count or client state belongs in one.

## How to verify current state
- Notes parse: `npx vitest run tests/unit/release-notes.test.ts` (checks every real file, the order, the pictures, the route, the wiring and the gate).
- Build output: `node -e "const e=require('./scripts/release-notes-env').releaseNotesEnv('content/releases');console.log(e.NEXT_PUBLIC_NEWEST_NOTE, JSON.parse(e.RELEASE_NOTES_JSON).length)"`.
- Live (logged in): `GET /api/release/notes?since=<an older note id>` returns the newer notes; `GET /releases` lists them. After ANY production deploy of this feature, open `/releases` once and read a real note (R115: parsing code that passes tests can still differ in the minified production build).
- Production-build safety (R115): `tests/unit/release-notes-production-build.test.ts` compiles the note rules with Next's own minifying compiler and runs the compiled code.
- Browser QA recipe that worked on the sandbox (2026-11-12): start `next dev` stamped `NEXT_PUBLIC_BUILD_SHA=aaaaaaa` with the newest few notes moved out of `content/releases/`, log in and open the CRM, then restart it stamped `bbbbbbb` with the notes back. **Block the dev server's live-reload socket in the test browser** (Playwright `routeWebSocket(/webpack-hmr/, ws => ws.close())`) — otherwise the restart reloads the page onto the new release and no bar ever shows. The bar appeared by itself after about a minute, "See what's new" listed exactly the moved-out notes, nothing reloaded until Refresh.
- The bar itself: keep a CRM tab open across the next deploy; when the blue bar appears, "See what's new" is next to Refresh and opens the notes written for that deploy. To test without a deploy, see the sandbox method in `pwa.md` (restart the local copy as a different release) with a newer note file present.

## Known limits
- A note whose id sorts BEFORE the newest note a page was built with is never offered to that page (the gate prevents this for new notes; a hand-renamed file could break it). The bar still shows, just without that text — never wrong text.
- The client portal, TD Talk, Marketing and the phone apps do not run the release check, so they have no panel (their staff-facing news lives elsewhere).
- Italian is not supported: notes are English, for the CRM team.
