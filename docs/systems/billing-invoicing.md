## What it is
Everything about money on invoices. There are **four separate money "worlds"** that look similar but must never be mixed up — confusing them is the #1 source of billing bugs:

1. **TD billing the client** — Tony Durante LLC's invoices *to* clients (our revenue). → `payments` table.
2. **The client's own sales** — invoices the client sends to *their* customers (their business, not ours). → `client_invoices` table.
3. **The client's expenses** — what the client owes, including a *mirror* of our TD invoices so they see them in the portal. → `client_expenses` table.
4. **TD's own operating costs** — vendor bills, filing fees, software TD pays. → `td_expenses` table.

## Business rules
- **R027** — `client_invoices` is for the client's sales invoices ONLY. **TD systems NEVER write to it.** (CLAUDE.md)
- **R092** — Invoice emails to clients must send them to the **portal Pay button** to pay. NEVER embed Stripe checkout links, wire details, or payment credentials in the email body. (CLAUDE.md)
- **R098** — Invoice-number generation is race-safe via a DB unique index + caller retry, NOT a code retry/timestamp fallback. Never write `invoice_number` directly — always go through the helper functions. (CLAUDE.md)
- **Credit netting (at invoice-creation only)** — a real (positive, unpaid) TD bill automatically applies the account's outstanding credit notes (oldest first, same currency, capped at the bill) **at invoice-creation time** (`computeCreditApplication`/`consumeCredits`). This is the ONLY remaining automatic credit application; for invoices that already exist, credits apply via click-to-apply Regenerate (below). Rule lives in code: `lib/operations/credit-netting.ts`.
- **Credit application = CLICK-TO-APPLY (2026-06-03)** — credits are NOT auto-applied to existing invoices. A new credit note / referral credit sits as available `credit_remaining` on the account and lands on a SPECIFIC invoice only when staff click **Regenerate** on it (see below). This replaced the old auto-reconcile-onto-oldest behaviour, which made a credit earned in June silently reduce an overdue January invoice (the Wise Strategies bug). `reconcileAccountCredits()` / `allocateCredits()` remain in `credit-netting.ts` but are **NO LONGER CALLED** — do not re-wire them into credit creation.
- **Regenerate invoice document = applies available credit (2026-06-03)** — `regenerateInvoice(paymentId)` (`app/(dashboard)/payments/invoice-actions.ts`) applies the account's available credit to THIS invoice (capped at what it still owes), shows it as a `Credit applied −$X` line, drops `amount_due`, and consumes the credit (stamping `credit_for_payment_id` = this invoice). **The invoice you click is where the credit lands.** In place — same invoice number, no money moved; `amount_paid` tracks REAL cash only (credit is shown purely as the line, never folded into `amount_paid`). Idempotent: a re-click with no remaining available credit re-renders the same document. Generic for ANY account-scoped invoice/service. Pure helpers in `lib/portal/invoice-regenerate.ts` (`computeClickToApplyCredit` etc.), unit-tested; applies/consumes via `computeCreditApplication`/`consumeCredits`. No-op when there is no existing or available credit. UI: Regenerate button on Draft/Sent/Overdue/Partial invoices in the Payment Tracker dialog (`invoice-detail-dialog.tsx`) AND both Finance views (`clients-invoices-tab.tsx`, `all-invoices-tab.tsx`).

## How it's built
### The two creator functions (single entry points)
- **`createTDInvoice()`** in `lib/portal/td-invoice.ts` — TD → client. Writes **`payments`** (primary, staff-facing) + **`payment_items`** + a **`client_expenses`** mirror row (vendor "Tony Durante LLC", its own `EXP-NNNNNN` internal ref) so the client sees the bill as an incoming expense in the portal. Sets `qb_sync_status='pending'` — a **legacy/inert column: QuickBooks is DEAD (decommissioned 2026-05-23), nothing ever reads or advances it**. **Never writes `client_invoices`.**
- **`createUnifiedInvoice()`** in `lib/portal/unified-invoice.ts` — client → their customer. Writes **`client_invoices` only**. No `payments` mirror, no QB sync. Resolves/creates a `client_customers` row.

### Invoice numbers
- `generateInvoiceNumber()` in `lib/portal/invoice-number.ts` — one **global** sequence `INV-NNNNNN`, computed as max+1 across **both** `payments` and `client_invoices` (strict `LIKE 'INV-______'` so legacy oddities don't poison the max). It is intentionally simple and **not race-safe by itself**.
- `generateCreditNoteNumber()` (same file) — separate **`CN-NNNNNN`** sequence (payments-scoped) for **credit notes**, so a credit never reads as an invoice. `createTDInvoice` picks CN- automatically whenever `grossTotal <= 0` (a credit note); INV- otherwise. (Added 2026-06-01.)
- Race safety = partial unique indexes `uq_payments_invoice_number` / `uq_client_invoices_invoice_number` + a **10-attempt retry loop** in the creator functions that regenerates on a 23505 unique-violation. `isUniqueViolation()` detects the specific constraint. **No timestamp-suffix fallback** (that produced the `INV-NNNNNN-XXXXXXXX` scars deleted after the April-12 collision incident — R098).

### Idempotency (content-level dedup)
Both creators accept an optional `idempotency_key`; if a row with that key exists, the existing invoice is returned (no duplicate). `payments` also has `uq_payments_idempotency_key` as a concurrent-insert guard. Standard keys: `offer-signed:TOKEN:CONTACT_ID`, `annual-installment:ACCT:N:YEAR`, `manual-crm:ACCT:HASH`.

### Status & sync
- `payments.status` = Pending/Paid (+ Partial/Overdue/Cancelled/Split); `payments.invoice_status` = Draft/Paid.
- `syncTDInvoiceStatus()` keeps the `client_expenses` mirror in step with the payment (maps payment status → expense status; partial payment stays Pending). `reconcileTDInvoiceMirror()` repairs a drifted mirror.
- `installment` uses `payment_type_enum`: Setup Fee, Installment 1 (Jan), Installment 2 (Jun), Annual Payment, One-Time Service, Custom.
- Currency USD/EUR; `bank_preference` is a free-form string. Resolution in `lib/invoice-auto-send.ts::resolveBankDetails` via the pure helper `selectSettingsBank()`: (1) `settings_bank:<uuid>` — the bank whose stable `id` matches in `invoice_settings.bank_accounts` (preferred; robust to reorder/delete); (2) `auto`/null — `is_default` bank from invoice_settings for matching currency, then first bank of that currency, then Mercury/Airwallex fallback; (3) legacy enum (`relay/mercury/revolut/airwallex`) → hardcoded constants. The legacy positional `settings_bank_N` form is still parsed as a harmless fallback but is no longer produced by the dialog nor accepted by the DB constraint. `is_default` is scoped per currency (radio button in Invoice Settings UI). DB guard `payments_bank_preference_check` allows null / the 5 enum values / `^settings_bank:[0-9a-fA-F-]{36}$`.

### Cancel ↔ Reactivate (2026-07-10)
- **Cancel** (`voidInvoice`) → `payments.status`/`invoice_status` = `Cancelled`, mirror synced, bank feeds unlinked, **and a `pre_void_state` snapshot written to `action_log.details`**.
- **Reactivate** (`reactivateInvoice`) → restores the snapshot when present, else derives via `resolveReactivateTarget` (`lib/billing/invoice-reactivate.ts`, pure + unit-tested). Preview (`reactivateInvoicePreview`) warns how many automatic chase emails the client will receive.
- **Where the buttons live:** Finance → All Invoices, Finance → By Client, account page → Payments tab. Cancel is hidden on Paid and on already-Cancelled invoices (Antonio's rule: *"if an invoice is paid there is no reason to void it; if a payment is matched but I need to change the invoice I can edit instead"*). Reactivate shows ONLY on `Cancelled` — never on `Waived`/`Voided`, which are different lifecycle ends.
- **Never relink bank feeds on reactivate.** The correct match is not recoverable; re-match from the Bank Feed tab.
- **Never point the By Client tab at `/api/portal/invoices/*` or `app/portal/invoices/actions`.** Those operate on `client_invoices` (the client's own sales ledger). This tab renders `payments`.

## Gotchas, invariants & past bugs
- **Never write `client_invoices` from any TD/staff flow** (R027) — it's the client's own sales ledger.
- **Never set `invoice_number` directly or add a timestamp fallback** — go through the two creator functions (R098). The April-12 collision came from a fallback format; it was deleted on purpose.
- **`createTDInvoice` is the ONLY entry for new TD invoices** — it deliberately uses raw Supabase (lint rule disabled inline) because the retry loop needs raw error codes that the `dbWrite` wrapper strips.
- **Credit netting is automatic** on real unpaid bills. To create a credit note itself (or any invoice that must not net), pass `skip_credit_netting: true` — otherwise a credit can wrongly net into it. A bill fully covered by credit is marked **Paid, $0 due** with an explicit "service − credit = $0" description.
- **Keep the `client_expenses` mirror in sync** via `syncTDInvoiceStatus` / `reconcileTDInvoiceMirror` — don't update the mirror by hand.
- **Invoice emails → portal Pay only** (R092). No Stripe/wire in the email body.
- **Card processing fee — CHARGED, booked at payment time, one authoritative column** (2026-07-15, dev_task `6ec6872a`, SANDBOX/branch `claude/card-fee-charge-6ec6872a`). The card surcharge (today 5%) was displayed everywhere but never collected on Stripe (regressed when Stripe replaced Whop). Now: both checkout routes charge `base × (1 + pinned rate)`; the Stripe webhook books the fee ONTO the invoice from the ACTUAL charge BEFORE the settle (`bookCardFee` in `lib/finance/card-fee-booking.ts` → then `applyMoneyToInvoice`), because the settle caps `amount_paid` at the invoice total. `bookCardFee` is ALL-OR-THROW + idempotent (one fee line via the partial unique index `uq_payment_items_one_fee_per_payment`; `total = charged` is a SET) → a failure returns non-200 and Stripe retries from a non-terminal invoice. Fee math lives ONLY in `lib/payments/card-fee.ts` (`computeCardTotal` for display+charge; `deriveFeeFromCharge` for booking — never recompute the rate at booking, book `charged − base`). **The money-truth is `payments.card_fee_amount`; the fee LINE (`payment_items.item_type='fee'`) is a projection kept equal. Invariant (live-tested): `card_fee_amount = sum(fee lines) = total − base`.** `base = sum(item_type<>'fee')`. **Every `payment_items` writer MUST preserve `item_type`** — `buildRegeneratedLineItems` + the credit-netting reinsert now do; `updateInvoice` is Draft-only (a fee only exists once Paid) so it never sees one; voids fully cancel (invariant untouched). A base/charge mismatch books NO fee and raises a staff `portal_issues` "!" alert (overage review); a paid-but-activation-failed case raises one too (deduped on the gateway payment id). Rate config in `app_settings.payment_fee_config.card_rate`, read ONLY at creation, PINNED onto `offers.card_fee_rate` / `payments.card_fee_rate` so editing it never re-prices a signed deal. **LIVE ON PROD since 2026-07-15 (PR #158, main @ 46cf4e1b) — deployed with the fee OFF per the go-live runbook.**
- **Global kill switch + Finance UI button (Council-approved Phase A, 2026-07-15).** `payment_fee_config.enabled` (default ON when missing) is checked by `resolveChargeRate()` at BOTH checkout routes: OFF → effective rate 0, overriding every per-deal pin, no redeploy. Admin-only switch card on Finance → Overview (`app/(dashboard)/finance/card-fee-switch.tsx` → `toggleCardFee` server action in `finance/actions.ts`): the role check lives INSIDE the action (`isAdmin`), not just page placement; two-step inline confirm; copy states the ~60s propagation (per-instance config cache) and that already-issued payment links keep their price. Flips are audit-logged to `action_log` (`card_fee_enabled_changed`, actor `finance-ui:<email>`).
- **Two hardening invariants (Council blockers, 2026-07-15):** (1) `setConfiguredCardFeeRate` MERGES into the `payment_fee_config` JSONB (`{ ...current, card_rate }`) — a whole-object write would delete `enabled:false` and silently re-arm the fee. (2) The offer-signed webhook passes the OFFER's pinned rate into `createTDInvoice` via `pinnedRateForInheritance()` (`lib/payments/card-fee-config.ts`) so the sign-time invoice INHERITS the deal's pin instead of re-reading live config — prerequisite for any per-deal waiver (a waived offer must not mint a 5% invoice). `agreement-signed` is deliberately NOT changed: it is an offer-less renewal root and correctly pins the configured rate. Tests: `tests/unit/card-fee-config.test.ts`, `tests/unit/card-fee-switch-action.test.ts`.
- **ASSUMPTION the card-fee refund policy rests on — do not break silently:** "refund keeps the 5%" (Antonio's decision) currently holds ONLY because **there is NO automatic refund path** — refunds are MANUAL credit notes (`createCreditNote`), staff-entered, so nothing auto-returns the fee. If anyone ever builds an auto-refund (e.g. a Stripe `charge.refunded` webhook → credit note), it MUST credit the BASE only (a −base line, `card_fee_amount=0` on the credit note) and leave the original invoice's fee line + `card_fee_amount` intact — else it silently hands back the service amount AND orphans a now-unmatched fee. (dev_task `6ec6872a`.)
- **The dunning PASS is `lib/billing/dunning.ts::runDunning` — shared by the daily `invoice-overdue` cron AND the dashboard "Run reminders now" button (`POST /api/invoices/run-dunning`, admin).** It does TWO jobs: (a) mark Sent/Partial invoices Overdue when past due — ALWAYS runs; (b) send due reminders — **queued to the background job system, not sent inline.** `enqueueDueReminders()` bulk-enqueues an `invoice_reminder` job (handler `lib/jobs/handlers/invoice-reminder.ts` → `sendInvoiceReminder`) per due invoice at **priority 8** (below operational priority-5 jobs, so a reminder burst never delays formation/onboarding), deduped against already-pending jobs in one query, via `enqueueJobs()` (single bulk insert + one worker trigger). The shared `process-jobs` worker (~10/5min, retries, Exception Center) delivers them — no function timeout, no email-reputation spike. The cap now **bounds enqueues per pass** (`getDunningCap()` reads `app_settings.dunning_autosend.cap`, default `DUNNING_RUN_CAP`=40, clamped 1–`DUNNING_CAP_MAX`=1000 via pure `clampCap()`; UI "Max per run" field). Eligibility = pure `shouldRemindNow()` (1st at r1, 2nd at r2, cap 2; unit-tested). At send time `sendInvoiceReminder` re-checks the invoice STATUS (so an invoice paid between enqueue and send is skipped, not emailed) and the ACCOUNT PAUSE (boolean `dunning_pause` + dated `dunning_pause_until`, 2026-07-03) — but NOT the 2-reminder cap (that is enqueue-time only). **Automatic sending is controlled from the UI, NOT an env var:** `isAutoSendEnabled()` reads `app_settings` key `dunning_autosend` (value `{enabled:boolean, cap:number}`, default OFF/40); the ON/OFF toggle + "Max per run" field + "Run reminders now" button live at the top of **Finance → All Invoices** (admin-only). The old `DUNNING_AUTOSEND_ENABLED` env var is retired. With auto-send off, invoices are still flagged Overdue so the dashboard list + manual/bulk "Send Reminder" (independent of the cron) keep working. Per-account `dunning_reminder_1_days` default 7, `_2_days` default 14, cap 2, `dunning_pause`; the `/api/invoices/[id]/remind` route and the manual "Send Reminder" finance action use the same function. **The cron MUST call it in-process — never via an internal `fetch` to `process.env.VERCEL_URL`.** That self-HTTP pattern hit the Vercel "Authentication Required" deployment-protection wall and sent ZERO reminders while logging ~119 errors/day (discovered 2026-06-19, dev_task `d2af38a1`). Reminder emails are bilingual EN/IT by `contacts.language`. Cadence is per-account configurable from the **account page → Payments tab → "Payment Reminder Settings"** (edits `dunning_reminder_1_days` / `_2_days` / `dunning_pause` via `updateAccountField`, which whitelists + range-validates them 1–365). Each invoice row in Finance → All Invoices also shows a reminder badge (count + last sent + auto/manual) and supports bulk reminders (`sendBulkReminders`, cap/pause-aware). `dunning_escalation_email` and a global default are not yet wired (read-but-unused / code-default 7/14).
- **Invoice recipient resolution is centralized in `resolvePaymentRecipient()` — never hand-roll a `role = 'Owner'` lookup.** Priority: `payment.contact_id` → owner-role contact (CASE-INSENSITIVE: "Owner"/"owner"/"Co-Owner" all qualify) → any linked contact with an email → `accounts.communication_email`. The old code duplicated an exact-case `.eq('role','Owner')` match in three send paths; accounts whose owner link was stored lowercase `"owner"` resolved zero rows, so resend errored "No contact email found" even though the contact had a valid email (the **ADWise incident, 2026-06-18**, dev_task `63431fc8`). All three paths now delegate to the resolver. NOTE: the *first* send for ADWise (INV-002346) still went out fine — only the account-anchored **resend** (payment with `contact_id` null) hit the brittle owner branch.
- **Banks are referenced by stable id, not list position.** An invoice stores `settings_bank:<uuid>`; each bank in `invoice_settings.bank_accounts` carries an `id` (assigned on add in the settings UI via `crypto.randomUUID()` + backfilled server-side in `app/api/invoice-settings/route.ts`). This replaced the old positional `settings_bank_N` (2026-06-16) which had a latent bug: the dialog indexed the active-filtered list while `resolveBankDetails` indexed the unfiltered list, so an inactive bank could put the wrong bank on an invoice. The DB CHECK constraint (`payments_bank_preference_check`) was widened to accept `settings_bank:<uuid>` via `scripts/migrations/20260616-1410-widen-payments-bank-preference-constraint.sql` (production DDL applied via Supabase dashboard — the MCP tool blocks DDL).
