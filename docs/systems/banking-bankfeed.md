## What it is
Two related-but-separate systems:
1. **Banking applications** — helping a client open a business bank/fintech account (Relay, Mercury, Revolut, Airwallex). Driven by the banking form + a "Banking Fintech" service delivery.
2. **Bank-feed reconciliation** — auto-matching TD's *own* incoming payments (wires/transfers) to the right TD invoice, marking it paid, and (if it was a signed offer) triggering the client's activation. This is the money-in engine.

Most of the complexity — and bugs — live in #2.

## Bank-feed reconciliation — how it works
1. **Incoming transactions land in `td_bank_feeds`** — synced from Plaid (`lib/plaid-sync.ts`), Airwallex (`lib/airwallex-sync.ts`), or the Banking Circle webhook (`app/api/webhooks/banking-circle/route.ts`). Cron: `app/api/cron/plaid-sync`, `airwallex-sync`, `run-matcher`.
2. **The matcher** `matchAndReconcile(feedId)` in `lib/bank-feed-matcher.ts` compares a feed against:
   - `payments` invoices that are NOT terminal (`Paid`/`Voided`/`Cancelled`), and
   - `pending_activations` with `status='awaiting_payment'`.
   Confidence levels: **exact** (amount within $1/€1), **high** (within 5% + sender name contains the account/client name), **medium** (within 5% only). An **invoice-number reference found in the memo + matching amount is the strongest** match. `STOP_WORDS` strips generic business words ("LLC", "consulting", "wise"…) so names don't cross-match.
3. **On a confident match** → marks the invoice **Paid**, sets the feed `status='matched'`. (It also calls `syncPaymentToQB`, but **QuickBooks is DEAD** — that call is an inert no-op; see "Gotchas" below.)
   - **Installment payments fire the installment handler (Tax Return Phase 1, 2026-06-08).** After marking an **installment** invoice Paid, the matcher dispatches `onInstallmentPaid` (`lib/operations/payment.ts`) — classified via `payment_category` (`isFirstInstallment`/`isSecondInstallment`), guarded to `account_type='Client'`, fire-and-forget so a handler error never rolls back the match. This is what advances the bundle's Tax Return card on a real wire 2nd-installment payment (previously only manual mark-paid / the June cron did, so wire-payers got stranded). See `tax-returns.md`.
4. **The orchestrator** `processBankFeedMatches()` (`lib/operations/process-bank-feed-matches.ts`) walks a batch and, when an invoice with a linked `pending_activation` is auto-paid, runs the activation chain (`runActivation`). Per-feed outcome is one of: `auto_activated`, `needs_review`, `activation_crashed`, `no_match`.
5. **Manual review** for anything not auto-matched: the **`/reconciliation`** page (`matchFeedToInvoice`, `ignoreFeed` in `actions.ts`) + the Finance "Bank Feed" tab; admin actions `bank-feed-confirm-match`, `bank-feed-reject-match`, `bank-feed-retry-activation`.

## Payment identity — the resolution ladder (2026-07-14)

**The question every incoming payment must answer: _whose money is this, and which invoice is it for?_** The ladder below is tried in order. Anything that cannot answer both halves goes to a human — it is never guessed.

| # | Signal | Certainty | What happens |
|---|--------|-----------|--------------|
| 0 | **Stripe PaymentIntent id** (`raw_data.payment_intent` == `payments.stripe_payment_id`) | Certain | Open invoice → settle. **Terminal invoice → audit link only, ZERO money** (`certain_retroactive`). >1 candidate row → prefer the one with an `invoice_number`; still ambiguous → `needs_review` with all candidates. |
| 1 | **Invoice number carried on the payment** (PaymentIntent metadata → `sender_reference`) + amount within 5% | Certain | Auto-settle (`exact`). This is the tier that makes card payments self-reconciling. |
| 2 | **Payer identity (billing email)** → contact → `account_contacts` → accounts | Strong | **Scopes the candidate pool to that payer.** With an exact amount → `high` (review-scoped, NOT auto-settled by default). |
| 3 | Company / contact **name** in the feed text + amount | Medium | `exact` on an exact-amount name hit; `high` within 5%. |
| 4 | **Amount only** | Weak | `medium` → `needs_review`. Never auto-settles. |

**Why identity is email-first, and why the NAME is not trusted on card payments.** Stripe's `sender_name` is the **cardholder**, not the client: Bilaal Rajan pays for Simple Holdings USA, and Tamás Fazekas arrived as the truncated "Fazek". Matching on it produced nothing useful — and worse, amount-only matching would then pin a *stranger's* invoice as the one-click candidate (a $50 card payment sat one click away from settling an unrelated company's $51 invoice). **When identity resolves, only that payer's invoices are candidates. If none of theirs fit, we do NOT fall back to everyone else's** — the feed waits for a human. Losing an automatic match is cheap; crediting the wrong client is not.

**Why a known payer with an exact amount still does not auto-settle.** A client can hold two invoices of the same price (Simple Holdings holds exactly that: two $50 notary invoices). Identity + amount cannot tell them apart — only the invoice number can. That is what tier 1 is for; it needs no human at all.

## The terminal rule — read BOTH columns, but they are not equal (2026-07-14, code review)

`payments` carries two status columns and they disagree in production. The rule is **not** "terminal if either is terminal" — that was the first attempt and it broke a real receivable.

1. `invoice_status` closed (Paid / Voided / Cancelled / Credit / Split) → **terminal**.
2. `status` says the money is **already settled or returned** (Paid / Refunded) → **terminal, always**, even if `invoice_status` still reads Sent or Overdue. *This is the landmine*: 48 production invoices are Paid via `status` with a NULL `invoice_status`, and reading `invoice_status` alone left them creditable a second time.
3. `invoice_status` is present and open → **MATCHABLE**, even when `status` says Cancelled or Waived. **Three live invoices are exactly this** — INV-002084 (Fiscalot) has been part-paid and still owes **$500**. Vetoing on `status` made that $500 impossible to receive: the matcher ignored it, staff could not select it, and a manual attempt reported success while moving no money. `invoice_status` is the operational column the Finance UI reads; it wins when present.
4. No `invoice_status` at all → fall back to `status`; the administrative states (Cancelled / Waived / Not Invoiced) mean nothing is owed.

**Audit-linking is only for an already-PAID invoice** (`isPaidInvoice`). A manual match onto a Cancelled or Voided invoice is **rejected loudly** — recording a cheerful "linked" with no money applied is the same silent-success failure this work exists to kill.

## The money-write invariants (do not "simplify" these away)

Every write to the `payments` money columns goes through **`applyMoneyToInvoice`** (`lib/finance/apply-payment.ts`). It is the only writer. It guarantees:

1. **Never credit a terminal invoice.** Returns `applied:false` + a reason. It does **not** silently no-op while reporting success — that silent-success is precisely how a "matched" feed could leave an invoice untouched.
2. **Never apply the same transaction to the same invoice twice.** The insert into `payment_applications` (UNIQUE on `(feed_id, payment_id)`) is the gate; a unique violation means *already applied*. **This is load-bearing**: `amount_paid` now ACCUMULATES, so without it a double-click or a cron re-run would credit the money twice.
3. **Never over-credit.** `resolveInvoiceStatusAfterPayment` caps `amount_paid` at the invoice total; the surplus stays visible on the feed.
4. **Always write the full tuple** (`status`, `invoice_status`, `amount_paid`, `amount_due`, `paid_date`) so the two status columns can never drift apart again.
5. **Always leave an `action_log` row.** Automatic settlement previously left no trace at all.

**A PART-PAYMENT NEVER ACTIVATES, AND NEVER SETTLES ITSELF.** Two guards, both needed: the orchestrator skips activation on a partial (auto path), and `settleInvoiceFromFeed` returns before the activation chain on a partial (manual paths, which have no orchestrator above them). Without the second one, staff manually matching a $500 wire to a $2,200 invoice triggered activation, which called the writer in `settle_full` mode and **credited the $1,700 nobody paid** — stamping the invoice Paid and logging an audit row swearing it was settled. The multi-invoice waterfall makes this the NORMAL path, not an edge case: its last funded invoice is a Partial by design. `activate-service` additionally refuses outright to settle an invoice that already carries a real part-payment — a Partial reaching activation means an upstream guard failed, and it must say so rather than invent the balance.

**Widened, deliberately (2026-07-14):** an invoice with `status='Cancelled'` and an OPEN `invoice_status` is matchable again. That is the Fiscalot fix (a real $500 receivable). Two other production rows share the shape — SupraEmerge INV-001381 ($51) and a $1,000 Tax Return — and appear to be genuinely cancelled invoices whose `invoice_status` was never updated. They now show in the Finance suggestion list reading "Overdue". A wire (which carries no email, so payer identity cannot scope the pool) could pin one as a candidate. Known and accepted; the cleanup is a per-record owner decision, not a bulk update.

**A `matched` feed does not always mean money moved.** `MatchResult.moneyApplied === false` marks the **audit-link** case — the invoice was already settled through another channel and the feed is linked for the trail only. Callers must not report that as a payment being reconciled. **The orchestrator does not activate a client's service on `moneyApplied === false` or on a `partial` settlement** — a part-payment does not meet the obligation, and activation follows the closing payment.

**TWO GUARDS, TWO DIFFERENT JOBS. NEITHER IS REDUNDANT — DO NOT DELETE EITHER.**

- **The compare-and-swap on the invoice guards CONCURRENCY.** The money write lands only if `amount_paid` is still exactly what was read moments earlier; zero rows affected means another process moved the invoice first, so nothing is applied. This makes "no double credit under a race" a database **fact** rather than an assumption. (NULL and 0 are different values to Postgres — the predicate must match how the row actually reads, and every invoice touched by the old writer has a NULL balance.) It is sufficient to guard `amount_paid` alone **because every money writer goes through the one writer, and the one writer always writes that column**. ⚠️ If a future writer ever moves money without touching `amount_paid`, this guard silently stops working.
- **The `payment_applications` ledger guards IDEMPOTENCY OVER TIME.** The CAS is perfectly happy to credit the *same transaction* to the *same invoice* an hour later — it re-reads the new balance and swaps cleanly. The `UNIQUE (feed_id, payment_id)` row is the **only** thing that says "this transaction has already paid this invoice". A restored feed, a cron re-run, a staff double-click after a refresh all land here.

**An error from the money write does NOT mean the write failed.** The client library reports an error whenever it cannot get a *response* — including when the update **committed** and the reply was lost (timeout, reset connection, function killed mid-flight). Assuming failure and releasing the lock sets up a double credit on the next pass, and the CAS cannot catch it because the retry reads the *post-write* value. So the failure path **goes and looks at the invoice**: balance equals the new value → the write landed, confirm the claim and report success; balance unchanged → it genuinely failed, release the lock; anything else → keep the lock and raise it loudly for a human. This is the last place an assumption was hiding.

**The lock is claim-then-confirm, and it releases by ID.** `applyMoneyToInvoice` claims the (feed, invoice) pair *before* writing, with `confirmed_at` NULL, and confirms it only once the money lands. Three rules, each earned in review:
  - **Release by the claim's own id, never by (feed, payment).** A delayed failing attempt deleting by the pair could remove a *different* attempt's row — one that had meanwhile succeeded — leaving the money applied with no lock, so the next pass credits it twice. Precisely what the table exists to prevent.
  - **An unconfirmed claim is not proof money moved** — only that someone started. A claim left behind by a process that died mid-write (function timeout, redeploy) is stale after 5 minutes and may be taken over. Without this, one crash brands a transaction *"already applied"* forever — a lie, with no UI escape.
  - Only **confirmed** rows count toward the invariant — and **the invariant is scoped**: `sum(confirmed applications) == amount_paid` holds **only for invoices settled from a bank feed**. Money credited through the Stripe webhook, Whop, `confirm-payment` or `activate-service` carries **no feed id**, so it writes **no ledger row**. In general the rule is `sum(confirmed applications) ≤ amount_paid`. ⚠️ Anyone building an invariant/health report from the unscoped version will flag **every card-paid invoice as corrupt** — which is exactly the kind of false alarm that gets a real report switched off.

**The ledger records what was CREDITED, not what arrived.** A $650 wire against a $500 balance credits $500 (the cap). The claim row records $500. Recording the raw $650 would make the ledger permanently disagree with the invoice, which defeats its only purpose.

**The invoice reference beats the amount.** An invoice named by the payment is never discarded on an amount mismatch — the amount filter runs *after* the reference check. A referenced-but-mismatched amount goes to review (how much to apply is a judgement call), it is not thrown away. Putting the number on the payment is pointless if the figures being off silently voids it.

**Never read `amount_due` to decide whether an invoice still owes money.** It is NULL on every invoice ever touched by the old writer — the very bug that produced the half-closed rows — and `Number(null)` is `0`, so a guard reading that column concludes "nothing outstanding" on precisely the rows most likely to be broken. It fails OPEN, on the worst possible set. Compute the balance as `total − amount_paid`.

**The refund check must protect the HUMAN too.** Guarding only the auto-matcher left staff able to one-click a refunded charge from the review queue, with the screen showing them the ordinary amber "confirm this match" banner. Both are now covered: the manual path re-checks Stripe and refuses, and the row renders a loud red REFUNDED block. The machine being protected while the person is not is exactly the wrong way round.

**A refunded Stripe charge must never be applied — on ANY tier.** The stored charge is a snapshot: a refund issued after we synced it leaves our copy saying "received" forever. **Every** settlement of a Stripe feed re-checks the charge with Stripe first — not just the payment-intent tier. (Guarding that tier alone was a trap: now that the invoice number travels with the payment, the *invoice-reference* tier becomes the dominant path, so the guard would have covered the route about to become rare and missed the one about to become common.) Outcomes: refunded/disputed → parked for review; a transient Stripe failure → **do not settle, retry next run** (the cash is already in the bank, waiting costs nothing, booking a refund costs a client); Stripe unconfigured or the charge id unknown → proceed unchecked with a warning, because deferring forever would strand the feed and help nobody.

## Business rules
- **R092** — clients pay TD via the portal; the portal Pay modal shows an **obligatory payment reference (the invoice number)**. The same required reference is now also on the **emailed invoice and the invoice PDF** — for wires, the typed reference is the ONLY identifying signal that exists. That reference is what makes auto-matching reliable — without it, only the amount can match (see the Patrick Covelli case below).
- Invoice payment recording flows through the invoice/billing system (see `billing-invoicing.md`); the matcher uses `syncInvoiceStatus`.

## Gotchas, invariants & past bugs
- **⛔⛔ THE REVIEW QUEUE NEVER WORKED — AND NOBODY KNEW, BECAUSE THE CODE THREW THE ERROR AWAY (2026-07-14).** `td_bank_feeds` has a CHECK constraint listing permitted `status` values. It was written when the table was created and never updated. `needs_review` and `activation_crashed` were added LATER, in code, with three UI surfaces each — a Needs Review tab, a Crashed tab, a sidebar badge, a Retry button — **and no migration**. Every attempt to park a transaction for a human was therefore rejected by the database. For months. Production had **zero rows, ever**, in either status. And the code never noticed: **supabase-js RETURNS errors, it does not throw**, and every feed write discarded the result. Staff looked at an empty review tab and reasonably concluded there was nothing to review.
  - **The constraint didn't break anything. The discarded error did.** A write you did not verify is not a write — the same sentence that closed the money-writer bug, sitting one file away, missed by three reviewers across five rounds of review.
  - **Every `td_bank_feeds` write now goes through `updateFeed()`** (`lib/finance/feed-write.ts`), which checks the result, reports failures via `reportSystemError`, and refuses up-front to write a value not in the shared vocabulary.
  - **The vocabulary lives once**, in `lib/finance/feed-vocabulary.ts`; the migration generates the CHECK from it; the **code↔database contract gate** asserts the database still agrees. It runs on every push (`npm run check:db-contract`, no credential — it compares the code against `db/constraints.prod.json`, production's checksum-verified constraint snapshot), and **daily against LIVE production** from inside this very cron (`lib/db-contract-monitor.ts`, step 6 of `check-wire-payments`), raising a dev-board job the moment the code and production disagree. Full design in `hooks-guardrails.md`. **The daily monitor is the only layer that can see prod DDL applied by hand in the Supabase dashboard — which is how prod migrations are actually run here, and which no push-time gate can ever see.**
- **⚠️ SANDBOX IS NOT A SCHEMA REPLICA — A GREEN TEST RUN THERE PROVES NOTHING ABOUT PRODUCTION.** Sandbox had **zero** CHECK constraints on `td_bank_feeds`; production had three. That is why a 32/32 integration harness passed while production rejected the writes. Any "sandbox verified" claim about a constrained column is worthless until the constraint exists in both. The parity migration (`20260714-2100`) fixes this table; **the rest of the schema is still unaudited.**
- **⛔ NEVER add `diagnostic` to the `match_confidence` CHECK.** Two CRM diagnose routes used to write it inside an **unbounded fuzzy-name bulk update** that stamped one payment id onto EVERY matched feed whose sender name merely *contained* the company string — no amount check, no limit, no review. It never landed a single row, purely because the constraint rejected the value: **the CHECK was accidentally shielding us from a mass mis-attribution of payments for months.** The write is deleted (2026-07-14). Legalising the value would switch the landmine on.
- **⚠️ `retroactive` IS LOAD-BEARING, NOT A LABEL.** The retroactive pass builds its "this invoice is already claimed by a transaction" set by querying it, and that set is what stops two payments being attributed to one invoice. A new audit-link confidence value would be **invisible** to the guard. Audit-link kinds (certain / fuzzy / manual) live in `review_metadata.link_kind`. As of 2026-07-14 the guard keys on `status='matched' AND matched_payment_id IS NOT NULL` instead — closing a **live hole** where an invoice *settled* by one wire (confidence `exact`) was not in the set, so a later similar-amount feed could still retro-link to it.
- **⚠️ EMAIL LOOKUPS MUST BE CASE-INSENSITIVE.** CRM emails are not reliably stored lowercase and Stripe reports whatever the client typed. An exact-match lookup resolves NO identity for any client with a capital letter in their address — and the failure is indistinguishable from "not our client", so the entire identity engine quietly does nothing for part of the client base. Caught in code review; the first sandbox harness passed only because its fixture happened to be lowercase. The harness now stores a mixed-case email deliberately.
- **⚠️ `payment_applications` MUST EXIST IN PRODUCTION BEFORE THE CODE DEPLOYS.** The writer refuses to move money it cannot record, so if the table is missing, EVERY settlement — automatic and manual — fails closed and reconciliation stops dead. It fails safe (no wrong money) but it is a total outage. Prod DDL is Supabase-dashboard-only on this project: run `scripts/migrations/20260714-1500-payment-applications.sql` and verify it, THEN deploy.
- **⚰️ NEVER dedup bank feeds on content (2026-07-14).** The `check-wire-payments` cron used to flag a feed as `duplicate` when it shared `source + amount + transaction_date + sender_name` with another unmatched row. `transaction_date` is a **DATE** — so a client legitimately paying two same-priced invoices on the same day with the same card produced two identical-looking rows, and **the second genuine payment was silently flagged a duplicate**. Every sync path already upserts on `external_id` (the provider's own transaction id) with a unique conflict target, so a true duplicate is impossible by construction. Content similarity is evidence of a client paying twice, NOT of a duplicate. The block is deleted. If a future source really does emit one deposit under two ids, dedup on the provider's transaction id — never on amount + name + day.
- **`duplicate` must stay VISIBLE.** It had no filter tab, no colour and no count, so it fell through to the "ignored" renderer — which is *why* the wrongly-flagged $50 went unnoticed. It now has a purple tab, a count and a **Restore** button (`restoreBankFeed`, which only touches rows whose status is `duplicate`).
- **Every ingest path MUST go through the orchestrator** (`processOneFeed` / `processBankFeedMatches`), never `matchAndReconcile` directly. `matchAndReconcile` marks the invoice Paid but knows nothing about `pending_activations`: a wire arriving via the Relay or Banking Circle webhook paid the client's invoice and **never activated their service** — and the cron could not rescue it, because by then the feed was no longer `unmatched`. Fixed 2026-07-14 for both webhooks + the run-matcher cron.
- **Stripe does NOT copy Checkout Session metadata onto the PaymentIntent or the Charge.** We set the invoice number on the Session for months; `charge.metadata` was `{}` on every payment we ever took, so the feed had no reference and reconciliation had only the amount to go on. Fix: set `payment_intent_data.metadata` at checkout AND read `charge.payment_intent.metadata` via `expand:['data.payment_intent']` in the sync — do **not** rely on Stripe's inheritance rules. **This assumption is the original bug; do not re-introduce it.**
- **`is_test` invoices are excluded from matching.** A QA fixture sharing an amount could otherwise absorb real client money.
- **⚠️ PostgREST enum filtering is unreliable** — `.in()`/`.eq()` on the custom `invoice_status` / currency enums returns wrong rows. The matcher deliberately **fetches broadly and filters status + currency in JS**, using a *blocklist of terminal statuses* (not an allowlist) so a new status never silently drops a matchable invoice. Keep this pattern.
- **Partial invoices** match against `amount_due` (remaining balance), not `total`.
- **No over-credit invariant (2026-06-17):** `resolveInvoiceStatusAfterPayment` caps `amount_paid` at the invoice `total` (`Math.min(currentPaid + applied, total)`). A wire larger than the balance (e.g. $650 manually matched to a single $500 invoice) marks it Paid for exactly $500 — `amount_paid` can never exceed `total`. The surplus is intentionally NOT applied to the invoice; the true received amount still lives on `td_bank_feeds.amount`, so an overpayment stays visible as feed-amount > invoice-paid. The multi-invoice waterfall already passes `min(remaining, balance)` so the cap is a no-op there. **(Updated 2026-07-14 — the sentence that used to sit here said this function "has exactly one caller, so the change is contained to manual matching". That is now the OPPOSITE of true: it lives in `lib/finance/invoice-money.ts` and is the shared money math for EVERY writer, via `applyMoneyToInvoice`. Do not reason from the old claim.)** It also rounds both outputs to cents — the columns are scale-2 but the arithmetic is float, and `0.1 + 0.2` would otherwise persist `0.30000000000000004` into an invoice.
- **`activation_crashed`** feeds are parked in the review queue with a Retry button — the invoice was paid but the downstream activation failed; don't treat as lost.
- **PAST BUG — Patrick Covelli (fixed 2026-05-29):** a third-party payer + a contact-scoped invoice (no company name) + no invoice reference in the memo → only the amount matched → stuck in needs-review, and the manual link UI was company-only. Fix: `invoice-party.ts` surfaces the person's name, the link UI handles contact-scoped invoices, and the portal Pay modal now shows the obligatory wire reference. Root lesson: **the invoice-number reference is the reliable matcher** — push clients to include it.
- **⚰️ QuickBooks is DEAD / decommissioned (kill-switch `QB_ENABLED` OFF since 2026-05-23, dev_task `eca3ce5c`).** `syncPaymentToQB` is still *called* here (and from invoice send and void in `finance/actions.ts` + `invoice-auto-send.ts`), but every function in `lib/qb-sync.ts` early-returns a no-op **before** any DB read/write or QB API call — it syncs nothing, writes nothing, logs nothing. These fire-and-forget calls are harmless leftover plumbing. **Do NOT treat QB as a live part of the system, do NOT build on it, and do NOT try to "complete" or re-enable it.** Removing the plumbing is a separate, planned cleanup — the three callers still `import lib/qb-sync.ts`, so deleting that file naively would break the build.
