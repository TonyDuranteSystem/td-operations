# CRM Storage
_Last verified against code: 2026-09-23 — Claude (dev job 762b2515)_

## What it is
A general-purpose, staff-only file storage area inside the CRM — folders and files organized however staff set them up, with no connection to the older Google-Drive-backed client documents system. Desktop-first by deliberate design (Antonio and Luca both run the CRM on desktop). Ships with three actions beyond plain browsing: click a file to preview it inline instead of downloading it, and share an existing file straight to email, a client's portal chat, an internal team chat thread, or a fax number. Sending for e-signature is explicitly out of scope — no tool in this codebase lets an existing file be dropped straight into a signature envelope; that would need its own follow-up.

## Business rules
- No per-file or per-upload size cap, by design (Antonio: needs to hold things like full Zoom call recordings). Every *share* destination has its own real ceiling instead, because each one copies the file into a different store: chat destinations mirror the `assets` bucket's own 100MB cap, email mirrors Gmail's ~18MB combined-attachment cap, fax is capped low (3MB) because the request has to survive being base64-encoded into a single JSON body with no server-side size guard of its own.
- Staff-only, end to end — a portal client can never reach any of it. Reachable by a managed partner (Cris) only at the database layer if they bypass the app entirely and call Supabase's own REST API directly with their own session; the app itself always blocks partners on these routes via `requireStaffRoute`/`isStaffUser` + `middleware.ts`'s blanket partner confinement.
- Sharing to a client's portal chat is the one client-facing action here. It always shows a mandatory confirm screen before sending, always pings staff with an instant alert the moment it sends (an unrecallable-send safety net), and is deliberately modeled on the same pattern already shipped and reviewed for the Captures screenshot tool.
- A stored file is a reusable library item, not a one-shot capture — sending the same file to the same place twice, deliberately, is allowed (e.g. resending an invoice a client says they can't find). What isn't allowed is *accidentally* sending it twice from one click — see Gotchas.

## How it's built
- **Tables:** `crm_storage_folders`, `crm_storage_files`, `crm_storage_favorites`, `crm_storage_send_locks` (a short-lived claim table, not user-facing data — see Gotchas).
- **Storage:** a dedicated private bucket, `crm-files`. Uploads go straight from the browser to Storage via the resumable (TUS) protocol, authenticated with the uploader's own session — not the service role — so the bucket's own RLS policy is the real gate on that one write path.
- **Key files:**
  - `app/(dashboard)/storage/` — the page and the (large, single) browser client component.
  - `app/api/crm-storage/` — every route: `tree`, `folders`, `folders/[id]`, `files/mint-path`, `files/register`, `files/[id]`, `files/[id]/download`, `files/[id]/preview`, `files/[id]/share-team-chat`, `files/[id]/share-portal-chat`, `search`, `favorites`.
  - `lib/crm-storage/` — `name-guard.ts` (name validation + the shared ILIKE-escape helper), `preview-kind.ts` (pure mime-type → renderer classifier, kept out of the `.tsx` file so it's unit-testable), `share-limits.ts`, `share-actions.ts`, `fetch-file.ts`, `constants.ts`, `folder-path.ts`.
  - `components/storage/` — `file-preview-modal.tsx`, `share-file-modal.tsx` (the destination chooser), `share-team-chat-picker.tsx`, `share-portal-chat-picker.tsx`, `share-fax-dialog.tsx`.
  - `lib/portal/chat-attachment.ts` — the active-content type block-list, reused (not duplicated) by both share routes.
- **Data flow, upload:** browser mints a unique path (`files/mint-path`) → uploads directly to Storage via TUS → registers the row (`files/register`), which now reads the *real* object size back from Storage itself rather than trusting whatever the browser claims.
- **Data flow, share:** validate (size, file type, recipient eligibility) → copy the bytes into the destination's own store (`assets` bucket for chat; nothing copied for email/fax, which fetch bytes client-side and hand them to the existing compose dialog / fax endpoint) → deliver through the real, already-hardened send route for that destination (never a shortcut).

## Gotchas, invariants & past bugs
- **The preview route and the download route are two different signed-URL calls on purpose.** Preview omits `download` so the browser renders the file inline; download sets it so the browser saves it. Don't merge them.
- **Duplicate-name checks must escape ILIKE metacharacters.** A raw name containing `_` or `%` is a SQL wildcard, not a literal character — an unescaped check produces false "already exists" rejections against unrelated names. Fixed via `escapeIlikePattern` in `name-guard.ts`, applied at every duplicate-check call site. The database's own partial unique indexes (case-insensitive, scoped by parent) are the real backstop against an actual race; the app-level check is only there for a friendly error message.
- **The two share routes hold a real, short-lived database claim (`crm_storage_send_locks`) for the duration of a send**, released whether it succeeds or fails. This exists specifically because a plain "check the recent message log" guard only catches a *sequential* double-click — two genuinely simultaneous requests (a double-click, or the same file open in two tabs) can both pass that check before either has written anything, since the copy-then-send round trip is multi-second. Verified live: firing two truly concurrent requests at the same file/destination, exactly one succeeds. Don't remove this table thinking the message-log check alone is sufficient — it isn't, under a real race.
- **Every file's declared size must come from Storage itself, never from the uploading browser's own claim.** `files/register` reads the real object back from Storage before writing `file_size` — a client-supplied size that was never checked used to quietly defeat every downstream size limit.
- **A stored file's type is checked against the same active-content block-list the portal's own chat-attachment upload path uses** (`lib/portal/chat-attachment.ts`), at share time, on both chat destinations — not just relying on whatever the browser reported when the file was originally uploaded. This closed a real gap: an unvalidated file could otherwise reach a client's portal chat and render inline at the CRM's own domain.
- **RLS on these tables excludes both `client` and `partner`**, matching the established convention for every other internal-only table (a real 2026-07-22 incident is why that convention exists) — not just `client` alone. The app itself already blocks partners via a stricter check and via `middleware.ts`, so this is defense-in-depth, not the only thing standing between a partner and this data — but don't let a new table drift back to excluding `client` alone.
- **No production auto-deploy is guaranteed from a `git push` alone** — verify a deployment actually started and went `READY` for the pushed commit before telling anyone something shipped; it has been unreliable before.

## How to verify current state
- Confirm the four tables and the `crm-files` bucket exist in whichever environment you're checking: `SELECT table_name FROM information_schema.tables WHERE table_schema = 'public' AND table_name LIKE 'crm_storage_%'` and `SELECT id, public FROM storage.buckets WHERE id = 'crm-files'`.
- Confirm the RLS policies exclude both roles, not just one: `SELECT tablename, policyname, qual FROM pg_policies WHERE tablename LIKE 'crm_storage_%'` — `qual` should reference both `'client'` and `'partner'`.
- Confirm the active migrations on disk: `scripts/migrations/20260920-2300-crm-storage-v2-desktop.sql`, `20260921-1230-crm-storage-unique-names.sql`, `20260923-1411-crm-storage-council-hardening.sql`.
- Confirm which tool file registers these routes and whether anything changed since: `grep -c "register.*Tools" app/api/[transport]/route.ts` is not relevant here (this is a plain Next.js dashboard feature, not an MCP tool) — instead just re-read `app/api/crm-storage/**` directly; there's no separate registration step to drift from the code.
