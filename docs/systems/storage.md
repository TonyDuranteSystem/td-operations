## What it is
A general-purpose, staff-only file storage area inside the CRM — folders and files organized however staff set them up, with no connection to the older Google-Drive-backed client documents system. Desktop-first by deliberate design (Antonio and Luca both run the CRM on desktop). Ships with three actions beyond plain browsing: click a file to preview it inline instead of downloading it, and share an existing file straight to email, a client's portal chat, an internal team chat thread, or a fax number. Sending for e-signature is explicitly out of scope — no tool in this codebase lets an existing file be dropped straight into a signature envelope; that would need its own follow-up.

## Business rules
- No per-file or per-upload size cap, by design (Antonio: needs to hold things like full Zoom call recordings). Every *share* destination has its own real ceiling instead, because each one copies the file into a different store: chat destinations mirror the `assets` bucket's own 100MB cap, email mirrors Gmail's ~18MB combined-attachment cap, fax is capped low (3MB) because the request has to survive being base64-encoded into a single JSON body with no server-side size guard of its own.
- Staff-only, end to end — a portal client can never reach any of it. Reachable by a managed partner (Cris) only at the database layer if they bypass the app entirely and call Supabase's own REST API directly with their own session; the app itself always blocks partners on these routes via `requireStaffRoute`/`isStaffUser` + `middleware.ts`'s blanket partner confinement.
- Sharing to a client's portal chat is the one client-facing action here. It always shows a mandatory confirm screen before sending, always pings staff with an instant alert the moment it sends (an unrecallable-send safety net), and is deliberately modeled on the same pattern already shipped and reviewed for the Captures screenshot tool.
- A stored file is a reusable library item, not a one-shot capture — sending the same file to the same place twice, deliberately, is allowed (e.g. resending an invoice a client says they can't find). What isn't allowed is *accidentally* sending it twice from one click — see Gotchas.

## How it's built
- **Tables:** `crm_storage_folders`, `crm_storage_files`, `crm_storage_favorites`, `crm_storage_send_locks` (a short-lived claim table, not user-facing data — see Gotchas).
- **Storage:** a dedicated private bucket, `crm-files`. Uploads go straight from the browser to Storage via the resumable (TUS) protocol, authenticated with the uploader's own session — not the service role — so the bucket's own RLS policy is the real gate on that one write path.
- **Key files:**
  - `app/(dashboard)/storage/` — the page and the (large, single) browser client component.
  - `app/api/crm-storage/` — every route: `tree`, `folders`, `folders/[id]`, `files/mint-path`, `files/register`, `files/[id]`, `files/[id]/download`, `files/[id]/preview`, `files/[id]/share-team-chat`, `files/[id]/share-portal-chat`, `search`, `favorites`.
  - `lib/crm-storage/` — `name-guard.ts` (name validation + the shared ILIKE-escape helper), `preview-kind.ts` (pure mime-type → renderer classifier, kept out of the `.tsx` file so it's unit-testable), `share-limits.ts`, `share-actions.ts`, `fetch-file.ts`, `constants.ts`, `folder-path.ts`.
  - `components/storage/` — `file-preview-modal.tsx`, `share-file-modal.tsx` (the destination chooser), `share-team-chat-picker.tsx`, `share-portal-chat-picker.tsx`, `share-fax-dialog.tsx`.
  - `lib/portal/chat-attachment.ts` — the active-content type block-list, reused (not duplicated) by both share routes.
- **Data flow, upload:** browser mints a unique path (`files/mint-path`) → uploads directly to Storage via TUS → registers the row (`files/register`), which now reads the *real* object size back from Storage itself rather than trusting whatever the browser claims.
- **Data flow, share:** validate (size, file type, recipient eligibility) → copy the bytes into the destination's own store (`assets` bucket for chat; nothing copied for email/fax, which fetch bytes client-side and hand them to the existing compose dialog / fax endpoint) → deliver through the real, already-hardened send route for that destination (never a shortcut).

## Gotchas, invariants & past bugs
- **The preview route and the download route are two different signed-URL calls on purpose.** Preview omits `download` so the browser renders the file inline; download sets it so the browser saves it. Don't merge them.
- **Duplicate-name checks must escape ILIKE metacharacters.** A raw name containing `_` or `%` is a SQL wildcard, not a literal character — an unescaped check produces false "already exists" rejections against unrelated names. Fixed via `escapeIlikePattern` in `name-guard.ts`, applied at every duplicate-check call site. The database's own partial unique indexes (case-insensitive, scoped by parent) are the real backstop against an actual race; the app-level check is only there for a friendly error message.
- **The two share routes hold a real, short-lived database claim (`crm_storage_send_locks`) for the duration of a send**, released whether it succeeds or fails. This exists specifically because a plain "check the recent message log" guard only catches a *sequential* double-click — two genuinely simultaneous requests (a double-click, or the same file open in two tabs) can both pass that check before either has written anything, since the copy-then-send round trip is multi-second. Verified live: firing two truly concurrent requests at the same file/destination, exactly one succeeds. Don't remove this table thinking the message-log check alone is sufficient — it isn't, under a real race.
- **Every file's declared size must come from Storage itself, never from the uploading browser's own claim.** `files/register` reads the real object back from Storage before writing `file_size` — a client-supplied size that was never checked used to quietly defeat every downstream size limit.
- **A stored file's type is checked against the same active-content block-list the portal's own chat-attachment upload path uses** (`lib/portal/chat-attachment.ts`), at share time, on both chat destinations — not just relying on whatever the browser reported when the file was originally uploaded. This closed a real gap: an unvalidated file could otherwise reach a client's portal chat and render inline at the CRM's own domain.
- **RLS on these tables excludes both `client` and `partner`**, matching the established convention for every other internal-only table (a real 2026-07-22 incident is why that convention exists) — not just `client` alone. The app itself already blocks partners via a stricter check and via `middleware.ts`, so this is defense-in-depth, not the only thing standing between a partner and this data — but don't let a new table drift back to excluding `client` alone.
- **No production auto-deploy is guaranteed from a `git push` alone** — verify a deployment actually started and went `READY` for the pushed commit before telling anyone something shipped; it has been unreliable before.

## The new store (replaces Google Drive) — foundation slice 1, SANDBOX ONLY
The permanent record model of the storage that will replace Google Drive (master plan v4.4, `memory/plan_drive_to_crm_storage_master_plan.md`, jobs `bbf7bca1` → `685467b5`). Applied to **sandbox** 2026-09-24 (`scripts/migrations/20260924-2300-crm-store-foundation-s1.sql`); **not in production**; dark — nothing writes to it yet (writers = slice 2). It sits beside the v1 `crm_storage_*` tables above, which stay until the Storage screen moves onto the new model.
- **Tables (`store_*`):** owners (company / person / formation-in-progress / one Unfiled), folders, files, file versions, record links (service case, tax return, signature request, e-sign envelope, fax), file subjects, tags, facts, events (append-only), external refs (the ONLY place Drive ids live). Private bucket `crm-store`.
- **Invariants enforced in the database:** one owner per file/folder (file owner = folder owner); cross-owner moves only via `store_rehome_subtree` / `store_rehome_file` / `store_attach_formation` (privileged flag + per-owner advisory locks); no cascade deletes, no deletes at all outside the (slice-4) purge; saved versions immutable except OCR text; a filed file never takes a new version or un-files; purged file = permanent tombstone; no folder loops; one root per owner; live names unique per folder (case/Unicode-insensitive); CRM service cases / tax returns / signature requests / e-sign envelopes that hold stored documents cannot be deleted (plain-English refusal).
- **Company lifecycle is never stored** — active/archived is read from `accounts.status` through the `storage_lifecycle_map` catalog; only storage-only overlays are stored (in formation / in onboarding / archived formation).
- **Formation:** storage-only owner keyed to the formation service case from payment; when Articles create the company, `store_attach_formation(case, account)` converts that owner in place (same folders/files, root renamed); `store_ensure_owner('company', …)` auto-attaches an in-formation owner whose case is linked to that account; idempotent; cancelled formations refused. The CRM formation model (person-first until Articles) is unchanged.
- **Contacts view:** `store_company_contacts(account)` — company–person links (not the members list; a Single-Member LLC has one owner, no members) with roles normalised via the `storage_contact_roles` catalog; owners + members only; a role-less single link = owner; ended links (`account_contacts.ended_at`, new) excluded; `store_unmatched_contact_roles()` reports roles nobody mapped. The members list's own end date will come from `members.end_date` (job `f4c5c023`, unshipped) — not duplicated here.
- **Catalogs (editable without a deploy):** `storage_folder_kinds`, `storage_folder_templates`, `storage_document_types` (seeded from the 42 `document_types`; explicit personal list: Passport, ID Document, Proof of Address, Utility Bill, ITIN Letter, Form W-7, Form 1040-NR; SS-4 and company returns incl. - **Access:** RLS on, no policies → service role only. Routes must use `lib/crm-store/access.ts` (explicit allow-list admin/team from `app_metadata` only — NOT the app-wide blocklist). Pure rules in `lib/crm-store/rules.ts` mirror the SQL normalisation.

## The new store — slice 2: the one writer (SANDBOX ONLY)
Applied to sandbox 2026-09-25 (`scripts/migrations/20260925-1100-crm-store-s2-writer.sql`), not in production, dark (no flow calls it yet).
- **One write step, `store_write(jsonb)`** (called only through `lib/crm-store/writer.ts`): identity = the caller key (flow + source record + slot), **globally unique among non-purged files** — a re-homed file keeps it, so a re-save versions it where it now lives; SHA-256 only decides same vs new version. Statuses: created / versioned / unchanged / frozen / trashed. Record links, subjects and facts are written in the same transaction on every non-refused outcome. Document type and year are set at creation only; filing status only moves forward; a filed file refuses new bytes (`StoreFrozenFileError`) but an identical retry or a re-render with `contentChanged:false` is "done". No-identity saves are always new files; names auto-suffix " (2)" within 255 chars.
- **Server bytes:** `saveBytesToStore()` uploads to an id-based path, reads the real size back, registers; removes its object only if no saved version refers to it (a lost reply can't destroy a committed save).
- **Browser uploads:** `createUploadIntent()` (explicit staff allow-list) → the browser TUS-uploads (x-upsert false) ONLY into its own slot in the private `crm-store-staging` bucket (one INSERT policy, `store_staging_upload_allowed`) → `registerStagedUpload()` registers small files at once and queues files over 150 MB as job `crm_store_register_upload`; the slot is a lease (`store_claim_intent`), so a killed attempt resumes; finalised by `store_finalize_intent`.
- **Cleanup:** `cleanupStore()` closes abandoned slots and removes crm-store objects no version refers to (`store_abandoned_intents`, `store_orphan_objects`). Not yet scheduled.
- **Production-Drive guard — LIVE IN PRODUCTION 2026-09-25, shipped alone (PR #556)** (`lib/google-drive-guard.ts`, called in every write function of `lib/google-drive.ts`): outside the production database (NEXT_PUBLIC_SUPABASE_URL or EXPECTED_SUPABASE_REF = production ref) every Drive write target must sit inside the configured TEST Shared Drive (`GOOGLE_SHARED_DRIVE_ID`, never the production drive); the "MyDrive"-named helpers are checked by their real parent. Proven against the real Drive: refused with no test drive, refused on a real production client folder, allowed (and trashed) inside the test drive. Production: early return, no lookup, no change.
- **Proofs:** `scripts/crm-store/s2-proofs.sql` (10 write-step checks, rolled back) and `npx tsx scripts/crm-store/s2-proofs.ts [--big-mb=N] [--prod-folder=<id>]` (18 MB save + retry, two simultaneous saves = one file, resumable staged upload, real Drive guard).
- **Upload size limit:** the Supabase project-wide upload limit was ~50 MB in both projects (sandbox test: 45 MB passed, 55 MB → 413). **Sandbox raised to 2 GB by Antonio 2026-09-25** → proven: 60 MB and **1 GB** resumable uploads registered (1 GB: upload ~191 s, streamed hash + move ~61 s — which is why files over 150 MB are registered by the background job, not inline). **Production's global limit was not measured** (not readable by SQL; two production buckets have their own 100 MB cap, so it may already be higher). Do not raise it first: that global limit is the only ceiling on most production buckets (the client form-upload and signed-document buckets have no limit of their own) — set per-bucket limits there first, then raise the global one. Production has never stored a file over 23.7 MB. At ~61 s per GB, a file of several GB would outrun the job runner's 300 s window — not yet handled.

## The new store — slice 4: trash, restore, purge, folder upload, folder zip (SANDBOX ONLY, dark)
Applied to sandbox 2026-09-25 (`scripts/migrations/20260925-2000-crm-store-s4-trash.sql`). Nothing calls it; **the purge is NOT scheduled** (scheduling needs Antonio's go, a kill switch default OFF, a dry-run, a fail-closed CRON_SECRET route like `email-bin-purge`, and slice 5's Drive safety copy live first).
- **Trash (`store_trash_file` / `store_trash_folder`)**: one action = one batch; bottom-up; one event PER item (batch id, filing status, purge date). Each item gets `purge_after` stamped when it is trashed — a later settings edit never shortens it; `store_trash_days()` reads `storage_settings/trash` but is clamped to 90–3650 (Antonio #31: 90 days) and falls back to 90 on a bad value. Only **custom** folders can be trashed (never the root or a template folder — the five-folder layout and the Drive mirror must hold). A second click is refused under the owner lock. Nothing in the trash can be re-homed to another client.
- **Restore (`store_restore_batch`)**: back to the original folder when it is live and the same owner, else into a caller-named folder of the SAME client (refused otherwise); " (2)" on a taken name (`store_free_name`); one event per restored item; anything not yet purged is restorable (a held or not-yet-swept file stays restorable); a fully purged batch is refused (no empty shells); an amendment whose original was meanwhile amended by another live file is skipped (never two current filings — the writer also refuses a second live amendment of one original).
- **Legal holds (Antonio #61, catalog `storage_purge_holds`, `store_file_purge_hold`)**: W-7 / W-7 COA, and passport/ID in the ITIN folder or linked to an ITIN case, held 3 years after their year (IRS acceptance-agent rule, Pub. 4520); filed/amended tax returns held forever. Held files stay in the trash, restorable, never purged. SOP 17 amended the same day.
- **Purge (`store_purge_due` / `store_purge_file` + `purgeExpiredStore` in `lib/crm-store/folders.ts`)**: only past the file's own `purge_after`, only on the database clock (`store_purge_clock`: a caller's future date is ignored unless a proof sets `store.purge_clock_test`), under the owner lock; returns `not_due` / `held` / `already_purged` instead of failing; tombstone FIRST (row + versions + events kept; links/subjects/tags/facts copied into the purge event then removed so CRM deletes are no longer blocked), bytes removed AFTER; a failed removal is retried from `store_purge_pending_objects()`. This order is deliberate (the email bin deletes bytes first) — do not "fix" it. The tally returns failures with file ids for the future route to report.
- **"Remove from view" (`store_remove_link`)**: drops ONE record link (the file leaves that staff workspace), logged; not a trash, and does not change what the client sees (that is the publish switch).
- **Folder upload (`startFolderUpload` + `store_ensure_folder_path(owner, parent, path[], actor)`)**: name rules applied BEFORE bytes move (no empty / "." / ".." parts, no control characters, ≤255; a backslash is a legal character in the database — the screens' naming rule refuses it); the database refuses a parent of another client; custom folders created once (case/space-insensitive); max 500 files per call; one bad file = one refused line, the rest proceed. `createUploadIntent` now also checks the folder is live and belongs to the owner.
- **Folder zip (`store_folder_zip_listing` + `streamZip`)**: the listing runs every file through the slice-3 per-file check for portal viewers (staff get all live files); the stream is pulled at the downloader's pace (no read-ahead), checks each file's byte count, makes paths safe on every OS and unique (`safeZipPaths`), and refuses up front above 2 GB / 2,000 files (`StoreZipTooLargeError`; the zip library supports files up to 4 GB). A file that cannot be opened becomes a "…could not be included.txt" note.
- **Proofs:** `scripts/crm-store/s4-proofs.sql` (11 checks) must end `ALL S4 CHECKS PASSED`; `npx tsx scripts/crm-store/s4-proofs.ts` (real zip, real folder upload, real purge) must end `ALL S4 STORAGE CHECKS PASSED`. Slice 3's amendment chain now walks through trashed/purged amendments (found by these proofs).
