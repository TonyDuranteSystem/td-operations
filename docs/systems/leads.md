The Leads behaviour is identical (the page body was moved, not rewritten — a test compares it with the stored original). The `booking` switch (off / page / live) does NOT touch the Leads tab. ## What it is
The place where new inquiries that have not signed yet are worked (the first stage of the client journey): a list (table or board), three groups (open leads / already-clients who booked / converted), a search box, filters, a row-click window with the lead's details, and the lead's own page. Staff (administrator and team logins) use it every day.

## Business rules
- **Who sees it:** every staff login — role `admin` or `team` (the same rule as the Booking page: `lib/auth/booking-access.ts`, allow-list in `lib/team/workspace.ts`). A client, a partner, a marketing login or a signed-out visitor gets the ordinary not-found page / refusal. Two layers: the middleware confines clients, partners and marketing to their own areas, and the Booking page checks the visitor first, before it reads anything. In the database the rule `auth_read_leads` lets any signed-in user read `leads` and `marketing_blocked` stops a marketing login (read from production on 14 Nov) — the list itself reads with the visitor's own login (not the service key), except the "client check" answers (service key).
- **The three groups** (the `client` parameter, mutually exclusive, applied to BOTH the table and the board): none = open leads (`existing_client_contact_id` empty, status not Converted); `clients` = people who are already clients and booked a call; `converted` = status Converted. Converted means payment confirmed (R094).
- **The `booking` switch has nothing to do with Leads.** Leads is daily work: it behaves the same when `booking` is off, page or live (a test feeds the page every state). The "Turned off" banner and the inactive buttons live only on the "Links and calls" tab.
- **Page size** 50 rows (table), the board shows at most 200; one group is fetched whole (up to 1000) so the filter buttons and counts are exact.

## How it's built
- **The address.** The list is the tab `leads` of `/booking`. Parameters the list reads: `q` (search), `page`, `view` (`kanban`; none = table), `client` (`clients` | `converted`; none = open leads), the filters `status`, `src`, `ref`, `offer`, `call`, `follow`, `quick`, and `focus` (scroll to a row after a search pick). The Booking page's own parameter is `tab` (`leads` | `links`); no list parameter is called `tab`, so they cannot collide. Pure helpers in `lib/leads/leads-url.ts` (`leadsListHref`, `parseBookingTab`, `linksTabHref`; `tests/unit/leads-url.test.ts`): `leadsListHref(params)` keeps every parameter in order, forces `tab=leads` (an old link carrying its own `tab` is overridden) and always returns a path on this site.
- **The old address.** `app/(dashboard)/leads/page.tsx` is only `redirect(leadsListHref(searchParams))`: every old link, bookmark and Home-card link (`/leads?id=<lead>` — note the list never read `id`, and still does not; it lands on the list) arrives on the tab with its query string. `app/(dashboard)/leads/loading.tsx` stays (it is also the loading screen of the lead page). The lead page `app/(dashboard)/leads/[id]/page.tsx` and its actions are untouched, except that "Delete lead" now returns to the Leads tab.
- **The body.** `components/leads/leads-workspace.tsx` (`LeadsWorkspace`, a server component) is the old page's body, unchanged below the imports. It checks nobody: only `app/(dashboard)/booking/page.tsx` imports it, after its staff check (a test pins that nobody else does). The client pieces stayed where they were: `app/(dashboard)/leads/components/{leads-kanban,leads-view-toggle,leads-client-filter-toggle,create-lead-dialog,create-lead-button,new-lead-from-call}.tsx` and `components/leads/{leads-table,leads-filter-bar,existing-client-new-calls,lead-row-actions,lead-window-host}.tsx`. Every control that changes the list's address builds it with `leadsListHref` (a test bans a bare `/leads?`).
- **Data/logic:** `lib/leads/*` (list-filters, phone-search, client-match, client-check-data, existing-client-new-calls, contact-calls…), the lead window routes `app/api/crm/leads/[id]/window/*`, the edit routes `app/api/crm/admin-actions/update-lead-*`.
- **Menu, tour, windows.** One left-menu row, **Booking** (`id: 'booking'`, in the Network group), replaced the old Leads row; it is lit on `/booking`, on `/leads` and on `/leads/<id>`. `revalidatePath('/booking')` replaced `revalidatePath('/leads')` (Intake and Client health actions). The windows tour's "fast way" step now practises on Booking (`isLeadsPracticeUrl`). `WINDOW_PAGE_ROOTS` keeps both `leads` and `booking` (the folders both still exist). A saved menu layout that held `leads` drops it and gets Booking back in Network.

## Gotchas, invariants & past bugs
- **Moving the body, not rewriting it, is the whole proof of "identical behaviour".** `tests/unit/leads-workspace-parity.test.ts` compares the component's body with `tests/unit/fixtures/leads-page-body-before-move.txt` (the old page's body, stored from main before the move): every line identical except the function name. If you change the body, change the fixture on purpose and say why.
- **A tag that follows a `}` in the Booking page must be closed with a closing tag, not `/>`** — the standing access scan reads `/>` after a `}` as a regex and refuses the file (see `booking.md`).
- **A redirect inside a page that has a `loading.tsx`** can come out as a page-level redirect instead of a plain HTTP redirect; the browser follows it either way. Check with the real address when you touch it.
- **Notes made on the list are labelled "Booking"** (`describeOrigin` falls back to the first path segment); notes made on a lead's page are still "Leads".
- **The list still has two headings** ("Booking" above the tabs, "Leads" inside the tab): the body was not rewritten on purpose.
