## What it is
One address book that shows everyone we already have in the CRM (read only: the Contacts people and the Partners) and lets staff save the OTHER people who have no place in the CRM (suppliers, lawyers, a banker met at an event). It has two books on the phone: **Company** (CRM people + people saved here, visible to the team) and **Personal** (only Antonio). The Contacts page and the contacts table are NOT touched and nothing saved here ever becomes a CRM contact.

## Business rules (Antonio, 14 Nov 2026)
- **Standalone.** Reads contacts (507 on 14 Nov) and partners (13) read only. Never writes to them, never adds a foreign key to them (86 tables already point at contacts; the WhatsApp matcher, name suggestions and the AI search read every contact).
- **No hard-coded types.** Types and each type's extra boxes are created by Antonio in the address book (catalog `address_book_types`; none seeded). Box kinds: text, date, number, yes/no, no rules between boxes. Hiding a type = status `deprecated`; its people keep working.
- **CRM people get their type by suggestion + his confirmation**, kept in `address_book_crm_labels`, never on the Contacts data.
- **Personal book = ONE login** (the primary owner, `lib/auth.ts` `PRIMARY_OWNER_EMAIL`). Not the other owners (`NEXT_PUBLIC_EXTRA_OWNER_EMAILS`), not admins, not the team, not the AI tools.
- **A copy to the iPhone's own Contacts** is wanted (Personal on by default, Company off). It needs a NEW TD Social build + Apple review: the app has no Contacts permission today. Not built.
- Defaults I chose and flagged to him: the Company book (with the people saved there) is visible to the whole team; Personal on phone and computer for him alone.

## How it's built
- **Tables** (migration `scripts/migrations/20261114-2100-address-book-foundation.sql`, UNDO next to it; all RLS on, `REVOKE ALL … FROM anon, authenticated`, service client only):
  - `address_book_entries` — the Company book's own people. Plain columns (name, company, job title, website, phones, emails, address, notes), `phone_keys` (digits only, plus the last ten digits of a longer number) and `emails` (lower case) written by code for "already saved" lookups, `extra` jsonb = the type's boxes, `type_entry_id` → catalog row, `source` (typed | email | whatsapp | card | other), `archived_at` soft delete.
  - `address_book_personal` — one **encrypted** payload per person (`payload_enc`, AES-256-GCM), `owner_user_id`. No readable column holds a name or number. **Also revoked from the `ai_readonly` role** (Slack worker, Hermes `crm_query`) and listed in `BLOCKED_TABLES` (`lib/mcp/tools/hermes-read.ts`).
  - `address_book_crm_labels` — `(subject_kind contact|partner, subject_id)` unique → confirmed type. `subject_id` has NO foreign key on purpose; a label whose person is gone or merged must be ignored by code.
- **Catalog:** `address_book_types` (definition inserted by the migration, no entries). Entry `metadata` = `{"boxes":[{"key","label","kind"}],"color","sort_order"}`. A unique index on the lower-cased name keeps two types from sharing a name.
- **Key files:** `lib/address-book/crypto.ts` (encrypt/decrypt, key from env `ADDRESS_BOOK_PERSONAL_KEY` ≥ 32 characters, owner id bound in as AAD so a payload cannot be moved to another owner), `lib/address-book/types.ts` (box schema, `parseTypeMeta`, `cleanExtra`, `phoneKey`, `normalizeEmail`, `lookupKeys`, `personInputSchema`), `lib/address-book/personal-access.ts` (`canUsePersonalBook` / `personalOwnerId`). Tests: `tests/unit/address-book-*.test.ts` and the two extra `address_book_personal` rows in `tests/unit/crm-query-readonly.test.ts`.
- **Env:** `ADDRESS_BOOK_PERSONAL_KEY` is NOT set anywhere yet (needed before the Personal book can store or open anything; the book is switched off while it is missing or short). Set it per environment (sandbox, production) when step 3 (phone) starts; never reuse another secret.
- **Database types:** `lib/database.types.ts` does not know the new tables (regenerate through the CI artifact, see the memory note), so `store.ts` and `type-admin.ts` use the client untyped, the way `lib/marketing` does.

## The page and how it works (step 2)
- **Who:** any STAFF login (an administrator or a team login) — `lib/address-book/access.ts` (`isAddressBookStaff`; app_metadata and the code's email list, never user_metadata). The page checks FIRST (ordinary "not found" for anyone else); every route's first statement is `requireStaff()` / `requireStaffJson(req)` (403, no-store; a change must also come from our own page: same-origin JSON). `tests/unit/address-book-routes.test.ts` walks every route and runs it as ten kinds of login with a database that throws on any touch.
- **Page** `app/(dashboard)/address-book/page.tsx` → `components/address-book/address-book-app.tsx` (list + chips + search; the browser holds the whole list and filters it itself), `person-form.tsx` (the Add / Change box), `type-manager.tsx` ("Manage types"). Menu item `address-book` is in the **Network** group after Contacts (`components/dashboard/sidebar.tsx`, `lib/nav/menu-layout.ts` STANDARD_GROUPS), and `address-book` is in `WINDOW_PAGE_ROOTS`.
- **What the CRM says a person is** — computed every time, never stored (`lib/address-book/crm-kind.ts`, `build-rows.ts`). Contacts that are not merged and not test: a live (not ended) link to an **Active Client** account = *Client with a company*; any other link (closed, cancelled, offboarding, one-time, or an ended link) = *Past or one-time client*; no company → by portal level: lead = *Lead*, active or formation = *Individual client*, onboarding (or any unknown level) = *Other*, none = *Not sorted yet*. Partners page rows: type "Banking Partner" = *Banker*, every other = *Partner*. Test accounts are left out of the links. Counts on 15 Nov 2026 (production): 272 / 74 / 36 / 13 / 3 / 109 for contacts (507) and 7 / 6 for partners (13).
- **Company shown for a contact:** a live Active client company first, the primary one first, then by name; a past client shows the company they had.
- **Saved people** live in `address_book_entries` (plain columns + `extra` for the type's boxes). `type_entry_id` may be empty ("No type"); a person under a hidden or vanished type shows as "No type" and comes back when the type is shown again. "Remove" archives (`archived_at`); there is no screen to bring one back yet.
- **A type for a CRM person** (`POST /api/address-book/label`): only a contact the CRM leaves *Not sorted yet* or *Other* can be given one (409 otherwise); stored in `address_book_crm_labels`; "Take the type back" deletes the label. A label whose type is hidden, or whose person the CRM has since sorted, is ignored by `buildRows`. Partners cannot be retyped.
- **"Already here?"** — the Add box asks `POST /api/address-book/check` when a phone or email box is left, and the server asks AGAIN on every save (`refuseDuplicates`): a phone or email held by a CRM contact/partner or by another saved person answers **409 with the matches**; "Save anyway" resends with `force: true`. A phone matches by digits and by its LAST TEN digits (`phoneKeysOf`), so "+1 555 010 0188" and "555-010-0188" are the same number. When changing a saved person only a phone or email that is NEW on them is checked.
- **Types** (`type-admin.ts`, `type-input.ts`) go through the catalog framework helpers (`addEntry`, `renameEntry`, `updateMetadata`, `deprecateEntry`, `restoreEntry`), so each change is in `catalog_decision_log`. A name is unique ignoring case, accents and spacing, hidden types included (409). A new type gets `sort_order` = highest + 10. **Boxes:** at most 20; an existing box keeps its key (even when renamed) and its KIND cannot change (saved values would stop fitting); a new box's key is made on the server from its label, never taken from the browser, and never reuses a key that exists or was removed earlier (`metadata.retired_keys`, so old hidden values can never show under a different box). Taking a box off hides its values, it does not erase them. A type is never deleted: "Hide this type" = status deprecated.
- **Columns follow the filter:** everyone = Name, What they are, Company, Phone, Email; Bankers / Partners add *Service area* (from the Partners page); a saved type shows its first two boxes.
- **Dates and the list:** CRM rows come from `contacts`, `accounts`, `account_contacts`, `partners` (SELECT only; a test in `address-book-routes.test.ts` fails if any address-book file inserts, updates, upserts or deletes on them).

## Gotchas, invariants & past bugs
- **"Only you" is enforced in layers, and the honest limit is stated:** RLS + no client grants; `ai_readonly` revoked; encrypted payload; every query scoped to `owner_user_id`. Any admin SQL tool (including a Claude session) can still read the ciphertext, not the names. A database admin with the server key could decrypt.
- The generic MCP `execute_sql` runs as the service role and has no per-table block for reads, so the encryption, not a block list, is what protects the Personal book from it.
- `address_book_crm_labels.subject_id` is a plain uuid. A merged contact keeps its label on the old id: ignore labels whose contact has `merged_into` set.
- Two types may not share a name (case and spaces ignored, hidden ones included); the accent-insensitive check lives in code (step 2).
- Personal rows hold their type inside the encrypted payload, so the Personal list is decrypted in code and filtered there (a person's book is small).

- **A DELETE needs the JSON header too.** The same-origin check refuses a change that is not `application/json`; the browser helper (`components/address-book/api.ts`) therefore sends the header and `{}` on every non-GET call. A first version sent nothing on DELETE and "Remove" answered "Not allowed from here" (found in the browser, fixed, `address-book-client-api.test.ts`).
- **Two phones that differ only by the country code are the same number** (last-ten-digit key). Two different countries with the same last ten digits would also match: accepted, the check only asks, "Save anyway" always works.
- **The sandbox is not the production CRM.** On 15 Nov the sandbox held 1,990 contacts and no partners, so its counts differ from production's; the rules are the same.
- **Not in step 2:** "Last talked" (needs email + WhatsApp + portal chat read together), the system's suggested type (step 4: reads emails), the Personal book on a screen (needs `ADDRESS_BOOK_PERSONAL_KEY` set), the top-bar "+ Add to address book" button on every page.
