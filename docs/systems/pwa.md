## What it is
Both surfaces install as PWAs: the staff **CRM dashboard** (this doc's focus) and the **client portal**. The PWA layer = a web-app manifest, a hand-written service worker per surface (no next-pwa/serwist/workbox), a push-notification pipeline, an update-prompt mechanism, and an offline fallback page. The service workers deliberately do **NOT cache data or pages** (beyond `/offline`) — a live CRM must never show stale financials.

## Parts (dashboard)
- **Manifest** `public/manifest.webmanifest` — name "TD Operations", `start_url: /`, `display: standalone`, icons from `/portal-icons/` (192/512 + maskable; shared with the portal — no dashboard-specific icon set, deliberate until a design decision says otherwise). Linked via `metadata.manifest` in `app/(dashboard)/layout.tsx`; theme-color/apple-touch-icon/appleWebApp in the root `app/layout.tsx`.
- **Service worker** `public/dashboard-sw.js` — versioned `CACHE_NAME` (`td-dashboard-vN`, bump when precached assets change). Handles: install (precaches `/offline`), activate (deletes old caches, `clients.claim()`), `SKIP_WAITING` message, `push` + `notificationclick` (focuses/opens `/portal-chats` by default), and a **navigation-only network-first fetch handler** that serves the cached `/offline` page when the network fails. Non-navigation requests (API, assets) are never intercepted.
- **Offline page** `app/offline/page.tsx` — self-contained server component (inline styles, no client JS) so it renders from SW cache without framework chunks.
- **Registration + update flow** — `components/dashboard/sw-register.tsx` (mounted in `app/(dashboard)/layout.tsx`) → `components/shared/update-banner.tsx` → `lib/hooks/use-sw-update.ts`: registers the SW, polls `reg.update()` every 60s, shows an update banner, applies via `SKIP_WAITING` + reload on `controllerchange`, force-updates after 24h.
- **Push subscribe** — `lib/push/dashboard-push.ts::subscribeToDashboardPush()` is the ONE implementation (register → VAPID key from `/api/admin/push` → permission → subscribe → POST). Callers: `components/dashboard/push-toggle.tsx` (header + sidebar) and the portal-chats `enableNotifications` handler. The portal's own toggle (`components/portal/push-toggle.tsx`, different endpoints) shares only `urlBase64ToUint8Array`. **Never re-roll this sequence inline.**
- **Middleware** — `middleware.ts` `PUBLIC_PREFIXES` must include `/manifest.webmanifest`, `/dashboard-sw.js`, `/portal-sw.js`, `/offline`: the matcher's extension exclusions don't cover `.js`, and the browser refetches SW scripts + the SW fetches `/offline` at install **without a session**. Auth-gating any of these silently breaks SW updates / install.

## Portal differences
`public/portal/manifest.webmanifest` + `public/portal-sw.js` (registered from `app/portal/layout.tsx` / `components/portal/portal-sw-register.tsx`); portal push uses its own endpoints. Not otherwise covered here — see `portal.md`.

**The portal worker holds ZERO Cache Storage** (stricter than the dashboard, which precaches `/offline`). Its offline fallback is a self-contained bilingual `Response` built inline in the worker — deliberately NOT a precached route, because `cache.add` rejecting on a flaky or non-200 fetch aborts `install`, which would leave the client with no service worker and silently no push. Nothing is precached, so there is no `CACHE_NAME` to bump.

**Scope is a single constant** — `PORTAL_SW_SCOPE` in `lib/portal/sw-scope.ts`. Every registration and `getRegistration` call MUST use it. `components/portal/push-toggle.tsx` previously registered the same script with no scope, defaulting to `/`: that produced a second, independent registration which the update machinery never polled and never sent `SKIP_WAITING` to, and which controlled `/portal` (the manifest `start_url`, outside scope `/portal/`). The scope deliberately keeps its trailing slash and was NOT widened to cover `start_url` — changing an existing registration's scope creates a new registration and orphans the old one still in control. With nothing cached, an uncontrolled launch URL costs only the offline screen at cold launch.

**Sign-out purges Cache Storage** (`components/portal/portal-sidebar.tsx` → `purgeAllCaches`). Belt-and-braces for devices still carrying a pre-2026-07-21 bucket; a no-op on current ones.

### The 2026-07-21 incident — why these rules are not negotiable
The portal worker cached every successful `/portal` GET and replayed it from `.catch()` on any network failure. Three consequences, all live on client devices for ~3.5 months:
1. **Dead shells.** Cached Next.js HTML references build-specific `/_next/` chunks, which the worker never cached and which 404 after a deploy — the portal rendered but never hydrated. Clients saw the app and could not type or send.
2. **Offline auth bypass.** The replay consulted no session; server gates were not in the path. Cached pages rendered client ITIN, EIN, home address and invoices with no login.
3. **A live signing credential at rest.** Portal signing pages embed `/sign-document/<token>/<access_code>` as an iframe `src`, and that route gates on token+code alone. A cached copy left a working, session-independent signature link in device storage.
Sign-out cleared none of it and `CACHE_NAME` had never been bumped, so `activate`'s purge never evicted anything.

**Recovery mechanics (the part that is easy to get wrong).** Neither worker calls `skipWaiting()` in `install` by default — activation waits for a `SKIP_WAITING` message from `lib/hooks/use-sw-update.ts`, which is React code inside the shell. A poisoned shell runs no JS, and a backgrounded phone PWA is a live controlled client for weeks, so the "all clients closed" escape never fires either. A fix that only rewrites the fetch handler installs, parks in `waiting`, and never reaches the clients it exists to rescue. The recovery release therefore calls `skipWaiting()` unconditionally in `install` and, in `activate`, deletes ALL cache buckets, claims clients inside the `waitUntil` chain, then re-navigates every open window — a path that runs entirely in the worker. The re-navigate is gated on having actually purged a legacy bucket so fresh installs are not reloaded out from under the user. **Accepted cost:** every client carrying a legacy cache gets one silent reload, which can lose an unsent chat draft.

## The rules
1. Mobile-first is mandatory for dashboard UI: Antonio uses every page from a ~380px phone. Tables need scroll wrappers (`overflow-x-auto` + `min-w-[...]`) or card collapse; toolbars need `flex-wrap`; grids need responsive prefixes.
1b. **Height chain (2026-07-08 scroll-trap incident):** the dashboard `<main>` compensates for the fixed mobile top bar with `pt-14 lg:pt-0` — PADDING, never a spacer div, so `h-full` pages size to the content box and end exactly at the viewport bottom. Any tab/pane rendered inside an `overflow-hidden` parent MUST own its vertical scroll (`h-full overflow-y-auto`, like finance's tabs) — a plain block there renders but can NEVER be scrolled (the "can't scroll invoices" production bug; invisible to static review, only a rendered ~390px viewport shows it).
2. Any new public PWA asset (SW, manifest, precached page) goes in `PUBLIC_PREFIXES`.
3. Bump `CACHE_NAME` when changing what the SW precaches.
4. No data/page caching in the SW beyond the offline fallback. **Enforced** by `tests/unit/service-worker-no-page-cache.test.ts` (no `cache.put` in any `public/*-sw.js`; precache URLs allowlisted; never a `/portal` route). This was prose-only until 2026-07-21 and was violated for 3.5 months — the system-doc freshness gate could not catch it because that gate fires on file EDITS and the file was never edited.
6. A precached page must be static and session-free. `/offline` is safe only because `app/offline/page.tsx` is deliberately JS-free server markup — the day it gains a client component, the offline fallback becomes a second stale dead shell.
7. The portal offline fallback must stay client-branded ("TD Portal") and bilingual. Do NOT point the portal at the dashboard's `/offline`: it is staff-branded "TD Operations" (R005 territory), English-only, and its Retry link sends an expired-session client to the STAFF login.
5. New push entry points call `subscribeToDashboardPush()` — no inline copies.
