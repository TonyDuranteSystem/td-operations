## What it is
A second installable app from the SAME site, next to the CRM app: name **TD Talk**, start address `/talk`, its own icon (`public/talk/icons/`, red speech bubble), its own manifest (`public/talk/manifest.webmanifest`, `id`/`start_url`/`scope` all `/talk`) and its own service worker (`public/talk-sw.js`, scope `/talk`). The screen is a WhatsApp-style chat for the team: it opens straight into a conversation (the one a tapped notification points at, else the one left open last time on this phone, else the one with the most recent activity), and a back arrow leads to the short list of people. It reads and writes the existing Team Chat data — direct messages (`internal_threads` rows with `thread_type='dm'` and their `internal_messages`; `team-workspace.md`) — through the existing routes, so the same conversation is visible in the CRM's Team Chat and every send rule applies unchanged. ## Rules
- **Voice note files (2026-10-13c):** `use-audio-note-recorder.ts` with `preferMp4` (TD Talk only) records MP4/AAC at 48 kbps and runs `fragmentedMp4ToFlat` (`lib/media/fmp4-to-flat.ts`) on the finished recording: collects every sample (size, duration, offset) from the fragments (`tfhd`/`trun`/`trex` defaults, base offsets, 32/64-bit headers), then writes `ftyp` + `moov` (mvhd, tkhd, mdhd, the original hdlr/smhd/dinf/stsd copied byte-for-byte, stts/stsc/stsz/stco) + one `mdat` of the same compressed bytes. Verified: ffmpeg decode of the result is byte-identical to the original (the 44 ms encoder-priming edit list is dropped — inaudible); real Safari reads 42.815 s for a 42.86 s note, 195.668 s for the 3:15 note, and plays to the correct end; a real browser recording is stored with 0 fragments. Anything unexpected (not fragmented, more than one track, not audio, truncated) returns null and the original recording uploads. **NEVER fill in the length of a fragmented MP4 (the 2026-10-13 `fmp4-duration` patch): Safari then counts the fragments twice.** Old notes recorded before the patch (header 0) read correctly in Safari desktop; notes recorded after it (until this change) read DOUBLE and need repair (convert the stored file in place).
- **READ RULE (2026-10-09g, fail-open):** a message is marked read only while `isBeingViewed()` (`lib/talk/window-front.ts`): the tab is visible AND the window is not known to be behind another one — in front by default; `blur` = behind; a tap/click/keypress or `focus` = back. NEVER use `document.hasFocus()` for this (false in phone/installed apps → chats never marked read, found 2026-10-09). Otherwise the thread GET goes out with `?mark_read=0`. Same rule in the CRM Team Chat page.
1. **Scope has NO trailing slash.** Next redirects `/talk/` → `/talk`; a `/talk/` scope would not contain the page the app really opens on (the same gap `pwa.md` documents for `/portal`). Manifest `scope`/`start_url`/`id` and the worker scope are all `/talk`.
2. **Middleware public list: only `/talk/manifest.webmanifest` and `/talk-sw.js`.** NEVER a bare `/talk` — the app is a staff-only page. (The matcher already skips `.webmanifest`/`.png` files.)
3. **Notification taps stay inside TD Talk.** The server builds `/team-chat?thread=…` links for the CRM; `talk-sw.js::talkUrlFor` rewrites them to `/talk?thread=…`, and anything else (another page, another site) becomes plain `/talk`. The same rule is `lib/talk/paths.ts::talkUrlFor`; `tests/unit/talk-sw.test.ts` runs the worker for real and keeps the two identical. The CRM worker (`dashboard-sw.js`) skips `/talk` windows on a tap (it uses `includeUncontrolled`), and `talk-sw.js` only ever moves `/talk` windows.
4. **A login/two-step detour keeps the destination.** Middleware sends a signed-out `/talk…` visitor to `/login?next=<path>` and the two-step check to `/mfa/verify?next=<path>`; the login page, `/mfa/verify` and `/mfa/enroll` follow `next` ONLY through `safeTalkNext` (a `/talk` address; everything else — `//host`, absolute URLs, backslashes, control characters — is refused, so it cannot become an open redirect). CRM behaviour is unchanged.
5. **Nothing automatic may mark a conversation read.** `GET /api/team/threads/[id]` upserts the caller's `last_read_at`, so TD Talk only calls it with the app on screen (`document.visibilityState === 'visible'`; otherwise `?mark_read=0`) and marks a new incoming message read only while visible. TD Talk opens ONE chat (never "General first"). ## Rules
1. **Scope has NO trailing slash.** Next redirects `/talk/` → `/talk`; a `/talk/` scope would not contain the page the app really opens on (the same gap `pwa.md` documents for `/portal`). Manifest `scope`/`start_url`/`id` and the worker scope are all `/talk`.
2. **Middleware public list: only `/talk/manifest.webmanifest` and `/talk-sw.js`.** NEVER a bare `/talk` — the app is a staff-only page. (The matcher already skips `.webmanifest`/`.png` files.)
3. **Notification taps stay inside TD Talk.** The server builds `/team-chat?thread=…` links for the CRM; `talk-sw.js::talkUrlFor` rewrites them to `/talk?thread=…`, and anything else (another page, another site) becomes plain `/talk`. The same rule is `lib/talk/paths.ts::talkUrlFor`; `tests/unit/talk-sw.test.ts` runs the worker for real and keeps the two identical. The CRM worker (`dashboard-sw.js`) skips `/talk` windows on a tap (it uses `includeUncontrolled`), and `talk-sw.js` only ever moves `/talk` windows.
4. **A login/two-step detour keeps the destination.** Middleware sends a signed-out `/talk…` visitor to `/login?next=<path>` and the two-step check to `/mfa/verify?next=<path>`; the login page, `/mfa/verify` and `/mfa/enroll` follow `next` ONLY through `safeTalkNext` (a `/talk` address; everything else — `//host`, absolute URLs, backslashes, control characters — is refused, so it cannot become an open redirect). CRM behaviour is unchanged.
5. **Nothing automatic may mark a conversation read.** `GET /api/team/threads/[id]` upserts the caller's `last_read_at`, so TD Talk only calls it with the app on screen (`document.visibilityState === 'visible'`; otherwise `?mark_read=0`) and marks a new incoming message read only while visible. TD Talk opens ONE chat (never "General first"). The CRM Team Workspace page also got the fix this found: `loadThreads(true)` applies a `?thread=` deep link BEFORE falling back to General — selecting General first loaded it and marked it read before the link applied, so every launch from a notification quietly cleared General's unread count.
6. **Sound/pop-up rule in TD Talk:** DIRECT messages only (`RealtimeNotifications teamOnly` ignores channel posts, topics and client conversations), and only for a chat you are NOT looking at — the open chat is in the address (`?thread=`), and a message in it just appears. In the CRM's `/team-chat` page everything stays silent, as before. Client conversations stay silent everywhere (`conversationNotifiesParticipants`) — the rule lives on the SENDING side and TD Talk adds no new path around it.
7. **Staff only.** Layout `isDashboardUser` check on top of middleware's client/partner confinement and MFA gate.
8. **One push helper.** `subscribeToDashboardPush(target?)` (`lib/push/dashboard-push.ts`) takes an optional `{ swPath, scope }`; with none it behaves exactly as before (`register(path)` then `serviceWorker.ready`). A scoped worker waits for ITS OWN registration to be active (`serviceWorker.ready` answers for whichever worker controls the PAGE — the CRM's on a first TD Talk load). `unsubscribeFromPush({ scope })` refuses to touch a registration whose scope is not the requested one (otherwise it would silently switch the CRM app's push off).

## Features in the chat (all through the existing CRM routes)
- **Reply:** swipe a message to the right, or long-press → Reply. `POST /api/team/threads/[id]/messages` with `reply_to_id`; the bubble shows the quote (tap = jump to the original). NOTE the server stamps `root_id` on ANY quoted reply, even in a direct message (Slack-style flattening), so TD Talk NEVER hides a message because of `root_id` (a first version did, and the reply vanished).
- **Reactions:** long-press → one of 👍 ❤️ 😂 😮 😢 🙏 → `POST /api/team/messages/[id]/react` (a toggle); pills under the bubble, tap a pill to toggle yours.
- **Edit / Delete (mine only):** `PATCH` / `DELETE /api/team/messages/[id]` (soft delete — R100 tombstone "This message was deleted"; edits show "edited"). Edit works on text messages without a file (the server only edits the text).
- **"typing…" / "recording a voice message…":** a Supabase Realtime BROADCAST on a per-chat channel `talk-typing-<threadId>` (nothing is stored, no database change). While you type (or record) your side announces at most every 2.5 s (`shouldAnnounceTyping`); the other side shows the line under the name for 4 s after the last signal, and a message from them clears it at once. Only another person's well-formed signal counts (`parseTypingSignal`). Privacy note: the channel is a public broadcast channel — anyone holding the project's public key AND the chat's UUID could listen to the typing signals (user id + 'typing'|'recording' only, never any text); the UUID is unguessable and no content crosses it.
- **Search:** the magnifier in the header searches the latest 500 loaded messages of THIS chat (text and file names); tap a hit to jump to it (flashes). Not the CRM-wide search.
- **Keeping the list honest:** a refresh MERGES with what is on screen (`mergeSnapshot`) — a slow poll that answers after a send cannot erase the new message; a voice note sent as a reply ends the reply; leaving Edit gives the stashed draft back.
- **Copy text**, 24h times, day headings, links, photos, files, voice notes, seen ticks — see Parts.

## Push routing — no double buzzing (DDL FIRST)
`admin_push_subscriptions.app` (NULL = CRM app, `'talk'` = TD Talk; `normalizeApp` stores only those two). `lib/push/route-subscriptions.ts::routeAdminSubscriptions` (pure, `tests/unit/push-route-subscriptions.test.ts`): TD Talk receives **direct messages only**; a person with a TD Talk subscription gets their DMs there **instead of** the CRM app; all else goes to the CRM app only. The DM branches of the message send route and `post-message.ts` pass `dm: true`; `sendPushToAdminUsers` strips it before sending. TD Talk's "Turn on" sends `app: 'talk'` (`subscribeToDashboardPush({ app })`; the CRM's own request body is unchanged). **Deploy order: apply the migration to the environment FIRST for TD Talk** — `POST /api/admin/push` writes `app` ONLY for `'talk'` (the CRM app's own subscribe never touches the column, so it keeps working even if the code is live before the DDL — a rejected insert right after the route's delete would have silently dropped the CRM app's subscription, a council finding) and the sender reads `*` so a missing column only means "everything is the CRM app". **Consequence to know:** a person who turns the CRM app's notifications OFF and keeps only TD Talk receives direct messages and NOTHING else — no client-message, payment or approval alerts, no channel mentions (those never reach TD Talk by design). Antonio and Luca should keep the CRM app's notifications on. Every sender that can push a direct message sets `dm` (messages route ×2, `post-message.ts` ×2, `claude-trigger.ts` "Claude replied" in a DM, `share/route.ts` share into a DM) — `tests/unit/admin-push-subscribe-route.test.ts` has a source guard so a new DM sender cannot forget it. Known edge: if TD Talk is deleted from a phone without turning notifications off, the subscription lingers until the push service reports it gone (deleted on the first failed send); a DM sent in that window shows in neither app — the unread count in the CRM still shows it.

## What it is
A second installable app from the SAME site, next to the CRM app: name **TD Talk**, start address `/talk`, its own icon (`public/talk/icons/`, red speech bubble), its own manifest (`public/talk/manifest.webmanifest`, `id`/`start_url`/`scope` all `/talk`) and its own service worker (`public/talk-sw.js`, scope `/talk`). The screen is a WhatsApp-style chat for the team: it opens straight into a conversation (the one a tapped notification points at, else the one left open last time on this phone, else the one with the most recent activity), and a back arrow leads to the short list of people. It reads and writes the existing Team Chat data — direct messages (`internal_threads` rows with `thread_type='dm'` and their `internal_messages`; `team-workspace.md`) — through the existing routes, so the same conversation is visible in the CRM's Team Chat and every send rule applies unchanged. It deliberately shows NO channels, topics, client conversations, board or search (those stay in the CRM's Team Workspace).

**What the first build did (replaced the same day):** it re-exported the whole Team Workspace page under `/talk`; on a phone that is the entire workspace (channels, topics, clients) and Antonio had to tap Luca. The page-level changes made for it were reverted except the deep-link fix (see Rules 5).
