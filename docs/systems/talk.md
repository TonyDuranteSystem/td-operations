## What it is
A second installable app from the SAME site, next to the CRM app: name **TD Talk**, start address `/talk`, its own icon (`public/talk/icons/`, red speech bubble), its own manifest (`public/talk/manifest.webmanifest`, `id`/`start_url`/`scope` all `/talk`) and its own service worker (`public/talk-sw.js`, scope `/talk`). The chat is the existing Team Chat page re-exported — `app/talk/page.tsx` is `export { default } from '@/app/(dashboard)/team-chat/page'` — so there is ONE set of messages, channels, DMs, reactions, unread pointers and rules (`internal_threads` / `internal_messages` / `internal_thread_reads`; see `team-workspace.md`). Nothing is copied: TD Talk is a second front door onto the same chat.

## Parts
- `app/talk/layout.tsx` — server layout, OUTSIDE `app/(dashboard)`: no CRM sidebar/header/notes. `getUser()` → `/login?next=%2Ftalk` if signed out; `isDashboardUser` else `/`. Metadata: manifest, apple-touch-icon, `appleWebApp` (title "TD Talk"), `viewportFit: 'cover'`, theme `#BE1E2D`.
- `components/talk/talk-shell.tsx` — full-screen frame (`100dvh`, minus the sandbox band; bottom padding for the iPhone home indicator). Mounts what the Team Chat page quietly relied on the CRM frame for: `RealtimeNotifications teamOnly` (sounds + pop-ups; no client-message or business-event alerts), `TalkSwRegister`, `TalkPushBanner`.
- `components/talk/talk-sw-register.tsx` — registers `/talk-sw.js` at scope `/talk` through the shared `UpdateBanner`, and answers the worker's `td-navigate` message with a client-side `router.push` (only a `/talk` address is followed).
- `components/talk/talk-push-banner.tsx` — the "Turn on notifications" strip (needs a tap on iPhone; only works from the installed app; explains both cases). Uses `subscribeToDashboardPush({ swPath: '/talk-sw.js', scope: '/talk' })`.
- `lib/talk/paths.ts` — pure rules, unit-tested: `isTalkPath`, `teamChatBase`, `safeTalkNext` (the ONLY return address the login page follows), `withTalkNext`, `talkUrlFor`.
- `public/talk-sw.js` — push (always shows a notification — iOS drops a subscription that gets silent pushes), tap routing, inline offline page. **Caches NOTHING** (`tests/unit/service-worker-no-page-cache.test.ts` covers every `public/*-sw.js`).

## Rules
1. **Scope has NO trailing slash.** Next redirects `/talk/` → `/talk`; a `/talk/` scope would not contain the page the app really opens on (the same gap `pwa.md` documents for `/portal`). Manifest `scope`/`start_url`/`id` and the worker scope are all `/talk`.
2. **Middleware public list: only `/talk/manifest.webmanifest` and `/talk-sw.js`.** NEVER a bare `/talk` — the app is a staff-only page. (The matcher already skips `.webmanifest`/`.png` files.)
3. **Notification taps stay inside TD Talk.** The server builds `/team-chat?thread=…` links for the CRM; `talk-sw.js::talkUrlFor` rewrites them to `/talk?thread=…`, and anything else (another page, another site) becomes plain `/talk`. The same rule is `lib/talk/paths.ts::talkUrlFor`; `tests/unit/talk-sw.test.ts` runs the worker for real and keeps the two identical. The CRM worker (`dashboard-sw.js`) skips `/talk` windows on a tap (it uses `includeUncontrolled`), and `talk-sw.js` only ever moves `/talk` windows.
4. **A login/two-step detour keeps the destination.** Middleware sends a signed-out `/talk…` visitor to `/login?next=<path>` and the two-step check to `/mfa/verify?next=<path>`; the login page, `/mfa/verify` and `/mfa/enroll` follow `next` ONLY through `safeTalkNext` (a `/talk` address; everything else — `//host`, absolute URLs, backslashes, control characters — is refused, so it cannot become an open redirect). CRM behaviour is unchanged.
5. **Nothing automatic may mark a conversation read** (loading a thread upserts `last_read_at`). `loadThreads(true)` now applies a `?thread=` deep link BEFORE falling back to General, and TD Talk on a phone (≤767px) selects NOTHING at launch — it opens on the list of chats, like WhatsApp — so a launch from a notification no longer clears General's unread count. (This also fixes the CRM's own cold deep-link.)
6. **Sound/pop-up rule in TD Talk:** only the chat you are LOOKING AT (`?thread=` in the address, kept there by `use-selection-history`) is silent; a message in another chat, or while on the chat list, sounds and pops up. In the CRM's `/team-chat` page everything stays silent, as before. Client conversations stay silent everywhere (`conversationNotifiesParticipants`) — the rule lives on the SENDING side and TD Talk adds no new path around it.
7. **Staff only.** Layout `isDashboardUser` check on top of middleware's client/partner confinement and MFA gate.
8. **One push helper.** `subscribeToDashboardPush(target?)` (`lib/push/dashboard-push.ts`) takes an optional `{ swPath, scope }`; with none it behaves exactly as before (`register(path)` then `serviceWorker.ready`). A scoped worker waits for ITS OWN registration to be active (`serviceWorker.ready` answers for whichever worker controls the PAGE — the CRM's on a first TD Talk load). `unsubscribeFromPush({ scope })` refuses to touch a registration whose scope is not the requested one (otherwise it would silently switch the CRM app's push off).

## Known limits / not built yet
- **Double buzzing:** a person with BOTH apps subscribed gets every push twice (`admin_push_subscriptions` is keyed per user + endpoint and every push goes to all of a user's rows); the TD Talk worker also shows pushes about non-chat things (iOS needs a notification per push) and sends the tap to plain `/talk`. Step 4 (needs an `app` marker on the subscription + a send-side rule).
- **No voice notes yet** — the composer's mic is still DICTATION (speech → text). Step 3 reuses `lib/hooks/use-audio-note-recorder.ts`; to check first: storage accepts audio, iPhone records mp4/m4a vs Chrome webm.
- **iOS is NOT VERIFIED from here:** whether two installs from one site stay separate apps with their own push; first launch of an installed app asks for login + two-step again (own storage).
- Sandbox has its own database — the first iPhone test uses sandbox conversations.
