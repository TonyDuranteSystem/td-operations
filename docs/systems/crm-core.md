## What it is
The foundational records everything else hangs off: **accounts** (companies), **contacts** (people), the **`account_contacts`** junction that links them, plus **tasks**, **deals**, **leads**, **payments**, and **service_deliveries**. Almost every other system references these.

## The account ↔ contact model (the thing to internalize)
- A **contact** (person) and an **account** (company) are linked **many-to-many** through `account_contacts` (`role`, `is_primary`). **One person can own several LLCs with completely different names; one LLC can have several contacts.**
- `crm_search_contacts` returns a contact **with all their linked accounts** (`account_contacts(account_id, role, accounts(company_name, status, …))`) — so when a client messages, search by name first, then act per account.
- A contact's `portal_tier` is computed as the max across their accounts (see `portal.md`); a contact with no account keeps their own tier.

## The canonical write path (R018)
- **Never use `execute_sql` to write CRM data — always `crm_update_record`** (R018), or the per-table operation-authority helpers.
- `crm_update_record` (`lib/mcp/tools/crm.ts`) validates status/stage against `STATUS_VALIDATION_MAP` (ENUM-backed tables: `accounts.status`, `payments.status`, `tasks.status`, `leads.status`, `deals.stage`, `tax_returns.status` — constants in `lib/constants.ts`), writes the change, logs to `action_log`, and mirrors to Airtable (`syncSupabaseToAirtable`). Enum membership is necessary but not sufficient on `leads`: `Converted`/`Paid` are valid `LEAD_STATUS` values but mean payment confirmed (R094), so `validateStatusField` refuses them regardless of membership (`STATUS_VALUES_REQUIRING_DEDICATED_FLOW`) — earning them is the job of the payment webhooks / Convert to Contact / Confirm Payment flows only, never a generic field write. The lead detail page's Status dropdown/endpoint and the `lead_update` MCP tool carry the identical restriction (dev job 6ba61663, 2026-09-18).
- **Operation-authority layers** — `updateAccount` / `updateTask` / `updateContact` (`lib/operations/contact.ts` etc.) are single-entry helpers that add optimistic locking + `action_log` audit. The **P2.4 ESLint rule blocks raw `.insert/.update/.upsert` on protected tables** — go through these helpers (workflow handlers and the AI agent already do).
- **Contact email is kept in sync with the portal LOGIN email.** Changing a contact's `email` (via `crm_update_record`, `updateContact`, or the inline contact/account email field) calls `syncPortalLoginEmail` (`lib/operations/portal-login-email.ts`): it finds the client's login **by `contact_id`** (never by email), and if the new email is free, updates the login and emails the client their new login (password unchanged). If the new email already belongs to **another** login it is a **conflict** — the contact email still updates but the login is left unchanged and flagged (never merges identities). Best-effort: a sync failure never blocks the contact update. This closes the historical drift where a contact's email changed but the login kept the old address.
- **Manual account creation** (dashboard "Create New Account" dialog) — `createAccount` / `createAndLinkContact` in `lib/operations/account.ts`, admin-client writes (accounts/contacts have no staff INSERT policy, see Gotchas). `createAccount`: requires entity type, member structure, formation state, and a primary contact; defaults `account_type` to `Client` (only `Client`/`One-Time` are offered at creation — see Gotchas on `Partner`); explicitly clears `portal_tier` (the DB default is `active`, wrong for an unformed company); runs a near-duplicate-name guard (`isNearDuplicateCompanyName` — normalizes, strips legal suffixes, catches one name contained in another, 6-char minimum fragment to avoid false positives on short generic words). `createAndLinkContact`: takes first/middle/last name (not one free-text field — first/last feed IRS forms and portal personalization elsewhere); composes the full legal name (incl. middle) for documents. **Identity matching only auto-links on an EXACT full-name match against a same-email contact** — this is the ONLY case treated as unambiguous. Two other cases are checked (independently, both can fire together) and produce a new contact + a non-blocking `warning` string surfaced to staff instead of guessing: (1) the email is already on file under a *different* name — could be the same person entered inconsistently, or a shared family/company inbox belonging to someone else; (2) an *exact* name match exists under a different email or no email — the "Damiano Mocellin" case, one real person on file as separate contacts per company role. Same "never guess, ask a human" rule as `lib/members/resolve-signer.ts`. Shared helpers: `escapeLikePattern` (`lib/members/member-identity.ts`, used by every ILIKE identity lookup in this flow so a raw `%`/`_` in an email/name can't be misread as a wildcard) and `resolveMemberContactId` (`lib/members/resolve-member-contact.ts`, the final fallback and the shared find-or-create used by the member-info wizard and the onboarding-setup job — same email+name matching, only refreshes fields that are currently blank on the matched contact; also exports `describeContactRoles`, moved here from this file). As of 2026-08-29 it ALSO runs the same-name-different-email check before creating a new contact (the two real recurring incidents both came through here, not this dialog) — same "never guess" rule, but since its automated callers have no human watching a screen, the flag is written to `action_log` (`action_type: 'flag'`) rather than returned as a UI-facing warning string. Candidate queries exclude merged (`merged_into IS NOT NULL`) contacts. For a multi-member account, the dialog does NOT collect the other members inline — it hands off to the existing Members panel on the new account's page (already wired to SS-4/OA side effects). **Picking an existing contact instead of typing a new one:** the dialog's primary-contact field also supports searching for and selecting a contact already in the system (`searchContacts` in `app/(dashboard)/accounts/actions.ts`) — when used, no identity matching runs at all (`createAccount`'s `existingContactId` param bypasses `createAndLinkContact` entirely and calls `linkContactToAccount` directly, extended with an `isPrimary` flag). Single-Member: the picked contact is linked as `role: 'owner'` AND `is_primary: true` (the account's main contact for every downstream `is_primary`-keyed consumer — SD contact resolution, portal chat language default, EIN-workflow routing, etc.). Multi-Member: linked as `role: 'owner'` but `is_primary: false` — never auto-assumed as the account's main contact or signer. Either way, a Multi-Member account created from this dialog returns `needsMemberSetup: true` and the dialog blocks on a real (non-dismissible-by-backdrop-click) modal telling staff to finish the member roster + primary contact + signer on the account page — this dialog is confirmed (2026-08-19) to be the ONLY caller of the `lib/operations/account.ts` `createAccount` function in the whole codebase, i.e. it is NEVER reached by the client formation workflow's own member-collection step, so a Multi-Member account created here always needs that follow-up regardless of which contact-entry method was used.

## Gotchas, invariants & past bugs
- **`accounts` and `contacts` have staff-facing RLS for SELECT only — no INSERT.** Only `service_role` (the admin client) can insert. This is BY DESIGN (see P2.4 above — writes go through the admin-client operations layer, not RLS) but it silently broke the dashboard's "Create New Account" dialog and the account-detail "Add Contact" flow from the day they were built (2026-08-19 fix, dev_task `693273fd`) — the raw insert used the RLS-scoped client and failed every single time, with zero successful creations ever in `action_log` history. If a NEW raw `.insert()` on either table looks like it should work but silently fails, check which Supabase client it's using before assuming the bug is elsewhere.
- **`account_type = 'Partner'` is NOT the real partner/commission system.** It's a narrow, mostly-vestigial tag (2 accounts total) that only exempts a company from the data-completeness audit (`lib/audit/completeness-rules.ts`). The real partner system — referral tracking, commission model, payouts — is `client_partners`, added via the Partners page's own "New Partner" button, entirely independent of `accounts.account_type`. Because the two looked confusingly similar, `Partner` is deliberately NOT offered as a choice when creating a new account (`CREATABLE_ACCOUNT_TYPE` in `lib/constants.ts` excludes it) — only the per-company editor on an existing account still shows it, for the handful of legacy accounts already tagged that way.
- **A person can own multiple LLCs under different names** — always search by a broad name root, try spelling/nickname variants, and check ALL linked accounts before saying "not in the system."
- **R018:** CRM writes go through `crm_update_record` / the authority helpers, never `execute_sql`. Raw writes to protected tables are blocked by ESLint (P2.4).
- **Status validation covers only ENUM-backed tables** (accounts/payments/tasks/leads/deals/tax_returns) — other fields aren't enum-checked.
- **Supabase is the source of truth; Airtable is a downstream mirror** — never treat Airtable as authoritative.
- **Contact merge is delicate** — `merge_contacts()` must repoint `auth.users.contact_id` and dedupe; the Contact Identity hardening is in progress (some machinery on prod is inert). Verify before merging.
