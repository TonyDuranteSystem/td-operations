## What it is
A one-time link that a client (ours, or an external one such as a Max Scale client) fills out to apply for a US business bank account through a third-party intermediary (Irshad Ahangar / Open Shift LLC). The client types their details and a plain description of the business, and uploads passport, proof of address, business registration, EIN letter, ITIN letter and lease. **Everything is archived with us in CRM Storage (Business › BofA).** Since 2026-11-02 the only outbound email to the bank contact is the one staff send with the **Submit** button AFTER marking the application Reviewed (see "Review before it goes out"); on submit our own people just get a link-only notice. The $2,500 client payment, a status-only shared sheet and any CRM/portal screens are deliberately NOT built (Antonio: "when the first account is opened and works we will build everything else").

## Business rules
- **One-time link.** Loading the page only READS the link's state. The visitor must press **Start application** (a POST) to claim it; the browser that does becomes its only owner (a secret cookie, 30 days; only the SHA-256 hash is stored). The same browser can refresh or return until it submits. Any other browser sees "already used". A submitted or revoked link is dead for everyone, including the opener. Staff can **Reset** an opened-but-unsubmitted link (client switched browser / cleared cookies): it goes back to "not opened" and the earlier uploads are deleted. **Revoke** also deletes the uploads.
- **Link scanners / preview bots.** Because loading the page never claims, a mail scanner or chat app that merely opens the URL cannot burn it (council finding). A real browser that presses Start can.
- **No CRM account needed.** Clients can be external; the row is keyed by token + a staff-chosen label only.
- **Documents:** PDF or photo (a missing browser type falls back to the file extension, e.g. iPhone .heic), 10 MB each, ONE per box (the server rejects two in one box). The bucket itself only accepts those types. Required: passport, proof of address, business registration, EIN letter, ITIN letter, lease. Optional: anything else.
- **The ITIN is the PERSON's, so it sits in the "About you" section next to citizenship (not in the company section)** — Antonio, 2026-10-12. The company section holds name, EIN, state of formation, address, website.
- **Addresses are always five fields** (street, city, region/province, zip code, country) — home and company.
- **Placeholders** in the form are invented neutral examples (Antonio: no Italy, none of his own data).
- **Decisions (Antonio):** consent wording / retention rule from the 2026-10-09 council were REJECTED by him ("bullshit") and verifying the intermediary is "not your business" — do not raise them again; the ITIN letter and the lease stay REQUIRED; **[REVERSED 2026-11-02 by Antonio: a separate release step now exists — Reviewed, then Submit; the addresses are the Forms-card setting, not typed per link];** submissions are archived in CRM Storage under Business › BofA (2026-10-12).

## Archive in CRM Storage (2026-10-12, Antonio: "every application must be saved in storage, under Business, BofA")
- **Where:** `Business › BofA › Standalone Applications › <client name>` (no third party) or `Business › BofA › Partner › <partner name> › <client name>` (a partner brought the client) — the six documents (named after their box, e.g. "Passport photo page.pdf") plus **"Application answers.pdf"** (a PDF of the answers; it names the partner — internal only). The Business area is the firm's own: staff only, never shown to a client, no CRM `documents` row. Passport / proof of address / ITIN letter carry NO document type there (a personal type is refused for a non-person owner).
- **Antonio's folders (2026-10-12):** he created `Business › BofA › Partner` and `Business › BofA › Standalone Applications` himself; the app finds them by name (any letter case) via `store_ensure_folder_path` and only creates one that is missing. The client folder is named with the client's NAME ONLY (no date, company or id), so a second application from the same name lands in the same folder and its files get " (2)" — the writer never overwrites. A partner gets its own folder under `Partner` (partner name = folder name).
- **How:** after a submit stores the answers, `lib/bofa-intake/archive.ts::archiveSubmission` calls `ensureArea("business")`, finds the Business top folder, `store_ensure_folder_path(owner, root, ['BofA', partner, applicant], null)`, and saves each file through the ONE writer `saveBytesToStore` with caller key `bofa:<request id>:<slot>` (a retry never duplicates). It never needs a login (actor null).
- **Temporary copies:** the applicant's browser still uploads to the intake's own private bucket (`bofa-intake-uploads`; a public visitor cannot write to CRM Storage). Only when EVERYTHING saved are those temporary objects removed; the row's `files` entries then carry `store_file_id` and `temp_removed`. `lib/bofa-intake/files.ts` reads a file from whichever side it is on (email delivery, staff download). On any failure nothing is removed, the reason goes to `store_error`, the client's submission is NOT failed, and the list shows "Not saved yet: <reason>" with a **Save to Storage** button (`PATCH {action:"archive"}`).
- **Limits are ours:** CRM Storage has no size or type limit, so the 10 MB / PDF-or-photo rules are enforced by the intake before the copy.
- **Stored versions are permanent** (a database trigger blocks deleting them) — test only in the sandbox.
- Migration `scripts/migrations/20261012-1800-bofa-intake-storage-archive.sql` adds `store_owner_id`, `store_folder_id`, `store_archived_at`, `store_error`.
- The Business owner id differs between sandbox and production: always look it up (`ensureArea`), never hard-code it. The local isolated test database has NO store tables, so the archive can only be proven on the shared sandbox.

## Review before it goes out (2026-11-02, Antonio — dev job `4effa56d`)
**The journey of one application:** the client presses Submit → answers + documents are filed in CRM Storage (Business › BofA, as before) → **our own people get a link-only email** ("a bank application is waiting for your review": the notify list; never the answers or documents) → it appears in **Calendar › Applications to review** (red count) → staff open it on `/bofa-intake` → **Reviewed** → **Submit to the bank contact** (a confirm box shows applicant, company, the documents, the shipping address and the exact address it goes to; "It cannot be taken back") → the one email with answers + documents leaves. At any time (also AFTER it was submitted — the bank contact once asked for a residential address a day after the first send) staff can **Send back to the client**.
- **States** (`lib/bofa-intake/review-state.ts`, pure; the staff page, the Calendar tab and the server all read it): `needs_review` → `ready` (Reviewed) → `sending` → `sent`; `send_failed` (Submit again retries — there is no separate Resend); `sent_back`. An application emailed under the OLD rule (`email_status='sent'`, never reviewed — Max Scale) is simply `sent`. The allowed values live in code, NOT in a database CHECK (a CHECK on the shared database turns other sessions' CI red).
- **The rule is enforced INSIDE the send, not by a greyed button.** `lib/bofa-intake/deliver.ts::deliverSubmission(id, {by, confirmTo})` claims the send with an atomic UPDATE that requires `status='completed' AND reviewed_at IS NOT NULL AND returned_at IS NULL` and `email_status` null / `failed` / a `sending` stuck 5+ minutes; it also refuses when `confirmTo` is not exactly the saved address list (the setting changed while the confirm box was open → nothing is sent). Then R037: send, record `sent` + `sent_by` + `sent_to` AFTER. It is the ONLY code that emails an application outside; the submit route does not import it (pinned by `tests/unit/bofa-intake-review-wiring.test.ts`). `PATCH /api/bofa-intake-admin/[id]` actions: `review`, `submit {confirm_to}`, `send_back {note}`, plus the old `archive` / `reset_lock` / `revoke`; `resend_email` no longer exists (400 "Unknown action").
- **Shipping address (locked, pre-filled "Seminole").** `lib/bofa-intake/shipping.ts`: 11125 Park Blvd Suite 104-153, Seminole FL 33772, United States — from `TD_OFFICE` (same source as the portal's Shipping Address card; a test pins the two together). The client sees it read-only on the form; the SERVER writes `shipping_name/street/city/region/zip/country` into the saved answers at submit (`withShippingAddress`), so a tampered form cannot change it and a form opened before this change still gets it. It is NOT in `BOFA_TEXT_FIELDS` (the client never sends it). It shows in the bank email, the answers PDF and the staff view; an older application with no shipping answers simply has no such section.
- **Two address settings, on the Bank-application card of the Forms page** (`components/forms/bank-application-settings.tsx`; Antonio: "the settings must be under Forms, in the BofA card"): `app_settings.bofa_submit_to` (where a Reviewed application is submitted; default `sekureye22@gmail.com`) and `bofa_notify_to` (who is told one arrived; default `support@tonydurante.us`). Value = `{ emails, changed_by, changed_at }` (who/when travel with the value). Read on every use (`lib/bofa-intake/settings.ts`), **fail closed for the submit list** (missing / empty / unreadable = Submit refuses; the notify list falls back to support@). Everyone with Forms access SEES them; **only the owner can change them** (`isOwnerOnly`, enforced by the PUT route; the boxes are disabled for others). Every change validates (valid addresses, 1–5 each) and emails the owner a before/after note. The per-link "send the submitted form to" box was removed (two places for one thing); new links are created with `recipients = []`; old rows keep their saved `recipients` for history only. NO other setting exists (Antonio dislikes settings screens — keep it to these two).
- **Send back to the client** (`lib/bofa-intake/send-back.ts`): staff write a required note → the old application is marked sent back (`returned_at/by`, `return_note`; an atomic claim, so a double click makes one link) → a NEW one-time link is made for the same partner (`replaces_id` = the old row, `staff_note` = the note) → the applicant (`form_data.email`) is emailed it (English, from support@, RFC 2047 subject, note HTML-escaped). The client opens a **blank** form with the note on top and uploads the documents again (their earlier answers/passport are never shown back to whoever holds a link). The old application stays on record; the replacement goes through the same Reviewed → Submit path, and its files land in the same storage folder with " (2)" names (the old ones are kept). If the email fails the link still exists and the staff dialog shows it to copy. A second send-back is allowed only when the earlier new link was revoked, and the database enforces it (partial unique index `bofa_intake_one_live_replacement_idx` on `replaces_id` where `status <> 'revoked'` — two staff pressing Send back at the same moment cannot give the client two links). If the new link cannot be made the old row is put back exactly as it was, including an EARLIER send-back's note and author. A sent-back row that had already been submitted still shows "Earlier submitted to X on <date>".
- **A send that never finishes (council re-check, 2026-11-02).** Submit now runs inside `PATCH /api/bofa-intake-admin/[id]`, which therefore has `maxDuration = 120` (the old submit route had it). If a Submit dies mid-way, or the email went out but the final database write failed (it is retried once; if it still fails the row stays `sending` and the failure is logged loudly), the application sits in "Submitting…". After 5 minutes (`isStaleSending`) the page and the confirm box say "the email may already have reached the bank contact — check the Sent mailbox before submitting again", and a deliberate **Submit again** appears (the server enforces the same 5-minute rule). A retry is never silent: a retry after a lost write would email the passports twice. A row whose OLD automatic send failed/stalled before reviews existed (sandbox only) can be marked Reviewed and then submitted.
- **Calendar › Applications to review** (`lib/bofa-intake/waiting.ts`, `components/bofa-intake/applications-tab.tsx`, tab param `applications` in `lib/new-calendar/params.ts`): a DERIVED list (never stored) of applications whose state is `needs_review` / `ready` / `sending` / `send_failed`, oldest first, red count. It is its own tab, NOT a What's New card, because What's New is built from per-client chat events and refuses an event with no client (`lib/portal/chat-events.ts`), and an applicant is not one of ours yet. Shown only to people who pass `canUseForms` (the page passes `showApplications`); anyone else who types `?tab=applications` lands on the first tab. The loader is tolerant (a failed read shows "could not load", never "nothing waiting").
- **Rollout order (and what happens if it is wrong).** Migration `scripts/migrations/20261102-1900-bofa-intake-review-gate.sql` (+ `.UNDO.sql`) adds `reviewed_at/by`, `sent_by`, `sent_to[]`, `returned_at/by`, `return_note`, `replaces_id`, `staff_note` a partial unique index (one live replacement per application) and seeds the two settings rows. **Antonio runs it on production FIRST, then the code is merged.** If the code is live before the SQL: the public submit never touches the new columns (a client's submission cannot break), the staff list/detail/Calendar reads fall back to the long-standing columns (`lib/bofa-intake/columns.ts::readWithReviewColumns`, `review_ready:false` → the page shows a banner and keeps Reviewed / Submit / Send back off), and a Submit attempt fails closed (the claim names the missing columns). No backfill is needed.
- **Verified in the sandbox (2026-11-02, real routes + a real browser):** a client submit leaves `email_status` empty, replaces a tampered shipping city with Seminole, notifies only the notify list; Submit before Reviewed → 409 "Mark it Reviewed first."; Reviewed → Submit dialog → one email to the saved address (captured, sandbox never delivers), `sent_by/sent_to` recorded; Send back AFTER Submit → email with the escaped note + new link, replacement submits and lands in "Needs review" while the old one leaves the list; settings validation (invalid / empty / too many), owner-only PUT (403 for luca@), owner alert email; the named staff see the tab, an unnamed team login does not and `?tab=applications` falls back.
- **Gotchas:** (a) a PostgREST `.neq("email_status","sending")` also skips rows where the column is NULL — the send-back claim uses `.or("email_status.is.null,email_status.neq.sending")`; (b) a bare `title` attribute on a button trips a repo lint rule (use `FastTooltip`) — the page just explains the switched-off state in a banner; (c) the sandbox mail capture decodes HTML entities when it stores a body, so a captured email shows the typed `<b>` where the real email carries `&lt;b&gt;`; (d) the shared sandbox holds old QA applications that show up as "Needs review" — that is test data, not a bug; (e) the sandbox table also has two columns from another session (`intended_contact_id`, `intended_name`) that production does not — never select them here.

## Gotchas, invariants & past bugs
- **Claim only on an explicit Start.** An earlier version claimed on page load; React's dev double-run fired two claims and the page wrongly said "already used", and preview bots could burn links. Now GET never claims; only POST (Start) does. The state fetch is still guarded with a ref (`loaded`).
- **A database hiccup is never "invalid link":** the lookup throws on a DB error and the routes answer 503 / "Something went wrong"; only a truly absent token is 404 "missing".
- **Retries don't pile up files:** the page remembers a finished upload per box and reuses it; signed upload URLs are `upsert: false` so one URL cannot overwrite a stored passport.
- **No IP or browser string is stored on submit** (the columns exist, unused).
- **Strict mode is off in this repo's TypeScript config**, so `if (!x.ok)` does not narrow the result unions here; the routes use `"reason" in gate` / `"error" in result`.
- **Never export a helper from a `route.ts`** (Next route export restriction) — the URL builder lives in `lib/bofa-intake/url.ts`.
- **Submit verifies every file really exists in storage under this link's own token** and only then flips `opened` -> `completed` (so a replay or double-click cannot submit twice).
- **Sandbox email:** the staff notification goes through `gmailPost`, which under `SANDBOX_MODE` captures instead of sending; production sends for real.
- **Local test admin** needs `app_metadata.mfa_exempt = true` or login stops at MFA enrollment.
- **A file goes out under the name and type of the bytes in Storage, never the phone's file name.** Any new place that attaches, links or lists a submitted file must call `describeSubmissionFile` (or `signedUrlForSubmissionFile`, which does). Calling it from `f.name` re-creates the ".HEIC over JPEG bytes" bug. `describeSubmissionFile` looks at the stored version's `mime_type`; a temporary (not yet archived) file keeps its own name.
- **Every Storage save of an applicant's file must pass `skipAnalysis: true`** (`archive.ts`, pinned by `bofa-intake-archive-analysis.test.ts`): passports/IDs/tax letters of an outside person are never queued for the AI reader.
- **Once the hand-off to Gmail begins, "failed" does not mean "not sent".** Errors after `handedToGmail = true` are saved with `SEND_UNCONFIRMED_PREFIX`; the page then warns before the next Submit. Do not reword that prefix without updating the tests that read it, and do not move `handedToGmail = true` earlier (it would cry wolf on errors that provably sent nothing) or later (it would call a possibly-sent email "did NOT go through").

## How to verify current state
1. `select status, count(*) from bofa_intake_requests group by 1` — links by state.
2. Open a fresh link in two browsers: first gets the form, second gets "already used"; first refreshes fine.
3. Staff: `/bofa-intake` as admin; a team (non-admin) user is redirected home.
