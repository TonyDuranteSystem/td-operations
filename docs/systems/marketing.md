## What it is
A separate, confined workspace for Rocco's sales team (Rocco = boss, Ale = his employee): leads from the ads, qualification, a paid strategic call sold with a payment link, then Antonio's upsell, with a Finance page. Today only the settings layer exists. The team record stays `draft` (nobody can log in) until Antonio switches it `active`.

## Business rules (Antonio's rulings, 2026-10-17)
- 80/20 on the strategic call is a SETTING (seller 80, TD 20), per person and per kind of sale, with an effective date. Paid to Rocco's own US LLC (Entregarse US LLC, CRM account `a2d2f660-8da9-4645-a478-54a8c1c1339d` on production).
- No price rules: any amount, any currency. No VAT or tax lines anywhere. Upsell terms are blank until Antonio sets them ("terms not set": nothing computed).
- **Rocco, as boss, has every option ON for his team, including creating offers and exporting leads** (Antonio, 2026-10-17 late); both are settings Antonio can switch off, and member-approval starts OFF. Only the commission terms, the Meta connection and the kill switch stay Antonio's. Everything else (stages, reasons, templates, permission bundles, currencies) is a stored value, never hardcoded.
- Legal/tax topics are parked (plan Appendix G) and never part of the build.

## How it's built
- Tables (migration `20261017-1900-marketing-p0-settings.sql`, undo alongside): `marketing_teams` (draft|active|paused), `marketing_settings` (key + optional team, jsonb), `marketing_settings_history` (append-only, written by a trigger on every change), `marketing_commission_terms` (append-only; shares must add to 100). RLS on, no policies: server (service role) only.
- Pure rules, client-safe: `lib/marketing/settings-schema.ts` (the setting keys, their rules and starting values; a stored value that no longer fits falls back to the default), `lib/marketing/commission.ts` (`termInForce`, `splitCents` in integer cents with the remainder to TD, `shareBase`), `lib/marketing/team-status.ts`.
- Server: `lib/marketing/settings.ts` (create team, change status, get/set settings, commission terms). Admin-only by the caller; it trusts the route to have checked.
- Payments: a Stripe checkout tagged `payment_kind` (see `docs/systems/offers.md`, job J-A) skips every client effect; the marketing ledger (P2) will read the stored webhook event. Marketing is Stripe-only because Whop carries no metadata.

- **Webhook** `app/api/webhooks/meta-leads/route.ts` (public under `/api/webhooks`, blocked by the sandbox guard in the test environment). GET = subscription handshake (answers only OUR `META_WEBHOOK_VERIFY_TOKEN`). POST = verify the HMAC-SHA256 signature of the RAW body with `META_APP_SECRET` (`lib/marketing/meta-leads/signature.ts`; **fails closed**: no secret = 503, bad/missing signature = 401; the older Calendly route skips its check when unset, this one never does), parse ids (`parse-webhook.ts`), STORE every notification first as a durable event, then fetch/store up to 5 leads inline; the rest and any failure are finished by the cron. Always answers 200 to a valid notification.
- **Pure logic with injected database/Graph** (`lib/marketing/meta-leads/ingest.ts`): event stored first (unique `leadgen_id`) → lead fetched → lead written once (unique `leadgen_id`) → event marked done. A failed fetch/write = event `failed` (attempts+1, short error, never the token); after 8 attempts `gave_up` with a loud log. A duplicate delivery/retry/re-read never makes a second lead. Existing-client hint: exact email (case-insensitive, both email columns) or the last 8 digits of a phone (both phone columns) against `contacts` → `existing_client` on the lead + a timeline entry; a FAILED check is flagged `check_failed`, never read as "not a client". Never an automatic merge.
- **Graph client** (`graph.ts`): token in the `Authorization` header, never in a URL; version `META_GRAPH_VERSION` (default `v25.0`; v26.0 exists since 2026-07-29); host fixed to Meta (only a loopback address is accepted, for the test double).
- **Cron** `app/api/cron/marketing-lead-retry` every 5 min (CRON_SECRET; registered in `vercel.json` and `lib/cron-coverage.ts`): retries open events older than 2 minutes, then re-reads the last 3 days of every form of `META_PAGE_IDS` (`service.ts:reconcileRecentLeads`) so a missed notification or an outage never loses a lead. Does nothing until `META_PAGE_ACCESS_TOKEN` is set.
- **Tables** (migration `20261019-1000-marketing-leads.sql`, undo alongside; ends with the standing lock call): `marketing_leads` (every form answer kept as received in `answers`, the whole Graph payload in `raw`, ad/campaign/form ids, `status` text = a pipeline-stage key, nullable `team_id` = not assigned yet), `marketing_leadgen_events` (the durable inbox), `marketing_lead_events` (append-only history). RLS on, NO policy: server only.
- **Which team a lead belongs to:** setting `lead_intake_team_id` (empty text = none chosen) → else the only ACTIVE team → else nobody (Antonio sees it as "Not assigned"). (It is empty text, not null, because a settings row cannot hold SQL NULL: found by the end-to-end test.)
- **Screens:** `/marketing/leads` and `/marketing/leads/[id]` (guard + `leads.read`; the team id comes from the guard and is IN the query, so another team's lead id is a 404); Antonio's `/marketing-leads` (strict admin only: all teams, unassigned leads, Meta connection health showing each secret as set/not set, never its value). - **Slice 1b — connect Meta from the admin page (no code, no console):** logic in `lib/marketing/meta-leads/connection.ts` (pure, Meta calls injected: `checkMetaConnection`, `subscribePages`, `explainGraphError` = Meta error codes said in plain words: 190 expired key, 200/10 missing permission, 4/17/32/613 rate limit), Graph helpers in `graph.ts` (`fetchTokenIdentity`, `listPageSubscribedApps`, `subscribePageToLeads`; the key still travels only in a header, also on the POST). The live lead ads run from the Page **Tony Durante LLC** (id `101824772644890`), NOT "Tony Durante US".

## Slice 2a — what a setter / the owner does with a lead (sandbox, built 2026-10-19)
- **Actions** on a lead, one route `POST /api/marketing/leads/[id]/action` (body `{action: claim | release | note | good | not_in_target | call_back, ...}`): picking and giving back need `leads.pick`; everything else needs `leads.mark`. The team id comes from the guard, never the request; another team's lead id is a 404 and writes nothing.
- **Pure decision** `lib/marketing/lead-actions.ts` (`planLeadAction`: allowed or not, and exactly what to write; no database) + `lead-actions-server.ts` (`applyLeadAction`: loads the lead with the team in the query, writes with a "nothing changed meanwhile" condition on the stage and the picker, then writes the history row). A lost race answers 409 "changed while you were looking"; a failed history write is reported, never silent.
- **Rules:** a free lead can be picked by one person; a lead someone else picked can only be worked by that person or the team owner (the owner can also give it back); Good records EVERY checklist item as ticked/unticked (it does NOT force all ticks: a decision to confirm with Antonio); Not in target needs a reason from the `not_in_target_reasons` setting; Call back later needs a real time (not older than 5 minutes, within 180 days). Each outcome moves the lead to the stage named by the new setting `setter_outcome_stages` ({good: qualified, not_in_target: not_in_target, call_back: contacted}); if that stage is no longer in `pipeline_stages` the action is refused in plain words (nothing written). The default `pipeline_stages` gained a last stage `not_in_target`.
- **Data** (migration `20261019-2300-marketing-setter-actions.sql` + UNDO, columns only on `marketing_leads`): `claimed_by`, `claimed_by_label` (the picker's email, so lists need no lookup), `claimed_at`, `callback_at`, `not_in_target_reason`, `qualification` (`[{item, ticked}]`). **Run the migration BEFORE the code reaches production**: the lead screens (and Antonio's master page) now read these columns. Every action also writes an append-only `marketing_lead_events` row (kinds `claimed`, `released`, `note`, `status_changed` with from/to/reason/note/callback).
- **Screens:** the lead page has a "What to do with this lead" panel (`components/marketing/lead-action-panel.tsx`, phone-first; server messages are shown as written); the list has filters (All / Not picked yet / Picked by me / Call backs, plus a stage row) in the address (`?show=&stage=`; nonsense falls back to All), call backs first and soonest first, and shows who picked each lead. History lines are plain English (`lead-view.ts:eventText`).
- **Not done yet (2b/2c):** the Team page (invite setters, pause, access), CSV import of old leads, Italian/English, the checklist wording (the setting starts empty, so "Good" shows no ticks until it is filled), a person's calendar of call backs, assigning an unassigned lead from a screen.

## Gotchas
- The shared apply script `scripts/apply-migration.js` forces SSL and fails on the private local stack ("server does not support SSL"). Apply with `docker exec -i <db container> psql -U postgres -d postgres < file.sql`.
- A rate change is a NEW term row with a later effective date. A sale will take a snapshot of the term when its payment link is created (P2), so old sales never change.
- Do not add a hardcoded stage name, reason, percentage or switch anywhere: add a key to `settings-schema.ts` instead.
- P1 (roles, middleware, login) edits protected files and needs Antonio's explicit go on the P1 plan first.
