## What it is
Antonio wants one staff-only page where he makes a Calendly link for a chosen person — lead / client / partner / private, free or paid, any length — and sends it. Calendly and Zoom stay. The link he sends is `app.tonydurante.us/r/b/<random id>` (Stage 1b); the visitor is redirected to Calendly with the id added as `utm_term`; when the booking arrives, the webhook finds the link by that id and applies the rule of the kind chosen: a **client's** call is saved under the client (no stray lead), a **new person** becomes a lead as today, a **private** call is saved nowhere, a **partner**'s new lead is marked. Anything unusual (wrong email, unknown or used link, a failure) falls back to **today's behaviour** and raises a card for a human; the webhook never drops a booking.

Antonio's decisions (13 Nov 2026): a wrong-email booking = a normal lead + a card ("Same person: link this email" comes with the screens); admin-only; portal clients get "Copy payment link" only (paid links, Stage 3); build order engine → screens → extras → paid.

## Business rules
- **A kind is catalog data, not code.** Catalog `booking_kinds` (4 seeds: Lead, Client, Partner, Private); each kind's rule is flat metadata: `existing_person` (attach | lead | none — what a booking by someone already a CONTACT does), `new_person` (lead | none), `mark_lead` (first line of the new lead's notes: `Booking kind: <label>`), `sales_template` (a free call for a new person uses the sales-questions Calendly template). A link pins a SNAPSHOT of the rule when made; renaming or retiring a kind never changes a link already sent. A kind with no rule is "needs setup" and is refused by the maker. Retiring writes `status='deprecated'`.
- **Length:** any whole number of minutes 1–720. Exactly 30 = the standard reusable link (never claims); anything else, every paid link, and every link with a referrer is one-time (a reusable link would credit whoever opens it).
- **One-time link = atomic claim.** The first booking that matches takes it; a second different booking becomes a normal lead + an `unknown_id` card (reason `used`). A reusable link never claims (the downstream event-address uniques stop doubles). **Expiry only stops a link nobody has claimed:** a link claimed before it expired still recognises its own booking's replay and reschedule (revoking still stops everything except a replay).
- **The tag is an untrusted hint.** A visitor can edit the address. So the booker's email must match one of the link's `person_emails` (snapshotted when the link was made: primary + `email_2` + alternate emails; may be EMPTY — then the first booker claims and `claimed_email` is remembered). A mismatch claims nothing, creates a normal lead, raises a `mismatch` card and gives NO referral credit. Only a utm_term of our strict 22-character shape counts; an ad keyword is ignored.
- **Referrer comes from the link ROW only** (never from the address). Credit (= the pending referral attribution the webhook already makes) only when the link is ONE-TIME AND carries at least one email to check (a reusable link, or one with no email, would credit whoever opens it) AND this booking creates a brand-new lead AND the booker is not an established client (alias-aware) AND the email matched. What happened is written on the row (`referral_outcome`: attributed, no_referrer, mismatch, reusable_link, no_email_to_check, not_new_lead, booker_is_client, booker_unchecked, failed). The link maker (Stage 1b) must therefore ask for the person's email whenever a referrer is set. While a link row is in play the old address-based referral lookup is skipped.
- **The paid-call step runs first and keys on the BOOKER's email, exactly as before.** Booking links add no money logic in Stage 1a.
- **Switch:** one key, `app_settings.booking` = `{mode: off|page|live}`; missing/malformed/unreadable = off. `page` = the page works but the webhook branch is skipped; `live` = everything. The webhook branch ALSO needs `CALENDLY_WEBHOOK_SECRET` (without it anyone could forge a link id): with no secret it never reads the setting at all. Claude flips it on Antonio's word; no screen for him.

## How it's built
- **Tables (migrations `20261113-1710…1740` + `.UNDO.sql`, applied to the SANDBOX only; each created table: RLS on, `REVOKE ALL FROM anon, authenticated`, ends with `marketing_lock_all_tables()`, a verify SELECT last; UNDO in reverse order = contact_calls, call_checks, booking_links, kinds; plain DROP TABLE so a wrong order is refused):** `booking_kinds` (catalog rows), `booking_links` (one row per link: `public_id` unique, `rule_snapshot`, `person_emails text[]`, `once`, `status` open|claimed, `claimed_invitee_uri` partial-unique, `effects_done_at`, `referrer_contact_id`, `referral_outcome`, real FKs all SET NULL), `call_checks` (cards: `unpaid_call | mismatch | unknown_id | effect_failed`; plain `UNIQUE (kind, dedupe_key)`, real FKs lead/contact CASCADE), `contact_calls` (append-only log of calls booked by an existing contact; states scheduled | moved | cancelled; no done state, no recording matching). No CHECK lists anywhere (a CHECK on the shared sandbox turns other sessions' CI red). Types: the code reaches the new tables through untyped clients; `lib/database.types.ts` and `lib/db-check-types.ts` are regenerated from the CI artifact (never by hand) once the tables are on production, then `npm run atlas`.
- **Pure rules:** `lib/booking/kinds.ts` (rule parse, snapshot, name dedupe), `lib/booking/plan.ts` (`decideLinkPlan`: length, template, pay mode, amount through the CRM's own `parseAmountCents`, referrer eligibility), `lib/booking-links/{id,tag,match,destination,referral,language,switch,missing-table}.ts`.
- **Database helpers (injected client, never throw, tolerant of a missing table):** `lib/booking-links/store.ts` (find, atomic claim, move claim on reschedule, effects-done, lead id), `call-checks.ts` (`raiseCallCheck`: one card per booking; if the card cannot be saved → system error + `webhook_events.review_status='link_check'`), `lib/leads/contact-calls.ts`, `lib/operations/contact-email-aliases.ts` (email + `email_2` + `alt_emails`, ignores merged contacts; the older `findContactIdByEmail` is untouched).
- **The webhook (`app/api/webhooks/calendly/route.ts` + `lib/booking-links/engine.ts`):** PHASE 1 (read-only, right after the booking is parsed; only when the switch is `live` AND the secret is set) finds the link by id, or — when the tag did not arrive on a reschedule — by `old_invitee` = `claimed_invitee_uri`. PHASE 2 (after the paid-call step, before the lead path) judges the match (`decideLinkMatch`: unknown → replay → inactive → mismatch → reschedule → used → reusable → claim), claims atomically, then applies the pinned rule: attach (log under the contact, answer `attached`, no lead) | lead (today's path, with hooks: notes prefix, language fallback, lead id + `effects_done_at` written back, referral outcome) | none (answer `calendar_only`). A replay re-runs the effects until `effects_done_at` is set and never reaches the legacy path by itself. Anything thrown → today's path + an `effect_failed` card. **Exception — a booking that carries OUR tag (the strict 22-character id) whose link lookup fails with a database error is answered 503** so Calendly sends it again: nothing is created meanwhile, a system error is reported, the stored copy is marked `link_check`, and the paid-call step (which ran first and is idempotent on the charge) cannot double. Untagged bookings, an ad keyword in utm_term, and a reschedule found only through its old booking stay fail-open exactly as before; a MISSING table is still read as "nothing here". The stored event insert now returns its id (`.select("id")`), and the referral-code lookup escapes `_`/`%`.
- **The legacy lead path moved, unchanged,** to `lib/calendly/legacy-lead-tail.ts` (`runLegacyLeadTail`: update the existing lead, or create the lead — tagged to an established client —, referral attribution, keep the call). Optional hooks only; with none it behaves exactly as before. **Proof it changed nothing:** the private replay (below).
- **Readers:** Zoom filing's third booking read (`lib/crm-store/zoom-call-filing.ts` → `listContactCallsInWindow`, tolerant: a missing table or read error = none, unlike the two older reads which throw by design); the contact page's **Booked calls** box (`components/contacts/contact-calls-section.tsx`), hidden for a day that already has a call summary.
- **Admin gate for the routes coming in Stage 1b:** `lib/auth/require-admin-route.ts` (`requireAdminRoute`, `requireAdminJsonRoute`: admin only, 403 + no-store, deny on throw, same-origin JSON proof for changes); `lib/security/booking-admin-gate-check.ts` scans every file under `app/api/booking/` and `app/(dashboard)/booking/` (none exist yet). It reads EVERY export form (function, const arrow / function expression, `export { a as POST }`, `export { POST }`), resolves a re-export to the function in the same file, requires the gate inside EACH exported handler (first await, answer kept and handed back: `const denied = await requireAdminRoute(); if (denied) return denied`; GET/HEAD/OPTIONS either gate, anything that changes data the JSON gate), and FAILS CLOSED on anything it cannot read (`export *`, a re-export from another file, a handler wrapped in a call, an expression-bodied arrow, a default export in a route, an unknown value export, a file that ends inside a string). Pages and layouts: a server component whose default export (and any `generateMetadata`-style function) turns a non-admin away with `if (!isSecureAdmin(user)) redirect/notFound/return/throw` BEFORE any database read; a `"use client"` page fails. The migration lock check (`lib/security/migration-lock-check.ts`) now ALSO demands RLS + REVOKE for every table created from migration `20261113-1700` on.
- **Settings keys** `booking` and `booking_templates` (event-type addresses, set by SQL; used by Stage 1b) are documented in `lib/settings.ts`.

## Gotchas, invariants & past bugs
- **The extraction is the riskiest edit** (it runs on every real booking even with the switch off). It is proven by `tests/unit/calendly-webhook-replay.test.ts`: ~100 stored real bookings (read from production `webhook_events`, kept OUTSIDE the repo — they hold emails — via `BOOKING_REPLAY_DIR`) × 20 situations, recorded from the unmodified route (golden sha256 = main's route) and compared after the change. Strict level (every query, write, log line, answer) differs ONLY by the one deliberate `.select("id")`; behaviour level (writes, money/referral calls, answer) is identical with the signing secret set and the switch absent / off / page / live / unreadable. The golden file must be recorded from unmodified code (the test refuses to overwrite it). Re-run it after the next production merge against the next real booking.
- A successful claim was once read as "claim lost" by the first draft (caught by the in-memory route tests) — the claim result is now an explicit flag.
- **Sandbox cannot receive real webhooks** (middleware answers 503) and has no Calendly token; the tests call the route handler directly. `tests/unit/booking-sandbox-real-run.test.ts` (skipped unless `BOOKING_SANDBOX_RUN=1`; refuses a non-sandbox database; cleans up) runs the real route against the real sandbox database: atomic claim race, unique-card behaviour, array/ilike filters, FKs, table lock.
- **Production apply is by hand:** Antonio pastes each migration in the Supabase SQL editor (it shows only the LAST statement, hence the verify SELECT at the end of each file). Do NOT call `marketing_lock_all_tables()` again to "read" it — it rewrites policies; read `relrowsecurity` and the grants instead.
- `utm_term` has never been seen in a real stored delivery (0 of 102): the proof of the tag is Calendly's side, from a controlled test on 13 Nov. The first real tagged delivery is the true proof — check one after the switch goes live.
- `contacts.language` is dirty ("en", "Italiano"...); `leads.language` is "Italian"/"English": a link's `person_language` goes through `normalizeLeadLanguage` and is written only when readable and only when the booking itself said nothing.
- "Hardening the route to refuse when the secret is unset in production" is NOT in 1a: if the production secret were unset it would drop every real booking. It waits for the unsigned-POST check (Stage 1b gate).
- A one-time link whose booking is cancelled in Calendly stays claimed (cancellations are not delivered to us); a new link is needed. Cancelled calls stay `scheduled` in the log until Stage 2 reads Calendly.

## How to verify current state
- Switch: `SELECT value FROM app_settings WHERE key='booking'` (no row = off). Secret: `vercel env ls` (project of the environment you mean) for `CALENDLY_WEBHOOK_SECRET`.
- Tables locked: `SELECT relname, relrowsecurity FROM pg_class WHERE relname IN ('booking_links','call_checks','contact_calls')` and no grants to anon/authenticated (`information_schema.role_table_grants`).
- Kinds: `SELECT slug, display_name, status, metadata FROM catalog_entries WHERE catalog_id='booking_kinds'`.
- Replay: `BOOKING_REPLAY_DIR=<folder with payloads.json + golden.json> BOOKING_REPLAY_MODE=compare BOOKING_REPLAY_LEVEL=behaviour npx vitest run tests/unit/calendly-webhook-replay.test.ts`.
- Real run (sandbox only): `BOOKING_SANDBOX_RUN=1 npx vitest run tests/unit/booking-sandbox-real-run.test.ts`.
- Cards waiting: `SELECT kind, status, count(*) FROM call_checks GROUP BY 1,2`; a booking whose card could not be saved: `SELECT id FROM webhook_events WHERE review_status='link_check'`.
