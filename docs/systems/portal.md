## What it is
The client-facing app at **portal.tonydurante.us** where clients log in to see their services, documents, invoices, deadlines, chat with the team, and complete data-collection wizards. This is NOT the internal CRM dashboard — "portal" always means the client app.

## Tiers — the master access control (R102)
A client's portal experience is gated by their **tier**. There are exactly **4** (`lib/portal/tier-config.ts`, ordered):
| Tier | When | Sees |
|---|---|---|
| `lead` (0) | Offer sent, not paid | View/sign/pay offer, chat, profile, guide |
| `formation` (1) | Paid for formation (no EIN yet) | + data wizard, documents, signatures |
| `onboarding` (2) | Existing LLC going through onboarding | + upload docs, fill wizard |
| `active` (3) | Data reviewed / company live | + services, invoices, deadlines |

- Each tier **includes** the previous tiers' features (`TIER_FEATURES`).
- **A feature shows only if BOTH gates pass:** the tier allows it AND the data exists (`getPortalNavVisibility`). Tier alone is not enough.
- **Account type** is a second axis: **Client** (annual management — full feature set per tier) vs **One-Time** (standalone service — limited; no billing/invoicing/customers/deadlines).
- The value `full` is **removed** — never use it (R102).

### How tier is set — `syncTier()` only
- **ALL tier writes go through `syncTier()`** (`lib/operations/sync-tier.ts`). Never write `accounts.portal_tier` / `contacts.portal_tier` directly (R102).
- **Downgrade guard:** `syncTier` refuses to lower a tier unless `allowDowngrade=true` — it returns **success as a silent no-op**. This stops offer-publish (which runs at `lead`) from clobbering an existing `active` client.
- **Contact tier is computed, not set:** a contact's tier = the **highest** tier across all their linked accounts (`computeContactTier` / `maxTier`). Setting an account tier propagates to its contacts.
- `tierForContract(contractType)`: `formation`→`formation`, `onboarding`→`onboarding`, everything else→`active` (`lib/portal/auto-create.ts`).

- **Home announcement banners** are client components rendered on the active-tier home dashboard (`app/portal/page.tsx`), each dismissed per-device via a versioned `localStorage` key read in a `useEffect` (no hydration mismatch): `GuideAnnouncementBanner`, `TeamAccessAnnouncementBanner` (key `td-team-access-announce-v1`, also drives the sidebar "new" badge), and `WhatsNewBanner` (key `td-whats-new-v1`, bilingual "What's New / Novità" feature announcement). Bump the key's version suffix to re-show after a major change. Lead/onboarding/formation tiers render different dashboard components and do not show these.
- **Documents:** auto-saved (`auto-save-document.ts`), templated (`document-templates.ts`); pages for general docs, `tax-documents`, `itin-documents`. Legal docs are view-only for non-signers.
- **Sales invoices (client's own tool):** the `/portal/invoices` Sales list has a per-row 3-dot action menu (View · Download PDF · Edit · Send · Reminder · Void) following the standard invoice lifecycle. These are the **client's own invoices** — no TD-accounting/tax impact — so Edit + Void are allowed at any stage incl. Paid; Send only advances Draft→Sent (never downgrades a paid invoice); Reminder is Sent/Overdue only; Split parents excluded. Full design + gating in `billing-invoicing.md` ("Portal Fatture per-row actions").
- **Invoices/payments:** `/portal/billing`, `/portal/invoices`; the **Pay modal is the only payment entry point** (R092) — invoice emails point here, never embed Stripe/wire. The expense list shows the **net amount due** (`client_expenses.amount_due`, the original `total` struck through when a credit was applied) and the Pay modal charges `amount_due`, so a credited invoice (e.g. a referral credit reconciled in — see `billing-invoicing.md` / `referrals-circleback.md`) shows the client the true balance. `getPortalExpenses` selects `amount_due`/`amount_paid` (added 2026-06-01).
- **Self-logged expense attachments are signed, not public (2026-08-26).** A client can attach a receipt/vendor invoice to a manually-logged expense (`client_expenses.source='upload'`, distinct from the `source='td_invoice'` TD-billing mirror above). `portal-uploads` is a **private** bucket — `attachment_url` is NEVER trusted or written at rest; the real file location lives in `attachment_storage_path`, and `getPortalExpenses`/`getPortalExpensesByContact` mint a fresh 1-hour signed link per request (parallelized across rows) via `lib/storage/signed-download.ts::createRecordedSignedUrl`. `createExpense`/`updateExpense`/`markExpensePaid`/`deleteExpense` (`app/portal/invoices/expense-actions.ts`) verify the caller owns the account (or, for a contact-only no-account expense, is the exact owning contact) before touching a row — never a teammate on a contact-scoped row. **`markExpensePaid` is now reachable from the UI (2026-08-26b)** — `components/portal/expense-list.tsx` shows a one-click "mark as paid" button for any non-`td_invoice` row that's Pending/Overdue (the action itself was already correctly ownership-gated; it simply had no caller before this). `updateExpense`/`deleteExpense` are still unreachable from any client-facing control — same gap, not yet built. **`createExpense` now find-or-creates the matching Suppliers (`client_vendors`) record for a typed vendor name (2026-08-26c)** — exact/case-insensitive match, never a database LIKE-style match — and `createVendor`/`updateVendor`/`deleteVendor` (`app/portal/invoices/vendor-actions.ts`) gained a single-branch (account-only — `client_vendors` has no contact-scoped mode) ownership check. Full incident + fix detail in the changelog entry at the top of this doc.

## Team Access — teammates (Option B, independent identity)
An **active client's account-admin** can invite their employees ("teammates") into that **one company's** portal, choosing per-section what each may see.
- **Identity model (Option B):** a teammate is an **independent identity** — its own row in `portal_team_members`, **NOT** a contact and **NOT** in `account_contacts` (so billing/ops flows never target a teammate). Auth lives in `auth.users` with `app_metadata.role='client'` + `kind='team_member'` + `account_id` + `team_member_id` markers, and a synthetic email (`tm-<token>@teammate.portal.tonydurante.us`). Login is **username + password** (`app/portal/login`).
- **Who can manage:** only the **account-admin** ("main person"). Resolver precedence (`lib/portal/team/account-admin.ts`): persisted override (`accounts.portal_admin_contact_id`) → MMLLC SS-4 signer → signer name-match → owner-role `account_contact` → sole contact. SMLLC = the stored owner.
- **Capabilities are owner-chosen, server-enforced, default-deny** (`lib/portal/team/capabilities.ts`): `documents`, `invoices_billing`, `chat`, `company_services`, `bank_applications`, `sales_customers`, `company_data_form`, `announcements`. Empty = see nothing beyond always-on (overview/guide). Owner-only/non-delegable sections (team, sign, request service, referrals, profile, offer) are **never** delegable.
- **Chat notifications include teammates** — `notifyClientOfAdminMessage` (the single admin→client chat-email chokepoint) emails account contacts AND active teammates who have the `chat` capability + a real email on file (placeholder emails live only on auth.users, so they're skipped). Revoked teammates and no-chat-cap teammates are excluded; recipients are deduped by email. Teammates have no language column, so they **follow the owner's language** (the `role='owner'` account contact, else any contact, else English).
- **The gate** (`lib/portal/team/gate.ts`): `canAccessAccount(user, accountId, capability)` is **default-deny** — it replaces the leaky `if (contactId) { check }` pattern that silently skipped the check for a null-contact (teammate) user. Staff (non-`client` role) bypass. Pages use `getTeammateScopeOrNull(cap)`; the identity seam is `resolvePortalIdentity` (`contact | teammate | none`).
- **Production safety:** prod RLS denies a teammate every **direct/realtime** read (their JWT has no `contact_id`, so `get_client_account_ids()`/`get_client_contact_id()` return empty). Granted sections still work because pages fetch **server-side** via `supabaseAdmin`. Owner accepts a **responsibility disclaimer** at invite time.
- **Manage:** `/portal/team` (admin-only tab) — invite/edit/revoke/reset-password; revoke also bans the auth user. Optional teammate email enables notifications + self-serve password reset. The invite dialog explains email is optional (only for notifications).
- **Feature announcement** — account-admins see a one-time dismissible violet banner on the portal home (`TeamAccessAnnouncementBanner`, gated by `canManageTeam` computed via `isAccountAdmin`) + a "NEW" badge on the Team nav item; both clear via the shared `localStorage` key `td-team-access-announce-v1` (on banner dismiss/click or first Team-page visit). The "Invite Your Team" guide article (id `team-access`, EN+IT) lives in `app/portal/guide/page.tsx`. A broader broadcast can be posted to all clients via the existing `portal_announcements` system (CRM Config → Announcements).
- **Teammate chat attribution** — a teammate has no contact, so their chat messages stamp `portal_messages.sender_name` with the teammate's **display name** at send time (chat route teammate branch). The read route resolves the display name via `pickChatSenderName(contactName, storedSenderName)` (`lib/portal/chat-sender-name.ts`): contact name for client/owner messages, stored display name for teammates, null → UI's generic label. So staff/owner see *which* teammate wrote. Admin/system messages still render "Tony Durante Team".
- **Teammate chat threading** — the chat page (`app/portal/chat/page.tsx`) and `usePortalChat` thread by `contact_id` for normal clients but by `account_id` for teammates (no contact_id; their messages are stored by account with `contact_id` NULL). The page resolves the teammate's account via `getTeammateScopeOrNull('chat')` instead of the old `if (!contactId) redirect('/portal')` that silently bounced teammates out of Chat. The Journey Log tab is hidden for teammates (contact-oriented).

## Business rules
- **R102** — 4 tiers; `syncTier()` is the only writer; `formation` = no EIN; never advance tier manually; `full` is forbidden.
- **R103** — admin portal message auto-emails the client (throttled 2h, bilingual).
- **R100** — client-visible content (chat, notifications, docs) uses soft-delete; clients never see deleted rows, staff see a tombstone.
- **R092** — clients pay via the portal Pay button only.
- **R099** — client-side fetches must surface the server's real error, not a generic toast.
- **No support@ fallback** — the portal IS the channel; don't tell clients to email support@ as an alternative.

## Gotchas, invariants & past bugs
- **⚠️ FORMATION ENTITY TYPE: the signed contract decides, and the wizard NEVER guesses (2026-08-09, dev job `fc69557f`).** The formation wizard rendered a SINGLE-member form to MULTI-member clients and then refused to submit — it demanded as many ITIN applicants as the client had bought while showing a form on which only one person could exist. Alessandro Della Bianca hit the deadlock after paying €4,000. **Cause: two lookups with different fallbacks.** `itinCount` resolved lead-independently (offer matched by client email), while the entity type came ONLY from the `?lead=` scope and otherwise fell to a hard `'SMLLC'`. **Nearly every entry point drops that lead** — the formation dashboard button, the services-page `?type=formation` link (which also skips the cookie rescue), the post-payment portal notification, the reminder cron, the sidebar. Present since the wizard's first commit (`a3f5eeed`, 2026-03-21); `contracts.llc_type` has held the client's own choice since 2026-03-15 and the wizard never read it. **The rule now:** signed contract → the formation offer (live statuses only, case-insensitive email match) → **ASK THE CLIENT one plain question** ("Just me" / "Me and other owners"). Never wall (a hard stop recreates the dead end) and never guess. **Placement is load-bearing:** after `wizardType` is final and the old account is dropped, and BEFORE `normalizeEntityType` — that helper returns `'SMLLC'` for empty input and would silently reinstate the default. **`account.entity_type` is IGNORED for formation** — a returning client's existing SMLLC was deciding the shape of their NEW MMLLC. Corporation short-circuits (asking an LLC ownership question would be nonsense and its answer would be written as SMLLC/MMLLC).
- **Never persist a guessed entity type (2026-08-09)** — formation materialization reads `formation_submissions.entity_type` back as one of its entity-type sources, so a fabricated `'SMLLC'` could later confirm itself as evidence. `buildSubmissionRecord` now writes NULL, **and only for `formation_submissions`** — `entity_type` is NOT NULL on `onboarding_submissions`, `tax_return_submissions` and `company_info_submissions` (verified in prod + sandbox), where NULL is a 23502 → false "submission failed" toast AND a skipped auto-chain enqueue.
- **A member with no email is still a member (2026-08-09, Antonio)** — on the filing, in the OA, ownership counted; they simply get no contact and no portal access. Their `members` row used to be skipped entirely (the whole write sat inside `if (contactId)`) while their percentage was still deducted from the owner's share, so the ownership table summed to LESS than 100 and the person was missing from the SS-4 and the OA. The row is now written unconditionally with `contact_id: null`, the insert's error is captured (supabase-js RETURNS errors — the enclosing try/catch cannot see them, so the step used to claim "ownership recorded" about a row that never wrote), and the step message distinguishes "no email supplied" from "contact creation failed". Who SIGNS is a separate question — see `docs/systems/lease-oa.md` (signing set).
- **NEVER hand-write a wizard label (2026-07-21)** — every client-facing name for a wizard type comes from `lib/portal/wizard-labels.ts` (`wizardLabelFor` / `completeWizardFormTitle`). That map is `Record<WizardType, …>`, so the compiler refuses a new wizard type without a label. Do NOT loosen it to `Record<string, …>` and do NOT add a local ternary/switch "just for this surface" — four such local maps are what leaked `banking_payset` to three real clients on the portal home the day after the same bug was fixed in the reminder cron. The CRM staff view (`components/accounts/account-journey.tsx`) deliberately keeps its own more detailed labels ("Banking (Payset EUR)") — it is staff-facing and complete; do not merge it into the client map.
- **Wizard number fields support a domain minimum (`FieldConfig.min`, 2026-07-15)** — set `min: 0` on any money amount; `wizard-field.tsx` renders the input `min` attr + an inline EN/IT "cannot be negative" error, and `wizard-client.tsx`'s `belowFieldMin` blocks the step gate (top-level, member-indexed AND repeater sub-fields). Added after the Rocco Papotti incident: the external tax form (and the wizard, which was worse — default step 1 means one ArrowDown from 0 writes **-1**) accepted negative money values; -0.03/-0.04 landed in a real accountant-facing submission. The four tax money fields + `rpt_amount` carry `min: 0` in `wizard-configs.ts`. NEVER add a money field without `min: 0`. Full rule + shared helpers: see `docs/systems/tax-returns.md` (2026-07-15c) and `lib/types/tax-form.ts`.
- **A failed downgrade looks like success** — `syncTier` silently no-ops a downgrade and returns `success:true`. Intentional (protects clients); don't "fix" it into an error.
- **Never set a contact's tier directly** — it's computed as the max across linked accounts.
- **Tier gate AND data presence** both required to show a feature — a tier change won't reveal a section that has no data.
- **One-Time accounts stay limited even at `active`** (no billing/invoicing/customers/deadlines).
- **The standalone `/portal/itin-documents` page is GONE (removed 2026-09-04) — do not re-add it or a nav entry pointing to it.** It was a pre-workspace duplicate of the ITIN "Client Signing" mailing instructions; ITIN document delivery has run entirely through the `/portal/flows/[id]` workspace since the workspace-only redesign (2026-06-25 — see `flows.md`). Confirmed via live production data (real active ITIN SDs at "Client Signing" today) and the `itin_form_*` MCP tool docs (`lib/mcp/tools/itin-form.ts`) that the workspace + a portal chat notification is the only real path — the standalone page was never part of that process. The `itinAtClientSigning` nav-visibility flag (and `hasItinAtClientSigning`/`getItinAtClientSigning`) that gated it are deleted too; `getPortalNavVisibility`/`getContactOnlyNavVisibility` no longer take a `contactId` for this reason. The one real dependency — the client's mail-confirmation action — was moved to `lib/portal/itin-mailing.ts` before the page was deleted, so the workspace's own confirm-mailed flow (`components/portal/itin-shipping-form.tsx`) is unaffected.
- **"NEW" badge and unpaid-invoice sidebar alert (2026-09-04).** Service-flow cards show a violet "NEW" tag (`flows.new` key — deliberately NOT `documents.new`, which means something different: read-state on the Documents tab, not an age window) for `NEW_FLOW_BADGE_DAYS` (7) after creation, via the exported `isWithinNewBadgeWindow` in `queries.ts`. The TD Billing sidebar alert (`getUnpaidInvoiceCount`) and the dashboard's own unpaid-invoice card (`getPortalActionItems(ByContact)`) now share the identical `Sent`/`Overdue`/`Partial` filter with no row cap, so the two can't disagree — a partially-paid invoice (payment-plan tranche) counts as unpaid in both places. The count query is routed through `countOrFailOpen` so a database error shows the alert rather than hiding a real unpaid invoice.
- **Teammates have no `contact_id`** — never gate portal access on `if (contactId)`; that silently skips the check for a teammate and leaks the resource. Use `canAccessAccount` / `getTeammateScopeOrNull` (default-deny). Teammates are never in `account_contacts` and must never be targeted by billing/ops flows.
- **Contact reuse is case-insensitive + alias-aware** (2026-06-10) — `autoCreatePortalUser`/`createFromEmail` resolve an existing contact via `findContactIdByEmail()` (`lib/operations/find-contact-by-email.ts`), NOT exact `.eq('email', …)`. A differently-cased or post-merge-alias email must reuse the real person, never spawn a duplicate contact + duplicate portal login (the Michele Cotti orphan bug). The helper matches `email` case-insensitively (ilike narrows, exact compare in JS to dodge the `_` wildcard) + folded `alt_emails`, and never returns a merged tombstone (`merged_into IS NOT NULL`). Never reintroduce a raw `.eq('email', …)` contact lookup in the activation/portal-creation path.
- Per-company chat isolation is the other in-flight multi-tenant project — verify current chat behaviour against code before assuming.
- **Wizard uploads have a 100MB max, checked in two places, not enforced by the platform (2026-08-26)** — `WIZARD_UPLOAD_MAX_FILE_SIZE_BYTES` in `lib/portal/wizard-uploads.ts` is the single source of truth; keep `wizard-client.tsx`'s browser check and `wizard-upload-url/route.ts`'s server check both importing it rather than hand-rolling a number. The `onboarding-uploads` Supabase bucket itself has no `file_size_limit` set (unlike `assets`/`td-comm-deliverables`, both 100MB) — a client bypassing the app-level check entirely is not yet blocked at the storage layer.
