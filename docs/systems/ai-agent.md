## What it is
A built-in AI chat assistant **inside the CRM dashboard** for staff — it can search the CRM, read Gmail/Drive, and take actions through its own tool set. This is **separate** from Claude Code and the Claude.ai MCP connector: it has its **own** tool definitions (`lib/ai-agent/tools.ts`), not the MCP server's ~217 tools.

## How it works
- **Endpoint:** `POST /api/ai-agent`, body `{ messages: [...] }`, returns `{ content, provider, tools_used }`. Rate-limited to **20 requests/min**.
- **Access:** **admin** (Antonio) always; **team** members only if `app_settings.ai_agent.enabled_for_team = true`; **clients are blocked**.
- **Providers** (`lib/ai-agent/providers.ts`): **Claude `claude-sonnet-4-6` (primary, `ANTHROPIC_API_KEY`)** with **GPT-4o (fallback, `OPENAI_API_KEY`)**. `callAgent()` runs the tool-use loop for whichever provider is configured (Anthropic first). Note: direct provider keys, not the Vercel AI Gateway.
- **Max tool-use iterations** (2026-06-05): the loop ceiling defaults to **`AGENT_MAX_TOOL_LOOPS` env var, then 8** (was a hardcoded `MAX_TOOL_LOOPS = 8`). `callAgent`/`callClaude`/`callOpenAI` accept an optional `maxIterations` per-request override; the max-iteration error string now reports the actual limit. The **same env var** governs the Hermes-bridge worker (`worker-tools.ts`) — see `agent-bridge.md`.
- **System prompt:** `lib/ai-agent/system-prompt.ts` (`SYSTEM_PROMPT`) — embeds business knowledge + instructions.

## The agent's tool set (`lib/ai-agent/tools.ts`)
~38 tools, each a schema + execute function over real Supabase tables:
- **Read:** `search_accounts/contacts/leads/deals/payments/services/tasks/tax_returns/deadlines/portal_messages/kb`, `get_account_detail`, `get_dashboard_stats`, `get_sop`, `run_sql_query`, `portal_chat_inbox`, `portal_chat_read` (full portal thread / inbox with unread counts).
- **Write/act:** `create_task`, `update_task`, `update_contact`, `update_service`, `advance_service_stage`, `send_email`, `update_deadline`, `send_team_message` (internal staff-only note — never client-visible). **Notes-only, append-and-timestamp (never touches other fields):** `update_account_notes`, `update_deal_notes`, `update_lead_notes`, `update_contact_notes`, `update_service_notes`, `update_task_notes`.
- **Gmail/Drive:** `gmail_search/read/read_thread/get_attachments`, `drive_search/list_folder/move/upload_file`, `preview_attachment`.
- **Conversation/memory:** `log_conversation`, `save_memory`, `recall_memories` — the agent has **persistent memory** (the "Antonio Brain" — see sysdoc `antonio-brain-architecture`).

## Enum normalization (`lib/ai-agent/enum-normalization.ts`, 2026-06-04)
Several tool params/filters map to real Postgres ENUM columns (`task_priority`, `task_status`, `task_category`, `service_status`, `conversation_channel`, plus the search-filter enums `account_status`, `payment_status`, `deal_stage`, `lead_status`, `tax_return_status`). An invalid value **throws `22P02` on a write** and **silently returns zero rows on a search**. This module is the single source of truth that maps flexible input (any casing + common synonyms: `medium→Normal`, `todo→To Do`) to the exact canonical DB value, or `null` if unrecognized.
- **Canonical value sets** are verified against `pg_enum` and mirror the migration DDL — keep them in sync if an enum changes.
- **Write paths** (`createTask`, `updateTask`, `updateService`, `advanceServiceStage` auto-tasks, `logConversation`) normalize before insert: `createTask` now defaults `priority→'Normal'` and `category→'Internal'` (the old literals `'medium'`/`'Admin'` were **not valid enum members** and made any category-less create_task throw); `updateTask`/`updateService` return a clear error on an unrecognized enum instead of letting the DB throw.
- **Search filters** normalize then **fall back to the original value** on no-match (an exact match returning nothing is harmless — no behavior regression).
- **Propose path** (`worker-tools.ts::proposeAction`) calls `normalizeToolParams()` BEFORE `validateToolParams` + `computeParamsHash`, so a proposal with `medium`/`todo` is accepted and the stored params (and hash) reflect exactly what executes. The schema `enum:` arrays in `AGENT_TOOLS` are the corrected canonical values (`['Low','Normal','High','Urgent']`, etc.) so propose-time validation still rejects genuine garbage.

## Contacts link through a JOIN TABLE, and the tool finder searches by WORD (2026-07-20)

Two defects fixed together; both had been live and silent.

**1. `contacts` has NO `account_id` column.** The link is the `account_contacts` join table. THREE places filtered `contacts` by `account_id` anyway — the CRM sidebar send rails, the Team Chat `@claude` trigger, and Drive folder naming. PostgREST returned an error; every call site destructured only `data`, so the error vanished and an empty result read as "this client has no contacts". Live consequences, for EVERY client: the sidebar's pinned address list came back empty — and an empty list is deliberately "refuse every address", so **emailing a client from a client page was dead**; and the client-scope allow-list held only the account id, so an action naming one of that client's own contacts was refused as "a DIFFERENT client's id" on the client actually on screen. It failed CLOSED (nothing was ever sent to the wrong person) but invisibly.
- The sidebar now **reports** a failed lookup (`reportSystemError`) instead of discarding it. The bug survived because a broken query and a client with genuinely no contacts were indistinguishable — they are not the same thing.
- **`tests/unit/contacts-account-link.test.ts` scans `lib/`, `app/` and `components/` and fails if ANY file filters `contacts` by `account_id`.** Deliberately repo-wide, not per-call-site: the defining feature of this bug was that it spread to three places unnoticed. It found the third instance on its first run.
- The rails moved OUT of the route file into `lib/ai-agent/sidebar-send-rails.ts`. Next.js refuses extra exports from a route file, so nothing could import — and therefore test — the function that decides which client the assistant may email. That is why the bug lived there. `scripts/test-sidebar-rails-e2e.ts` now exercises the REAL function against a real database (12 checks). **Do not test this by copying the query into a driver** — an earlier driver did exactly that, reproduced the broken lookup, and agreed with the bug.

**2. `find_tool` matched the WHOLE query as a literal substring.** One word worked; a sentence never did. Measured against the real 216-tool catalog: "add note to account" → 0 hits, "account note" → 0, "log conversation" → 0, "note on account" → 0, "add a note" → 0, "record conversation" → 0, "update account notes" → 0 — every one had a perfectly good tool sitting there. The assistant asked for a tool the way a person would, got nothing, concluded it had no way to do the job, and told the staff member to do it by hand. Replaced by ranked word overlap in `lib/ai-agent/tool-search.ts`: name matches outrank description matches, an exact phrase still wins outright (so it is **strictly additive** — everything the old search found, this finds). Deliberately NOT fuzzy or semantic: 216 items, instant, no model call, obvious from reading it. The seven measured phrases are the regression suite.

**3. Catalog tools now forgive capitalisation** (`lib/ai-agent/bridge-param-coercion.ts`). Agent tools have normalised values before validation for a long time; catalog tools went straight into a strict schema check, so a proposal saying `"inbound"` was rejected for wanting `"Inbound"`, and the assistant retried, ran out of turns and asked the staff member to do it by hand. Case-only rewriting, applied BEFORE validation and hashing. **It does not guess** — `"incoming"` is left alone to be rejected, because mapping near-synonyms would change the action.

**4. `find_tool` returned a tool's NAME and DESCRIPTION and nothing else (fixed 2026-07-29, dev job `6ffd2d5e`).** So the assistant reached every bridged tool with GUESSED parameters, and any behaviour living behind an unguessed setting was unreachable. Luca's report of 2026-07-27 is the clean case: he asked for a letter for Lepren LLC without the "Tony Durante LLC" header, repeatedly, and got it every time — because `pdf_create`'s `letterhead` param (whose own description says `Pass "" for a bare document`) was invisible. The instruction had nowhere to land, so repeating it could not help. **This was never PDF-specific**: it applied to all ~218 catalog tools, and it makes the assistant look like it is ignoring a request when it simply does not know the knob exists.

`listBridgeTools()` now returns `params` alongside name/description, derived by `describeZodShape` in `lib/ai-agent/tool-params.ts`, and `formatToolSearch` prints one line per setting (`name*` = required, base type, first ~140 chars of the author's own `.describe()`), capped at 12 settings per tool with an "…and N more" tail, plus a single `(* = required)` legend.
- **Zod 3 AND zod 4 shapes are both read** (`kindOf` checks `_def.typeName` then `_def.type`). The repo is on zod 4, where kinds are lowercase (`"optional"`, `"enum"`) and enum members live on `_def.entries` as an OBJECT, not `_def.values` as an array. A version bump that broke this would NOT throw — every setting would silently render as `value`, which is worse than useless because it still looks like it worked.
- **Wrapper unwrapping is an explicit allow-list, not "descend into any inner schema".** `ZodArray` keeps its ELEMENT on `_def.element`/`_def.type`, so a generic unwrap reports `z.array(z.string())` as `string` and the assistant passes a bare value where a list is required. Caught by the array + enum tests failing on exactly that.
- **Enum choices are enumerated in the type** (`enum(Inbound|Outbound)`), first 8 shown. Guessing the wrong capitalisation is a failure this catalog has already produced once — see item 3.
- **SETTINGS ARE SEARCHABLE, not just printable** (`scoreTool`). Printing them fixes nothing if the tool cannot be FOUND by them: `letterhead` and `header` appear in no tool name and no tool description — only inside `pdf_create`'s parameter text — so Luca's literal words ("remove the Tony Durante LLC header") scored zero on every tool and returned "No tools match". Settings rank BELOW description, so a tool genuinely about the topic still beats one that merely mentions the word in a footnote. The bug-hunter found this: without it the whole change only helps someone who already thought to search "pdf".
- **Requiredness is STRUCTURAL, never `isOptional()` alone** (`isRequired`). zod 4 implements `isOptional()` as `safeParse(undefined).success`, and `z.any()` accepts undefined — so `offer_create`'s `services` and `cost_summary` (bare `z.any()`, both genuinely required) rendered WITHOUT the required marker, telling the assistant the two fields that make an offer an offer were optional. A param is optional only when its OUTER kind is in `OMITTABLE_TYPES`; `isOptional()` is a fallback for unrecognised kinds only. Note `z.string().nullable()` is REQUIRED — you must still supply `null`.
- **Required settings sort FIRST, before the 12-per-tool cap.** In declaration order the cap dropped a required field declared 13th behind "…and N more" — the same "you were never told the knob exists" failure, relocated. Optional-but-important settings can still fall past the cap (`offer_create`'s `entity_type`, #25, decides SMLLC vs MMLLC); that is the cap's accepted cost, and required fields are now structurally safe from it.
- **`.describe()` must come LAST in the chain.** zod 4's `describe()` registers on the instance it is called on and inheritance walks only `_zod.parent`, which `.optional()` does not set — so `z.string().describe(x).optional()` renders a BLANK description. Every current tool writes `.optional().describe(...)`; the reverse order fails silently.
- **Total settings output is budgeted** (`SETTINGS_CHAR_BUDGET = 6000` in tool-search.ts), spent best-ranked-hit-first. Unbudgeted, 15 hits × 12 settings ≈ 35 KB — and a tool result is fenced into the message array and re-sent on EVERY tool-loop iteration with NO prompt-cache breakpoint (only the system block carries one), so it would be re-billed up to 8 times per turn. Measured after the budget: 5–8 KB for `client` / `account` / `email` / `pdf`.
- **Live catalog size is 216** (`listBridgeTools().length`), 210 of which expose settings. Counting `server.tool(` in `lib/mcp/tools/*.ts` gives 218 and the `find_tool` description says "~215" — use the registry length, not either of those.

**5. `letterhead: null` silently restored the default header** (`lib/pdf/letter-pdf.ts`, same job). `(opts.letterhead ?? DEFAULT_LETTERHEAD)` folds `null` into the default, so only `''` suppressed the header and the more obvious of the two ways to say "no letterhead" produced one. Now: **absent ⇒ firm default; `''` or `null` ⇒ bare.** The paired change is mandatory — `documents-generate.ts` passed `letterhead: letterhead ?? null`, which under the new meaning converts "caller said nothing" into "caller asked for none" and would have stripped the header off EVERY generated document. It now passes the value through unchanged. Only one caller of `renderLetterPdf` exists, which is why the meaning of `null` is safe to pin in the renderer.

## Gotchas, invariants & past bugs
- **Two different tool worlds** — the AI agent's `lib/ai-agent/tools.ts` (~34 tools) is NOT the MCP server's ~217 tools. A change in one doesn't affect the other; adding an MCP tool does NOT give the dashboard agent that capability (and vice-versa).
- **Never re-introduce hardcoded enum literals in `tools.ts`** — route every enum-backed param/filter through `enum-normalization.ts`. The `create_task` `'medium'`/`'Admin'` defaults were a live break (invalid enum members → insert threw). Canonical values live in one place by design.
- **`tasks.attachments` is `jsonb NOT NULL` with no DB default** — every task insert MUST supply `attachments: []` (see `lib/operations/task.ts`). `createTask` and `advanceServiceStage`'s auto-task insert omitted it and threw `23502` on every real insert; mocked unit tests can't catch a NOT-NULL violation, so a payload-shape regression test (`tests/unit/agent-tools-insert-shape.test.ts`) pins it. Surfaced by the Slice 3 sandbox rail E2E (`scripts/test-approval-rail-s3.ts`).
- **`advance_service_stage` takes a `service_deliveries.id`, not a `service_id`** — `service_deliveries` has no `service_id` column; the agent gets the id from `search_services`/`get_account_detail` (both expose `service_deliveries.id`). The lookup filters `.eq('id', …)`. The old `.eq('service_id', …)` errored on a nonexistent column, so the tool never worked. Don't revert.
- **Provider fallback can change behaviour** — Claude (sonnet-4-6) primary, GPT-4o fallback; outputs/tool-use may differ if it falls back. `provider` is returned in the response so you can tell which ran.
- **`run_sql_query` runs against the deployment's DB** — staff-only, but on production it hits production. Treat it like any production query.
- **Agent memory is separate** from `session_checkpoints` and from Claude Code memory — it's the dashboard agent's own `save_memory`/`recall_memories` store.
- Model `claude-sonnet-4-6` is hardcoded in `providers.ts` — a model change is a code edit there.
