_Last verified against code: 2026-07-18f — WINDOWED OCR: documents longer than Google's per-call page limit are now readable. Document AI's synchronous endpoint refuses a PDF over 15 pages (non-imageless; 30 needs an allowlist we are not on), so a 35-page scanned tax return failed WHOLESALE — and that same failure ran in the STORE path too (`processFile` → `extractTextFromFile` → `ocrDriveFile`), so `documents.ocr_text` was never written for long scans and every later read found nothing saved. THREE changes, all additive: (1) `ocrDriveFile(fileId, opts?)` gained optional `pages` (an inclusive 1-based range), `pageLimit` and `maxBytes`. When `pages` is set AND the file is a PDF, it splits locally with pdf-lib and sends ONLY that window. OPT-IN by design — all 14 existing call sites pass nothing and execute the same bytes as before; a windowing DEFAULT would silently feed truncated documents to passport/ITIN identity writeback and to the stored-text pipeline. Raster images (TIFF/GIF/JPEG/PNG/BMP/WEBP) NEVER go through the splitter — pdf-lib cannot load them — so fax receipts and ID photos keep their exact path. (2) The duplicated Document-AI response parser (previously verbatim TWICE, in `ocrDriveFile` and `ocrRawContent`) is now one pure `parseDocaiDocument` + one `processWithDocai`. Anchors are resolved INSIDE the response that produced them and never across a concatenation — slicing merged text with per-response anchors silently returns another page's content. (3) `OcrResult` gained `documentPageCount` (the TRUE length from the local split) and `windowStart` (absolute page of `pages[0]`). `pageCount` still means pages OCR'd; conflating the two makes a reader report '15 pages' for a 35-page return. SIZE: `DOCAI_INLINE_MAX_BYTES` (15MB, the per-REQUEST ceiling, unchanged default) is now distinct from `DOCAI_SPLIT_MAX_BYTES` (40MB, only for a windowed read) — the inline limit constrains what we SEND, not the file we split. The pre-download metadata check is KEPT (raised, not removed): an oversize file must be a returned error, never an OOM kill, which no catch block can observe. The phrase 'too large' in that error is load-bearing — `lib/itin/finalize-approval.ts` string-matches it. Encrypted PDFs are NOT loaded with `ignoreEncryption` (which yields blank pages that OCR to nothing and read as 'poor scan'); the load is allowed to throw so 'locked' stays distinguishable from 'blank'. STORE PATH: `extractTextFromFile` keeps its single whole-document call as the fast path and falls back to a bounded window loop (`MAX_STORE_WINDOWS` = 8 → 120 pages) ONLY on a page-limit error, sequentially (the client throws on the first non-2xx with no backoff, so parallel windows would turn a rate-limit into the very failure being fixed). New pure module `lib/docai-windows.ts` holds all the arithmetic + the coverage contract; `STORED_PAGE_DELIMITER` is now the single source of truth shared by the writer (`lib/mcp/tools/doc.ts`) and the readers. `MAX_OCR_TEXT` stays 50k — DECIDED, not inherited: raising it is blocked behind fixing the document lister, which SELECTs the whole column just to slice a 500-char preview. Safe meanwhile because the cut is no longer silent (see the coverage contract in `ai-agent.md`). ## What it is
A research/discussion channel that lets the **Hermes** Telegram bot (running on the Mac Mini, talking to Antonio on mobile) ask **Claude** (a server-side worker using `claude-sonnet-4-6`) questions and get answers back, without Antonio having to be the human relay between the two tools. Eliminates the "copy from Telegram into Claude Code, copy findings back to Telegram" workflow.

This is **Phase 1 — research/discussion only.** Action authorization (Antonio approving before Claude does anything that mutates state) is **Phase 2** (`approval_queue` + `approval_decide` + the `approval-executor` worker; `/portal/team/approvals` + Telegram push are later slices), being built in slices — **Slices 1–4 have shipped** (1: QUEUE + READ; 2: DECISION + EXECUTION, kill-switch-gated; 3: enum normalization + full-rail E2E; 4: proposal formatter + Hermes-side approval wiring — see the Phase 2 sections below). Re-tiering existing write tools (`gmail_send`, CRM mutations) onto that approval rail is **Phase 3**.

## Business rules
- **Hermes is restricted to research/discussion.** It can ask Claude things and read findings — it cannot ask Claude to send emails, modify records, push code, or run anything with side effects via this rail. (Phase 2 will move action requests to the approval rail.)
- **Mandatory approval rule on `agent_msg_send`** — same discipline as `gmail_send` (CLAUDE.md R092 / R108). Hermes (and Claude Code) must show the full draft (recipient, subject, body verbatim) in chat and wait for Antonio's explicit OK before calling the tool. Established after the 2026-06-03 unauthorized-send incident on `gmail_send`. Enforced in both `CLAUDE.md` and `~/.hermes/memories/USER.md`.
- **Worker is read-only.** The set of tools the worker can invoke is a curated subset of `lib/ai-agent/tools.ts` — no `send_*`, no `create_*`, no `update_*`, no `advance_*`, no `save_*`, no `run_sql_query`. Tests assert this. (See `lib/ai-agent/worker-tools.ts`.) **This invariant governs the Hermes/Telegram path.** `worker-tools.ts` is shared with the Slack worker, which has opt-in capabilities the Hermes path never receives — `start_code_task` + `promote_code_branch` (both gated by `enableCodeTasks`) and, as of 2026-06-13, `send_portal_message` (a direct portal-chat send, gated by `enableSlackSend`). Both are **deliberately kept out of the shared `WORKER_TOOLS` array** and injected only when the Slack flag is set, so the Hermes research worker stays send-free. See `slack-claude-worker.md` → "Portal-chat send rail".
- **Antonio is the only Telegram user the bot answers.** Enforced at the Hermes config layer (`TELEGRAM_ALLOWED_USERS=307359927`), not by this subsystem.

## How it's built
- **Tables / columns:**
  - `agent_messages` — `id`, `sender`, `recipient`, `subject`, `body`, `status`, `reply`, `replied_at`, `claimed_at`, `claimed_by`, `context_json`, `idempotency_key (UNIQUE)`, `error_text`, `created_at`, `updated_at`.
  - Enums: `agent_message_party` (`hermes`, `claude`, `worker`), `agent_message_status` (`pending`, `processing`, `done`, `failed`, `cancelled`).
  - RLS enabled with no policies → service-role-only (`supabaseAdmin`). No anon/authenticated/portal access. Ever.
  - Migration: `scripts/migrations/20260603-1510-agent-messages-bridge.sql`.
- **MCP tools:** `lib/mcp/tools/agent-messages.ts`
  - `agent_msg_send` — Hermes-allowlisted write tool. INSERT, then an **awaited** POST to the worker route, bounded by a 3s `AbortController` timeout (so the trigger reliably leaves the function but the tool still returns promptly). Idempotency: if `idempotency_key` matches an existing row, return that row WITHOUT firing the worker again.
  - `agent_inbox_list` — perspective-relative read. `filter` ∈ `inbound_pending | inbound_all | my_replies | my_sent | all`.
  - `agent_inbox_reply` — manual fallback writer; the cron worker is the primary writer.
  - Registered in `app/api/[transport]/route.ts` via `registerAgentMessageTools(server)`.
- **Worker:** `app/api/cron/hermes-bridge/route.ts`
  - Auth: `CRON_SECRET` Bearer (same key the cron scheduler uses and the MCP tool uses for the direct trigger).
  - Two modes, same handler, both `GET` and `POST` accepted:
    - **Direct mode** (`?message_id=<uuid>`): claim + process exactly that row. Called from `agent_msg_send` via fire-and-forget `fetch` for low latency.
    - **Scan mode** (no query param): cron behaviour. (1) Stale-claim recovery — any `processing` row with `claimed_at < now() - 10 min` is set back to `pending`. (2) Process up to 5 oldest pending Hermes→Claude rows from the last 24h.
  - Atomic claim: `UPDATE … SET status='processing', claimed_at, claimed_by WHERE id=$1 AND status='pending' RETURNING *`. If 0 rows, the row was already claimed (race lost) — exit quietly for that row.
  - Per-row processing: `callWorker(row.body)` → on success update `status='done', reply, replied_at`; on error update `status='failed', error_text`. Errors are NOT re-thrown — caller wants a summary, not a 500.
  - Logging: `lib/cron-log.ts::logCron` with `details: { mode, processed, results }`.
- **Worker call path:** `lib/ai-agent/worker-tools.ts`
  - `WORKER_READ_ONLY_TOOL_NAMES` — the allow-list set.
  - `WORKER_TOOLS` — `AGENT_TOOLS.filter(t => allowlist.has(t.name))`.
  - `executeWorkerTool(name, params)` — wraps `executeTool` with an allow-list check (defense-in-depth).
  - `WORKER_SYSTEM_PROMPT` — research-only framing, plain-English output discipline.
  - `callWorker(userBody)` — mirrors `callClaude` in `lib/ai-agent/providers.ts` but uses the worker subset + worker system prompt. Direct Anthropic API (`claude-sonnet-4-6`), **240s per-call timeout** (raised from 55s so the 16384 max_tokens cap is usable for long pure-text replies; cron route's `maxDuration=300` covers the whole loop with a 60s buffer). **Max tool loops** default to `AGENT_MAX_TOOL_LOOPS` env var, then 8 (was a hardcoded `8`); `callWorker`/`runWorkerLoop` accept an optional `maxIterations` per-request override, and the cron worker derives it from `agent_messages.context_json.max_iterations` (parsed + bounded to `[1,50]`). The max-iteration reply now reports the actual limit, not a hardcoded "(8)".
- **Cron schedule:** `vercel.json` `{ path: "/api/cron/hermes-bridge", schedule: "*/5 * * * *" }` — runs every 5 min as the safety net.
- **Direct-trigger URL resolution:** `lib/mcp/tools/agent-messages.ts::getInternalBaseUrl()` — `APP_BASE_URL` (explicit override / local) → `https://${VERCEL_PROJECT_PRODUCTION_URL}` (the project's STABLE public alias) → `http://localhost:3000`. **Never `VERCEL_URL`** (deployment-specific host behind Vercel Deployment Protection → 401s self-calls; see the "claimed_at stayed null" gotcha below). Shared by `fireExecutorTrigger` (approval-executor) too.

## Data flow / triggers
1. Antonio + Hermes discuss on Telegram. Antonio approves the draft.
2. Hermes calls `agent_msg_send({ recipient: 'claude', subject, body })`.
3. MCP tool INSERTs the row, then `await fireDirectTrigger(id)` issues `POST /api/cron/hermes-bridge?message_id=<id>` with `Authorization: Bearer ${CRON_SECRET}`, bounded by a 3s timeout. The await guarantees the request leaves the function; the timeout caps how long the tool blocks.
4. Worker route (direct mode) atomically claims, then runs `callWorker(body)` to completion server-side and writes `reply` + `status='done'`. For simple queries this is ~5-10s end to end; the route function keeps running even after the trigger's 3s client timeout.
5. (Parallel safety net) every 5 min the cron tick runs the route in scan mode. Stale `processing` rows older than 10 min get recovered. Up to 5 pending rows get processed.
6. Hermes, on Antonio's next Telegram turn, calls `agent_inbox_list({ as_party: 'hermes', filter: 'my_replies' })` — gets the row(s) with replies, summarizes to Antonio in plain English.

## Gotchas, invariants & past bugs
- **Direct trigger 401'd on `VERCEL_URL` → rows stayed `pending` with `claimed_at=null` (found 2026-06-04).** `getInternalBaseUrl()` used to fall back to `https://${VERCEL_URL}` when `APP_BASE_URL` was unset — and `APP_BASE_URL` is NEVER set (the codebase's domain var is `PUBLIC_APP_BASE_URL`, see `lib/config.ts`). `VERCEL_URL` is the deployment-specific host, which sits behind Vercel Deployment Protection and 401s unauthenticated server-to-server calls, so the worker route never ran the atomic claim; the 5-min cron then picked the row up late as `cron-worker`. Fix: resolve to `VERCEL_PROJECT_PRODUCTION_URL` (the project's stable, public production alias — same project ⇒ same DB + same `CRON_SECRET`). Same bug class as the PDF font self-fetch (`lib/pdf/unicode-fonts.ts`, commits b953aaa/386390a). The regression is pinned in `tests/unit/agent-bridge-fire-direct-trigger.test.ts` ("NEVER uses … VERCEL_URL"). The fix is shared by `fireExecutorTrigger`, so the approval-executor direct trigger was fixed in the same change.
- **A correct cron schedule does not guarantee a registered cron.** Both `hermes-bridge` and `approval-executor` are `*/5 * * * *` in `vercel.json` AND `lib/cron-coverage.ts`, yet a cron can "run once then stop" if a different deployment becomes the project's active production-target and registers a different cron subset (the sandbox-alias fragility). The remedy is a **redeploy** of the intended production target (a push to `main` re-registers all `vercel.json` crons) — NOT a config edit. Verify with `vercel cron list` and the `cron_log` table per endpoint, never by reading `vercel.json` alone.
- **The Phase 1 worker has NO write tools.** Any action implied by the request is described in the reply text, never executed. Adding a write tool to `WORKER_READ_ONLY_TOOL_NAMES` is a deliberate security decision — the unit test asserts the set contains no write-shaped names (`send_/create_/update_/advance_/save_/delete_/insert_/mark_`).
- **`run_sql_query` is INTENTIONALLY excluded** even though it's read-only in `lib/ai-agent/tools.ts`. Raw SQL bypasses the schema-level validation in `search_*` tools and adds risk for no upside. Don't re-add.
- **Direct trigger is awaited but timeout-bounded (3s).** The original fire-and-forget fetch was getting killed when the MCP serverless function froze right after returning, so rows only got processed by the 5-min cron (~1-5 min latency — observed live 2026-06-03). Fix: `agent_msg_send` now `await`s the trigger so it reliably leaves the function, but with a 3s `AbortController` timeout so the tool doesn't block on the full sonnet loop — the worker route runs to completion **server-side** regardless of the client timeout. Never throws (the AbortError is expected; cron is still the net). **Tried and rejected:** `@vercel/functions` `waitUntil` to background the worker — importing it broke the route on Next 14.2 ("No response is returned from route handler", both modes). Do not reintroduce it without verifying on a sandbox deploy first.
- **Atomic claim is the only race protection.** Both the direct trigger and the cron can fire on the same row near-simultaneously. The `UPDATE … WHERE status='pending' RETURNING *` pattern makes exactly one win. Don't replace with a non-atomic check-then-update.
- **Stale-claim recovery has a 10-min cutoff.** A row stuck in `processing` because the worker function crashed mid-job (after claim, before reply write) is reclaimed by the next scan-mode tick. 10 min is long enough to comfortably exceed the longest sonnet loop (~2 min) but short enough to keep latency bounded.
- **Idempotency_key check happens BEFORE INSERT.** A duplicate `idempotency_key` returns the existing row and does NOT fire the worker again. Without this guard, a Telegram retry would re-trigger sonnet for free.
- **The MCP tool description itself contains the approval rule.** Defense-in-depth: not just `USER.md` / `CLAUDE.md` text, but the tool's MCP description string tells the calling agent the rule. Don't strip those instruction lines.
- **Phase 1 is research only.** If you add an MCP tool that proposes a mutation on behalf of a Hermes message, you've broken the Phase 1 contract. Mutations belong on the Phase 2 approval rail (not yet built).

Then `fireExecutorTrigger(id)` — an **awaited, 3s-`AbortController`-bounded** `POST /api/cron/approval-executor?id=<uuid>` (`Authorization: Bearer ${CRON_SECRET}`). Mirrors `fireDirectTrigger` exactly (reuses the exported `getInternalBaseUrl`). **No `waitUntil`.**
  - **reject:** atomic `UPDATE … SET status='rejected', decided_by, decided_at WHERE id=X AND status='pending'`, then `writeOutcomeCallback(id, tool, 'Proposal <tool> rejected: <note>', 'rejected')`.
  - **MANDATORY discipline** carried in the tool description: Hermes/Claude must show Antonio the exact tool_name + params + recipient/cascade/external flags and wait for explicit OK before `approve` — same rule as `gmail_send` / `agent_msg_send`. Never auto-approve.
  - Registered via the same `registerAgentApprovalTools(server)`; described in `lib/mcp/instructions.ts`.
- **Executor route:** `app/api/cron/approval-executor/route.ts` — thin auth wrapper (`CRON_SECRET` Bearer, `maxDuration=300`); all logic in `lib/ai-agent/approval-executor.ts`.
  - **Kill switch:** `APPROVAL_RAIL_ENABLED` must `=== 'true'`, else the route returns `{ok:true, disabled:true}` and runs nothing. `propose_action` keeps queuing regardless — the switch only stops execution.
  - **Direct mode** (`?id=<uuid>`): claim + execute exactly that row.
  - **Scan mode** (no `?id`, cron `*/5 * * * *`): (1) recover rows stuck in `executing` > 10 min back to `approved`; (2) execute up to 10 `approved` rows a direct trigger missed; (3) expire `pending` rows past `expires_at` (+callback each).
- **Per-row execution** (`lib/ai-agent/approval-executor.ts`):
  1. **Atomic claim:** `UPDATE … SET status='executing', claimed_at, claimed_by='approval-executor' WHERE id=X AND status='approved' RETURNING …`. 0 rows → return early (already claimed/decided). **This is the only double-execution guard.**
  2. **params_hash re-check:** recompute `computeParamsHash(stored params)`; mismatch → `status='failed'`, `error_text='params_hash integrity mismatch'`, callback, **action never runs**.
     - **JSONB key-order gotcha (found via the Slice 2 sandbox E2E, 2026-06-04):** `params` is stored as JSONB, which does NOT preserve object key insertion order — it reorders keys internally. The hash MUST therefore be computed over a **canonical** (recursively key-sorted) JSON form on BOTH sides, or the execute-time recompute never matches the propose-time hash for any params with ≥2 keys, silently failing every real action with `integrity`. `computeParamsHash` canonicalizes; a regression test pins key-order independence (`tests/unit/approval-rail.test.ts`). Unit mocks preserved key order, so only the real-Postgres E2E exposed this — keep an E2E in the loop for any future hash change.
  3. **Execute:** `await executeTool(tool_name, params)`.
  4. **Outcome:** success → `status='executed', result=<jsonb>, executed_at`; throw OR error-shaped result → `status='failed', error_text, executed_at`. **`executeTool` catches its own errors and returns an `{error:…}` string rather than throwing — `interpretToolResult` inspects the result so a logically-failed action is marked `failed`, not `executed`.** (Deviation from the literal "on throw → failed" plan, made deliberately so a failed send is never reported as executed.)
  5. **Callback:** `writeOutcomeCallback` always fires on a terminal state.
- **Outcome callback helper:** `lib/ai-agent/approval-callback.ts::writeOutcomeCallback(approvalId, toolName, summary, status)` — INSERTs an `agent_messages` row `sender='worker', recipient='hermes', status='done', reply=<summary>, context_json={approval_id, tool_name, outcome_status}`. (`agent_messages.subject`/`body` are NOT NULL, so it supplies both; `sender<>recipient` CHECK is satisfied by worker→hermes.) Used by the executor (executed/failed), `approval_decide` (rejected), and the expiry sweep (expired). Kept dependency-light (imports only `supabaseAdmin`) so the MCP tool doesn't pull the `executeTool` graph.
- **Cron registration:** `vercel.json` + `lib/cron-coverage.ts` both carry `/api/cron/approval-executor` at `*/5 * * * *` (the completeness test pins them in sync).
- **Slice 2 invariants:**
  - Idempotent by atomic claim: a row is executed at most once even if direct trigger + cron race.
  - Nothing executes unless `APPROVAL_RAIL_ENABLED='true'` AND a human approved the row.
  - `executed` rows are never re-run (claim only matches `approved`).
  - Tests: `tests/unit/approval-executor.test.ts` (happy path, error-shaped result, throw, atomic single-winner claim, integrity mismatch, reject, approve, expiry, crash recovery, kill switch).

## Phase B — safety + notifications (retry sweep + CRM mirror + propose heads-up)
_Shipped 2026-06-04 (sandbox). No new migration — builds on the Phase A `approval_queue.notification_sent` column. Hardens the Slice 2 one-shot callback into a reliable, CRM-visible notification layer._

- **Why:** Slice 2 wrote a single `agent_messages` callback to Hermes at each terminal transition. If that one write failed, Hermes was never told; and proposals/outcomes were invisible in the CRM until Hermes surfaced them on Telegram. Phase B adds (1) a durable retry keyed on `notification_sent`, (2) a CRM "Team" tab mirror, (3) a propose-time heads-up.
- **New module — `lib/ai-agent/approval-notifications.ts`** (the single notification path; imports only `supabaseAdmin` + `approval-callback` + the pure formatter — **no `executeTool` graph**, so MCP-side callers stay light):
  - `sendApprovalNotification(row, kind, detail?)` — mirrors a proposal/outcome into the CRM team chat. **The executor is plain lib code and cannot call the `portal_team_send` MCP tool**, so this writes `internal_threads` + `internal_messages` directly (same shape that tool uses). **Best-effort: NEVER throws** (any failure, including an unavailable table in a test harness, is swallowed and returns `false`) — a CRM/push failure must never block execution or the Hermes callback.
  - `emitApprovalOutcome({id, tool_name, status, summary, row?, detail?})` — the ONE terminal-notification path used by every terminal transition. (a) writes the durable Hermes callback (`writeOutcomeCallback` → `agent_messages`); (b) **only if that succeeded**, flips `approval_queue.notification_sent=TRUE`; (c) mirrors to the CRM chat (best-effort). `notification_sent` tracks the **Hermes channel specifically** — the CRM mirror never gates it. Returns true iff Hermes was notified AND the flag flipped (→ the sweep won't re-touch it).
  - `runNotificationSweep()` — the retry safety net. Selects `approval_queue` rows where `notification_sent=FALSE`, filters to terminal statuses **in JS** (avoids a `.in()` filter the query builder/test mock may lack), and re-emits each via `emitApprovalOutcome`. A row that fails to notify stays `FALSE` and is retried next tick. Batch cap 50.
- **System channel (no sentinel account needed):** outcomes/proposals have no single client context, so they post to a dedicated null-account/null-contact team thread titled **`🤖 Approval Rail (system)`**. This mirrors the existing `__team_general__` pattern (`app/api/team-chat/route.ts`) — a titled client-less thread renders cleanly in the Team tab (the list route falls back to `… ?? thread.title ?? 'Team Thread'`, verified in `app/api/internal/threads/route.ts`). `internal_threads.created_by` / `internal_messages.sender_id` are **NOT NULL but have NO FK** (verified against the sandbox schema), so the all-zeros `SYSTEM_SENDER_ID` (the same convention as `lib/portal/chat-events.ts`) is valid for both. Find-or-create is matched on the unique title (eq only) for query-builder portability, with a re-read fallback on a concurrent-insert race.
- **Formatter** (`lib/ai-agent/format-approval-proposal.ts`): two new pure functions reuse the SAME `toolBlock` (label + surfaced params from `APPROVABLE_TOOL_CONSTRAINTS`) + risk-flag rendering as the proposal card, so all three views can't drift:
  - `formatApprovalOutcome(row, status, detail?)` — outcome header (`✅ executed` / `❌ failed` / `🛑 rejected` / `⌛ expired`), tool block, risk flags, optional `📄 <detail>` line, **no APPROVE/REJECT footer** (it already happened).
  - `formatProposeNotification(row)` — `🆕 New action proposed — awaiting approval` banner above the full proposal card.
- **Wiring:**
  - `lib/ai-agent/approval-executor.ts` — all five terminal sites (integrity-fail, execute-throw, tool-error, success, expiry) now call `emitApprovalOutcome` instead of bare `writeOutcomeCallback`; `runExecutorScan` appends `runNotificationSweep()` (returned as `notified` in the scan result). The expiry select now pulls `params, rationale` for richer mirror formatting.
  - `lib/mcp/tools/agent-approvals.ts` — the `approval_decide` **reject** path now calls `emitApprovalOutcome` too (so rejects also flip `notification_sent` and mirror to CRM, and aren't duplicated by the sweep).
  - `lib/ai-agent/worker-tools.ts::proposeAction` — fires `sendApprovalNotification(row, 'proposed')` (best-effort) on a fresh insert only (NOT on an idempotent-dup return).
- **Invariants / gotchas:**
  - **No duplicate callbacks:** every terminal transition flips `notification_sent=TRUE`, and the sweep only touches `FALSE` rows. Residual window: a crash *between* the `agent_messages` write and the flag flip yields one duplicate next sweep — accepted on purpose ("always notify" beats "never duplicate").
  - **`notification_sent` semantics = the Hermes channel.** The CRM mirror and push are bonuses; their failure does NOT leave the flag false. Don't gate the flag on the mirror or you'll loop the sweep forever when push/CRM is down.
  - **Best-effort must never break the core.** `sendApprovalNotification` swallows everything (the propose-side test mock throws on any non-`approval_queue` table, and `proposeAction` still returns success — that's the contract).
  - **Push** goes to all admins via `sendPushToAdmin` (dynamic import, swallowed). System sender isn't a real admin, so "exclude self" is intentionally not used.
- **Tests:** `tests/unit/approval-notifications.test.ts` (sendApprovalNotification create/reuse/never-throws, emitApprovalOutcome callback+flag+mirror + callback-fail-leaves-flag-false, sweep terminal/already-notified/non-terminal/mixed, proposeAction propose-notification fires/skips-on-reject), extended `format-approval-proposal.test.ts` (outcome headers, flags, propose banner) and `approval-executor.test.ts` (expiry flips `notification_sent`). **Real-DB sandbox E2E:** `scripts/test-approval-notifications-phaseb.ts` (`npx tsx …`) → 10/10, self-cleaning — the only thing that proves the `internal_threads`/`internal_messages` inserts land with the right NOT-NULL columns (mocks can't).

## Phase C — intelligence (thread summaries + type routing + context watermark)
_Shipped 2026-06-04 (sandbox). No new migration — pure code on Phase A's `thread_summaries` table + `agent_messages.thread_id`. Turns the bridge from a stateless one-shot research call into a **threaded, type-aware, memory-backed** agent. Dormant by default: today every `agent_messages` row has `thread_id = NULL`, so the whole layer only activates once a message carries a `thread_id`._

- **Why:** Phase 1/2 answered each message in isolation. Phase C gives a conversation (a) durable, searchable **memory** (so Hermes can say "remember the tax-return mismatch thread?"), (b) a **type** that narrows the worker's tool surface (a client_audit can't reach codebase tools; an internal_ops thread can't reach client data) and shapes its output, and (c) **prior-turn context** so a follow-up isn't answered cold.
- **Thread summaries — `lib/ai-agent/thread-summaries.ts`** (the durable memory; writes `thread_summaries`):
  - `createThreadSummary(threadId, type, title?)` — INSERT; **idempotent on the PK** (a duplicate `thread_id` returns the existing row via the 23505 path, never throws). `thread_type` is NOT NULL, so an unknown/absent type is coerced to the default (`investigation`) via `normalizeThreadType`.
  - `resolveThread(threadId, outcome, summaryText)` — UPDATE-only: stamps `resolved_at = now()`, `outcome`, `summary_text`. **There is NO `updated_at` column on `thread_summaries` — do not add a write for it** (a stray write 42703s; the real-DB E2E pins this). Returns null if the row doesn't exist (callWorker always creates first).
  - `getThreadSummary(threadId)` — single read.
  - `searchThreads(query, {type?, tags?, limit?, scanLimit?})` — pushes the cheap structured filters (`.eq('thread_type')`, `.contains('tags', …)`) to Postgres, pulls a bounded candidate pool newest-first (`scanLimit`, default 500), then applies the **free-text match in JS** (`filterThreadSummaries` / `threadMatchesQuery` — pure, matches title/type/tags/affected-account-ids/outcome/summary). Returns `{ rows, scanned, truncated }`; `truncated` is surfaced (no silent cap). Doing free text in JS avoids PostgREST array/or-filter fragility and keeps the matcher unit-testable. The table is one row per resolved thread, so fetch-then-filter is cheap for the foreseeable future.
- **Thread-type tool routing — `lib/ai-agent/thread-routing.ts`** (pure, name-based):
  - `THREAD_TYPES` = `investigation | action_request | bug_report | client_audit | internal_ops`. `normalizeThreadType` coerces anything else to the default `investigation`.
  - `getToolsForThreadType(type)` → the filtered `WORKER_TOOLS` subset the worker is handed instead of the full list. `toolNamesForThreadType(type)` is the pure name-set behind it. Mapping:
    - `investigation` / `action_request` → full set (incl. codebase + `propose_action`); action_request's prompt REQUIRES ≥1 proposal.
    - `bug_report` → codebase tools + CRM read tools (no propose, no gmail/drive); output framed as Summary / Repro steps / Root cause (file:line) / Suggested fix.
    - `client_audit` → **CRM read tools ONLY** (no code, no propose); client-facing output.
    - `internal_ops` → codebase + KB/SOP only — **no client data** (no CRM/gmail/drive).
    - unknown → full set (safe default).
  - `getPromptAddendumForThreadType(type)` → per-type formatting guidance appended to `WORKER_SYSTEM_PROMPT`.
  - **Safe import cycle:** thread-routing imports `WORKER_TOOLS` from worker-tools, which imports thread-routing's functions inside `callWorker`. Every cross-reference is deferred to call time (never evaluated at module top-level), so init order can't bite — do NOT precompute `WORKER_TOOLS.filter(...)` at module scope.
- **Thread context watermark — `lib/ai-agent/thread-context.ts`**:
  - `buildThreadContext(threadId, {watermark?, excludeMessageId?})` — fetches every `agent_messages` row for the thread (oldest→newest), then `formatThreadContext` (pure) keeps the most-recent `HISTORY_WATERMARK` (=20) rows in full and folds any older ones into a compact **extractive** preamble (no second LLM call). `excludeMessageId` drops the turn currently being answered so it isn't shown twice.
  - **Role labels:** the FIRST Hermes message in the thread → `Antonio directed` (Hermes relays Antonio's approved words per R108); later Hermes messages → `Hermes said`; worker/claude turns and every `reply` → `Claude said`.

  - `callWorker(userBody, { threadId?, messageId?, systemPromptOverride? })`. **No `threadId` → identical to before** (full `WORKER_TOOLS` + default prompt, no thread bookkeeping). The raw sonnet loop is extracted into `runWorkerLoop(body, tools, systemPrompt)` so the tool list + prompt can be swapped per thread.

When set, it replaces `WORKER_SYSTEM_PROMPT` as the starting system prompt while the thread addendum + prior-turn context (if a `threadId` is present) are still appended on top. Added for the **Slack worker** (`lib/ai-agent/slack-claude.ts`), a second `callWorker` consumer that needs a conversational discuss-first prompt instead of the research framing. See `slack-claude-worker.md`.
  - With a `threadId`: resolve the type (read `thread_summaries`; create it if new) → narrow tools via `getToolsForThreadType` → prepend the thread context + type addendum to the system prompt → after the reply, `resolveThread` with a derived `outcome` (`action_proposed` if `propose_action` was used, else `investigation_complete`, or `incomplete` if the loop hit max iterations) and a one-paragraph extractive `summary_text` (`oneParagraphSummary`).
  - **Every thread step is best-effort** — wrapped in try/catch that falls back to the full tool set + default prompt; a thread-layer bug never breaks the core research reply.
  - The cron route (`app/api/cron/hermes-bridge/route.ts`) now SELECTs `thread_id` (and, since 2026-06-05, `context_json`) and passes `{ threadId: row.thread_id, messageId: row.id, maxIterations: readMaxIterations(row.context_json) }` into `callWorker`.

## Phase D — foundations (prompt provenance + env lanes + batch grouping)
_Shipped 2026-06-04 (sandbox). No new migration — pure code on the columns Phase A already added (`thread_summaries.prompt_version`, `approval_queue.env`, `approval_queue.batch_id`). Three independent foundations; none changes default behaviour._

- **Why:** (1) when a thread later misbehaves we need to know **what instructions the worker had**; (2) a future **staging lane** must be able to run its own proposals without touching production; (3) related actions proposed together should be **queryable as a group** ahead of a real batch-approval UX.
- **1. prompt_version hashing — `lib/ai-agent/worker-tools.ts`:**
  - `WORKER_PROMPT_VERSION` = **SHA-256 hex of the base `WORKER_SYSTEM_PROMPT`**, computed once at module load. The per-thread-type addendum is deliberately NOT folded in — `thread_type` is stored alongside and `getPromptAddendumForThreadType(type)` is deterministic, so base-hash + type reconstruct the full instruction set.
  - `createThreadSummary(threadId, type, title?, promptVersion?)` gained the 4th arg and writes it to `thread_summaries.prompt_version` (NULL when omitted). `callWorker` passes `WORKER_PROMPT_VERSION` at both create sites.
- **2. env lane — `lib/ai-agent/approval-env.ts` + `approval-executor.ts` + `worker-tools.ts`:**
  - `currentApprovalEnv()` = `APPROVAL_ENV ?? NODE_ENV ?? 'production'` (never empty). **The single source of truth for "which lane am I?"** Both the proposer and the executor call it, in the SAME process env, so they always agree.
  - `proposeAction` stamps `env: currentApprovalEnv()` on every queued row.
  - The executor filters by env at **all four query sites** — the atomic claim (`claimApproval`), the scan-execute select (`runExecutorScan`), crash recovery (`recoverStuckExecuting`), and expiry (`expireStalePending`) — each adds `.eq('env', currentApprovalEnv())`. So an executor strictly manages only its own lane's rows.
  - **INERT by default:** on Vercel (prod AND the sandbox project) `NODE_ENV='production'`, `APPROVAL_ENV` is unset → every row and every executor resolve `'production'`, which equals the column default and every pre-existing row. Nothing changes until someone sets `APPROVAL_ENV='staging'` on a deployment to carve a lane. **Foundation only — the filter is in place but does not separate anything yet.**
- **3. batch grouping — `worker-tools.ts` + `agent-approvals.ts`:**
  - `proposeAction` accepts an optional `batch_id` (persisted; NULL = solo).
  - `batchPropose(proposals, { batch_id? })` mints one `batch_id` (`crypto.randomUUID()`, or reuses a supplied one) and routes every proposal through `proposeAction` — so per-row validation / enum-normalization / hashing / idempotency / the propose notification all still apply. Returns `{ batch_id, count, results }`. **UX prep only: there is NO batch approve/reject — each proposal is still decided individually.** `batchPropose` is a server-side helper, NOT exposed to sonnet.
  - `approval_list` gained an optional `batch_id` filter (`.eq('batch_id', …)`) so a group is queryable.
- **Invariants / gotchas:**
  - **No migration, no new column** — Phase D is pure code on Phase A columns. Verified live.
  - **Lane agreement is the safety property.** The env filter is only safe because proposer + executor read the same `currentApprovalEnv()`. Don't compute env two different ways. Don't default it to anything but `'production'` (the column default) or you'd orphan every existing row.
  - **prompt_version hashes the BASE prompt only** — re-fold the addendum and you'd get a different hash per thread type for identical base instructions, defeating the "reconstruct" goal.
  - **batch has no transactional semantics** — `batchPropose` is a sequential loop; a mid-batch validation failure still leaves the earlier rows queued (each result string reports its own status). That's intended (independent proposals), not a bug.
- **Tests:** `tests/unit/approval-env.test.ts` (precedence), extended `approval-rail.test.ts` (env stamp, `batchPropose` shared-id + per-row validation, `approval_list` batch filter), extended `approval-executor.test.ts` (cross-lane skip + same-lane claim), extended `thread-summaries.test.ts` (prompt_version). **Real-DB sandbox E2E:** `npx tsx scripts/test-phase-d-sandbox.ts` → 11/11, self-cleaning (also deletes the CRM-mirror messages it triggers) — the only thing that proves the real `prompt_version`/`env`/`batch_id` column writes + the Postgres `.eq('env')` claim filter (mocks can't).

## WP1 — confirmation-code gate + Operating-Agent pull rail
_Shipped 2026-06-04 (sandbox). One migration (`approval_queue.confirmation_code`). Adds a typed-code safety gate on approval, plus three MCP tools that let an external Operating Agent (Hermes) PULL approved actions, execute them itself, and report back — the first step toward Hermes (not the server executor) being the thing that runs approved actions._

- **Why:** (1) a one-word "approve" is too easy to fire on the wrong proposal — a 6-digit code typed against a specific card binds the approval to exactly that action (mechanical version of the gmail_send / agent_msg_send discipline). (2) The server-side `approval-executor` runs actions with TD's own tool stack; WP1 lays the rail for the **Hermes Operating Agent** to be the executor instead, claiming and running approved actions on its own side and reporting the outcome back through the same row.
- **Migration:** `scripts/migrations/20260604-2330-approval-confirmation-code.sql` — `approval_queue += confirmation_code TEXT` (nullable, additive, idempotent). Nullable on purpose: **pre-WP1 rows have no code and therefore cannot be approved (fail-closed)** — they should expire, not be approved. No backfill.
- **Confirmation code:**
  - `generateConfirmationCode()` (`lib/ai-agent/worker-tools.ts`) — `Math.floor(100000 + Math.random()*900000).toString()`, always exactly 6 digits. `proposeAction` mints one on every fresh INSERT (NOT on an idempotent-dup return) and stores it in `confirmation_code`.
  - `formatApprovalProposal` (`lib/ai-agent/format-approval-proposal.ts`) — renders a `🔑 Code: <code>` line and the approve instruction becomes `APPROVE <short-id> <code>` (falls back to `<code>` placeholder when a row carries none). The `ApprovalProposalRow` type gained `confirmation_code`.
  - `approval_decide(approve)` (`lib/mcp/tools/agent-approvals.ts`) now takes `confirmation_code` and **requires** it: it reads the row's stored code, and a missing or non-matching code returns an error with the row **left pending — the action never runs**. The code is immutable so reading it before the atomic `pending→approved` flip is race-safe; status atomicity is still the `.eq('status','pending')` guard. `reject` needs no code. `approval_list` now selects + returns `confirmation_code`.
- **Operating-Agent pull rail (all in `lib/mcp/tools/agent-approvals.ts`, registered via the existing `registerAgentApprovalTools` — no route.ts change):**
  - `hermes_heartbeat(instance_id)` — upserts `hermes_instances` (`onConflict: instance_id`) stamping `last_heartbeat=now()`, `status='online'`. Returns `{ok, instance_id, last_heartbeat}`. Pairs with the Phase A `/api/cron/hermes-health` monitor that flips stale instances offline.
  - `approval_claim(instance_id)` — atomically claims the **oldest approved + unclaimed** row **in this env lane** (`currentApprovalEnv()`), flipping `approved→executing` with `claimed_by=instance_id`. Because **PostgREST can't `ORDER BY … LIMIT` an UPDATE**, it SELECTs the oldest candidates then does a **guarded UPDATE per candidate** (`WHERE id=? AND status='approved' AND claimed_by IS NULL`); the guard makes it a single-winner even under a race, and a lost race (0 rows) falls through to the next candidate. After claiming it **re-checks `computeParamsHash`** — a mismatch sets the row `failed` (`error_text='integrity'`), emits the outcome, and the row is **never handed back**. Returns the row to execute (`id, tool_name, params, rationale, thread_id, confirmation_code`) or a "nothing to claim" message.
  - `approval_complete(id, status, result?, error_text?)` — finalizes a row the instance previously claimed: only a row **still in `executing`** is updated (idempotent / race-safe), stamping `status`, `result`/`error_text`, `executed_at`, `executed_by` (= the row's `claimed_by`), and `notification_sent=false`; then `emitApprovalOutcome` writes the Hermes callback, flips `notification_sent` back true, and mirrors to the CRM team chat. Calling on a non-executing row is a no-op.
- **Coexistence with the server executor (IMPORTANT — read before cutover):** WP1 does NOT remove the server rail. `approval_decide(approve)` still fires `fireExecutorTrigger` → `/api/cron/approval-executor`, and that executor (when `APPROVAL_RAIL_ENABLED='true'`) also claims `approved` rows. So the server executor and `approval_claim` **compete for the same rows**. The atomic claim guarantees **no double-execution** (exactly one wins), but *which* one wins is a race, and they run via different tool stacks. **To cut over to the pull model, turn `APPROVAL_RAIL_ENABLED` off** so the server executor no-ops and Hermes is the sole runner — that toggle is a deliberate ops step, not WP1 code. As of this writing sandbox has `APPROVAL_RAIL_ENABLED=true`, so the server executor still wins most races; the pull tools are wired and tested but not yet the live executor.
- **Hermes-side wiring (Mac Mini, NOT in this repo):** `~/.hermes/config.yaml` `td_sandbox_readonly.tools.include` adds `hermes_heartbeat, approval_claim, approval_complete`; `~/.hermes/memories/USER.md` gains the confirmation-code discipline (approve = `approval_decide(id,'approve',confirmation_code)`, read the code from Antonio's `APPROVE <id> <code>`, never invent it) and an "Operating Agent — execution pull rail" section. Hermes must reload its MCP config for the new include entries to take effect.
- **Invariants / gotchas:**
  - **Confirmation code is fail-closed.** A NULL stored code (pre-WP1 rows) can never be approved. A blank/absent provided code is rejected before any DB write.
  - **The guarded-update claim is the only double-claim guard** — do not "simplify" it to a check-then-update or rely on `.order().limit()` on an UPDATE (PostgREST ignores them and would update ALL matching rows).
  - **`executed_by = claimed_by` is read-then-write** (PostgREST can't reference another column in an UPDATE): `approval_complete` reads `claimed_by` first, then writes its value.
  - **Server executor still fires on approve.** Until `APPROVAL_RAIL_ENABLED` is flipped off, do not assume `approval_claim` is the executor — verify which one ran via `claimed_by`/`executed_by` on the row.
- **Tests:** `tests/unit/wp1-approval-wiring.test.ts` (15 cases — code on approve correct/wrong/missing, reject without code, heartbeat create+update, claim row/null/integrity-fail, complete executed/non-executing, proposeAction 6-digit, formatter code line + APPROVE `<id> <code>`), plus the updated `approval-executor.test.ts` approve test (now passes the matching code + a wrong-code rejection case). **Real-DB sandbox E2E: not yet written** — recommended follow-up (drive a row through propose → approve-with-code → claim → complete against the live sandbox, mirroring `scripts/test-phase-d-sandbox.ts`), since mocks can't catch a NOT-NULL/wrong-column write the way prior phases' E2E scripts did.
