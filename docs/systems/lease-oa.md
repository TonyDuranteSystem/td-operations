## What it is
Two client documents TD generates, sends, and tracks to signature:
1. **Lease** — the registered business-address / virtual-office lease TD provides to the client (annual, per `contract_year`).
2. **Operating Agreement (OA)** — the LLC's operating agreement (SMLLC or MMLLC), generated from CRM account data.

Both follow the same pattern: create a record → send a tokenized link via Gmail (with open tracking, through `safeSend`) → client views/signs → a signed webhook records it.

## Lease
- Tools (`lib/mcp/tools/lease.ts`): `lease_create`, `lease_get`, `lease_list`, `lease_update`, `lease_send`, `lease_agreements`.
- **Status lifecycle:** `draft → sent → viewed → signed → active → expired`.
- `lease_send` **approves + sends immediately** (not a draft) via Gmail with open tracking, sets status `sent`, requires `tenant_email`. Use `gmail_track_status` to confirm the client opened it. Uses `safeSend` (R037).
- Link: `${APP_BASE_URL}/lease/{token}/{access_code}`. Signed webhook: `app/api/lease-signed/route.ts`. PDF (re)generation: `app/api/lease-regen-drive`, `app/api/crm/admin-actions/regen-lease-pdf`.
- `leases` columns: `token`, `access_code`, `tenant_company`, `suite_number`, `status`, `contract_year`, `term_start_date`/`term_end_date`, `monthly_rent`/`yearly_rent`, `view_count`, `signed_at`, `tenant_email`.
- **Tenant/signer resolution (2026-08-18):** `createLease` (`lib/operations/lease.ts`) resolves who gets named on the lease via `lib/members/resolve-signer.ts::resolveAccountSigner` whenever the caller doesn't pass an explicit `contact_id` — the SAME rule SS-4 uses (`members.is_signer` flag, company member via representative, SMLLC/no-members falls back to the role-aware `account_contacts` default). An explicit `contact_id` always wins. Every caller of `createLease` that wants the correct signer should simply OMIT `contact_id` rather than pre-resolving its own contact.

## Operating Agreement (OA)
- Tools (`lib/mcp/tools/oa.ts`): `oa_create` (from CRM account data; SMLLC or MMLLC), `oa_get`, `oa_send` (Gmail + tracking, `safeSend`), `oa_agreements`, `oa_id`, `oa_signatures`.
- **Only supported states** — `OA_SUPPORTED_STATES` (`lib/types/oa-templates.ts`) gates which states have an OA template.
- Tokenized link + access code. Signed webhook: `app/api/oa-signed/route.ts`.
- **Three creation paths** (all insert `oa_agreements`):
  1. MCP `oa_create` (staff, free-form members params for MMLLC).
  2. CRM button (`app/api/crm/admin-actions/generate-document/route.ts::generateOA`) — MMLLC members come from the **`members` table** (real `ownership_pct`, company members included; individual address falls back to `contacts.residency`). Errors if an MMLLC has no members rows or ownership ≠ 100%. Never fabricates an even split (Datavora incident, 2026-05-25).
  3. Portal self-service (`app/api/portal/operating-agreement/create/route.ts`) — client "Create & Send for Signing" in `/portal/documents/generate`. MMLLC: reads `members` table, ownership must total 100%, creates one `oa_signatures` row **per SIGNER** (not per member — see the signing-set rule below) and portal-chats each a per-signer link.

### ⚠️ Membership ≠ signing — the signing set (2026-08-09, Antonio; amended later the same day)
`lib/members/signing-set.ts::resolveSigningSet` is the ONE place that decides who signs, and `describeSigningBlock()` is the ONE place that decides whether the agreement may be issued at all. Both writers of `oa_signatures` — the portal create route and the welcome-package job (`lib/jobs/handlers/welcome-package-setup.ts`) — call both, so they cannot drift.

- **Membership is a legal fact; portal access is not.** Every member stays in the OA roster with their ownership, whether or not they can ever log in.
- **Individual with an email → signer.** **Individual with NO email → member, counted in ownership, named in the agreement, NOT in the signing set, no portal.**
- **Company member → member AND signer, signing through its representative.** Keyed on `members.contact_id` FIRST, `representative_name`/`representative_email` only as fallback. Live reason: Advertising Apex LLC (99% of Azarexa) has blank representative text but its `contact_id` points at Umberto Moretti — the system does know who signs. A company with NEITHER a contact NOR a representative email is a member but not a signer.
- **🔒 AN AGREEMENT IS NEVER ISSUED WITH FEWER SIGNERS THAN MEMBERS (2026-08-09, Antonio — amends the same day's earlier rule).** Verbatim: *"A multi-member operating agreement signed by only one owner must never exist. The client generates it, not us, but it is a legal document and it must contain all members."* So a non-signer is a **HARD STOP**, not something to route around: `describeSigningBlock()` names the blocking member, the portal route 422s with a client-safe message on the Generate Documents screen, and the welcome-package job records an `error` step **and** calls `reportSystemError` (no screen there, so the reason has to reach a human by itself). It **can** leave a client stuck until someone supplies the missing email — Antonio: that is the correct failure for a legal document, provided the reason is visible and reaches a human. Membership itself is unchanged: the blocked member still belongs in the roster and in the ownership.
- **`total_signers` counts the SIGNING SET — which now always EQUALS the roster for an MMLLC**, because the gate above refuses to issue otherwise. (History: counting the roster while filtering the signers left `signed_count` permanently short whenever someone could not be sent a request, and the agreement sat "in progress" forever. Counting only the signers fixed that but created the blocker below.)
- **🔒 Per-member signing is decided by the EXISTENCE of `oa_signatures` rows, NEVER by `total_signers > 1`.** *Regression caught 2026-08-09, live on production, never fired.* Under the brief "refuse only when nobody can sign" rule a two-member LLC could reach exactly ONE expected signature, and every per-member gate keys off "more than one signer" — they all switched off together: `app/portal/sign/oa/page.tsx` emitted no `?signer=` code, `app/operating-agreement/[token]/[code]/page.tsx` rendered the signature pad for **anyone** holding the shared access code (skipping "each member must use their personal signing link"), and `app/api/operating-agreement/[token]/sign/route.ts` ignored the submitted signer code entirely and recorded `signed_by_name` from `oa_agreements.member_name` — the FIRST roster row — instead of the signature row. Live exposure: **Full Throttle Media LLC** (two owners, Jayesh Hans has no email on the member row *or* his contact; both member rows created in the same millisecond, so which name got printed was a tie-break). It had no agreement, so nothing was executed wrongly. Nebroo LLC matched the shape but is Closed. All four sites now key on row existence; the sign route also prefers the signature row's own name over the agreement header. **Safe against existing data** (checked on production): SMLLC agreements have no signature rows, and the only three one-signature agreements carrying rows are single-member and already signed.
- **One person can hold TWO capacities and it is NOT a duplicate.** Umberto Moretti is Azarexa's 1% individual member AND the contact behind its 99% corporate member, so he signs twice. `resolveSigningSet` maps rows 1:1 and never dedupes by contact. `app/portal/sign/oa/page.tsx` previously fetched his signature row with `.maybeSingle()`, which ERRORS on two rows — he was handed no signing link at all, silently, while legally required to sign. It now orders his rows by `member_index` and hands him the first UNSIGNED one.
- **Signature line copy:** `signerDisplayName()` renders "Rep Name (for Company LLC)" — and suppresses the suffix when the two are equal, so a company with no representative name does not print "Apex LLC (for Apex LLC)" on the executed agreement.

### 🔒 A member's address in ANY document is the MEMBER's own — and the screen shows exactly what gets stored (2026-08-12, Antonio)

This rule turned out to be written **nowhere** — not in the KB, not in the SOPs, not here — while four code paths silently depended on it. It is the rule Michele Cotti (AI Venture Labs LLC) had to report as a bug. Dev job `61f184ca`.

- **🔒 A COMPANY member's address is THE ENTITY'S OWN (`members.address_*`). NEVER the representative's (`members.representative_address_*`), never the linked contact's.** The representative is a person authorised to sign for the entity; the member of record is the entity. Article 2.1 prints "The Members of the Company, **their addresses**, and their respective ownership interests" and there is no notice block or signature-block address in either template that wants a person's home address. **Live incident:** `getPortalMembers` resolved `representative_address_* ?? address_*`, so Whalecot Consulting LLC — a Florida company — was shown to its own owner carrying his personal Portuguese home address. Blast radius when found: 9 company-member rows across **7** accounts, 7 of them genuinely wrong across 5 accounts (AI Venture Labs, Dynamiq SR, Economicamente, Estro, Oh My Creatives ×3); Prowave and Azarexa were harmless (addresses identical / same suite differently formatted). **Nothing was stored or signed wrongly** — every stored `oa_agreements.members` blob composes from `address_*` — so it was display + prefill only. The one legitimately rep-first site is `app/api/member-info/[token]/[access_code]/route.ts` (~line 306), which refreshes the REPRESENTATIVE'S OWN `contacts` row: **do not "fix" that one** — a blanket inversion writes company addresses into real people's contact records.
- **🔒 The address of record is resolved in ONE place: `lib/members/member-address.ts`.** `getPortalMembers` (the screen) and the portal OA create route (the document) both call it, so what a client reviews and what they sign cannot drift. They previously composed the address independently and disagreed on two axes at once — source, and whether the postal code was included at all.
- **The POSTAL CODE is part of the address.** `getPortalMembers`' select omitted `address_zip` / `representative_address_zip`, so every address on screen lost its ZIP while the stored agreement kept one. Anything selecting member address columns selects the zip too.
- **No substitution for a missing address.** A member with nothing on file resolves to null and the template prints "As on file with the Company"; the screen says "Not on file — contact support". Never the representative's address, never a placeholder that reads as an address.
- **🔒 THE RECORD WINS AND NOTHING ON THAT SCREEN IS EDITABLE (Antonio, verbatim):** *"A legal document must never be able to disagree with the system of record."* The Generate Documents screen renders every member address READ-ONLY, for every company shape. The old `member_addresses: string[]` body field is **DELETED — do not reintroduce it**: it was pre-filled, looked editable, and was then discarded by the server for every account that had member records (i.e. all of them), and it was position-matched against a *separate* members query ordered only by `is_primary`, so tied rows could pair a typed address with a different member in a legal document. Both defects are gone by construction. The route REFUSES any posted address, for every company shape, so the guarantee does not depend on what the browser chose to render — the only realistic sender is a stale tab still running the previous build, so the message says the page is out of date rather than blaming the client's data.
- **A Single Member LLC has ONE OWNER and no member roster — by design, not a gap** (216 of the active accounts). Its address is read from the owner's contact record and shown read-only like every other address here; the route reads the same record for the stored agreement. There is NO editing, NO write-back to the contact, and NO address splitter anywhere in this flow. An earlier attempt at an editable field for these accounts corrupted client contact records — a joined address is lossy, and splitting it back apart guessed wrong for 35 of the 271 contacts with an address — and was removed entirely rather than repaired.
- **Individual members keep their pre-existing precedence** (the contact record first, then the member row); only the postal code was added. Whether the member row should win there is REPORT-ONLY on dev job `271bbe46`. The document continues to name the logged-in contact, exactly as before — an owner-of-record rework was attempted and **cancelled**; do not re-derive it from this section.
- **Individual members read from the member row too** (their own member-info submission), not from `contacts`. The screen used to prefer the contact record, so a client could review an address they never submitted; the stored document always used the member row and is unchanged. Which source *should* win for individuals — and the fact that the STAFF door still falls back to `contacts.residency` where a member row has no address — is tracked on dev job `271bbe46`.

### ⚠️ Entity-type normalization — MANDATORY invariant
`accounts.entity_type` stores **long form** ("Single Member LLC" / "Multi Member LLC" / "C-Corp Elected") — the value 'MMLLC' NEVER appears in accounts. `oa_agreements.entity_type` stores the **short code** ('SMLLC'/'MMLLC'). ANY comparison of an entity type string against 'MMLLC' MUST go through `normalizeEntityType()` (`lib/portal/entity-type.ts`). **Precedent (2026-07-07, Umberto Moretti / Azarexa):** the portal create route compared raw `accounts.entity_type === 'MMLLC'` — false for every account — so every portal-generated OA was built single-member with the primary contact at 100%, ignoring the members table; Datavora LLC signed a legally wrong OA. Fixed in: portal create route, `app/operating-agreement/[token]/[code]/page.tsx`, `app/portal/sign/page.tsx`, `app/portal/sign/oa/page.tsx`, `generate-documents-client.tsx`.

## OA public pages — how data reaches the browser (2026-07-22)

**The two public OA pages MUST NOT read `oa_agreements` / `oa_signatures` with the anon key.**
They go through `GET /api/operating-agreement/[token]/fetch`, which holds the service key,
verifies the access code SERVER-SIDE, and returns the whitelist in `lib/oa/public-view.ts`.

Why (dev job 023c7d06): both pages used to `select('*')` with the anon key and compare the
access code in the BROWSER — i.e. after the row had already been delivered. Policies were
`USING (true)` for role `public` and `anon` held SELECT on both tables. Tokens are
`${companySlug}-oa-${year}`, derivable from a company name that is public in state
registries. One unauthenticated PostgREST request therefore returned, across ALL agreements:
`access_code`, `ein_number`, `member_email`, `member_address`, the members blob — and every
co-signer's personal signing code, which is the credential that authorises signing AS that
member. Reproduced and then verified closed on an isolated local stack seeded with
production's exact policy set (`scripts/migrations/20260722-0100-oa-close-public-read.sql`).

Rules that follow:
- **Never widen `toPublicAgreement` / `toPublicSignature` by spreading a row.** `assertNoSecrets`
  throws on `access_code` / `member_email` / `email` / `account_id` / `contact_id`, including
  inside nested JSONB — the `members` blob carried member emails and was caught only by
  inspecting the route's real output, not by reading the mapper.
- **`tests/unit/anon-grant-contract.test.ts` is the gate.** It derives the browser's anon
  privilege needs from the code. If it fails, the code's needs changed — reconcile it
  deliberately, and never revoke a grant on the strength of a grep.
- **Admin preview cannot sign.** `canSign` excludes `isAdmin`, and the route requires a real
  staff session via `isStaffPreview` (2026-07-21 incident) — the query flag alone proves nothing.
- **New public/token-gated routes need a `middleware.ts` PUBLIC_PREFIXES entry** or they 307 to
  the staff login. This one did, and only a real request surfaced it.

**STILL OPEN — `anon` retains UPDATE on both tables.** The signing page still writes its
signature row, the counter and the final status straight from the browser, so an attacker who
guesses a token can corrupt an agreement. Closing it means moving those writes server-side
first; the read fix does NOT close it. Separately open: the signing-integrity defects
(browser-side finalization, no server reconciliation) — see the council review on that job.

## OA draft download & sign-by-hand (2026-07-23)
A client can complete an Operating Agreement three ways from the signing page (all three render **inside the portal iframe** too — the download used to be hidden whenever `?portal=true` was set, i.e. on every route a client actually uses):
1. **Sign online** — the existing e-sign flow.
2. **Download the draft** — `GET /api/operating-agreement/[token]/pdf?code=<code>`. Renders the agreement ON DEMAND (nothing stored) and is **DRAFT ONLY, never executed**. That single rule dissolves the whole class of review blockers: it reads no signature images (so it never touches the anon-writable `signed-oa` bucket with the service key), it is not a second producer of the signed instrument, and `generateOperatingAgreementPDF({ draft: true })` stamps every page + rewrites the preamble and the IN WITNESS WHEREOF recital to their **unexecuted** form so the copy cannot be passed off as signed. Gates (all AFTER the code check): voided → 410, signed → 409, plus a per-request rate limit.
3. **"I signed it by hand"** — `POST /api/operating-agreement/[token]/hand-signed` (multipart; optional `file`). Marks the agreement `signed` with **`signature_method='by_hand'`** and leaves `pdf_storage_path` NULL (TD holds no executed instrument unless the client uploads a scan). Files the unsigned draft named "(Unsigned Copy — client signed by hand)"; when a scan is uploaded THAT is filed as the signed copy. Emails support either "scan received" or "NO SIGNED COPY ON FILE — chase it". Filing is best-effort and escalates via `reportSystemError`; the client's confirmation is never undone by a Drive hiccup.

**`signature_method`** (`electronic` | `by_hand` | NULL) distinguishes an agreement TD holds a real signature for from one the client only *declared*. NULL = signed before the distinction existed (74 legacy rows, deliberately NOT backfilled). Migration `20260723-1200-oa-signature-method.sql`.

**Design note for the next session:** the on-screen SIGNED render still uses the browser html2pdf capture (pre-existing), so the executed PDF and this server draft are still two renderers — the draft download deliberately sidesteps that by refusing signed agreements rather than re-rendering them. Retiring the browser capture (have the sign POST call `generateOperatingAgreementPDF` server-side) is the follow-up that makes it one renderer; see `lib/operations/esign.ts` `flattenEnvelopeToSignedPdf` for the pattern.

## Gotchas, invariants & past bugs
- **`lease_send` sends a real email immediately** (not a Gmail draft) — don't call it to "preview." Use `?preview=td` for review.
- **OA generation is state-gated** — if the company's state isn't in `OA_SUPPORTED_STATES`, there's no template; add the template before generating.
- **Use `safeSend`** for any new lease/OA send path (R037) — mark "sent" only AFTER the send succeeds, with idempotency first.
- Lease is annual (`contract_year`) — a new year is a new lease record, not an edit of the old one.
- **A caller that wants the correct lease signer should never pre-resolve its own `contact_id`** — just call `createLease` without one. This WAS a real, separate defect for the OA side too: welcome-package setup and legacy portal transition used to fetch one generic "primary contact" and feed it into their `oa_agreements` inserts (`contact_id`/`manager_name`/`member_name`/`member_email`) — fixed 2026-08-19 (dev job `9ad76300-6181-4250-a1de-c77f37933f82`), both now resolve via `resolveAccountSigner` per-account, and both now build a real MMLLC roster (`members`/`total_signers`/`oa_signatures`) instead of filing a single-signer document regardless of actual member count. Any NEW automated flow should still resolve the signer itself rather than reusing a "primary contact" fetched for something else — that pattern is what caused this class of bug three separate times.
