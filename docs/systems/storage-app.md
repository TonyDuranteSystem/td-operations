## What it is
A native Mac app (Apple File Provider) that shows the REAL CRM storage (not the Drive backup) as "TD Storage" in the Finder sidebar and in every Open/Save window, for Antonio and Luca (both on Mac). All areas: Clients by state, People, Companies being formed, Closed/Cancelled, One-time customers, Business, My files (owners only). Second need: save a downloaded/external file straight into a chosen storage folder. **Nothing of the Mac app exists yet; this doc covers the SERVER pieces that exist.**

## How it's built (what exists now)
- **Tables** (migration `scripts/migrations/20261017-0100-storage-app-p0.sql`, UNDO beside it; applied to the SANDBOX only, NOT production): `storage_app_devices` (one row per approved Mac; `revoked_at`), `storage_app_auth_codes` (one-time PKCE codes, 60 s, hash only), `storage_app_tokens` (access 15 min / refresh, hash only, `used_at` for rotation). RLS on, no policies (service role only). `store_change_log` + `store_change_floor` + triggers on `store_files`, `store_folders`, `store_owners`, `accounts`, `contacts`; functions `store_changes_since(txid, seq, limit)`, `store_changes_head()`, `store_change_log_prune(interval)`.
- **Sign-in** (`lib/storage-app/device-auth.ts`, `tokens.ts`): OAuth code + PKCE (S256) with loopback redirect exactly `http://127.0.0.1:<port>/cb`. Tokens are opaque (`sa_at_` / `sa_rt_` / `sa_ac_`), only SHA-256 stored. Approval = a staff member signed in to the CRM (page `/storage-app/approve`, routes `/api/store-devices/approve|revoke` and `GET /api/store-devices`, all COOKIE routes → behind the CRM's two-step login). Refresh rotates; a refresh token reused after the 10 s grace revokes the whole device; a device is good for 30 days. EVERY call re-reads the user from the auth server: role = `app_metadata` via `isStoreStaffUser` only (never `isAdmin()`), not banned, and `userMayUseApp` asks the CRM's own `resolveMfaGate` whether the person would still get in.
- **Routes (token only, never the cookie)** `app/api/storage-app/{token,whoami,navigation,folder,changes,item}` (`item` = one file/folder by id WITH its parent, what Finder asks when it only knows an id); each (except `token`) starts with `withDevice` (`lib/storage-app/guard.ts`, fails closed). The exact list is `lib/storage-app/public-paths.ts`; `tests/unit/storage-app-routes.test.ts` pins it to the route files (and to the gatekeeper once that edit exists).
- **Same permissions as the Storage page**: the three helpers in `app/api/crm-store/browse/_auth.ts` now accept an optional `user` (the token's user); with none they read the cookie exactly as before.
- **Listing** (`lib/storage-app/listing.ts`): the Storage page's own `navigation()` and `folderContents()`; LIVE storages only (hidden study copies are not shown; a study copy asked for by id answers Not found); someone else's My files is Not found.
- **Change feed** (`lib/storage-app/changes.ts`): the log is written by DATABASE TRIGGERS (so no code path can miss a change — CRM, imports, Drive pickup, purge). Cursor = `<txid>.<seq>`; only rows of transactions older than every transaction still open are returned, ordered by (txid, seq) — a late commit can never fall behind a cursor already handed out. `resync:true` when the cursor is older than the pruned part (keep 30 days; prune function exists, **no cron calls it yet**). Visibility filter is the pure `filterChanges`: other people's private areas never mentioned; a hidden/gone storage still delivers DELETES (no name).

## Updating a file this Mac saved — now through the one safe save (2026-10-25, sandbox, dev job bd21e833 follow-up)
- **`saveUpdate` (lib/storage-app/save.ts) no longer uses `registerStagedUpload`/`store_write`.** It claims the slot (`store_claim_intent`, a lease), reads the staged bytes and calls `appendVersionBytes({ source: "mac", deviceId, expectedVersionNo })` → `store_append_version` (the same locks, same-bytes and conflict rules as the web page); then closes the slot and removes the staged object.
- **Optional `baseVersionNo`** in the `POST /api/storage-app/save` body (the version the Mac started from; the answer now carries `versionNo` so the Mac can send it next time). Absent → today's last-write-wins (history kept). Present and stale → **409 `conflict`** with plain words and nothing overwritten.
- **Plain answers the SHIPPED Mac understands** (`lib/storage-app/update-rules.ts::answerForAppend`; the Mac shows `message` and does not retry 409/413/422, and retries 500): locked (signed / passport-ID / replaced) → **422 `locked`**, filed → **422 `frozen`**, amended → 422, trashed → 409, conflict → 409. (`423` was NOT used: the shipped app treats it as a retryable server error.) A locked file is also refused at `upload-slot` time, before any upload.
- **One slot per update.** The update slot's caller key is `<file key>:u:<itemKey>` (`updateCallerKey`); only an open slot of THIS update is reused, and a used slot is answered `repeated` only when it carries this update's key. An older-style slot (the file's own key) is still accepted once but never answered as a repeat. This fixes "the second update got the first slot and was told `repeated` though its content was never registered".
- Proof: `tests/unit/storage-app-update-rules.test.ts`. The live HTTP script `t37-storage-app-update-own.ts` needs the sandbox service keys and was NOT re-run in this follow-up — run it before shipping.
