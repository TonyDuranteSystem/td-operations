## What it is
A native Mac app (Apple File Provider) that shows the REAL CRM storage (not the Drive backup) as "TD Storage" in the Finder sidebar and in every Open/Save window, for Antonio and Luca (both on Mac). All areas: Clients by state, People, Companies being formed, Closed/Cancelled, One-time customers, Business, My files (owners only). Second need: save a downloaded/external file straight into a chosen storage folder. **Nothing of the Mac app exists yet; this doc covers the SERVER pieces that exist.**

## Business rules (Antonio's decisions, 2026-10-16/17)
- Drive is only the backup; never the way to see the storage.
- Mac only. Sensitive documents are NOT downloadable to a Mac: Passport, ID Document, ITIN Letter, Form W-7, Form 1040-NR, ITIN Application, ITIN Schedule OI — and ANY untyped file inside a PERSON's storage (`lib/storage-app/sensitive.ts`). Enforced on the SERVER (the listing says `downloadable:false`; the file route, built in P1, must refuse a device token for these).
- Existing files are READ-ONLY in Finder at first; saving NEW files comes in P3 (hidden from the client, no type, flagged needs-review, via a new `registerFromApp`). Editing in place is a later, separately approved phase.
- Antonio: the Apple Developer account is his to open. The protected `middleware.ts` was edited with his OK on 2026-10-17 (see below). WHO may use the app: a setting, `app_settings.storage_app_allowed_emails` (JSON array of login emails; missing / empty / malformed = nobody; read on every request, no cache; checked IN ADDITION to the CRM's own rules — `mayUseAppNow` in `device-auth.ts`, `allow-list.ts`). SANDBOX is seeded with `antonio.durante@tonydurante.us` and `luca@tonydurante.us`. **PRODUCTION has no row yet (so nobody can use the app there) — at phase P4 Antonio runs: `insert into app_settings (key, value, updated_at) values ('storage_app_allowed_emails', '["antonio.durante@tonydurante.us","luca@tonydurante.us"]'::jsonb, now()) on conflict (key) do update set value = excluded.value, updated_at = now();`**

## How it's built (what exists now)
- **Tables** (migration `scripts/migrations/20261017-0100-storage-app-p0.sql`, UNDO beside it; applied to the SANDBOX only, NOT production): `storage_app_devices` (one row per approved Mac; `revoked_at`), `storage_app_auth_codes` (one-time PKCE codes, 60 s, hash only), `storage_app_tokens` (access 15 min / refresh, hash only, `used_at` for rotation). RLS on, no policies (service role only). `store_change_log` + `store_change_floor` + triggers on `store_files`, `store_folders`, `store_owners`, `accounts`, `contacts`; functions `store_changes_since(txid, seq, limit)`, `store_changes_head()`, `store_change_log_prune(interval)`.
- **Sign-in** (`lib/storage-app/device-auth.ts`, `tokens.ts`): OAuth code + PKCE (S256) with loopback redirect exactly `http://127.0.0.1:<port>/cb`. Tokens are opaque (`sa_at_` / `sa_rt_` / `sa_ac_`), only SHA-256 stored. Approval = a staff member signed in to the CRM (page `/storage-app/approve`, routes `/api/store-devices/approve|revoke` and `GET /api/store-devices`, all COOKIE routes → behind the CRM's two-step login). Refresh rotates; a refresh token reused after the 10 s grace revokes the whole device; a device is good for 30 days. EVERY call re-reads the user from the auth server: role = `app_metadata` via `isStoreStaffUser` only (never `isAdmin()`), not banned, and `userMayUseApp` asks the CRM's own `resolveMfaGate` whether the person would still get in.
- **Routes (token only, never the cookie)** `app/api/storage-app/{token,whoami,navigation,folder,changes,item}` (`item` = one file/folder by id WITH its parent, what Finder asks when it only knows an id); each (except `token`) starts with `withDevice` (`lib/storage-app/guard.ts`, fails closed). The exact list is `lib/storage-app/public-paths.ts`; `tests/unit/storage-app-routes.test.ts` pins it to the route files (and to the gatekeeper once that edit exists).
- **Same permissions as the Storage page**: the three helpers in `app/api/crm-store/browse/_auth.ts` now accept an optional `user` (the token's user); with none they read the cookie exactly as before.
- **Listing** (`lib/storage-app/listing.ts`): the Storage page's own `navigation()` and `folderContents()`; LIVE storages only (hidden study copies are not shown; a study copy asked for by id answers Not found); someone else's My files is Not found.
- **Change feed** (`lib/storage-app/changes.ts`): the log is written by DATABASE TRIGGERS (so no code path can miss a change — CRM, imports, Drive pickup, purge). Cursor = `<txid>.<seq>`; only rows of transactions older than every transaction still open are returned, ordered by (txid, seq) — a late commit can never fall behind a cursor already handed out. `resync:true` when the cursor is older than the pruned part (keep 30 days; prune function exists, **no cron calls it yet**). Visibility filter is the pure `filterChanges`: other people's private areas never mentioned; a hidden/gone storage still delivers DELETES (no name).

- **Review fixes folded in (2026-10-17, senior engineer + bug hunter + security + system counselor):** a refresh token used twice at the SAME instant no longer reads as theft (the used-at time is read again after losing the race); a file or folder moved into a place this login cannot see (someone's My files, a hidden study copy) now arrives as a DELETE at the old place (no ghost in Finder) and private ids are never handed out; approval shows a CHECK CODE (derived from the PKCE challenge; the Mac app shows the same one; fixed test value `VYF9-RWG3` in both languages) and no misleading IP line; approval needs a FRESH two-step check (aal2) when the person has an authenticator (the CRM alone lets a remembered browser through); the cookie routes `/api/store-devices/*` refuse a request that is not same-origin JSON; "not allowed" is one sentence for every cause (the cause goes to the audit log); audit rows in `store_events` (`app_device_approved`, `app_device_signed_in`, `app_signin_refused`, `app_device_revoked`); a trashed folder answers Not found; no half-registered device; prune uses `<=` so a cursor ON the pruned tip is told to refresh in full. **Contract for the app:** an `owner` upsert means "list this storage again from the top" (writes made while a storage was hidden are never delivered). Take `changes?head=1` BEFORE walking the tree.
- **The Mac app (`mac/TDStorage/`)**: `Package.swift` + `Sources/TDStorageCore` (PKCE, models, `StorageAPI` with one shared renewal for parallel 401s, Keychain store, loopback sign-in, item ids, name mapping NFC / ":" ↔ "/", duplicate-name suffixes, change-to-folder signals) tested by `swift test` (29 tests, no signing needed); `App/` (SwiftUI sign-in window: FileVault check, check code, sign in/out, open in Finder); `FileProviderExtension/` (read-only File Provider: folder listing, item lookup, working-set change enumerator, no downloads, every write refused); `generate_xcodeproj.rb` builds `TDStorage.xcodeproj` (NOT checked in; `GEM_HOME=~/.gem/ruby/2.6.0 ruby generate_xcodeproj.rb`) with two configurations — Debug = dev server `http://localhost:3050`, Sandbox = `https://td-operations-sandbox.vercel.app` — each with its own bundle ids / Keychain group; there is NO Production configuration (P4). The core is compiled into BOTH targets. `xcodebuild … CODE_SIGNING_ALLOWED=NO build` succeeds for both and the app embeds the extension.

- **Found by running it for real (2026-10-17):** (1) a File Provider extension needs `NSExtensionFileProviderSupportsEnumeration = true` in its Info.plist or `NSFileProviderManager.add` fails with `NSFileProviderErrorDomain -2001 "The application cannot be used right now"`; (2) the CRM's state groups are keyed `state:Florida` — a colon — so the item-id parser must take EVERYTHING after `g:` as the group key (the first version lost every state group: Finder said "The file couldn't be opened"; test `testGroupKeysMayContainColons`); (3) signing: `xcodebuild … DEVELOPMENT_TEAM=<team id> -allowProvisioningUpdates` signs both targets with the Personal Team profile (the team id is the OU of the certificate: `security find-certificate -c "Apple Development" -p | openssl x509 -noout -subject`); the free team accepted the keychain access group; (4) the Debug build may run with FileVault OFF (it only talks to the sandbox's test data; shown as an orange note) — Sandbox/Production configurations always require FileVault. **Antonio's Mac mini has FileVault OFF** — decide before P4 (the Mac mini also runs other services; enabling FileVault there needs a password at every restart). (5) The app window shows the real error text for sign-in / Finder-registration failures. (6) The approval page opens in the default browser (Chrome here); the window has "Open the page again" and "Copy link".

## Gotchas, invariants & what is NOT done
- **Not done:** running the Mac app at all (signing), the file-open route with signed URLs + the sensitive-type refusal (the listing already flags `downloadable:false`), cache encryption with a deletable key + the 24-hour lease + eviction (only the FileVault check exists), the "My devices" page, rate limits/alerts, crons for the two prune functions, `registerFromApp`, the middleware public-path entries, the production migration. Each is in plan v3.
- **Mac signing is the blocker for the Finder gate:** this Mac has no code-signing identity and Xcode has no Apple account; a File Provider extension cannot be loaded unsigned. A free "Personal Team" certificate (Xcode › Settings › Accounts, Antonio's Apple ID) may be enough to TEST on his own Mac; the paid developer account is needed to install it on Luca's Mac without warnings.
- **Who may use the app = the allow-list setting (Antonio and Luca), AND the CRM's rules.** The system counselor flagged (2026-10-17) that on production `jodi@` (admin) and `support@` (team, **`mfa_exempt = true`**, no authenticator) would otherwise be let in by the CRM's rule alone; the allow-list is what keeps them out. A person on the list who is MFA-exempt with no authenticator is still allowed by the CRM's own gate decision — keep exempt logins off the list.
- `tests/unit/cron-coverage.test.ts` ("matches vercel.json exactly") FAILS on the base commit: the `drive-pickup` cron from PR #718 is in `vercel.json` but not in `SCHEDULED_CRONS`. Not caused by this work; not fixed here.
- A saved file produces TWO feed rows (the insert, then the link to its first version); Finder keeps the last per id.
- Folder writes lock their own storage, so tests that hold a transaction open must change a DIFFERENT storage in the meantime.
- A refresh token used twice inside 10 s is treated as a lost answer and gets a NEW pair (a thief inside that window is accepted; this was a deliberate, reviewed trade-off).
- `middleware.ts` (protected file) now imports `STORAGE_APP_PUBLIC_PATHS` and lets EXACTLY those five paths through without a cookie (`isPublicPath`). NEVER add the bare prefix `/api/storage-app`: it would skip the staff two-step-login check for every future route under it. `tests/unit/storage-app-routes.test.ts` keeps the list, the route files and the gatekeeper in step; `t34` proves it over HTTP (unlisted and "starts-with" paths refused, the token opens no other route, a cookie is no substitute).
