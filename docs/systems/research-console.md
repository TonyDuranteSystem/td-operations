# Research Console
_Last verified against code: 2026-08-17 — Claude (initial build, confirmed working by Antonio in sandbox)_

## What it is
A top-level CRM page (`/research`, admin-only) where Antonio or Luca build an advanced filter — pick one or more record types, add conditions field-by-field — and get back a live results list, in a choice of layouts, with an Excel export. Modeled on Salesforce/HubSpot/Zoho-style advanced search, not a chatbot. There is no free-text-question/AI-research layer — that direction (from the original work order) was explicitly superseded mid-build in favor of this filter-builder shape; see "Gotchas" below.

## Business rules
- Trigger + view access: admin only (`isAdmin()`), same gate as every other whole-client-base CRM surface. Matches Antonio + Luca today. No read-only tier exists for anyone else (e.g. a future "India tax team" ask) — would need a new role, not assumed.
- A filter condition applies to every currently-selected record type that actually has that field; it silently skips (never errors, never excludes) a selected type that lacks the field. The UI labels a condition with which types it's scoped to when it doesn't apply to all of them.
- Filters apply the instant they're complete (a picked date, a checked box, a blurred text/number field) — there is no separate "commit" step a user has to discover. This was a real bug Antonio hit live; see Gotchas.
- Multi-type search has no combined cross-table pagination: each selected type is capped at 50 rows on screen, with a plainly visible "truncated" notice if there's more. Excel export is NOT capped at 50 — it re-paginates through the real query up to 5,000 rows per type and adds a "truncated" note sheet only if even that cap is hit.

## How it's built
- **Tables:** reads across whichever real CRM tables are registered (`accounts`, `contacts`, `leads`, `deals`, `service_deliveries`, `payments`, `tasks`, `offers`, `lease_agreements`, `oa_agreements`). Writes only to its own table, `research_saved_searches` (`id, name, entities text[], conditions jsonb, created_by, created_at`).
- **Key files:**
  - `lib/research/entity-registry.ts` — the whitelist: every searchable record type, its table, display field, and typed field list. Adding a new searchable record type = add one entry here, nothing else.
  - `lib/research/query-builder.ts` — translates a `{field, operator, value}` condition into real Supabase query-builder calls (`.eq/.ilike/.in/.gte/...`), validating field+operator against the registry first. This is the whole injection defense — never bypass it with a raw string filter.
  - `lib/research/run-entity-search.ts` — runs one entity's query with only the conditions it has fields for. Shared by the search route and the Excel export route so the download can never disagree with the screen. (This used to live inside `app/api/research/search/route.ts` — Next.js's App Router rejects any named export from a `route.ts` file that isn't a recognized handler/config export, which only surfaces as a *build*-time failure, not `tsc --noEmit`. Keep shared logic in `lib/`, never export helpers from a route file.)
  - `lib/research/draft-condition.ts` — pure "is this filter-in-progress actually complete yet" check (`draftToCondition`). Deliberately separate from the React component so it's unit-testable without a component renderer (this repo has none installed).
  - `components/research/research-console.tsx` — the page's client component: multi-select record-type chips, filter chips, the field/operator/value editor, the three result views (table / cards / grouped-by-type), Excel export button, saved searches.
  - `app/api/research/search/route.ts`, `.../field-values/route.ts`, `.../export/route.ts`, `.../saved-searches/route.ts` + `[id]/route.ts`.
- **Nav / gating:** `/research` added to `ADMIN_ONLY_PATHS` in `middleware.ts`; sidebar entry (`id: 'research'`) in `components/dashboard/sidebar.tsx` with a one-off placement fix (see Gotchas) so it lands near the top even for a returning user with a pre-existing custom sidebar order.

## Gotchas, invariants & past bugs
- **The scope pivoted mid-build.** The original work order envisioned a free-text research question + AI-generated evidence board (modeled on a one-off Claude-built report Antonio had seen). Antonio redirected this explicitly: he wanted a real filter/search builder like Salesforce/HubSpot, not an AI narrative layer. That AI-research direction was NOT built and is not planned — don't resurrect it from the original work order without re-confirming with Antonio first.
- **Filters must auto-apply — this was a real, live bug, not a hypothetical.** The first shipped version required an explicit "Add filter" click after setting a condition's value; Antonio set a filter, the results silently kept showing the OLD, unfiltered set, and reported "it doesn't give me the list with this filter." Fixed by applying a condition the instant it becomes complete (date picked, checkbox checked, text/number field blurred or Enter pressed) — see `autoApply` in the component and the completeness check in `draft-condition.ts`. If you touch the filter-editing UI, do NOT reintroduce a silent "configured but not applied" state.
- **A helper function cannot be exported from a `route.ts` file.** Next's App Router build step (not `tsc`, not eslint) rejects any named export that isn't a recognized route handler/config. This only surfaces in a real `npm run build` / actual Vercel deploy — caught this the hard way after a deploy's wrapper script reported success (exit code 0) while the actual build had failed inside. **Always read the real deploy log text, never trust a wrapper script's exit code alone**, and put any shared logic in `lib/`, not in a route file.
- **This worktree's `node_modules` can be stale relative to `package.json`.** Hit a build failure on an unrelated, pre-existing script (`scripts/qa/mfa-exemption-qa.ts` importing `otplib`) that turned out to be a real, already-declared dependency simply not installed locally — confirmed via `git blame` before touching anything, fixed with a plain `npm install` (no `package.json`/lockfile changes). Not a Research Console bug; don't assume every build failure you hit while working on this feature belongs to this feature.
- **Sidebar placement for a brand-new nav item.** A brand-new default nav entry added when a user already has a saved custom sidebar order needs a one-off insertion (see the `research` special-case splice in `sidebar.tsx`'s merge logic) or it silently lands at the very bottom of a long personalized list. Traced in depth: the sidebar's own loading effect actually resets a stale saved order to the fresh default (including the new item's position) whenever any current default id is missing from it — so this splice is defensive/redundant in the common case, not the actual mechanism, but is cheap and harmless to keep.
- **No relational joins.** Multi-type search runs N independent per-type queries and unions the results in the UI — it is not "companies whose linked contact matches X." That's flagged as real future work, not silently unsupported.

## How to verify current state
- `SELECT id, name, entities, conditions, created_at FROM research_saved_searches ORDER BY created_at DESC LIMIT 5;` — confirms the table is live and a saved search round-trips.
- `npx vitest run tests/unit/research-query-builder.test.ts tests/unit/research-console-auto-apply.test.ts tests/unit/research-union-fields.test.ts` — pure-logic tests, no DB needed.
- `npx vitest run --config vitest.esign-live.config.ts tests/live/research-console.test.ts` — exercises the real registry + query logic against real sandbox data (schema drift check per entity, every operator type, multi-entity fan-out, saved-search CRUD).
- Load `/research` as an admin in sandbox: pick 2+ record types, confirm the view-mode switcher appears; add a filter and confirm the result count changes without an extra click; hit Export to Excel and confirm the download has one sheet per selected type.
