## SMLLC tax intake wizard — clarity + Form 5472 compliance (shipped 2026-06-11, PRs #106/#107)

The portal `tax` wizard (entity SMLLC) is how a foreign-owned single-member LLC submits the data for its pro-forma **1120 + Form 5472**. Config: `TAX_FIELDS` in `components/portal/wizard/wizard-configs.ts`; rendered by `app/portal/wizard/wizard-client.tsx` via the shared `WizardField`.

**The problem (before).**
- It asked **beneficial-owner questions** (100%-direct owner, ultimate-owner name/address/country/tax-id) that make no sense for a single member — **8 clients entered *themselves* as the "ultimate owner".**
- The **owner address** didn't say it was the *personal* residence — clients entered their citizenship country, or the company address.
- **Related-party transactions were an OPTIONAL free-text repeater** — a client could skip them entirely, and the foreign party's tax ID + the transaction *type* weren't captured. Result: 5472 reportable-transaction data frequently missing or uncategorized. **An incomplete Form 5472 is treated by the IRS as a failure to file → a $25,000 penalty** (per related party, +$25k/30 days after notice) — and this applies even though SMLLC clients owe **no US income tax** (5472 is an information return; "I don't pay US tax" does NOT remove the penalty).
- Per-field help was hidden behind a click-to-reveal **"i" tooltip clients never clicked.**

**What the system does now (after).**
- **No beneficial-owner fields** on the SMLLC owner step. SMLLC company fields are isolated in their own `TAX_SMLLC_COMPANY` array, so the MMLLC/Corp tax forms are untouched.
- **Owner address is explicitly the personal residence** — "Personal Home Address — where you physically live", with the "Italian citizen living in Dubai/Portugal → enter the Dubai/Portugal address" example, and the country field clarifies residence ≠ citizenship.
- **Related-party transactions are gated and required.** A required Yes/No question (transactions with any company you/your family own, or that owns your LLC). **"No"** shows an amber **$25,000-penalty confirmation**; **"Yes"** REQUIRES ≥1 fully-completed transaction. Each transaction captures: party name, **full address**, country, **required foreign Tax ID/VAT** (5472 Part III — "None" allowed only if the party genuinely has none), **amount**, **direction** (money in vs out), **transaction type** (a dropdown mapped to the 5472 **Part IV** categories: sale of goods, services, rent, royalties, interest, loan, capital, management fee, reimbursement, other), and a **required description**.
- **US business activities** is now a Yes/No gate + a conditional detail box (was a vague free-text field).
- **Field help is always visible** under every field (the "i" tooltip was removed — a shared `WizardField` change, so it applies to **all** portal wizards).
- The **accountant Drive package** (`lib/form-to-drive.ts`) surfaces all new/renamed keys and prints direction/type as readable labels (not raw codes like `to_llc`).

**Two enforcement layers.** Client: `validateStep` (`wizard-client.tsx`) blocks Next/Submit until a "Yes" has ≥1 complete transaction. ## The status pipeline
A tax return moves through a status on `tax_returns.status`. The **current** flow (installment + wizard model) is:
`Payment Pending` → `1st Installment Paid` → `Wizard Available` → `Data Received` → `Sent to Accountant` → `TR Completed - Awaiting Signature` → `TR Filed`, with `Extension Requested` / `Extension Filed` as the extension branch and `Not Invoiced` for un-billed returns. _(`Sent to Accountant` was `Sent to India` until the 2026-06-09 rename; the old label still exists in the `tax_return_status` enum and is kept mapped defensively in code, but the current flow only produces `Sent to Accountant`.)_

> **Legacy statuses — still in the enum, NOT produced by the current flow:** `Activated - Need Link` and `Link Sent - Awaiting Data` are vestiges of the old *"email the client a data link, then wait for their data"* model that predates the installment + wizard redesign. The data link was replaced by the portal wizard, and the old "2nd Installment Paid" stage was renamed "Wizard Available". No tax return currently carries either status, and the pipeline stages that once produced them (`Payment Verified`, `Data Link Sent`) no longer exist. They remain valid enum values — an admin could still set one manually — so they are kept mapped defensively: `lib/operations/tax-return-sd-bridge.ts` aliases both to live SD stages, and the portal pause-banner keeps them in its pre-data-receipt set so a manually-set legacy row still pauses correctly during a tax-season pause. **Do not treat them as live pipeline steps.**

Separately, boolean **workflow-progress flags** track milestones: `paid`, `link_sent`, `data_received`, `sent_to_accountant`, `extension`, `accountant_status`. _(Renamed from `sent_to_india` / `india_status` on 2026-06-09; the legacy columns still exist in the DB until Phase 2 but code no longer reads/writes them.)_

## The accountant hand-off
- `tax_send_to_accountant` (`lib/mcp/tools/tax.ts`) gathers the document package from Drive `3.Tax/{year}/` — **Tax Organizer PDF, P&L Excel (MMLLC/Corp), prior-year return, bank statements** — and sends one email with all attachments to the accountant (default `tax@adasglobus.com`), then updates the return's status (`status → "Sent to Accountant"`, `accountant_status → "Sent - Pending"`).
- **Always run `dry_run=true` first**, review the package, get Antonio's approval, then run with `dry_run=false`.
- **Idempotent**: skips if already sent (stamps `sent_to_accountant_date`) unless `force_resend=true`.
- **Every attachment must PROVABLY belong to its tax year** (`lib/tax/pick-tax-file.ts`, Council 2026-07-17). The picker used to take the first filename regex match across the year subfolder AND the Tax root with no year check at all — so a two-year client's 2024 workbook could be attached to a 2025 send and filed as the 2025 return. The rule now:
  - **Proof by name** = the year in the name is the ONLY year in the name. A name carrying two years (a revision date "PnL 2024 (revised 2025-01-30)", a fiscal span "FY2024-2025", a comparative) proves NOTHING — it is reported for a human, never auto-picked.
  - **The company name is stripped first**, wherever it sits and however it was slugged (`Tax_Data_{Company}.pdf` puts it in the middle with underscores). It is evidence about neither the year ("Trend 2025 LLC - PnL 2024.xlsx" must not file as 2025 — and that name is machine-generated) nor the KIND of file (a client called "PNL Consulting LLC" must not have every spreadsheet read as a P&L; `matchesCategory`). Years are read from the name with EVERY occurrence stripped; the category is matched with only the first stripped, so a company literally named "Profit Loss" keeps its own P&L.
  - **Proof by location** = a name with no year at all, sitting in the `3.Tax/{year}/` folder. Location never overrides an explicit wrong year in the name.
  - Anything unprovable is **reported missing, never attached**. The organizer, the P&L, the bank statements AND the prior-year return all go through this (statements left out are listed; the prior year is proven by its folder but still ranked, so a "return DRAFT (not filed).pdf" can't beat the filed one on Drive's name ordering).
  - **A Tax-root file whose name also exists in the year folder is a legacy copy and is ignored.** The confirmed workbook used to be archived flat into the root and is now archived into the year folder, and the upsert only replaces same-named files within ONE folder — so every client who attested before this shipped has an orphaned root twin with a byte-identical name. Left as rivals they were indistinguishable in the "which of these is it?" prompt, and picking the stale one filed superseded numbers silently.
  - **When a genuine tie remains, candidates are described by location + last-modified date, not just name** — two files can share a name exactly, and choosing between two identical lines is guessing.
  - **A truncated Drive listing refuses the send.** `listFolder` does not paginate; it now requests `nextPageToken` so a caller can TELL. On a partial listing the "two files match → stop" check would pass by accident, which is worse than no check.
- **Three separate gates — do not re-merge them** (`force_resend` used to silently do all three, which switched the document checks off for precisely the corrected re-sends that need them most):
  - `force_resend` = the **idempotency** override only (re-send a year already sent).
  - `send_incomplete` = the explicit opt-out for **missing optional** documents.
  - `pnl_file_id` / `organizer_file_id` = the human **resolving an ambiguity** by naming the exact file. A named file of the wrong KIND is refused (the organizer's id pasted into `pnl_file_id`); a named file whose YEAR can't be proven is allowed — that's a real human decision — but is recorded in "YOUR EXPLICIT CHOICES" in the preview, in the summary, and in `action_log`.
  - `no_pnl_reason` = a genuinely dormant/first-year company that still files an informational return. Only accepted when NO P&L-shaped file exists at all — if one exists but is unreadable, the answer is "name the file", not "declare the company dormant". Recorded in `action_log`, and only when it was actually used.
  - The gates themselves are a pure, unit-tested function (`decideSendGate`): **missing P&L** on an entity that files one is a **hard stop no flag bypasses**; an **unresolved ambiguity blocks the send** (checked BEFORE the optional-docs gate, so `send_incomplete` cannot skip past it) — it is not a footnote printed after the email is gone. A preview of an ambiguous package is allowed, because that is how the operator gets the ids to resolve it.
  - **A bare "✅ Ready to send" is suppressed whenever any warning exists.** A warning under a green tick is a warning nobody reads.
- **The email describes only what actually attached.** A failed Drive download used to be swallowed while the body was built from the files we *meant* to attach — the accountant could receive a mail listing a P&L that wasn't there. Losing a required document now aborts the send (a Google-native Sheet cannot be downloaded as a file — re-upload it as a real `.xlsx`).
- **The client-confirmed workbook is archived to `3.Tax/{year}/`, upserted** (`lib/tax/attest-handoff.ts`) — one confirmed workbook per year, replaced in place on re-confirmation. It used to land in the flat Tax root via a plain create, piling every year's near-identically-named workbook into one folder and leaving a stale twin on re-confirm. If the archive fails, the staff task says so rather than pointing at a file that isn't there.
- **A P&L-shaped file whose year can't be read BLOCKS the send** (`decideSendGate`'s `pnl_conflict`), even when a clean P&L was picked. That unreadable file is the *more* suspicious of the two — "PnL 2024 (revised 2025-01-30)" is exactly how a correction gets named — so printing it as a footnote under a successful send is the theatre this whole change exists to stop. `pnl_file_id` settles it either way (name the correction, or confirm the one already picked). A supporting document's conflict does NOT block — only the P&L's.
- **`findOrCreateYearFolder` refuses rather than create on a truncated listing.** Creating a SECOND `{year}` folder is durable corruption: the attest handoff would archive into the invisible twin while every reader resolves the other, so the client's confirmed workbook becomes unfindable — and no amount of picker hardening can detect that. This matters *because* the archive now targets the year folder; the old flat-root write had no folder to resolve.
- **This is a stop-gap over file names, and it does NOT fully die with the snapshot.** Recording the archived Drive **file id** at attestation and fetching BY ID (dev_task `fa37121d`) retires name-matching for the **P&L** only. The organizer, the client-uploaded bank statements and the prior-year return have no attestation event to snapshot an id at — they keep this module. Do not delete it when fa37121d ships.

## MMLLC questionnaire — foreign partners are DERIVED, not asked (2026-07-28)
Born from Nexo Agency LLC: the client answered **No** to "Any foreign partners?" while both members are Slovak individuals resident in Slovakia. A production sweep showed the question was answered usably by **2 of 15** submitted MMLLC forms — **6 answered No** with an all-non-US member roster (Imperium Commerce, LT Program, MPG Performance, Nexo Agency, PAMAG, TP Balance) and **7 came back blank** because the field was `required: false` (Adact Studio, Aumianna, Economicamente, Nova Ratio, TITAN REAL ESTATE, Uxio Test, Zhang Holding). Nothing had been FILED with a wrong answer — every 2025 MMLLC return was still pre-accountant — but the input data was ~1-in-6 correct.

- **The question is GONE.** `mmllc_foreign_partners` is no longer rendered; the key survives in `FORM_FIELDS`/label maps (`required: false`) so historic submissions still read and print. The clients had already typed every underlying fact one step earlier — being asked to restate it in tax vocabulary is what produced the wrong answers ("partner" means "member": IRC §761(b); a US MMLLC is a partnership by default, Treas. Reg. §301.7701-3(b)(1)(i); "foreign partner" = not a US person under §7701(a)(30), Treas. Reg. §1.1446-1(c)(1)). Schedule B-1 Part II asks **Country of Citizenship** for INDIVIDUAL owners, so it plainly reaches non-US individuals and not only foreign entities — the source form TD rebuilt from (James Baker CPA) says "foreign **(Non US)** partners"; our rebuild dropped the clarifier.
- **Derivation lives in `lib/tax/foreign-partners.ts`** (pure, DB-free, 18 unit tests). A PERSON is foreign unless: US citizen, **holds a US green card**, or lives in the US. A COMPANY is foreign unless formed under US law — **place of formation decides, so a US-formed entity is a US person even when foreigners own it.** Missing data ⇒ `unknown` reported BY NAME, never a guessed "domestic"; one confirmed foreign member settles Yes even while another member is incomplete.
- **Two new member fields feed it.** Per-person **`member_green_card`** — the one fact citizenship + residence cannot supply (a lawful permanent resident is a US person, IRC §7701(b)(1)(A)), asked per member because the return reports each member individually, so "someone has one" is unusable. Per-company **`member_company_country`** (country of formation) — the tax member card collected name, tax number and beneficial owner but NEVER where the entity was formed, leaving the entity half underivable and Schedule B-1 Part I col (iv) without a source. The formation/onboarding members form always asked it; the tax one did not.
- **Country matching normalises what production actually holds:** `USA`, `United States`, `Stati Uniti`, and the state `Florida` typed into a country box. 10 company-type members exist across MMLLC clients and **6 clients have mixed US/foreign ownership** (AI Venture Labs, Azarexa, Dynamiq SR, Economicamente, Estro, Oh My Creatives) — so both halves of the rule are live, and a single company-wide yes/no could never have expressed them.
- **Why not flip it to "is any member a US person?"** — those 6 mixed-ownership clients would answer Yes truthfully while hiding the foreign members that drive the filing.
- **What it drives:** Schedule B line 14, Schedule B-1 disclosure, and above all **Schedules K-2/K-3** — a single non-US member breaks the domestic filing exception. It does NOT by itself create US tax (§1446 withholding needs effectively connected income), which is why the copy reassures rather than alarms.
- **Still open / NOT done:** the derived answer is not yet shown back to the client for confirmation before submit, and the accountant export still prints the legacy `mmllc_foreign_partners` key rather than the derived result. Also flagged, deliberately untouched: **"Total assets over $50,000?"** matches nothing on Form 1065 — Schedule B line 4 uses receipts < $250,000 and total assets < $1,000,000.

## SS-4 Responsible Party is NOT a tax-wizard requirement (2026-07-28)
A multi-member client could complete the whole questionnaire and be refused at the FINAL step by a toast naming a tick box several steps back, with no link to it — reproduced on the QA fixture, and the reason Nexo's reopen was held.

- **It belongs to the EIN application.** The SS-4 *is* that form; naming one responsible person is required to file it, at formation (or onboarding for a company TD did not form). It reached tax by inheritance: the old gate was a BLOCKLIST that switched the check on for every MMLLC wizard; when that stranded the personal ITIN wizard (Adam Mihaly / LUMA Beauty, 2026-07-24) it became an allowlist and tax was carried across rather than re-examined.
- **Nothing consumed it.** Verified zero references to a signer in `app/api/portal/wizard-submit`, `app/api/portal/tax-confirm`, `lib/tax/apply-confirmed-submission.ts`, `lib/mcp/tools/tax.ts` and `lib/tax/financials-orchestration.ts`. Clients were blocked on an answer that was then discarded — and by tax season the EIN already exists, so there is no SS-4 to sign.
- **Split, not deleted.** `wizardCollectsOwnerMembers` ALSO gates the members-ownership check, and tax NEEDS that (every member lands on a Schedule K-1, so shares must total 100%). Dropping tax from that allowlist — the tempting one-line fix — would have silently disabled it. New **`wizardRequiresSs4Signer`** (formation + onboarding only) is strictly narrower, and `tests/unit/wizard-ss4-signer-scope.test.ts` guards the distinction explicitly.
- The signer picker is hidden on tax too, so no dead control is left behind.

## Business rules
- **Send-to-accountant is dry-run-first + approval-gated** (built into the tool's contract) — never blast documents without reviewing the package.
- **Tax pause is gated on the 2nd installment** — a client's tax work resumes when they've paid installment 2, OR when the global pause is lifted.

## Gotchas, invariants & past bugs

- **A blank member name matches EVERY transaction — `"anything".includes("") === true` (2026-08-04).** Ten `account_contacts` rows across six accounts WITH bank data have NULL first AND last name. One in the roster books the whole year as owner equity and the P&L reads zero income, zero expenses. `isUsableMemberName` in `lib/tax/member-names.ts` is the only thing standing between that data and a wiped-out return: never remove it, never "simplify" it to a truthiness check, and never add a roster source that bypasses it.
- **The member roster is a UNION of `members` and `account_contacts` — do not "clean it up" to one source.** `members` is written only for MMLLCs (47 of 330 accounts have a row), so a single-owner company's owner exists ONLY as a contact link; and `members` is current-state with no dates, fully DELETEd and re-inserted by the client's own member-info form, so a mid-year departure erases the person the tax year still needs. Contacts are never unlinked, which is exactly why they are kept. Over-including shows a correctable review card; under-including silently deducts an owner draw on a filed return. Favour recall.
- **Judge a member NAME by shape, not by length, and never require every part to be substantial.** The original `>= 5` characters was invented and let a lone "Alessandro" through while nearly costing the blank-name catastrophe. The rule is ≥2 parts, ≥5 chars overall, ≥1 part of ≥3 chars. Requiring EVERY part to be ≥3 looks tidier and silently drops company members whose names carry initials ("B&P International LLC", "F.INVEST Holding LLC") — the dangerous direction, since their distribution then books as a deducted expense.
- **Match member names accent-folded and on whole words.** Banks send "JOSE MUNOZ" where the CRM holds "Josè Muñoz"; a raw lowercase `includes` misses that, and a missed member is a silently deducted draw. Whole-word matching is what stops "Ada Rossi" hiding inside "canada rossignol". Both live in `matchMemberName` — never hand-roll a second comparison (`validation-breakdown` had one and it would have drifted the moment the categoriser normalised).
- **`uncategorized` is NOT a neutral holding state — it means opposite things on the two surfaces.** The client portal FOLDS undecided outflows INTO `totalExpenses` (`defaultUncategorizedBySign: true`); the staff workspace EXCLUDES them (`false`). So "just leave it uncategorized and let the client decide" applied broadly produces two different taxable incomes for the same company-year. Any demotion to uncategorized must be NARROW and deliberate.
- **"Ask the client when unsure" has to be aimed, or it is worse than guessing.** Reopening every unconfirmed payee on the `Sent money to|Inviato denaro a` catch-all would have turned 946 rows across 136 payees into questions — nearly all genuine suppliers (one payee alone: 302 payments, −1,257,576). `findNearMissMember` fires only on an OUTGOING row that a GUESS produced, whose PAYEE carries a member's surname without their full name. And only the payee half of the line counts: `payeePart` cuts at the first reference marker, because a supplier's invoice number mentioning a member is not a payment to that member.
- **An OUTGOING wire always names your own company — as the SENDER. Never treat "the row mentions us" as "it is our own account" (2026-08-03, Titan).** Self-transfer detection must ask whether the company is the RECIPIENT: payee field, or a destination marker before the name, or the Mercury payee-first shape. If none applies, do NOT auto-hide — send it to the client's question queue. Auto-hiding is uniquely dangerous here because a wrong hide is invisible from BOTH sides: gone from the P&L and never asked about. The income half of this same rule was already tightened in 2026-07-02 and the outgoing half was left loose for a year; if you touch one direction, check the other.
- **Never validate a categorisation rule by sampling — replay it over every real row.** The Titan fix looked perfect against hand-picked cases; replaying it over all 581 production own-entity rows immediately exposed a false positive (Dynamiq's genuine Mercury→Relay move) that sampling had missed. The bar for a money rule is: the replay releases exactly the rows judged wrong by hand, and nothing else.
- **Categorisation runs at ingest / staff workspace-save / manual MCP re-run — and NOT when the client record changes. The stale-classification sweep (`/api/cron/tax-restale-sweep`, 4-hourly) is the safety net.** REPORT-ONLY until `TAX_RESTALE_SWEEP_DRY_RUN="false"`. It NEVER touches a confirmed return (the client attested to those numbers — a correction there is staff reopening it) and can never overwrite a human answer (`manual:` rows are refused by the engine itself). Deterministic passes only — `recategorizeAccountYear` gained a `dryRun` option so the preview reuses the real function rather than re-gathering rows/rules/members somewhere else, which is how a preview drifts from the thing it previews. Every account-year it would change is posted to `td-taxreturn`: a silent re-sort of client money is precisely the failure this exists to fix. Decision logic + the dry-run switch are pure and mutation-proven in `tests/unit/restale-sweep.test.ts`.
- **Categorisation runs ONCE at ingest and never revisits itself.** Member-name rules, related-entity flags and own-name matching all read the client record AS IT WAS at ingest time. Owner draws to Lucia Terracciano / Antonio Pezzella were mis-booked purely because those people were linked as contacts AFTER their statements were ingested. When you fix or enrich a client record (members, related companies, legal name), the existing transactions do not re-evaluate — a re-run is needed, and nothing triggers one automatically.
- **Undecided rows have TWO halves — never report only the expense one (2026-08-03).** `foldedUncategorizedExpense` is a positive magnitude and `foldedUncategorizedIncome` is signed positive; a disclosure that reads only the expense field shows "−0.00" to a client whose undecided rows are inflows, while the gate beside it shows the real positive figure. The netting lives ONCE, in `lib/tax/disclosure-text.ts` (`pendingCount` / `pendingNet`), and both the gate and the portal component call it. Do not re-derive it at a new surface.
- **If the screen says a file is locked, the SERVER must refuse everything the screen implies (2026-08-03).** A banner is not a lock. Before adding one, enumerate every mutating control beneath it and check each route: `attest` and `upload` had no lock at all when the banner first shipped, and a locked client pressing Confirm fired the accountant hand-off mid-review. In the component, gate mutating controls on `busyOrLocked`, never on `busy` alone — `locked` can only be true in client mode (the staff workspace payload never carries `editable`), so it is safe to apply broadly. Leave read-only affordances live; the banner promises the client can still read. Known accepted gap: `add-bucket` is UI-disabled only (it takes no `tax_year` and writes global vocabulary, not the client's numbers).
- **Every lock read must use the SAME lookup: latest submission for the account+year, NO `status` filter.** `coverage` used the `completed` row and could therefore contradict the banner on a same-year multi-row account. Writing to a different row than you lock on is fine; reading the lock differently is not.
- **A client-facing string must have an `it` branch — including gate text.** The portal renders every gate `detail` verbatim to the client. `lib/tax/completeness.ts` assumes gate text "stays technical/internal"; that assumption is false at the render site. Gate 6 is rendered via `gateSixText()`; the other gates are still English-only on the portal (pre-existing, open decision).
- **`resubmitted` IS client-editable — never "tidy" it out of `CLIENT_EDITABLE` (2026-08-03 freeze).** The only states that lock a client are `under_review` (staff actively reviewing) and `confirmed`. `resubmitted` reads like a lock and is not one: it means the CLIENT just handed data back and nobody has started. Omitting it froze five accounts out of the whole tax-financials screen AND their wizard for over a week, because all eight write routes and `decideTaxWizardEligibility` share this one predicate. Mutation-proven guards in `tests/unit/review-status.test.ts` + `tests/unit/wizard-eligibility.test.ts`.
- **NEVER read `draft.pnl.uncategorizedCount` alone to decide whether work is outstanding.** On every CLIENT-side draft the `defaultUncategorizedBySign` policy FORCES that field to 0 while the undecided rows are folded into income/expenses under the bucket the AI suggested. That is precisely how the portal came to tick "All transactions are categorized" over 394 unanswered items. Use `uncategorizedCount + foldedUncategorizedCount` (exactly one is non-zero by construction; the pair works for the staff workspace and the portal alike), and describe folded rows as **INCLUDED in** the totals, never "excluded" — the excluded wording belongs only to the folding-off path.
- **No gate blocks confirm (2026-08-03, Antonio).** Gate 6 was the last `blocking` gate and is now informational, so `can_accept_as_is` is always true and `canConfirm(gates)` always passes. A client may confirm with items undecided — *"we just suggest but they know the truth"*. What still refuses a confirm lives OUTSIDE the gates: unanswered/incomplete **coverage** questions and in-flight ingestion. If you add a barrier, add it there and say which one is blocking — the old UI hint blamed the categorization queue for a coverage block and sent clients to the wrong list.
- **A refusal must be visible where the finger is.** This screen is ~2,500 lines; an error shown only in the top strip is invisible to a client working the queue at the bottom (Bence Koncz reported "nothing happened" while the server refused every tap). Any new failing action here sets `cardError` alongside the page-level `error`. Related: the page needs the lock state from the API (`editable`) to warn BEFORE the tap — and that lookup must mirror the write routes' query (latest submission, no `status` filter), or the banner and the 409 can disagree.
- **Money fields can never be negative — domain minimums live in the shared field layer (2026-07-15, Rocco Papotti incident).** Both tax-form pages rendered currency inputs as bare `type=number step=0.01` with NO `min` — a scroll-wheel/spinner decrement from 0 submitted `-0.03`/`-0.04` as "Personal Expenses Paid Through LLC" for Levante + Venere Consulting (verified client-side accidental input by a full Council pass; the system stored it faithfully, no code computes/prefills that field). Fix: `FieldConfig.min` + `fieldMin()`/`violatesFieldMin()` in `lib/types/tax-form.ts` — **currency ⇒ min 0 by type default**; both twin pages (`app/tax-form/[token]/[code]/page.tsx`, `app/tax-form/[token]/page.tsx`) enforce it in `isStepValid` (blocks Next even on optional fields) + render the `min` attr + an inline EN/IT error; the portal wizard mirrors it (`min: 0` on the four money fields + `rpt_amount` in `wizard-configs.ts`, `belowFieldMin` gate in `wizard-client.tsx`, inline error in `wizard-field.tsx`). NEVER add a money input without a `min` — use the shared helpers, not per-page JSX checks. Regression net: `tests/unit/tax-form-field-min.test.ts` (asserts every currency field's effective min ≥ 0). NOTE: there is deliberately NO DB constraint — two prod rows already hold negatives and later review-flow UPDATEs would re-validate and 500 (AI-architect finding); data repair for the Rocco rows happens after the client confirms real figures.
- **The tax-form completion auto-chain is client-fired; the SWEEP CRON is its safety net (2026-07-16).** The external form triggers `/api/tax-form-completed` from the browser, fire-and-forget with a swallowed catch — in spring 2026, 5 of 12 external submissions silently got no team email/review dispatch (Rocco Papotti incident; the 5 were handed to Luca via team chat, NOT auto-refired). `/api/cron/tax-completion-sweep` (every 30 min) re-fires the chain server-side for external rows where `status='completed' AND completed_at ≥ 2026-07-16 AND completed_at older than 30 min AND review_status IS NULL AND token NOT LIKE 'portal-%'` — pure predicate + result parsing in `lib/tax/completion-sweep.ts` (unit-tested). **DRY-RUN BY DEFAULT: set `TAX_COMPLETION_SWEEP_DRY_RUN=false` on prod to go live; sandbox stays report-only.** Every find posts a **⚠️ team-chat alert to `td-taxreturn`** (fallback `general`) @mentioning Luca — one alert per submission for watch-mode candidates and gave-up rows (`financials_meta.completion_sweep_alerted` stamp prevents 30-min repeats), every rescue/failed-attempt alerts as it happens; a failed post never fails the sweep (logged as `alert_failed`). Cap 3 fires/run; per-row attempt counter in `financials_meta.completion_sweep_attempts` (incremented BEFORE each fire, max 3 then alert-only via `reportSystemError`); success = the response `results[]` shows the `review_status` step ok (the route ALWAYS answers HTTP 200 — never trust the status code); target URL via `getInternalBaseUrl()` (NEVER the hardcoded `INTERNAL_BASE_URL` — a sandbox cron would fire PROD chains). **INVARIANT the predicate leans on:** for external rows, the route's step 4C is the sole first writer of `review_status`; the portal wizard sets `review_status` synchronously at submit, never writes `completed_at`, and mints `portal-` tokens — if any of that changes, revisit the predicate. **Known limits (accepted, documented):** step 4C runs BEFORE Drive save + P&L, so a chain that dies after 4C is invisible to the sweep (email+dispatch are the critical steps); a refire after a partial run can duplicate the internal team email, an SD stage-history entry, and the passport-missing task (everything else in the chain is deduped — verified per step in the 2026-07-16 council pass). The route also now bails early (`skipped: already_processed`) when `review_status` is set and ≠ `revision_requested`, so a late refire can never regress an in-flight review.
- **`/api/tax-form-completed` picks the upload bucket by path prefix — NEVER hardcode it.** `tax/` prefix ⇒ portal wizard bucket (`onboarding-uploads`), else external bucket (`tax-form-uploads`) — same rule as `tax_form_review`. From 2026-06-12 to 2026-07-16 the route hardcoded `onboarding-uploads` (commit `77e10bbd` over-applied the portal fix), which would have failed EVERY external submission's Drive copy + P&L; zero external completions happened in that window, so no production damage — caught by the council pass before the sweep could replay through it.
- **The accountant-workflow fields are `sent_to_accountant` / `accountant_status` / `sent_to_accountant_date` / `accountant_follow_up_count`** (renamed from `india_*` on 2026-06-09, legacy columns dropped Phase 2 2026-06-10). Don't read them as a literal country status. The legacy `Sent to India` enum label still exists in the `tax_return_status` DB enum for rollback safety and is mapped defensively in `tax-return-sd-bridge.ts`, `enum-normalization.ts`, the portal queries exclusion list, and `tax.ts` `isInProgress`.
- **Never flip `app_settings.tax_season_paused` to reactivate ONE client** — that reactivates ALL on-hold returns. Use the per-SD installment reactivation (`reactivateOnHoldTaxReturns`) for a single client whose 2nd installment landed while the global pause is still on.
- **`tax_send_to_accountant` is idempotent + dry-run-first** — check the package before sending; re-send needs `force_resend=true` (idempotency ONLY — it does not bypass the document checks; that is `send_incomplete`, and a missing P&L is a hard stop regardless).
- **Never loosen the year proof in `lib/tax/pick-tax-file.ts` to "the year appears in the name".** That was the first fix attempt and it is broken: a revision date or a company name containing a year both "prove" the wrong year, and the file gets emailed and filed. The year must be the ONLY year in the name (company name stripped first), or proven by the year folder.
- **Status (a long string) and the workflow-progress booleans are separate** — update the right one; don't infer one from the other.
- **Prerequisites for the accountant send**: the tax form must be completed and the documents must already be in the Drive `3.Tax/{year}/` folder, or the package will be incomplete.
- **Upload bucket is path-dependent (2026-06-10 bug fix).** The PORTAL wizard uploads ALL tax files to the shared `onboarding-uploads` bucket (`app/api/portal/wizard-upload[-url]/route.ts`, path scheme `tax/{account_id}/...`). The EXTERNAL public tax form uploads to `tax-form-uploads` (path scheme `{slug}-{year}/...`). `FORM_CONFIGS.tax_return.bucket` defaults to `tax-form-uploads` (external), so `saveFormToDrive("tax_return", ...)` MUST be passed `opts.bucket="onboarding-uploads"` for portal submissions — otherwise `copyUploadsToDrive` downloads from the wrong bucket, EVERY file fails (`0 files copied`), and because the bank statements never reach `3.Tax/{year}/`, step 7's statement parse finds nothing and produces no P&L/Balance Sheet. The portal handler (`tax-form-setup.ts` step 6) hardcodes the override; `tax_form_review` (`tax.ts`) infers it from the path prefix (`tax/` → portal). This was the root cause of MMLLC portal submissions arriving with no attachments and no P&L in June 2026.
- **Statement parsing: Wise fast path + AI fallback + zip (2026-06-10).** `parseBankStatement` accepts PDF, CSV and `.zip`. Wise CSVs/PDFs use the free hand-coded parser; everything else (Mercury/Relay/Chase/any bank) — and any parse that yields 0 rows — goes to Claude-based extraction (`lib/bank-statement-ai-extract.ts`). **Never trust an unreconciled AI extraction for a filing**: check `reconciliation.reconciled` — `false` = the transactions don't add up to the statement's own closing balance, human review required; `null` = statement printed no balances / multi-currency / archive partially unverifiable. Truncation (`max_tokens`) is reported in `errors` as TRUNCATED. Kill-switch: `BANK_STATEMENT_AI_DISABLED=true`. Needs `ANTHROPIC_API_KEY` (set on prod; sandbox set 2026-06-10 via CLI after dashboard save silently failed on a stuck var).
- **AI extraction reads what the document actually is — review the bank_name it reports.** Real case (2026-06-10): Nexo Agency's only "bank statement" upload was a **Kraken 1099-DA crypto form** ($1.04M gross proceeds from stablecoin disposals — NOT revenue). The extractor labeled it `bank=Kraken (Payward Interactive)`. Feeding it to the P&L as income would have misstated the return; a human must reclassify or request real bank statements.
- **`portal_messages.sender_id` is NOT NULL** — any code inserting a system-generated portal message must use the zero-UUID placeholder `"00000000-0000-0000-0000-000000000000"`, not `null`. Passing `null` violates the constraint and the insert silently fails (supabase-js default mode returns an error object, not a thrown exception). Convention documented in `lib/portal/chat-events.ts`. Fixed in `app/api/crm/tax-review/action/route.ts` and `app/api/portal/wizard-submit/route.ts` on 2026-06-10.
- **PDF summary: label/value column overlap (2026-07-02 bug fix).** `generateFormSummaryPDF` used to draw every value at a FIXED x=200 while labels start at x=50 (x=70 nested) — any label wider than the column (e.g. "Personal Expenses Paid Through LLC (USD):" = 192pt at 9pt bold) got overprinted by its value, making the number unreadable (reported by the accountant for an SMLLC package; also hit every flattened `related_party_transactions_N_rpt_*` row in "Additional Information"). Fix: all four field render sites now go through one `drawFieldRow` closure — value starts at `valueStartX()` (aligned x=200 when it fits, else after the measured label + 8pt gap), and values that can't fit beside the label wrap below via `wrapByWidth()` (measured-width wrap, hard-breaks giant words; replaces the old 80-char count wrap). Layout constants in exported `PDF_LAYOUT`. Regression net: `tests/unit/pdf-field-layout.test.ts` parses generated PDFs with pdfjs and asserts no two same-line text items intersect — NEVER add a `drawText` for a field value at a hardcoded x; use `drawFieldRow`.
- **PDF summary: WinAnsi character encoding (2026-06-12 bug fix).** `pdf-lib` StandardFonts use the WinAnsi encoding — they only support U+0000–U+00FF (Latin-1). Client names or form values containing characters outside that range (e.g. Maltese ħ/Ġ/Ċ/Ż, Arabic, CJK, emoji) crash `generateFormSummaryPDF` with `WinAnsi cannot encode "ħ" (0x0127)`. Fix: `sanitizeForPdf()` in `lib/form-to-drive.ts` (exported, has unit tests in `tests/unit/sanitize-for-pdf.test.ts`) maps known Maltese substitutions (ħ→h, Ġ→g, Ċ→c, Ż→z) and replaces everything else with `?`. Applied to all four user-data `drawText` call sites in `generateFormSummaryPDF`. If a new character set is seen in the future, add explicit rules to `sanitizeForPdf` before the fallback `?` catch-all.
