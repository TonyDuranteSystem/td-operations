## What it is
TWO separate client journeys share one table (`onboarding_submissions`) and, since 2026-09-21, one staff review screen. Both are for a client bringing an **existing LLC** to TD (as opposed to formation, which creates a brand-new LLC).

1. **The real journey (primary, what actually happens today):** a lead's offer is sent → a portal login is auto-created for them at that moment → the client signs, pays, AND fills out the onboarding data, all inside that one logged-in portal session (`/portal/wizard?type=onboarding`). No separate link, no separate form — everything happens inside the portal the client is already in. `onboarding_submissions.source = 'portal_wizard'`.
2. **The manual token-link tool (secondary, staff-initiated):** an older, separate mechanism (`onboarding_form_create` → a standalone link with a token + access code, no portal login involved) that staff can still use for edge cases. `onboarding_submissions.source` is null for this path.

**Do not assume the manual tool is "the" onboarding flow** — it was mistakenly treated as the whole system for months in this doc and in earlier work sessions. The real client journey is #1.

## Lifecycle (real journey, `source='portal_wizard'`)
1. **Offer sent** → `autoCreatePortalUser` gives the client a portal login immediately, independent of any account (tied to their Contact record).
2. **Sign + pay + fill out onboarding data**, all inside `/portal/wizard?type=onboarding` in that same portal session.
   - For a client's FIRST/only company, the wizard resolves their existing account normally.
   - For a returning client bringing a SECOND (or third+) already-existing company: there is NO lead for this — staff create the offer directly on the client's Contact record. The link MUST carry a verified `?offer=<offer_id>` (the offer's own id, since every offer has one whether or not a lead started it) or the wizard has no way to tell this apart from an existing company — see the 2026-09-22 entry above. All link sites that matter (the sidebar's dynamic link, the activation/welcome notification, the reminder cron, the switcher) already do this correctly, and this same `?offer=` anchor is now used for a FIRST-time onboarding's link too (unified mechanism, not a separate `?lead=` path).
   - The multi-owner (MMLLC) question, member step, and SS-4 responsible-party picker are driven entirely by the client's SIGNED CONTRACT (`contracts.llc_type`) for a new company — never a code default, never guessed. If the contract can't be resolved, the client is asked once directly (never silently defaulted).
3. **Submission saved, job enqueued, job stops immediately** — `handleOnboardingSetup` runs validation/OCR only, then checks `onboarding_submissions.reviewed_at`. If null (always true at this point), it completes cleanly with NOTHING created (no Account, no Contact link, no Drive folder, no tasks) and the row surfaces on `/onboarding-review`.
4. **Staff reviews** — opens the row, checks the submitted data and any uploaded documents, clicks Confirm. This sets `reviewed_at`/`reviewed_by` (idempotency-locked, safe against a double-click or two staff confirming at once) and re-enqueues a fresh `onboarding_setup` job.
5. **The resumed job runs the real chain** — Account creation (or update, if the company already has one), Drive folder, follow-up tasks, tax return record (if applicable). Portal tier stays at `onboarding` (NOT bumped to `active` automatically — that stays a separate, deliberate staff action). **Lease and Operating Agreement are NEVER auto-created** — a lease is a manual staff button; the OA is entirely client self-service, generated later from inside their own portal.

## Lifecycle (manual token-link tool, `source` null)
1. Staff creates a form link (`onboarding_form_create`) and sends it manually.
2. Client fills it out via the standalone link (no portal login involved).
3. Staff reviews via the SAME `/onboarding-review` screen (or the `onboarding_form_review` MCP tool) and clicks Confirm.
4. `applyOnboardingReview` (`lib/operations/onboarding-review.ts`) creates/updates the Contact and Account INLINE (synchronously, unlike the real journey's job-based creation) and upgrades tier to `active` directly.

## Business rules
- **Onboarding = existing LLC** (no formation/EIN step) — the key difference from formation, which creates the company and advances tier on EIN.
- **Staff review gate, real journey only (Antonio, 2026-09-20): nothing gets created until a staff member has reviewed the submitted data and documents and clicked Confirm.** This does not apply to the manual tool, which was already staff-initiated before the client ever saw it.
- **R102** — tier moves only through `syncTier()`. The real journey stays at `onboarding` tier after Confirm (full activation is separate); the manual tool goes straight to `active` at Confirm, matching its own long-standing design.
- **Entity type comes from the signed contract, never a code default** (Antonio, 2026-06-11, originally for formation — extended to onboarding 2026-09-21).
- **Lease = manual staff button only. Operating Agreement = client self-service only, never staff/system-created.** (Antonio, standing decision, reaffirmed 2026-09-20.)
- **R035** — always provide/review the `?preview=td` link before sending the manual tool's form to a client.

## Gotchas, invariants & past bugs
- **Don't confuse the two journeys, and don't assume the manual tool is primary.** See "What it is" above.
- **Don't confuse with formation.** Onboarding clients already have an EIN/LLC.
- **A brand-new account has no `entity_type` to read** — for the real journey's second-company case, entity type MUST come from `resolveEntityTypeForFormation`, not a default. This bit twice: once for formation (2026-06-11), once for onboarding (2026-09-21).
- **`resolveEntityTypeForFormation`'s `leadId` param is a hard pin, not a hint** — as of 2026-09-21 it queries strictly by that lead when given; before that fix it silently broadened to the whole contact and could blend in an unrelated signed contract. A client can legitimately have multiple companies with genuinely different entity types.
- **The account-resolution page logic (`app/portal/wizard/page.tsx`) has several formation-only gates that needed an onboarding equivalent** (`formationLeadId` everywhere needed a matching `onboardingOfferId`) — a new gate added for one wizard type but not the other is exactly the bug class that kept recurring across this dev job's QA rounds. Check both when touching this file.
- **A second (or third+) company for a returning client has NO lead at all — never assume one exists.** Confirmed directly by Antonio 2026-09-21: only a client's FIRST onboarding is lead-based; every one after that is an offer created straight on the Contact. Any code that keys onboarding off `lead_id` alone will silently no-op for this case — use `offer_id`.
- **The staff-document-visibility ownership-prefix list has bitten three separate times for missing one identifier variant** (`account_id`, then `offer_id`, then discovered `lead_id` had never been there at all) — `app/api/onboarding-review/[id]/documents/route.ts`'s `ownedPrefixes` must cover every value `wizard-client.tsx`'s upload `identifier` fallback (`leadId || offerId || accountId || contactId`) can produce, or documents silently vanish from staff's view with a scary warning instead of an error.
- **`onboarding_form_review` (manual tool) sets `ra_renewal_date = today`** (treats onboarding as the RA-change date).
- **Tier upgrade is via `syncTier` only** (R102) — never set `portal_tier` by hand, and watch for the `accounts` table's raw column DEFAULT of `'active'` on INSERT, which bypasses `syncTier` entirely unless explicitly corrected right after account creation (both journeys' account-creation code now does this).
- Shares the welcome-package job + form infrastructure with formation — changes there affect both.
