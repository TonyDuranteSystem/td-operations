## What it is
The automated safety net that keeps a session from breaking production or skipping discipline. Three kinds: **Claude Code hooks** (fire on session/tool events), **git pre-push/pre-commit gates**, and **code-level guards**. Plus the 35 policy rules (R-rules) in CLAUDE.md.

## Claude Code hooks (wired in `.claude/settings.json`)
- **PreToolUse:**

- **Worktree auto-isolation** (`scripts/worktree-auto-isolate.sh`, SessionStart): when a session starts in a LINKED git worktree, it ensures that worktree has its own private local DB so concurrent sessions don't collide on the shared cloud sandbox. Fail-soft (any error → exit 0, never blocks a session); skips the main checkout instantly; idempotent (skips if already local); RAM-capped (`TD_LOCAL_STACK_CAP`, default 4 — at/over the cap a new worktree stays on the shared sandbox); seeds the worktree's sandbox `.env.local` from the main checkout, then provisions in the BACKGROUND via `env-up.sh` (the session opens immediately; the worktree is fully isolated from its NEXT session on). Per-worktree state in `.auto-isolate.status` / `.auto-isolate.log` (gitignored).
- **Worktree stack CLEANUP** — two layers. (1) Immediate: when a worktree's job ships (PR merged) the session OFFERS to tear it down (`env-down.sh --purge`) per **R110** — never auto-runs without confirmation. (2) Backstop: `scripts/worktree-stack-sweep.sh` runs backgrounded from the auto-isolate SessionStart hook on EVERY session (even the main checkout).

  **Orphan detection — THREE detectors** (rewritten 2026-07-18 after a leak; shared helpers in `scripts/lib-local-stacks.sh`):
  1. **Marker** — `env-up.sh` records the absolute worktree path in `~/.td-local-stacks/<name>/.worktree-path`; the sweep reclaims when that path no longer exists. Exact and clone-agnostic. Still the primary test.
  2. **Git fallback** — for a stack whose marker AND config are BOTH missing (the signature of a half-finished purge). Since a stack is named after its branch, `git worktree list` can still say whether any live worktree maps to it. Deliberately narrow: a healthy stack always has its config, so this can never touch one in use — which also keeps it safe when run from a different clone.
  3. **No directory at all** — containers running under a `tdlocal-*` compose project with no stack directory anywhere. Nothing can manage those.

  **NEVER delete the directory before the containers are confirmed gone** (`stack_remove_dir_if_stopped`). This is the rule the old code broke.

  ⚠️ **Docker TRUNCATES the compose project label at 40 chars**, so `--filter label=...=tdlocal-<name>` matches NOTHING for a long stack name — silently. Always compare via `label_matches_stack`, never by string-stripping the label: naive stripping yields a name matching no directory and no worktree, which would classify the LONGEST-named (healthy, in-use) stacks as orphans and delete them.

  **THE INCIDENT (2026-07-18)** — the previous version of this section claimed "closed worktrees never leak their ~8 GB stacks". That was false. Three stacks were found running with ~1 GB each, belonging to worktrees that no longer existed, and nothing could reclaim them. Chain: a purge ran `supabase stop` with its failure swallowed (`|| true`, output to `/dev/null`) and then deleted the stack directory **unconditionally**; when that stop silently did nothing (Docker down, or a config already gutted by an earlier half-purge) the containers survived while their config was destroyed. A container with no config is unmanageable — `supabase stop` in an empty directory exits 0 and does nothing, so every later attempt "succeeds" while the containers keep running, and their `unless-stopped` policy revives them on every reboot. The sweep could not see them either, because the same deletion removed the marker it keys on. In short: the cleanup destroyed both of the things that could have reclaimed the memory. ~3 GB was recovered by hand and by the rewritten sweep.

## Git gates (`.husky/pre-push`, in order)
1. **Sandbox-first guard** — if pushing to `main` and `.vercel/project.json` is the production project, block unless `ALLOW_PRODUCTION_PUSH_AFTER_SANDBOX_QA=1`.
2. Remote-ahead check (another machine pushed) → rebase first.
3. Hardcoded client-facing domain check (R012).
4. Hardcoded `/Users/...` path check in hook scripts.
5. ESLint (max-warnings 0) on changed files.
6. Schema-drift check (`npm run gen:types` vs committed types).
7. **Code↔PRODUCTION database contract** (`npm run check:db-contract`) — see below.
8. Unit tests → integration tests → full build.
9. **R107 System Reference Library freshness** (`scripts/check-system-docs-freshness.sh`) — blocks if documented subsystem code changed without its doc.
Pre-commit (`lint-staged`) runs ESLint on staged files with zero-warning tolerance.

## The code↔database contract (4 layers, zero credentials)
The code must never write a value the database will reject — a rejected write does not shout, it returns an error the caller may discard, and the feature silently does nothing. That is exactly how the bank-feed review queue stayed empty for months (see `banking-bankfeed.md`).

| Layer | What it compares | Blocks? | Credential |
|---|---|---|---|
| `db/constraints.prod.json` | production's 190 CHECK constraints, committed + **checksum-verified against the database that produced them** | — | none |
| `npm run check:db-contract` (pre-push + CI) | the code's declared vocabularies ⟷ **that file** | **YES** | **none** — it is a file comparison |
| `npm run check:db-contract:live` (CI) | the code ⟷ **live sandbox**, and sandbox ⟷ production's snapshot on every registered contract | **YES** | existing `SANDBOX_*` secrets |
| `lib/db-contract-monitor.ts` (daily, inside the `check-wire-payments` cron) | the deployed code + the snapshot ⟷ **LIVE PRODUCTION** | no — raises a **dev-board job** + `system_errors` row | none (the app already has service-role access to its own database) |

- **Why a committed file and not a live read at push time:** a live read means a production Postgres password in CI — a new credential and a new exposure surface, to read a list of allowed strings. The previous design did exactly that, the secret was never set, and the step warned + exited 0: **a green checkmark enforcing nothing.** An unarmed gate is worse than none; it manufactures the feeling of coverage.
- **Why the file can be trusted:** Postgres fingerprints its own constraint set (`md5(string_agg(conname || '|' || pg_get_constraintdef(oid), E'\n' ORDER BY conname))`) and we recompute the same digest over the file. Editing the file to silence a failing gate breaks the checksum and **fails the push**. The only honest way to change it is to change production and run `npm run snapshot:constraints` (which **refuses to run against any database but production** — regenerating it from sandbox would gate the code against sandbox's rules, which is the original hole).
- **Why the monitor lives inside the payments cron:** a standalone cron can be quietly unscheduled — this repo has the precedent (the error-auto-audit loop). One that runs inside reconciliation cannot be switched off without switching off payments.
- **Why the alarm goes to the dev board:** `/system-health` is a page someone must choose to open. Nothing obliges them to — and "a signal nobody was forced to look at" is the whole incident. The dev board prints at the start of every session.
- **The registry is self-maintaining:** any CHECK-constrained column in the snapshot that isn't registered in `CONSTRAINT_CONTRACTS` (and isn't in the frozen `UNAUDITED_BASELINE` ratchet or `NOT_A_VOCABULARY`) **fails the check**. "Remember to register new columns" is a note; this is a gate.
- **⚠️ The baseline is a RATCHET, not an amnesty** — 165 constrained columns the code has never been verified against. It may shrink; it must never grow. (It was originally frozen from **sandbox** — missing 76 of production's columns and listing 10 that don't exist there. The same wrong-database error had reproduced inside the tool built to prevent it. Re-frozen against production 2026-07-14.)

## Gotchas, invariants & past bugs
- **⚠️ CRITICAL (R104): `git push origin main` is NOT unconditionally blocked.** The repo is wired to BOTH the sandbox AND production Vercel projects, and `bash-production-guard` only blocks the push when `.env.local` holds the prod URL (not set during dev). **So pushing to main = deploying to production. Discipline is the only guard — NEVER push to main without Antonio's explicit "ship it."**
- **⚠️ MCP tools bypass the sandbox enforcement entirely (R096).** Production is reachable via MORE than one connection name — `af7d85f2-*` (the claude.ai OAuth connector) AND static-bearer connections registered per-machine (`td-ops-prod` hand-added, `td-ops-production` from `scripts/setup-prod-mcp.sh`). All are hardwired to PRODUCTION. `.env.local`, `.vercel/project.json`, and the `supabase-admin` ref check do NOT apply to MCP calls — every production `execute_sql` hits production. The only MCP-side guard is `production-write-guard.sh`, which now covers ALL of these (it gates every non-sandbox `execute_sql`). For sandbox DB work use `mcp__td-ops-sandbox__*` or `psql`.
- **PAST BUG (2026-06-07): the write-guard was name-blind to new prod connections.** Both the `settings.json` matcher and the script's internal check were hardwired to `mcp__af7d85f2.*__execute_sql`. When a production connection was hand-added on the Mac Mini under the name `td-ops-prod`, its writes/DDL sailed past the brake — and dispatch/phone Code sessions run on that real machine. Fix: flipped to fail-safe — guard fires on every `execute_sql` and exempts ONLY sandbox, so any current/future production name is gated by default. (`scripts/setup-prod-mcp.sh`'s header still claims the guard covers it "automatically"; that was only true after this fix.)
- **Production DDL via `execute_sql` is blocked outright** (R105) — even with a `migration:` reason on the prod MCP tool. The real promotion path is running the migration in the Supabase SQL editor. (CLAUDE.md R105 wording is stale on this — flag/fix it.)
- `verify-before-edit` will block your first edit until you've read `session-context`.
- The Stop `r093-verifier` can re-open a turn if it finds an unsupported external-state claim — write only what the session's tool output supports.
