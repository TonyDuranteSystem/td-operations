## What it is
A direct, realtime messaging channel between TD staff and an external managed **partner** (first user: Cris). Staff use it from inside the CRM; the partner uses a confined standalone page. It is a generic conversation model (conversations → participants → messages), not tied to a specific client/account.

## Business rules
- A partner reaches the channel only if authenticated as `role='partner'` **and** their `client_partners.partner_scope` array contains `td_communication`. Default-deny otherwise.
- A `role='partner'` user is **confined by middleware** to `/collab` + `/api/conversations` — they can never reach the CRM dashboard.
- Staff (any dashboard user) see and post to **all** conversations. A partner sees and posts to **only their own** (`partner_id = their client_partners.id`).
- Messages are soft-deleted, never hard-deleted (R100). The server never returns soft-deleted bodies; the realtime UPDATE event drops the row live.

## How it's built
- **Tables** (migration `scripts/migrations/20260627-1400-comm-conversations-foundation.sql`):
  - `comm_conversations` — `subject`, `status`, `partner_id` → `client_partners`, `created_by_*`, `last_message_at`.
  - `comm_participants` — membership + per-participant `last_read_at`; unique `(conversation_id, participant_type, participant_id)`. Staff `participant_id` = `auth.uid()`; partner `participant_id` = `client_partners.id`.
  - `comm_messages` — `sender_type` (staff/partner), `sender_id/name`, `body`, `deleted_at/by`.
  - `client_partners.partner_scope text[]`.
  - Namespaced `comm_*` because the generic `conversations` table is the legacy Airtable/Fireflies comms log.
- **RLS / realtime:** `comm_messages` has **RLS ON** + a **participant-scoped SELECT policy** (`comm_messages_participant_select`) and is in the `supabase_realtime` publication, so postgres_changes deliver a row only to its participants (a partner sees only their own threads). `comm_conversations` / `comm_participants` are RLS-on with no policy (not in the publication). All authoritative reads/writes use the service role (bypasses RLS) after an explicit auth check in the API. **Staff are joined as a participant when they OPEN a thread** (`ensureParticipant` on GET messages) — that is what makes realtime deliver to them under the strict policy.
- **The policy calls a `SECURITY DEFINER` helper `public.comm_can_read(conv, uid, contact)`** — NOT an inline subquery. The participation check reads `comm_participants` + `client_partners`, which are RLS-protected; an inline subquery in the USING clause runs as the `authenticated` role, sees zero rows, and denies EVERYONE — including realtime delivery. Caught in sandbox QA (2026-06-27): Cris received none of his own messages until the policy was switched to the SECURITY DEFINER helper (runs as owner, bypasses RLS on those two tables). EXECUTE granted to `authenticated` only. Verified end-to-end on the sandbox deploy: partner + staff realtime delivery PASS, cross-conversation isolation PASS, middleware confinement PASS.
- **Middleware confinement:** `middleware.ts` has a `role==='partner'` branch that allows only `/collab`, `/collab/*`, and `/api/conversations*`, redirecting everything else to `/collab`. Without it, `role='partner'` (≠ 'client') would pass the dashboard guard and expose the whole CRM.
- **Auth helpers:** `lib/partner-auth.ts` (`isPartner`, `getPartnerForUser`, `getCommPartner`). `lib/td-communication/queries.ts::resolveCommParticipant` maps a user → `{ type:'staff'|'partner', id, name }`.

This is what triggers the client-side reveal.
- **Concept images are gated end-to-end.** `listReleasedConceptsForClient(enrollmentId)` (`disclaimer-queries.ts`) returns released (`released_at IS NOT NULL`), non-deleted, IMAGE deliverables grouped by concept, each with a signed **preview URL only** (no forced-download — drafts stay download-blocked). The server page passes **no image URLs**; the reveal fetches them from the API, which returns `{ disclaimer_required: true }` (no URLs) until accepted. CSS protection (`select-none`, `pointer-events-none`, blocked context menu, `draggable=false`) is a deterrent only — a signed URL is always fetchable from devtools.
- **Client responses** (`concept-actions.ts`, service-role): `approveConcept` flips status → `approved` (optimistic `.eq('status', current)`) + posts **"Client approved the concept"**; `requestDiscussion` posts **"Client wants to discuss the concept"** (no status change). Both post as `SYSTEM_STAFF` into the project's `comm_conversations` (the client has no seat in `comm_messages`), creating the conversation idempotently via `ensureEnrollmentConversation` if `conversation_id` was null.
- **Client API** (all under `/api/portal/td-communication/`, **client-only** — `isClient` gate, mirroring the `tax-financials/attest` consent precedent; staff/admin may NOT accept/approve on the client's behalf): `GET concept` (gated concept list + company name), `POST disclaimer` (logs acceptance; IP/UA via `lib/esign/request-meta.ts` `clientIp`/`userAgent`, never from the body; idempotent `{already}`), `POST approve` (`{decision:'approve'|'discuss'}`; requires accepted disclaimer). The client never supplies an enrollment id — `resolveClientActiveEnrollment(user)` (`client-access.ts`) resolves THEIR OWN active enrollment by identity (no IDOR). No middleware change (clients pass `/api/portal/*`; partners are confined away from it; the view-as read-only lock correctly blocks these POSTs).
- **UI** `components/td-communication/concept-reveal.tsx` (`'use client'`, bilingual EN/IT inline): disclaimer card (checkbox + disabled-until-checked "View My Brand Concept") → dark "Presenting your brand concept…" overlay (~1.5s) → logo fades in `scale .95→1` on a white card + "Created by TD Communication for {company}" → concept tabs (A/B/C) + "I Love It" / "Let's Discuss". Approved enrollment shows the approved banner + concept, no action buttons. Respects `prefers-reduced-motion`. Already-accepted reload skips the animation.
- **Portal page** `app/portal/td-communication/page.tsx`: when `canRevealConcept(enrollment.status)`, returns `<ConceptReveal>` (with server-checked `disclaimerAccepted`, locale-resolved text, resolved company name) **instead of** the landing. Post-`delivered` (terminal) reverts to the marketing landing — the concept disappears from the client's view (spec covers only concept_ready/approved). Locale uses `getLocale(user)` (consistency with the page), not `contacts.language`.

## Phase 10 — SLA / deadline system
Projects now carry a real, automatic deadline and a professional SLA layer. Before this, the board read `metadata.deadline`, a value **no app code ever wrote** (seed-only) — so projects effectively had no deadline, no compliance metric, and nothing flagged an overdue project.
- **Column** `td_comm_enrollments.deadline_at timestamptz` (migration `20260629-1800-td-comm-deadline-at.sql`, sandbox applied; prod promotion pending). Backfill set `created_at + delivery_days` for every non-`enrolled` row (fallback `default_sla_days` → literal 7 for a missing package row / null `delivery_days`, e.g. `brand-identity`).
- **Set once, on the first exit from `enrolled`** (never overwritten): `ensureDeadlineAt(enrollmentId, baseISO)` in `lib/td-communication/sla.ts` reads the row's `deadline_at` + `package_slug`, resolves delivery days (`resolveDeliveryDays`: package `delivery_days` → `default_sla_days` → 7), and writes `computeDeadlineAt(base, days)` under a `.is('deadline_at', null)` TOCTOU guard. Called from THREE chokepoints so no path leaves a project deadline-less: `submitBrandAudit` (base = `form_submitted_at`), `setEnrollmentStatus` (manual, base = now, when entering any non-terminal non-`enrolled` status), and the deliverables `advanceStatus` (base = now, when a deliverable advances a still-`enrolled` project). Never throws — a failed deadline must not fail the caller's write.
- **Effective deadline** = `deadline_at ?? metadata.deadline` (computed in `pipeline-queries.ts::withDerived`); `metadata.deadline` is the legacy fallback for seed rows only.
- **Pure helpers** (`pipeline.ts`, unit-tested in `tests/unit/td-communication-sla.test.ts`): `computeDeadlineAt` (base + N days, null-safe), `isSlaTracked(status)` = NOT `delivered`/`cancelled` (terminal projects show no SLA dot/countdown/overdue tint — fixes the pre-existing "delivered but overdue" noise on all four surfaces), `slaSummary(enrollments, now)` → `{onTime, overdue}`. `deadlineLabel` reworded to "Due in N days" / "Due tomorrow" / "Due today" / "Overdue by N days". `slaIndicator` unchanged (red overdue / yellow today-or-tomorrow / green) — already matched the spec.
- **Overdue alerts** (`postOverdueAlerts`, no cron): called fire-and-forget from BOTH board server components (`/collab`, `/dashboard/td-communication`) after `listEnrollments()`. For each SLA-tracked, overdue, conversation-linked enrollment not yet alerted, it **claims** the row (`UPDATE … WHERE metadata->>'sla_alert_sent' IS NULL OR <> 'true'`, expressed in supabase-js as `.or('metadata->>sla_alert_sent.is.null,metadata->>sla_alert_sent.neq.true')` — the `.is.null` clause is REQUIRED, a plain `.neq('…','true')` would drop never-alerted rows where the key is NULL) then posts `⚠️ Project {name} is overdue by X days` as `SYSTEM_STAFF`. Claim-before-post = at most one alert even across two near-simultaneous renders; whole thing try/catch so alerting never breaks a render.
- **Admin compliance** (`computeEnrollmentStats(enrollments, now)` — now takes `now`): `slaCompliancePct` = delivered-on-time / delivered-with-a-deadline-and-`delivered_at` × 100 (on-time = delivered **calendar day** ≤ deadline day, via `daysRemaining`, so a few hours past midnight isn't "late"); null when none qualify. `overdueCount` = SLA-tracked rows currently past deadline. The Enrollments tab renders an SLA-compliance chip (green >90 / amber 70–90 / red <70 / neutral null) + an Overdue chip, and tints overdue rows red.
- **Board** (`pipeline-board.tsx`, shared by `/collab` and the CRM Projects tab): overdue cards get a red border + tint; an "X on time · Y overdue" summary sits above the columns; SLA dot/countdown render only when `isSlaTracked`.
- **`SYSTEM_STAFF`** moved from `brand-audit.ts` to `queries.ts` (the neutral hub) and re-exported from `brand-audit.ts`, so `sla.ts` can post system notices without a `brand-audit ⇄ sla` import cycle.
- **Known gaps (deliberate):** no package-edit UI, so a later package change can't retro-move a frozen deadline (snapshot-at-start). A staff project that goes straight to `delivered` without ever leaving `enrolled` gets no deadline (it's already done). Overdue alert claim does a read-merge-write of `metadata` — a concurrent edit to another `metadata` key in the same instant could be clobbered (low-stakes, internal, rare).

## Gotchas, invariants & past bugs
- **`role='partner'` is load-bearing AND dangerous.** It lets the partner past the middleware dashboard guard (good) but, without the confinement branch, would expose the entire CRM (bad). Both behaviours live in `middleware.ts`. Existing partners that log in as `role='client'` are unaffected.
- **RLS-gated realtime is a NEW pattern here.** Unlike `portal_messages` (RLS off), `comm_messages` relies on the SELECT policy for delivery. If the policy is wrong, postgres_changes silently deliver nothing — must be browser-verified. The policy resolves a partner via `auth.jwt()->'app_metadata'->>'contact_id'`, so the partner's auth user MUST carry `contact_id` in app_metadata.
- **Provisioning is separate from code.** Creating Cris's `role='partner'` auth user (with `contact_id`), his `client_partners` row, and `partner_scope = '{td_communication}'`, plus promoting the migration to production, are pending Antonio's approval.
- **The login door (`app/portal/login/page.tsx`) admits partners.** The page previously hard-rejected any non-`client` role ("This account does not have portal access"), so a `role='partner'` user could authenticate but never get past login — Phase 1 shipped `/collab` + confinement but no working door (Cris was never login-tested). Fixed in Phase 2: the email-login path admits `client` OR `partner` and routes a partner straight to `/collab` (middleware then keeps them there; `/collab` still gates on the `td_communication` scope). Staff teammates still use the username path. Caught in Phase 2 browser QA.
