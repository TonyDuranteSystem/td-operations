## What it is
A direct, realtime messaging channel between TD staff and an external managed **partner** (first user: Cris). Staff use it from inside the CRM; the partner uses a confined standalone page. It is a generic conversation model (conversations → participants → messages), not tied to a specific client/account.

## Business rules
- A partner reaches the channel only if authenticated as `role='partner'` **and** their `client_partners.partner_scope` array contains `td_communication`. Default-deny otherwise.
- A `role='partner'` user is **confined by middleware** to `/collab` + `/api/conversations` — they can never reach the CRM dashboard.
- Staff (any dashboard user) see and post to **all** conversations. A partner sees and posts to **only their own** (`partner_id = their client_partners.id`).
- Messages are soft-deleted, never hard-deleted (R100). The server never returns soft-deleted bodies; the realtime UPDATE event drops the row live.

## How it's built
- **Tables** (migration `scripts/migrations/20260627-1400-comm-conversations-foundation.sql`):
  - `comm_conversations` — `subject`, `status`, `partner_id` → `client_partners`, `created_by_*`, `last_message_at`.
  - `comm_participants` — membership + per-participant `last_read_at`; unique `(conversation_id, participant_type, participant_id)`. Staff `participant_id` = `auth.uid()`; partner `participant_id` = `client_partners.id`.
  - `comm_messages` — `sender_type` (staff/partner), `sender_id/name`, `body`, `deleted_at/by`.
  - `client_partners.partner_scope text[]`.
  - Namespaced `comm_*` because the generic `conversations` table is the legacy Airtable/Fireflies comms log.
- **RLS / realtime:** `comm_messages` has **RLS ON** + a **participant-scoped SELECT policy** (`comm_messages_participant_select`) and is in the `supabase_realtime` publication, so postgres_changes deliver a row only to its participants (a partner sees only their own threads). `comm_conversations` / `comm_participants` are RLS-on with no policy (not in the publication). All authoritative reads/writes use the service role (bypasses RLS) after an explicit auth check in the API. **Staff are joined as a participant when they OPEN a thread** (`ensureParticipant` on GET messages) — that is what makes realtime deliver to them under the strict policy.
- **The policy calls a `SECURITY DEFINER` helper `public.comm_can_read(conv, uid, contact)`** — NOT an inline subquery. The participation check reads `comm_participants` + `client_partners`, which are RLS-protected; an inline subquery in the USING clause runs as the `authenticated` role, sees zero rows, and denies EVERYONE — including realtime delivery. Caught in sandbox QA (2026-06-27): Cris received none of his own messages until the policy was switched to the SECURITY DEFINER helper (runs as owner, bypasses RLS on those two tables). EXECUTE granted to `authenticated` only. Verified end-to-end on the sandbox deploy: partner + staff realtime delivery PASS, cross-conversation isolation PASS, middleware confinement PASS.
- **Middleware confinement:** `middleware.ts` has a `role==='partner'` branch that allows only `/collab`, `/collab/*`, and `/api/conversations*`, redirecting everything else to `/collab`. Without it, `role='partner'` (≠ 'client') would pass the dashboard guard and expose the whole CRM.
- **Auth helpers:** `lib/partner-auth.ts` (`isPartner`, `getPartnerForUser`, `getCommPartner`). `lib/td-communication/queries.ts::resolveCommParticipant` maps a user → `{ type:'staff'|'partner', id, name }`.
- **Pure logic (unit-tested):** `lib/td-communication/helpers.ts` — `tests/unit/td-communication.test.ts`.
- **API:** `app/api/conversations/route.ts` (GET list / POST create), `app/api/conversations/messages/route.ts` (GET list+join+mark-read / POST send). Server errors surfaced per R099.
- **UI:** `components/td-communication/conversation-chat.tsx` (shared realtime chat, subscribes to `comm_messages`), `components/td-communication/td-communication-client.tsx` (CRM list+create shell). CRM page `app/(dashboard)/dashboard/td-communication/page.tsx` → `/dashboard/td-communication`. Partner page `app/collab/page.tsx` → `/collab`. Sidebar entry in `components/dashboard/sidebar.tsx` (`id: 'td-communication'`).

## Chat feature parity (with the portal chat)
Migration `20260627-1800-comm-chat-parity.sql` adds the portal-chat columns to `comm_messages` (`attachments` jsonb, `read_at`, `reply_to_id`, `edited_at`, `original_body`, `pinned_at/by/by_type`, `kept_unread`, plus the pre-existing `deleted_at/by`). The `conversation-chat.tsx` component now matches the portal chat: **attachments** (multi-file, images+docs, drag/drop, signed-URL upload to the public `assets` bucket under `comm-attachments/<conversation_id>/` via `/api/conversations/upload-url` + `lib/td-communication/upload-attachment.ts`, image grid + lightbox), **emoji** picker, **voice-to-text** (`useVoiceInput`), **reply/quote**, **edit** (sender-only, preserves `original_body`, shows "edited"), **soft-delete** (sender or any staff; partner never receives deleted rows, staff see a tombstone), **pin** (any participant; pinned tray), **keep-unread**, **read receipts** (✓✓ via `read_at`, stamped on GET by `markMessagesRead`), drafts, date headers, jump-to-latest, link rendering. Endpoints: `message/[id]` PATCH+DELETE, `message/[id]/pin`, `message/[id]/keep-unread`, `badge` (staff sidebar unread = unread partner messages, wired through `getBadgeCounts` → sidebar item `td-communication`). **Deliberately NOT ported** (don't map to this model): portal *topic tabs* (conversations already organize threads) and *per-company entity scoping* (a partner has one identity).

## Phase 2 — Project pipeline (Cris's creative-studio dashboard)
The `/collab` page is no longer a bare chat: it is a dashboard (`components/td-communication/collab-dashboard.tsx`) with a left sidebar (**Projects** / **Chat** / **Settings**) and a top bar. The Phase 1 chat is now the **Chat** section (same `ConversationChat`, unchanged). The hero is a **read-only Kanban board** of creative projects.

- **Table `td_comm_enrollments`** (migration `20260628-1200-td-comm-enrollments-and-stages.sql`): one row per creative project. **Polymorphic subject** — `account_id` / `contact_id` / `lead_id` / `partner_id` (all nullable) + `CHECK (num_nonnulls(...) >= 1)`, mirroring `offers` / `client_threads`. So a project's client can be a company, an individual, a lead, or a partner — extensible to more actor types with one nullable column. Also: `service_delivery_id` (nullable enrichment), `client_type` (new_brand/rebrand), `package_slug`, `status` (8-value enum), `form_data` jsonb (brand brief), `conversation_id` → `comm_conversations` (the per-project chat), `metadata` jsonb (`deadline`, `notes`, `notes_updated_at`, `form_submitted_at`). RLS ON, **no policy** — service-role reads/writes only after API auth (same pattern as `comm_conversations`).
- **Stages**: 7 `pipeline_stages` rows seeded with `service_type='TD Communication'` (Package Selected … Final Delivery) — the client-facing label vocabulary for a linked SD. The **board itself groups by `enrollment.status`**, not the SD stage (SD is nullable). The 8 statuses map onto **6 columns** in `lib/td-communication/pipeline.ts::statusToColumn` (New ← enrolled+form_submitted · In Progress · Ready for Review ← concept_ready · Revision · Approved · Delivered; `cancelled` is hidden).
- **Pure logic** (`lib/td-communication/pipeline.ts`, unit-tested `tests/unit/td-communication-pipeline.test.ts`): columns, status→column map, `slaIndicator`/`daysRemaining` (UTC-calendar-day, deterministic), `deadlineLabel`, `packageLabel`, `subjectTypeLabel`, `groupBrief` (groups `form_data` into Business Description / Target Audience / Style Preferences / Color Choices / Additional Notes + Other Details + uploads, tolerant of missing keys). **Client-safe** — imports only types. SLA dot: red overdue, yellow due today/tomorrow, green on time.
- **Subject resolver** (`lib/td-communication/subject.ts`, server): `resolveSubjectsBatch` collects ids per actor type, runs ≤1 IN-query per table (no N+1), assembles with precedence **account → contact → lead → partner** and a `"Client"` fallback when a subject row was deleted (FKs are `ON DELETE SET NULL`). Mirrors `resolveEntityName` in `lib/ai-agent/client-thread-follows.ts`.
- **Server queries** (`lib/td-communication/pipeline-queries.ts`): `listEnrollments` (board), `getEnrollment` (brief: subject + linked-SD snapshot + timeline), `updateEnrollmentNotes` (merges `metadata.notes`, last-write-wins).
- **API** (`app/api/td-communication/projects/…`): `GET /projects` (list), `GET /projects/[id]` (detail), `PATCH /projects/[id]/notes`. Auth = `resolveCommParticipant` (staff OR scoped partner); errors surfaced per R099. **Middleware** allows `role='partner'` on `/api/td-communication*` (added to the confinement allowlist alongside `/api/conversations`).
- **UI components**: `pipeline-board.tsx` (6 read-only columns; cards show resolved subject name + type badge, package label, submission date, deadline countdown + SLA dot); `project-brief-panel.tsx` (right slide-in: Client Info, Brand Audit Answers, Uploaded Materials, Project Timeline, embedded per-project Chat, Private Notes). Read-only board — drag-to-advance is deferred to the deliverables manager.
- **Partner `display_title`** (cosmetic, migration `20260628-1200`): nullable `client_partners.display_title`. When set it is the partner's display identity — `app/collab/page.tsx` computes `displayName = display_title ?? partner_name` and uses it for BOTH the `/collab` header (`CollabDashboard.partnerName`) and the chat sender name (`viewer.name`, stamped onto the partner's `comm_messages.sender_name` at send, so staff see the title). Role + scope are unaffected. `getPartnerForUser` (`lib/partner-auth.ts`) reads `display_title` **resiliently**: if the column isn't migrated yet in an environment, the select errors and it retries without it (title→null), so login never breaks on deploy-order. Cris = "Communication Expert" (seeded by the migration via `partner_email`).

## Phase 3 — Deliverables manager
The brief panel gains a **Deliverables** section (`components/td-communication/deliverables-section.tsx`) where Cris/staff upload creative files, organize them by concept (A/B/C) + version (v1/v2…), mark drafts vs finals, release to the client, and soft-delete. Phase 2 deferred board status-advancement "to the deliverables manager" — Phase 3 owns it.

- **Table `td_comm_deliverables`** (migration `20260628-1600-td-comm-deliverables.sql`): `enrollment_id` → `td_comm_enrollments` ON DELETE CASCADE; `type` CHECK (logo_draft/logo_final/landing_page/brand_guide/business_card/other); `file_url` (storage PATH), `drive_file_id` (nullable future mirror), `file_name`, `file_size`, `mime_type`; `is_draft` (default true — watermark + download-block flags, **client-side enforcement is future**), `concept_number`, `version_number`, `watermark_applied`; `released_at`/`released_by`; `deleted_at`/`deleted_by` (soft-delete, R100). Indexes `(enrollment_id,type)`, `(enrollment_id,concept_number)`, partial `(enrollment_id,created_at desc) where deleted_at is null`. **RLS ON, no policy** — service-role only (same as `td_comm_enrollments`).
- **Private storage bucket `td-comm-deliverables`** (created in the same migration, `public=false`, 100 MB). NOT the public `assets` bucket — a public bucket would defeat the draft download-block + leak unreleased work. All access is **service-role signed URLs**: upload via `createSignedUploadUrl`, list/read via batch `createSignedUrls` (inline `preview_url`) + per-file `createSignedUrl(..., { download })` (forced-attachment `download_url`). No storage.objects policy (signed URLs bypass RLS). Path = `<enrollment_id>/<uuid>.<ext>`; the POST route guards `file_url` starts with that enrollment's folder.
- **Validation** (`lib/td-communication/deliverables.ts`, pure + unit-tested): an **allow-list** (`validateDeliverable`) of images (png/jpg/jpeg/webp/gif/**svg**) + design/doc (pdf/ai/psd/eps/tiff) + 100 MB cap. SVG is allowed here (the chat blocks it) because deliverables are private, served via signed URL, previewed only inside `<img>` (no script exec) and downloaded as an attachment. Also `isImageThumbnailable`, `nextConceptNumber`/`nextVersionForConcept`, `groupByConcept`, `conceptLabel`, type labels.
- **Version numbering is server-authoritative**: `createDeliverable` (`lib/td-communication/deliverables-queries.ts`) always assigns `max(version)+1` within `(enrollment, concept)` — no two-uploads-same-concept race. The client only suggests a concept.
- **Status flow** (pure helpers in `pipeline.ts`, unit-tested): uploading a deliverable nudges `enrolled/form_submitted/in_progress/revision → concept_ready` (`nextStatusOnUpload`); "Release Final" nudges `→ delivered` unless cancelled/delivered (`nextStatusOnReleaseFinal`). Advancement is **forward-only + optimistic** (`.eq('status', current)` guard — no-op under concurrent edits) and **never throws** (auto-advance must not fail the write). A **manual** status dropdown in the panel (`PATCH /api/td-communication/projects/[id]` → `setEnrollmentStatus`, validated by `isEnrollmentStatus`) covers every status; `approved` is reachable only manually (no client-approval action yet). The `/collab` board reads from **state** (`collab-dashboard.tsx` lifted `initialProjects` → `useState` + `reloadProjects()`), so changes from the panel (`onChanged`) refetch the board live.
- **API** (auth `resolveCommParticipant` — staff or scoped partner; R099 errors): `GET`/`POST /projects/[id]/deliverables`, `POST /projects/[id]/deliverables/upload-url`, `PATCH`/`DELETE /projects/[id]/deliverables/[delivId]` (ownership: deliverable's `enrollment_id` must equal the route id), `PATCH /projects/[id]` (status). The only **UI** surface is `/collab` (partner-only via `getCommPartner`); staff have no deliverables UI this phase.
- **NOT built this phase** (flags only, by decision): watermark image generation + payment-gated client download. The manager always allows preview+download regardless of `is_draft` — `is_draft` is a future *client* gate. No realtime on deliverables (local refetch after each action).

## Gotchas, invariants & past bugs
- **`role='partner'` is load-bearing AND dangerous.** It lets the partner past the middleware dashboard guard (good) but, without the confinement branch, would expose the entire CRM (bad). Both behaviours live in `middleware.ts`. Existing partners that log in as `role='client'` are unaffected.
- **RLS-gated realtime is a NEW pattern here.** Unlike `portal_messages` (RLS off), `comm_messages` relies on the SELECT policy for delivery. If the policy is wrong, postgres_changes silently deliver nothing — must be browser-verified. The policy resolves a partner via `auth.jwt()->'app_metadata'->>'contact_id'`, so the partner's auth user MUST carry `contact_id` in app_metadata.
- **Provisioning is separate from code.** Creating Cris's `role='partner'` auth user (with `contact_id`), his `client_partners` row, and `partner_scope = '{td_communication}'`, plus promoting the migration to production, are pending Antonio's approval.
- **The login door (`app/portal/login/page.tsx`) admits partners.** The page previously hard-rejected any non-`client` role ("This account does not have portal access"), so a `role='partner'` user could authenticate but never get past login — Phase 1 shipped `/collab` + confinement but no working door (Cris was never login-tested). Fixed in Phase 2: the email-login path admits `client` OR `partner` and routes a partner straight to `/collab` (middleware then keeps them there; `/collab` still gates on the `td_communication` scope). Staff teammates still use the username path. Caught in Phase 2 browser QA.
